## Findings Addressed

### H1 — SystemEvent Idempotency Guard (FIXED)

**File:** `src/app/admin/cron/session-auto-close/route.ts`

**Change:** Added `SystemEvent.findOne({ eventType, date, status: 'completed' })` check before executing `autoCloseSessions`. If a completed record exists for the dateString, route returns early with `skipped: true`. After successful execution, creates `SystemEvent` with `status: 'completed'`, `completedAt`, and `meta.sessionsClosed`.

Uses `CRON_NAMES.SESSION_AUTO_CLOSE` constant from `@constants/cron-names` — no magic strings.

**Result:** Double-execution on same date is now idempotent. TC-ATT-012 satisfied.

### M5 — Cron Route Path Alignment (DEFERRED — accepted risk)

**Finding:** Spec referenced `midnight-session-close`; implementation uses `session-auto-close`.

**Assessment:** Renaming is not low-risk:
- `vercel.ts` schedules `{ path: '/api/cron/session-auto-close', schedule: '0 18 * * *' }` — rename breaks Vercel cron trigger
- `src/constants/cron-names.ts` exports `SESSION_AUTO_CLOSE: 'session-auto-close'` — used as SystemEvent `eventType`
- Two route files use this name: `src/app/cron/session-auto-close/` (Vercel stub) and `src/app/admin/cron/session-auto-close/` (implementation)

**Decision:** Per remediation scope ("Do not redesign cron architecture"), M5 is deferred. The implementation is functionally correct — the name difference is a spec terminology mismatch, not a behavioral gap. SystemEvent records now use the constant consistently, so the eventType is stable.

---

### M6 — attendanceLimiter Enforcement (FIXED)

**Files:**
- `src/middleware/rateLimiter.ts` — added `attendanceLimiter` (60 req/min per employee, `prefix: 'rl:attendance'`)
- `src/app/api/v1/attendance/checkin/route.ts` — `checkRateLimit(attendanceLimiter, payload.userId)` after auth
- `src/app/api/v1/attendance/checkout/route.ts` — `checkRateLimit(attendanceLimiter, payload.userId)` after auth

**Result:** Both attendance mutation endpoints now enforce per-employee sliding window rate limit. Keyed by `userId` so one employee cannot flood the endpoint without impacting others.
