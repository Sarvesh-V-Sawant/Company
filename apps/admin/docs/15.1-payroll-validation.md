## 12. Findings

### MEDIUM Findings

#### M1 — `finalisedBy`, `unfinalisedAt`, `unfinalisedBy` not persisted to DB

**Location:** `src/services/PayrollService.ts` — `finalise()` (line 279-283), `unfinalise()` (line 319-324)

**Detail:**
- `finalise()` returns `{ finalisedBy: params.adminId }` in response but `PayrollRecord` schema has no `finalisedBy` field; it is never written to DB.
- `unfinalise()` returns `{ unfinalisedAt, unfinalisedBy }` but neither field exists in schema; not written to DB.
- Subsequent `GET /payroll/:id/:yearMonth` (via `formatRecord`) cannot return these values.
- Spec (docs/02 §12): `finalisedBy?: ObjectId` required in model; 08.6 spec for unfinalize (BR-PAY-13): "Sets `unfinalisedAt`, `unfinalisedBy`".

**Impact:** API clients relying on the admin detail endpoint for audit trail cannot see who finalised/unfinalised payroll without checking AuditLog separately.

---

#### M2 — PAY_004 HTTP status is 409 instead of spec's 422

**Location:** `src/services/PayrollService.ts:292` — `unfinalise()`

**Detail:**
```typescript
// Current (wrong):
throw new AppError('PAY_004', 409, 'Payroll is not finalised.');

// Spec (docs/04 §2 error catalog):
PAY_004 | PAYROLL_NOT_FINALISED | 422 | ...
```

**Impact:** Clients checking status code for PAY_004 would receive 409 (Conflict) instead of the spec's 422 (Unprocessable Entity). API contract deviation.

---

#### M3 — `adjust()` audit log is not transactional

**Location:** `src/services/PayrollService.ts:419-439` — `adjust()`

**Detail:** `PayrollRecord.findOneAndUpdate()` is called without a Mongoose session. `AuditLog.create()` is called afterwards without a session. Neither is wrapped in `withTransaction()`.

Compare with `finalise()` and `unfinalise()` which correctly use `withTransaction` for both the update and the AuditLog.

**Risk:** If `AuditLog.create()` throws after the findOneAndUpdate succeeds, the adjustment is committed but leaves no audit trail. Under load, partial failures could produce unaudited payroll adjustments.

---

#### M4 — Multiple spec-required fields missing from PayrollRecord model

**Location:** `src/models/PayrollRecord.ts`

**Missing fields** (per docs/02 §12 and 08.6 D2):

| Field | Spec source | Impact |
|-------|-------------|--------|
| `computedBy: ObjectId` | docs/02 §12 | Can't identify who computed payroll without cross-referencing AuditLog |
| `finalisedBy?: ObjectId` | docs/02 §12 | See M1 |
| `year: number`, `month: number` | docs/02 §12 | Missing compound index `{ employeeId, year, month }` for efficient monthly queries |
| `workingDaysInMonth: number` | docs/02 §12 | Mobile payslip cannot display "Working Days: 22" (different from `effectiveWorkingDays` for mid-month joiners) |
| `presentDays: number` | docs/02 §12 | Attendance detail on payslip incomplete |
| `sickLeaveDays`, `casualLeaveDays` | docs/02 §12 | Leave breakdown by type unavailable |
| `lwpDays: number` | docs/02 §12 | Full LWP days separate from effective (needed for display) |
| `holidayDays`, `weekendDays` | docs/02 §12 | Calendar summary on payslip unavailable |
| `joiningDateSnapshot?`, `leavingDateSnapshot?` | docs/02 §12 | Cannot audit proration basis after employee record changes |

**Most critical:** `workingDaysInMonth` — the mobile payslip spec (08.6 §12.2) shows "Working Days: 22" which is the total configured working days in the month, not the employee-adjusted `effectiveWorkingDays`. These differ for mid-month joiners. This field is not computed or stored.

#### L2 — `/me` routes do not assert employee role

**Location:** `src/app/api/v1/payroll/me/route.ts`, `src/app/api/v1/payroll/me/[yearMonth]/route.ts`

Spec says Role: employee for these routes. Routes only call `getAuthUser()` with no `assertRole`. Admins can call `/me` routes and see their own payroll.

This is functionally harmless (the service resolves by `userId` correctly for both roles) but deviates from the spec's role annotation.

#### L4 — Collection named `payrollrecords` vs spec's `payrollSummaries`

**Location:** `src/models/PayrollRecord.ts:85` — `mongoose.model('PayrollRecord', ...)`

The model name `PayrollRecord` results in MongoDB collection `payrollrecords`. Spec uses `payrollSummaries`. No runtime impact within the application but matters for direct DB queries, monitoring, migration scripts, and ops documentation.
