## 8. Findings

### HIGH

**H1 — GET /employees: paginated response envelope double-wraps**

- **File:** `src/app/api/v1/employees/route.ts:31`, `src/services/EmployeeService.ts:149–157`
- **Root cause:** `EmployeeService.list()` returns `{ data: [...], meta: {...} }`. Route calls `success(result)`, which wraps the whole object into `data`, producing:
  ```json
  { "success": true, "data": { "data": [...], "meta": {...} } }
  ```
- **Spec requires** (`docs/04-api-specification.md` §4.1):
  ```json
  { "success": true, "data": [...], "meta": { "page": 1, "limit": 20, "total": 5, "totalPages": 1 } }
  ```
- **Impact:** Any client parsing `response.data` as an employee array receives an object. Completely breaks list endpoint for mobile and admin UI.
- **Fix:** In `employees/route.ts`, replace:
  ```typescript
  return success(result);
  ```
  with:
  ```typescript
  return NextResponse.json({ success: true, data: result.data, meta: result.meta });
  ```

### MEDIUM

**M1 — Testing tooling mismatch: spec Vitest 2.x vs impl Jest 29**

- `docs/03-testing-strategy.md` mandates Vitest.
- Implementation uses Jest with `next/jest` SWC transform (required workaround for SWC's `jest.mock` hoisting limitation).
- Coverage thresholds not enforced via spec tooling.
- Impact: CI may pass but not satisfy the approved testing strategy gate.

**M2 — No integration tests**

- `docs/03-testing-strategy.md` requires integration tests for service-to-DB flows.
- Only unit tests exist (with Mongoose model spies, not real DB).
- Route handler behavior (auth header parsing, body parsing errors, content-type handling) is untested.

**M3 — `registeredDevice.platform` hardcoded to `'android'`**

- `src/services/EmployeeService.ts:420`
- Register-device spec body has no `platform` field; the field is not derivable from admin input.
- DB schema stores `platform: enum['ios', 'android']`; all devices registered by admin will be tagged `android` regardless of actual device.
- Impact: Mobile app filtering by platform will receive incorrect data.

**M4 — `AppError('AUTH_006', 403)` missing message in `list()`**

- `src/services/EmployeeService.ts:125`: `throw new AppError('AUTH_006', 403)` — no `message` argument.
- Route returns `apiError(err.code, err.message, err.httpStatus)` where `err.message` resolves to `''`.
- Spec error format includes a human-readable message; empty string violates contract.
- Only triggered for employee-role `GET /employees` calls — low frequency but wrong response shape.

**M5 — `email` excluded from list search**

- `src/services/EmployeeService.ts:131–132`: search regex covers `firstName`, `lastName`, `employeeId` only.
- Admins cannot search employees by email, a common lookup pattern.
- Spec §4.1 does not enumerate search fields explicitly, but email exclusion is likely unintended.

**L1 — AuditLog field naming divergence (pre-existing)**

- Model uses `performedBy`/`targetType`/`targetId`.
- `docs/02-database-design.md` shows `actorId`/`entityType`/`entityId`.
- Pre-existing from scaffolding phase; all audit writes use the model's actual fields, so runtime is correct.

**L2 — No coverage report baseline established**

- `npm run test:ci` would generate coverage but has not been run post-implementation.
- `docs/03-testing-strategy.md` requires ≥80% unit coverage for service files.
- Cannot confirm threshold is met without a coverage report.

**L3 — `dateOfJoining` future-date check uses local clock**

- `src/validators/employee.ts`: `new Date(d) <= new Date()` compares against server local time without timezone normalization.
- If server is UTC and employee joins on the last day of a timezone, the check may incorrectly reject a valid date.
- Edge case; low risk.
