## Section 1 — Tracking Policy Resolution

### Problem with doc 30.1 design

Doc 30.1 stores `trackingEnabled: boolean` on `AttendanceSession`. This captures only the resolved boolean from company-level settings. When department or employee overrides are introduced later, the session would need new fields, and historical sessions would have no record of which policy level was in effect. Additionally, the resolved interval is not stored — only `trackingEnabled`. The mobile must request settings again to get the interval.

### Policy Resolution Engine

A `TrackingPolicyResolver` service resolves the effective tracking policy at check-in time from a priority-ordered stack:

```
Priority (highest to lowest):

  3. Employee Override        (future: EmployeeTrackingOverride collection)
  2. Department Policy        (future: DepartmentSettings.locationTracking)
  1. Company Policy           (current: CompanySettings.locationTracking)
```

Each level returns a complete `TrackingPolicySnapshot` or `null` (meaning "no override at this level — continue down the stack").

```typescript
// apps/admin/src/services/TrackingPolicyResolver.ts

export interface TrackingPolicySnapshot {
  enabled:         boolean;
  intervalMinutes: number;
  policySource:    'company' | 'department' | 'employee';
}

export class TrackingPolicyResolver {
  static async resolve(employeeId: string, departmentId: string): Promise<TrackingPolicySnapshot> {
    // Phase 16.1: only company policy implemented
    // Stubs for future levels return null → triggers next fallback

    // Level 3: Employee override (future)
    const employeeOverride = await resolveEmployeeOverride(employeeId);  // stub → null
    if (employeeOverride) return { ...employeeOverride, policySource: 'employee' };

    // Level 2: Department policy (future)
    const deptPolicy = await resolveDepartmentPolicy(departmentId);      // stub → null
    if (deptPolicy) return { ...deptPolicy, policySource: 'department' };

    // Level 1: Company policy (always present)
    const settings = await SettingsService.getSettings();
    return {
      enabled:         settings.locationTracking.enabled,
      intervalMinutes: settings.locationTracking.intervalMinutes,
      policySource:    'company',
    };
  }
}
```

### AttendanceSession — policy storage (replaces `trackingEnabled: boolean`)


```typescript
// Mongoose schema sub-document

  {
```

**Why store the resolved snapshot (not just `enabled: boolean`):**
- Immutable audit record of what policy governed this session — survives future settings changes
- `intervalMinutes` needed in check-in response and by live dashboard to compute expected ping count
- `policySource` enables future analytics: "X% of sessions governed by department override"

### Check-in response (updated)

```typescript
  }

```

Mobile reads `trackingPolicy.enabled` to decide whether to start tracking. If `enabled`, it uses `trackingPolicy.intervalMinutes` for the background timer.

`GET /api/v1/attendance/today` also returns `trackingPolicy` in the active session response — allows mobile to restore tracking state on app resume.

## Section 2 — Tracking Health Model

### Design

Nine discrete health states covering all device and network conditions during an active tracking session:

| State | Trigger | Source |
|---|---|---|
| `healthy` | Ping received within 1.5× interval | Server (on ping receipt) |
| `offline` | Mobile lost network connectivity | Mobile-reported |
| `gps_disabled` | Mobile GPS/location service turned off | Mobile-reported |
| `permission_revoked` | Background location permission removed by user | Mobile-reported |
| `battery_optimized` | Last ping `batteryLevel ≤ 20` | Server (on ping receipt) |
| `waiting_for_sync` | Offline queue flushing — pings with `syncStatus: 'queued'` arriving | Server (on queued ping receipt) |
| `tracking_suspended` | Mobile explicitly suspended tracking (e.g. prolonged airplane mode) | Mobile-reported |
| `no_update_threshold_exceeded` | Ping gap > 3× interval with no known device state reason | Server-computed at query time (not stored) |
| `checked_out` | Session `isActive = false` | Derived from `isActive` at query time (not stored) |

`no_update_threshold_exceeded` and `checked_out` are **computed in the API response layer**, not persisted. All other states are stored on `AttendanceSession`.

### AttendanceSession additions (health fields)

```typescript
// Added to IAttendanceSession
trackingHealth:   TrackingHealthState | null;  // null = tracking not active this session
trackingHealthAt: Date | null;                 // when this state was last written

type TrackingHealthState =
  | 'healthy'
  | 'offline'
  | 'gps_disabled'
  | 'permission_revoked'
  | 'battery_optimized'
  | 'waiting_for_sync'
  | 'tracking_suspended';
// 'no_update_threshold_exceeded' and 'checked_out' are computed, not stored
```

```typescript
// Mongoose schema additions
trackingHealth:   { type: String, enum: [...], default: null },
trackingHealthAt: { type: Date, default: null },
```

### State transition rules

**On `LocationService.upload()` (new ping received):**
```
if ping.syncStatus = 'queued'           → set 'waiting_for_sync'
else if ping.batteryLevel ≤ 20         → set 'battery_optimized'
else                                    → set 'healthy'
Update: AttendanceSession.trackingHealth + trackingHealthAt = now
```

**On `POST /attendance/tracking-status` (mobile-reported):**
```
'gps_disabled'       → set 'gps_disabled'
'gps_restored'       → set 'healthy'
'offline'            → set 'offline'
'online'             → set 'healthy' (next ping confirms)
'permission_revoked' → set 'permission_revoked'
'battery_low'        → set 'battery_optimized' (mobile reports crossing ≤20% threshold)
'tracking_suspended' → set 'tracking_suspended'
'sync_completed'     → set 'healthy'
Update: AttendanceSession.trackingHealth + trackingHealthAt = now
Write AuditLog event
```

**At query time (`GET /workforce/live`, `GET /attendance/[sessionId]/location`):**
```
if session.isActive = false                             → return 'checked_out'
if session.trackingPolicy.enabled = false              → return null (not applicable)
if lastPing = null AND tracking has been on > 2× interval → return 'no_update_threshold_exceeded'
if lastPing.timestamp < now - (3 × intervalMinutes)   → return 'no_update_threshold_exceeded'
else                                                   → return session.trackingHealth
```

The computed override only applies in the response — it does not overwrite the stored `trackingHealth` field. This preserves the last known device-reported state.

### New endpoint: POST /api/v1/attendance/tracking-status

**Auth:** employee JWT

```typescript
// Request body
{
  "status":       "gps_disabled" | "gps_restored" | "offline" | "online" |
                  "permission_revoked" | "battery_low" | "tracking_suspended" | "sync_completed",
  "timestamp":    string,           // ISO 8601
  "batteryLevel": number | null     // optional
}

// Response 200
{ "success": true }

// Response 403 — no active session for this employee
// Response 400 — unknown status value
```

**Server logic:**
1. Find active session for `employeeId`
2. If none: 403 (session already closed — mobile should stop tracking)
3. Map status → `TrackingHealthState`, update session
4. Write AuditLog entry
5. Return 200

**Mobile triggers this endpoint when:**
- User turns off GPS → `gps_disabled`; turns back on → `gps_restored`
- Network connectivity lost → `offline`; restored → `online`
- Background permission revoked (detected on next background launch) → `permission_revoked`
- Battery crosses 20% → `battery_low`
- App enters extended airplane mode → `tracking_suspended`
- Offline queue successfully flushed → `sync_completed`

### Operational visibility improvement

The live dashboard now surfaces actionable information without admin needing to reason about timestamps:

```
Before: "Last ping: 2h ago" — admin must guess why
After:  "GPS Disabled · 2h ago" vs "Offline · 2h ago" vs "Stale (no reason)"
```

This enables the admin to take different actions: contact the employee (GPS off) vs. wait (offline on underground train) vs. escalate (no update threshold exceeded with no known reason).

## Section 3 — RouteSession Architecture Evaluation

### Comparison

| Concern | Raw LocationPing Queries | RouteSession Entity |
|---|---|---|
| **Dashboard latency** (50 active employees) | ~20–50ms — indexed aggregation per session | ~5ms — read 50 documents |
| **Dashboard latency** (500 active employees) | ~200–400ms — still acceptable | ~20ms |
| **Stats computation** (distance, time inside) | Read all pings → compute in app layer | Pre-computed, updated per ping |
| **Write path complexity** | 1 write per ping | 2 writes per ping (ping + RouteSession update) |
| **Schema complexity** | No new collection | New `routesessions` collection + update logic |
| **API contract** | Stats computed in service | Same API contract, different backing |
| **Historical accuracy** | Always exact (recomputed from raw data) | Approximate if update fails mid-write |
| **Regression risk** | Low | Medium (atomic update of aggregate counters) |

**Scale threshold where RouteSession pays off:** ~300+ concurrent tracked sessions with dashboard polling every 30–60 seconds. Below this, MongoDB Atlas M10 handles the aggregation comfortably.

**Decision: Defer RouteSession to Phase 16.5.**

Phase 16.1 implements stats via `LocationService.computeSessionStats(sessionId)` — reads all pings, computes in TypeScript. If Phase 16.5 performance profiling shows dashboard response time > 200ms at production load, RouteSession is introduced as a transparent cache layer with no API contract changes.

**API contract is preserved for future migration:**

```typescript
interface SessionStats {
  pingsReceived:                number;
  pingsExpected:                number | null;   // null if session still active
  missedPings:                  number | null;
  timeInsideGeofenceMinutes:    number;
  timeOutsideGeofenceMinutes:   number;
  estimatedDistanceKm:          number;          // haversine sum of consecutive pings
  avgAccuracyMetres:            number;
  minBatteryLevel:              number | null;
  peakDistanceFromOfficeMetres: number;
}
```

In Phase 16.1: computed from raw pings by `LocationService.computeSessionStats()`.  
In Phase 16.5 (if needed): same interface, backed by `RouteSession.findOne({ attendanceSessionId })`.  
No API or client changes required at migration.

## Section 5 — Automatic Location Events

### First-class AuditLog events

**12 action codes defined:**

| Action Code | Trigger | Generated By |
|---|---|---|
| `LOC_PING_RECEIVED` | Every successful ping upload | `LocationService.upload()` |
| `LOC_LEFT_GEOFENCE` | Previous ping inside → new ping outside | `LocationService.upload()` |
| `LOC_RETURNED_TO_GEOFENCE` | Previous ping outside → new ping inside | `LocationService.upload()` |
| `LOC_GPS_DISABLED` | Mobile reports GPS off | `POST /attendance/tracking-status` handler |
| `LOC_GPS_RESTORED` | Mobile reports GPS restored | `POST /attendance/tracking-status` handler |
| `LOC_TRACKING_OFFLINE` | Mobile reports connectivity lost | `POST /attendance/tracking-status` handler |
| `LOC_TRACKING_ONLINE` | Mobile reports connectivity restored | `POST /attendance/tracking-status` handler |
| `LOC_PERMISSION_REVOKED` | Mobile reports background permission removed | `POST /attendance/tracking-status` handler |
| `LOC_BATTERY_LOW` | Mobile reports battery crossed ≤ 20% | `POST /attendance/tracking-status` handler |
| `LOC_SYNC_COMPLETED` | Mobile reports offline queue flushed | `POST /attendance/tracking-status` handler |
| `LOC_HISTORY_VIEWED` | Admin views session location history | `GET /attendance/[sessionId]/location` handler |
| `LOC_TRACKING_SETTINGS_UPDATED` | Admin updates `locationTracking` settings | `PATCH /settings/location-tracking` handler |

**No `LOC_PING_THRESHOLD_EXCEEDED` as stored event:** This would require a cron job to detect and write, adding operational complexity. Instead, `no_update_threshold_exceeded` is a computed health state returned in API responses. If a stored event is needed for analytics in Phase 16.5, a scheduled job can backfill from ping gap analysis.

### Geofence transition detection (in `LocationService.upload()`)

```typescript
// After inserting the new LocationPing:
const previousPing = await LocationPing.findOne(
  { attendanceSessionId, _id: { $ne: newPing._id } },
  {},
  { sort: { timestamp: -1 } }
).lean();

if (previousPing) {
  const wasInside = previousPing.insideGeofence;
  const isNowInside = newPing.insideGeofence;

  if (wasInside && !isNowInside) {
    await AuditLog.create({
      performedBy: employeeObjectId,
      action: 'LOC_LEFT_GEOFENCE',
      targetType: 'AttendanceSession',
      targetId: attendanceSessionId.toString(),
      changes: {
        latitude: newPing.latitude, longitude: newPing.longitude,
        distanceFromOffice: newPing.distanceFromOffice,
        previousPingTimestamp: previousPing.timestamp,
      },
    });
  } else if (!wasInside && isNowInside) {
    await AuditLog.create({
      performedBy: employeeObjectId,
      action: 'LOC_RETURNED_TO_GEOFENCE',
      targetType: 'AttendanceSession',
      targetId: attendanceSessionId.toString(),
      changes: {
        latitude: newPing.latitude, longitude: newPing.longitude,
        distanceFromOffice: newPing.distanceFromOffice,
        previousPingTimestamp: previousPing.timestamp,
      },
    });
  }
}
```

**Performance:** Indexed query — `{ attendanceSessionId: 1, timestamp: -1 }` index already defined. Adds ~1–3ms to the ping upload path. Acceptable.

**AuditLog index addition:**

```typescript
// New compound index for location events feed query
AuditLogSchema.index({ action: 1, createdAt: -1 });
```

No schema change to `AuditLog` model — `action: string`, `changes: Mixed`, `targetType/targetId: string` already support all required fields.

## Section 6 — Implementation Phasing

### Adopted 5-phase plan

**Phase 16.2 / 16.3 boundary clarified:**

- **Phase 16.2 (Mobile Tracking):** Real-time ping upload with graceful fail on network error (silently skip, log to device console). Mobile fully operational when connected. Offline is a known limitation at this phase.
- **Phase 16.3 (Offline Sync):** `LocationPingQueue` class inserted between the ping attempt and the graceful fail. No changes to Phase 16.2 code — extension only. Connectivity monitoring via `connectivity_plus`.

This split means Phase 16.2 is testable on a live-network device without simulating connectivity loss. Phase 16.3 adds resilience without changing any tested Phase 16.2 behaviour.

```
Phase 16.1 — Backend Foundation
  ├─ LocationPing model
  ├─ CompanySettings.locationTracking
  ├─ AttendanceSession.trackingPolicy + trackingHealth + trackingHealthAt
  ├─ TrackingPolicyResolver service
  ├─ LocationService (upload, history, live, stats, geofence event detection)
  ├─ SettingsService.updateLocationTracking() + TTL management
  ├─ AttendanceService.checkIn() → resolve policy, store snapshot, return in response
  ├─ GET /attendance/today → include trackingPolicy in active session
  ├─ POST /attendance/location
  ├─ POST /attendance/tracking-status
  ├─ GET /attendance/[sessionId]/location
  ├─ GET /workforce/live
  ├─ GET /employees/[id]/location/current
  ├─ GET + PATCH /settings/location-tracking
  ├─ AuditLog index: { action: 1, createdAt: -1 }
  └─ Unit tests: LocationService, TrackingPolicyResolver

Phase 16.2 — Mobile Tracking (real-time, Android + iOS)
  ├─ Android: LocationTrackingService.kt (Foreground Service)
  ├─ Android: BootReceiver.kt
  ├─ Android: manifest permissions + service declaration
  ├─ iOS: AppDelegate.swift CLLocationManager background setup
  ├─ iOS: Info.plist (UIBackgroundModes: location + usage strings)
  ├─ Dart: LocationTrackingService (MethodChannel bridge, ping upload, health reporting)
  ├─ Dart: TrackingProvider (Riverpod)
  ├─ home_screen.dart: start/stop + tracking status chip + battery warning
  ├─ main.dart: WorkManager watchdog registration (Android)
  └─ pubspec.yaml: workmanager, connectivity_plus

Phase 16.3 — Offline Sync
  ├─ Dart: LocationPingQueue (SharedPreferences-backed queue, max 20 entries)
  ├─ Dart: connectivity_plus subscription → flush queue on reconnect
  ├─ LocationTrackingService: intercept failed upload → enqueue
  ├─ Queue pruning: discard pings older than maxOfflineQueueDurationHours
  └─ 409 response handling: clear queue + stop tracking

Phase 16.4 — Admin Portal
  ├─ npm: react-leaflet, leaflet, @types/leaflet
  ├─ /workforce-tracking page (live dashboard)
  ├─ /workforce-tracking/[employeeId] page (route detail + map + timeline)
  ├─ /settings/location-tracking page
  ├─ Sidebar nav entry: Workforce Tracking
  └─ Attendance detail page: "View Route" button link

Phase 16.5 — Analytics, Validation & Production Verification
  ├─ Route replay animation (Leaflet marker animation along polyline)
  ├─ Dashboard analytics charts (distance/time/compliance trends)
  ├─ RouteSession collection (if Phase 16.4 performance profiling warrants)
  ├─ Suspicious movement detection (speed anomaly → AuditLog LOC_SUSPICIOUS_MOVEMENT)
  ├─ Battery health reporting (admin report: employees with chronic low battery)
  └─ docs/33-location-tracking-production-verification.md (E2E verification doc)
```

### Regression risk mitigation per phase

| Phase | Risk | Mitigation |
|---|---|---|
| 16.1 | `AttendanceService.checkIn()` change breaks existing check-in tests | Add `trackingPolicy` to existing `AttendanceService.test.ts` mock; all other return fields unchanged |
| 16.1 | `AttendanceSession` schema change (new fields) | All new fields have `default: null` — existing documents unaffected; no migration needed |
| 16.2 | Mobile foreground service kills app-level state | Service uses SharedPreferences for session state — independent of Flutter widget tree |
| 16.2 | `home_screen.dart` changes break existing check-in test | Isolate tracking calls in `_handleCheckIn` and `_handleCheckOut` — new `try/catch` branches |
| 16.3 | Queue flush sends duplicate pings | `syncStatus: 'queued'` pings are deduplicated by server on `timestamp` proximity check; server is idempotent |
| 16.4 | Leaflet SSR error in Next.js | Import map component dynamically: `const Map = dynamic(() => import('./MapComponent'), { ssr: false })` |

## Architecture Gaps Resolved

| Gap | Resolution |
|---|---|
| `trackingEnabled: boolean` — no policy level or interval stored | Replaced with `TrackingPolicySnapshot` on `AttendanceSession`; `TrackingPolicyResolver` service added |
| No first-class tracking health model | `trackingHealth` + `trackingHealthAt` on `AttendanceSession`; 7 stored states; 2 computed; new mobile-to-server endpoint |
| RouteSession — evaluated | Deferred to Phase 16.5. `SessionStats` interface preserved for migration-free upgrade |
| Dashboard — no health visibility, no event feed | Health summary bar + battery warning + Recent Location Events feed added |
| Location events — not first-class | 12 AuditLog action codes; geofence transitions auto-detected in `LocationService.upload()`; AuditLog index added |
| Phase 16.2/16.3 boundary — offline sync scope unclear | Phase 16.2 = real-time only (graceful fail); Phase 16.3 = `LocationPingQueue` inserted as extension with no Phase 16.2 rework |

---

## Final Recommendation

All five architectural areas evaluated. No structural gaps remain. The design is internally consistent, backward-compatible (all new `AttendanceSession` fields default to `null`), and scalable to enterprise deployment without schema migrations below Phase 16.5.
