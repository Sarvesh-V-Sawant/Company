## H1 — Fix: forgot-checkout reconciliation

### Root Cause

`RegularizationService.approve()` looked for `{ isActive: true }` sessions when handling `forgotCheckOut` type. The `session-auto-close` cron (`AttendanceService.autoCloseSessions()`) runs nightly and marks all previous-day sessions as `isActive: false, closedBySystem: true, systemCloseReason: 'midnight-rollover'`. Any valid `forgotCheckOut` regularization (minimum 1 day old by the lookback window) would find no `isActive: true` session and always throw `REG_006`.

### Fix Applied

**File:** `src/services/RegularizationService.ts` (approve method, forgotCheckOut branch)

```typescript
// BEFORE (broken — only finds isActive sessions):
const openSession = await AttendanceSession.findOne(
  { employeeId: employeeOid, dateString, isActive: true },
).session(dbSession).lean();

// AFTER (fixed — also finds midnight-rolled sessions):
const targetSession = await AttendanceSession.findOne(
  {
    employeeId: employeeOid,
    dateString,
    $or: [
      { isActive: true },
      { isActive: false, closedBySystem: true, systemCloseReason: 'midnight-rollover' },
    ],
  },
).sort({ createdAt: -1 }).session(dbSession).lean();
```

**Additional change:** When updating the found session, `systemCloseReason` is now set to `'admin-force-close'` (overwriting `'midnight-rollover'`), and the `checkOut` timestamp is replaced with the admin-approved `requestedCheckOut`. This correctly represents the session's final state.

**Logic clarification:**
- `isActive: true` — handles same-day edge case (employee submits regularization before midnight rollover runs)
- `isActive: false, closedBySystem: true, systemCloseReason: 'midnight-rollover'` — handles the normal past-day case where the cron already closed the session

REG_006 is still correctly thrown when no session exists at all (employee never checked in on that day — forget-checkout has nothing to reconcile against).

## M2 — Fix: requestedCheckIn/requestedCheckOut boundary validation

### Change

Added `validateTimestampBoundaries()` helper in `RegularizationService.ts`, called in `create()` after loading company settings (needed for timezone).

```typescript
function validateTimestampBoundaries(
  dateStr: string,
  requestedCheckIn: Date | undefined,
  requestedCheckOut: Date | undefined,
  timezone: string,
): void {
  if (requestedCheckIn) {
    const localDay = localDateString(requestedCheckIn, timezone);
    if (localDay !== dateStr) {
      throw new AppError('GEN_001', 400,
        `requestedCheckIn must be on the same calendar day as date (${dateStr}) in the company timezone.`);
    }
  }
  if (requestedCheckOut) {
    const localDay = localDateString(requestedCheckOut, timezone);
    const nextDay  = new Date(new Date(dateStr + 'T00:00:00Z').getTime() + 86_400_000).toISOString().slice(0, 10);
    if (localDay !== dateStr && localDay !== nextDay) {
      throw new AppError('GEN_001', 400,
        `requestedCheckOut must be on the same day or the following day as date (${dateStr}) in the company timezone.`);
    }
  }
}
```

Uses `date-fns-tz`'s `toZonedTime` to convert UTC timestamps to the company timezone before extracting the calendar date. This ensures IST-correct boundary enforcement.
