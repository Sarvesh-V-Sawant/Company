## HIGH Severity Findings

### R-UI-001: No Login / Authentication Screen Designed

**Severity:** HIGH

**Finding:** `docs/05-admin-ui-ux.md` lists the Login screen in Appendix A (Screen #1) and Forced Change Password (Screen #2) but provides NO design specification for either. The login page is the entry point of the entire portal; missing its design is a gap.

**Missing:**
- Login page layout (email + password form, logo, company name)
- Error states for invalid credentials (`AUTH_001`, `AUTH_004`)
- Rate-limit error state (`AUTH_002`)
- Account inactive error state (`AUTH_007`)
- "Forgot Password?" link and self-service reset flow
- Forced password change screen (`requiresPasswordChange: true`) layout, restricted navigation (no sidebar)
- "Change password" form fields + validation rules

**Business Impact:** Developers have no design reference for implementing the first user-facing screen.

**Fix:** Add Section 3.0 (Pre-Authentication Screens) covering: Login, Forgot Password (email input), Password Reset (token + new password form), Forced Change Password. Include error states for all API error codes returned by these endpoints.

---

### R-UI-002: Payroll Bulk Compute Concurrency Warning Not Addressed in UI

**Severity:** HIGH

**Finding:** API specification deferred finding R-API-009 (concurrency guard for bulk payroll compute) to implementation. The UI design for "Compute Payroll" modal (Section 9.2) does not show any UI for:
- Preventing double-clicks / re-triggering while compute is in progress
- Handling the API returning a conflict error (another compute already running)
- Showing partial failure states (some employees computed, others failed mid-batch)

If two admins are logged in simultaneously and both trigger compute, the UI has no handling for the resulting conflict.

**Business Impact:** Race condition can produce duplicate computations or confusing partial-success states with no recovery path shown in the UI.

**Fix:** Add to Section 9.2:
- Disable "Compute Payroll" button once clicked (single-submission guard)
- "Conflict" error state: "Payroll computation is already in progress. Refresh in 30 seconds."
- Partial failure state: show per-employee error list with retry option for failed employees
- Store compute job status in session state; re-entering the modal shows "last run" status

---

### R-UI-003: Leave Revocation After Payroll Finalization — No Clear Recovery Path in UI

**Severity:** HIGH

**Finding:** The payroll state machine (`draft → finalised → unfinalize → draft`) is documented. However when an admin revokes a leave (Section 7.2) for a month whose payroll is already finalised, the API returns a `warnings[]` array. The UI shows a `toast.warning`, but there is no guidance on WHAT the admin should do next.

Missing UI workflow:
- Clear call-to-action after a warning toast: "Payroll for June 2026 is finalized. Unfinalizing and recomputing is required. [Go to Payroll →]"
- No visual indicator on the Payroll list that a month has pending recomputation needed
- No "stale" badge on payroll records that have had post-finalization changes

**Business Impact:** Admin revoking leave may not realize payroll needs recomputation. Employee's June payroll may be incorrect and finalized permanently.

**Fix:**
- After leave revocation with payroll warning: show a persistent alert banner on the Leave History page (not just a toast) linking to the affected payroll month
- Add `needsRecompute` indicator (amber badge) on Payroll list for months with post-finalization changes
- Document this flow as a "cross-module warning" pattern in Section 3 (Global Patterns)

---

### R-UI-004: No 404 / Error Boundary Pages Designed

**Severity:** HIGH

**Finding:** The UI design has no specification for:
- **404 page** — when navigating to `/employees/invalid-id`, `/payroll/2026-99/invalid`, etc.
- **500 / API error boundary** — when the server returns an unexpected error during page load (not form submit)
- **Session expiry** — when the 15-minute access token expires and the silent refresh fails (e.g., refresh token revoked because employee deactivated, 90-day absolute expiry hit)
- **Unauthorized access** — if an employee role somehow accesses an admin-only route

**Business Impact:** Without these states, the app will show blank pages, React render crashes, or infinite loading spinners when errors occur.

**Fix:** Add Section 15 (Error & Edge Case Pages) covering:
- `not-found.tsx` design: centered message + back button
- `error.tsx` design: error message + retry button + contact support link
- Session expired overlay: non-dismissible modal "Your session has expired. Please log in again." → redirects to `/login` with `?redirect=` param
- Unauthorized: redirects to `/dashboard` with toast "You don't have permission to view that page."

## MEDIUM Severity Findings

### R-UI-005: Employee Create — Temporary Password Display is Insecure UX

**Severity:** MEDIUM

**Finding:** Section 5.2 states the temporary password is shown in a toast for 15 seconds with a [Copy] button. This is problematic:
- Toast can be dismissed accidentally by the admin
- If admin is on a screen share / recording, the password appears in the notification area
- 15 seconds is insufficient for admins who multi-task
- There is no second way to retrieve the password if the toast is missed

**Risk:** Admin creates employee but misses the toast; employee cannot log in; admin has no recovery path other than triggering a password reset email.

**Fix:**
- Show temporary password in a **modal** (not toast) that requires explicit dismissal
- Include a [Copy Password] button in the modal
- Show the modal BEFORE closing the create drawer
- Add a note: "After dismissing, send this password securely to the employee. It cannot be shown again."
- Employee can always use self-service password reset as recovery path

---

### R-UI-006: No Pagination / Virtualization Strategy for Attendance Weekly Grid

**Severity:** MEDIUM

**Finding:** Section 6.2 states "No pagination — all employees shown (virtual scrolling if >50 employees)." However, virtual scrolling is not specified — no library choice, no implementation approach, and no threshold for when to activate it. A company with 200 employees would have a 200×7 = 1400-cell grid. Without virtualization, this is a significant performance concern.

**Fix:** Specify:
- Use `@tanstack/react-virtual` (TanStack Virtual) for row virtualization when row count > 50
- Fixed row height: 48px
- Container height: `calc(100vh - 200px)` (fills viewport)
- Fallback for ≤50 employees: standard DOM rendering

---

### R-UI-007: Settings — No Confirmation for Destructive Setting Changes

**Severity:** MEDIUM

**Finding:** Multiple settings changes have significant side effects with no confirmation guard:
- Changing `leaveYearStartMonth`: documented as needing a warning modal, but only mentioned for the cron schedule — the impact on existing leave balance records is not addressed
- Changing `workStartTime`/`workEndTime`: affects ALL future attendance calculations retroactively for the current month
- Disabling geo-fence: immediately allows check-in from any location
- Changing `payrollCutoffDay`: affects current month if changed mid-month

Section 13.2 only adds a warning modal for `leaveYearStartMonth`. The others have no guard.

**Fix:** Define a "destructive settings change" pattern:
- When admin changes certain fields (geo-fence enabled/disabled, work hours, payroll cutoff), show a confirmation modal explaining the impact before saving
- List specific fields that trigger this pattern

### R-UI-008: Reports — No Preview Row Limit Communicated Before Generation

**Severity:** MEDIUM

**Finding:** Section 10.1 mentions "max 50 visible rows in preview" but this is not surfaced to the user before they click [Generate Report]. Admin expecting 990 records may be confused when only 50 show. No indication of truncation is visible.

**Fix:**
- Show record count estimate in filter area after date range is selected (using `meta.total` from a count-only API call or estimate)
- After generate: show "Preview showing first 50 of 990 records. Download XLSX for complete data." banner above the table
- Add `aria-live="polite"` region for this count update

### R-UI-009: Drawer Dirty-State Warning — Not Consistently Specified

**Severity:** MEDIUM

**Finding:** Section 3.4 mentions "with confirmation if form is dirty" when closing drawers via Escape or outside click, but this is only mentioned once. It is unclear which drawers implement this and how it works.

**Fix:** In Section 3.4, add a standard "Unsaved Changes" dialog specification:
```
Discard changes?
You have unsaved changes that will be lost.

[Keep Editing]    [Discard Changes]
```
- Triggered by: Escape key, clicking outside drawer, clicking X button when `form.formState.isDirty` is `true`
- All create/edit drawers implement this
- Confirmation drawers (approve/reject/deactivate) with single text area: no dirty check required (too low-friction)

### R-UI-010: Notifications — No Pagination for Sidebar Badge Refresh

**Severity:** MEDIUM

**Finding:** Section 2.2 states sidebar badge counts refresh every 5 minutes via a client-side interval. Issues:
- After an admin approves a leave from the dashboard quick-approve, sidebar badge is stale for up to 5 minutes
- No manual refresh trigger is defined
- Badge count only updates if user stays on the page; navigating resets the interval

**Fix:**
- After any action that changes pending counts (approve leave, approve reg), invalidate and refresh badge counts immediately (use SWR `mutate()` or React Query `invalidateQueries()`)
- Remove 5-minute global interval; replace with SWR with a 2-minute `refreshInterval` + on-focus revalidation (`revalidateOnFocus: true`)

### R-UI-011: No Design for Employee Whose Device Is Not Registered

**Severity:** MEDIUM

**Finding:** The employee profile (Section 5.3) mentions "Device: ✓ Registered" / "Device: ✗ Not Registered" but there is no design for what admins see when an employee has NO registered device and tries to log in. This state is critical for onboarding new employees.

Also missing: what happens when admin views an employee's profile before device registration — no call-to-action flow to guide the admin through device registration as an onboarding step.

**Fix:** Add to Section 5.3:
- "Device: ✗ Not Registered" in header → amber badge
- An inline banner on the profile: "This employee has no registered device and cannot check in. [Register Device →]"
- Register Device action prominently highlighted (not just in Quick Actions dropdown) when device is unregistered

### R-UI-012: Leave Balance Display — Carry-Forward Expiry Edge Case

**Severity:** MEDIUM

**Finding:** Section 7.3 mentions "CF Expiry" column with "amber badge if within 30 days." However, when carry-forward has ALREADY expired, the displayed balance may show stale carry-forward days that employees and admins think are still available.

**Fix:**
- When `cfExpiryDate < today`: show balance with strikethrough or separate "Expired CF" label in gray
- Expired carry-forward days must be visually distinct from current-year balance
- API response should distinguish `currentYearBalance` vs `carriedForwardBalance` vs `expiredCfBalance` — confirm this is returned by `GET /leaves/balance`

## LOW Severity Findings

### R-UI-013: Color System Missing Dark Mode Strategy

**Severity:** LOW

**Finding:** Section 1.3 defines CSS variables for light mode only. No dark mode strategy is defined. While dark mode is not a V1 requirement, the shadcn/ui component library supports it out-of-the-box via `class="dark"` on `<html>`. Not planning for it now makes it harder to add later.

**Recommendation:** Add a note in Section 1.3 indicating dark mode is deferred to V1.1. Add `.dark {}` overrides as a placeholder comment block in `globals.css` so the structure is ready.

**Severity:** LOW

**Finding:** Section 12.1 shows action types like `LEAVE_APPROVED`, `EMPLOYEE_UPDATED`, `PAYROLL_FINALISED` but there is no complete list of all possible action types. Admins viewing the audit log won't know what all values mean without documentation.

### R-UI-016: No Breadcrumb Design for Settings Nested Navigation

**Severity:** LOW

### R-UI-018: Mobile Viewport Handling — No 403 / Redirect for Small Screens

**Severity:** LOW

**Finding:** The admin portal is explicitly desktop-first (minimum 1366px). However no design handles what happens when an admin opens the portal on a 375px mobile screen. The current design will simply render broken (sidebar 240px + content area collapsing).

**Recommendation:** Add a mobile-viewport guard: detect viewport width < 1024px and show a full-screen message:
```
┌──────────────────────────────────┐
│                                  │
│  ⬡ WorkForce Pro                 │
│                                  │
│  Admin portal is designed for    │
│  desktop. Please open on a       │
│  computer with a screen width    │
│  of at least 1366px.             │
│                                  │
└──────────────────────────────────┘
```
Implemented via CSS `@media (max-width: 1023px)` + overlay or middleware redirect. No need for responsive redesign.

## Scalability Concerns

### SC-001: Dashboard Live Attendance — Real-Time at Scale

The dashboard polls attendance data every 30 seconds (SWR `refreshInterval`). With 500 employees, each poll returns up to 500 records. At 20 concurrent admin sessions, this generates 20 × 2 = 40 API calls per minute to `GET /attendance/today`. This is manageable at M10 Atlas, but should be documented as a known scaling point. At 2,000+ employees, consider:
- Server-sent events (SSE) or WebSocket for live updates
- Pagination on live attendance panel (only fetch first 20; "View All" loads rest)

### SC-002: Payroll Compute Progress — No Real-Time Feedback for Large Companies

Section 9.2 shows a "Processing 45 employees... 38/45" progress bar. However, `POST /payroll/compute` is a single API call. The progress display would need to either:
a) Poll a job status endpoint repeatedly (not designed in current API spec)
b) Use SSE or chunked response
c) Simply show a spinner until the response completes

For >100 employees, compute can take 30–60 seconds. The current design assumes near-instant. This needs a job-status pattern or an explicit "check back later" UX.

### SC-003: Leave Balances Table — No Virtualization at Scale

Section 7.3 loads all employees with no pagination for the Leave Balances table. At 500+ employees, this is a single API response with 500 rows and 4–6 balance calculations per row. Add pagination (20/page) or TanStack Virtual.
