## Root Cause: Category C — Dev-Mode First-Request Compilation

### Breakdown of First-Request Timing

| Component | Time | Source |
|---|---|---|
| Turbopack compile `settings/route.ts` | **2.7s** | `next.js: 2.7s` in server log |
| MongoDB `findById('company-settings')` | ~250ms | `application-code: 307ms` includes connection reuse + query |
| Network (Node.js native fetch, localhost) | ~35ms | end-to-end – server time |
| **Total first request** | **~3.0s** | measured client-side |

Second and subsequent requests: **~246ms** (compile artifact cached, only MongoDB round-trip).

### Why Earlier Tests Showed ">55s Never Completes"

1. **PowerShell client TCP overhead**: `Invoke-RestMethod` to `localhost:3001` was measuring 12–16s of connection overhead per request. This is a Windows PowerShell HTTP client behavior — verified by comparing server log (login: 1.2s) vs PowerShell timing (~15–20s for same login).

2. **Server cold state**: First tests were run against a colder server with no prior login. When the very first request ever to `settings/route.ts` arrived, Turbopack needed to resolve and compile all imported modules (SettingsService, CompanySettings model, requireAuth, requireRole, api-response utils). This may have taken 15–30s on a cold module graph.

3. **30-second default PowerShell timeout**: The initial tests used `TimeoutSec 30` (PowerShell default). With 13s client overhead + 20–30s cold compilation = 33–43s total, the 30s timeout fired before the response arrived.

4. **Appearing as a "hang"**: PowerShell timeout = no output written (process exits with exception). Subsequent re-test attempts reused the same server process which had already compiled more of the module graph, giving inconsistent timing.

### What Is NOT the Root Cause

| Candidate | Ruled Out By |
|---|---|
| A. Missing CompanySettings document | Endpoint returns 200 with real data from MongoDB |
| B. Bug in `requireSettings()` | Returns correctly; `if (!s) throw` path not triggered |
| D. JWT/auth failure | HTTP 200 returned; auth passed |
| E. MongoDB connection hang | Login and /settings/company both work; same connection used |
| F. Import cycle | Build passes; no module-resolution errors |
| G. Route conflict | `/settings/company` and `/settings` coexist correctly |

## Minimal Fix (If Required)

No fix required. The behavior is expected in Next.js Turbopack dev mode. Newly created route files are compiled on first request rather than eagerly at server startup.

If faster first-request DX is desired, warm up the route by sending a request at server startup (not needed for production).

---

## Regression Risk

None. The endpoint is implemented correctly, returns HTTP 200 with properly shaped data, and performs at ~250ms after the one-time compilation warm-up.

---

## Conclusion

**`GET /api/v1/settings` is functional.** The reported ">55s hang" was a measurement artifact caused by the combination of:

1. Turbopack on-demand compilation of a newly created route file (~20–30s on cold server, ~2.7s on warm server)
2. Windows PowerShell HTTP client overhead (~13s per localhost request)
3. A 30-second default `Invoke-RestMethod` timeout that fired before the compilation completed

The endpoint returns HTTP 200 with correct data. The CompanySettings document exists in MongoDB Atlas. No code change is required.
