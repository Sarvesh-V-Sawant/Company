## 5. Approval Recommendation

### Would I approve this testing strategy for implementation and QA execution?

**Yes — approved for implementation.**

---

### Justification

**What earns approval:**

**The strategy now fully closes the five gaps that would cause the most expensive mid-project corrections:**

1. **Timezone correctness (R-001).** Silent `dateString` attribution errors in a workforce management platform accumulate quietly into payroll discrepancies that are discovered only at month-end when someone compares the system to manual registers. Five explicit test cases with exact UTC/IST pairs make this testable from day one.

2. **Session security lifecycle (R-005).** The refresh token policy was the only authentication design that remained unspecified after the architecture and database phases. Without a defined policy, both the service implementation and the Flutter client would make independent assumptions that are almost certainly incompatible. Section 2.11 closes this — one document, one decision, tested from both directions (U-AUTH-15 to U-AUTH-20 at unit level; TC-SEC-021 to TC-SEC-025 at integration level).

3. **Leave-attendance interaction (R-003).** The explicit rule "approved leave overrides attendance status" is a domain decision that cannot be inferred from the schema. Without it, some implementors would write the leave service to fail if an active session exists; others would let both records coexist with undefined payroll behavior. TC-LVE-026 to TC-LVE-030 enforce the decision.

4. **Payroll amendment workflow (R-004).** The unfinalize operation fills a genuine functional gap: every HRMS must handle the scenario where a payroll is finalised and then a leave decision changes retroactively. Without the unfinalize pathway, admins have no recourse except direct database manipulation. The five new test cases plus the two unit tests make this workflow fully testable and auditable.

5. **Employee reactivation integrity (R-002).** The deactivation and reactivation scenarios are infrequent in practice but high-stakes when they occur. The five test cases ensure that security (session revocation), data integrity (balance preservation), and auditability (continuous audit trail) are all verified — not assumed.

**What is still acceptable at this stage (not blocking):**

- The 8 MEDIUM findings are genuine edge cases (fiscal year half-day boundary, pro-rated leaver, `monthlySalary: 0`), not functional gaps in the primary paths. They can be added incrementally during implementation as the relevant services are developed.
- Missing CI YAML and Atlas isolation strategy are infrastructure configuration, not design — they belong in the implementation phase.
- The mutation testing advisory and performance baseline persistence are V1-advisory quality improvements that do not affect whether the strategy is safe to implement against.

**The test counts:**
- 291 total scenarios (186 enumerated TC-IDs + 105 implied unit test scenarios)
- Well above the 150-scenario minimum
- Spread correctly across the pyramid: more unit tests, fewer E2E tests

**The strategy is correct in what it tests hardest:** the payroll engine (100% specified coverage), concurrency (real Atlas required), and security (25 scenarios covering every threat in the architecture security score). These are the three areas where defects cause the most damage — financial, operational, and reputational respectively.

**Conditions for this approval:**

1. Apply R-006 through R-014 (MEDIUM findings) before implementation of `leaveService.carryForward()` and `payrollService.compute()` — these are the two services where the remaining gaps bite hardest.
2. Add `deviceSessions.absoluteExpiresAt` to `docs/02-database-design.md` and `payrollSummaries.unfinalisedAt / unfinalisedBy` during the database implementation phase (not before — they are well-defined here and do not require another document cycle).
3. Write GitHub Actions CI YAML alongside the first service implementation — not before.

**Bottom line:** This testing strategy documents every ambiguous business rule that would otherwise cause a mid-sprint correction, covers all critical concurrency and security scenarios, and specifies tooling precisely enough for implementation to begin without further design work.

**Approved for implementation and QA execution — subject to the 3 conditions above.**
