## Summary of Changes from Initial Design (doc 30)

| Area | Old Design | Revised Design |
|---|---|---|
| Tracking trigger | Only when outside geofence at check-in | All check-ins when company tracking is enabled |
| `insideGeofence` evaluation | At check-in only | Independently per ping, server-side |
| `AttendanceSession` | No tracking field | Add `trackingEnabled: boolean` at session creation |
| Settings | 4 fields | 8 configurable fields including visibility rules |
| LocationPing model | 9 fields | 14 fields including `speed`, `provider`, `syncStatus`, `clientQueuedAt` |
| Android background | WorkManager only | Foreground Service (primary) + WorkManager heartbeat (fallback) |
| iOS background | BGAppRefreshTask only | Significant Changes + BGAppRefreshTask combo → `UIBackgroundModes: location` in later phase |
| Admin UI | Employee sub-page | Dedicated Workforce Tracking module with live dashboard |
| Check-in response | `requiresTracking` (geofence-conditional) | `trackingEnabled` (settings-driven, unconditional) |

## Part 1 — Current State Confirmed

**Continuous employee location tracking does not exist anywhere in the codebase.**

Confirmed absent (full audit results in doc 30, Part 1):
- No background location service of any kind
- No `LocationPing` / `LocationHistory` DB collection
- No location upload, retrieval, or history APIs
- No admin map or workforce visibility UI
- No `CompanySettings.locationTracking` sub-document
- `AttendanceSession` stores only the check-in GPS point for geofence validation

What exists and is reused:
- `geolocator: ^13.0.0` already in `pubspec.yaml` — used for check-in, extended for tracking
- `CompanySettings.geoFence` — lat/lng/radius — reused for per-ping `insideGeofence` computation
- `AttendanceSession.employeeId` + `isActive` index — used as the session-boundary for tracking
- `AttendanceSession.flags.outsideGeoFence` — already flags first-ping anomaly; tracking provides richer history

## Part 2 — Refined Business Behaviour

```
Employee opens app → taps Check In
        │
        ▼
POST /api/v1/attendance/checkin → success
        │
        ├─ settings.locationTracking.enabled = false
        │        └── No tracking. Normal session. Done.
        │
        └─ settings.locationTracking.enabled = true
                 │
                 ▼
         Response includes: { trackingEnabled: true, trackingIntervalMinutes: 30 }
         AttendanceSession.trackingEnabled = true  (stored on session)
                 │
                 ▼
         Mobile starts background tracking service
         (Android: Foreground Service | iOS: CLLocationManager + bg mode)
                 │
                 ▼ every N minutes (configurable)
         1. Get GPS fix (medium accuracy)
         2. POST /api/v1/attendance/location
                 ├─ online → server stores ping, computes insideGeofence
                 └─ offline → enqueue locally, flush on reconnect
                 │
                 ▼
         Employee taps Check Out
                 │
                 ▼
         Mobile stops background tracking service immediately
         POST /api/v1/attendance/checkout → success
```

**Key behavioural rules:**
1. Tracking starts on ALL check-ins when `settings.locationTracking.enabled = true` — no geofence-at-checkin gating
2. `insideGeofence` is independently evaluated on the server for every incoming ping
3. Employees never manually control tracking — it is automatic and policy-driven
4. If the app is force-killed mid-session, the background service restarts automatically (Android: `START_STICKY`, iOS: location updates resume on device wake)
5. On app relaunch after kill/reboot, `GET /api/v1/attendance/today` response includes `trackingEnabled` so mobile restores service state without user interaction

## Part 4 — Database Design

### 4.1 New collection: `locationpings`

```typescript
// apps/admin/src/models/LocationPing.ts

interface ILocationPing extends Document {
  employeeId:          mongoose.Types.ObjectId;  // ref: User._id (= Employee._id)
  attendanceSessionId: mongoose.Types.ObjectId;  // ref: AttendanceSession
  
  // Coordinates (client-reported, validated by server)
  latitude:            number;              // -90 to 90
  longitude:           number;              // -180 to 180
  timestamp:           Date;                // client-reported event time
  accuracy:            number;              // metres — horizontal accuracy of fix
  speed:               number | null;       // m/s at time of fix; null if unavailable
  
  // Device state at ping time
  batteryLevel:        number | null;       // 0–100; null if unavailable
  provider:            'gps' | 'network' | 'fused' | 'passive' | 'unknown';
  
  // Server-computed on receipt
  insideGeofence:      boolean;             // computed from CompanySettings.geoFence
  distanceFromOffice:  number;              // metres from office centre
  
  // Delivery metadata (for analytics on offline behaviour)
  syncStatus:          'synced' | 'queued'; // 'synced'=real-time; 'queued'=was offline
  clientQueuedAt:      Date | null;         // when ping was queued offline on device; null if real-time
  
  createdAt:           Date;                // server receipt time (set by Mongoose timestamps)
}
```

**Mongoose schema:**
```typescript
const LocationPingSchema = new Schema<ILocationPing>(
  {
    employeeId:          { type: Schema.Types.ObjectId, ref: 'User', required: true, index: true },
    attendanceSessionId: { type: Schema.Types.ObjectId, ref: 'AttendanceSession', required: true },
    latitude:            { type: Number, required: true, min: -90, max: 90 },
    longitude:           { type: Number, required: true, min: -180, max: 180 },
    timestamp:           { type: Date, required: true },
    accuracy:            { type: Number, required: true, min: 0 },
    speed:               { type: Number, default: null, min: 0 },
    batteryLevel:        { type: Number, default: null, min: 0, max: 100 },
    provider:            { type: String, enum: ['gps', 'network', 'fused', 'passive', 'unknown'], default: 'unknown' },
    insideGeofence:      { type: Boolean, required: true },
    distanceFromOffice:  { type: Number, required: true, min: 0 },
    syncStatus:          { type: String, enum: ['synced', 'queued'], required: true, default: 'synced' },
    clientQueuedAt:      { type: Date, default: null },
  },
  { timestamps: true },
);

// Indexes
LocationPingSchema.index({ attendanceSessionId: 1, timestamp: 1 });       // primary query: session route
LocationPingSchema.index({ employeeId: 1, timestamp: -1 });               // employee history queries
LocationPingSchema.index({ employeeId: 1, attendanceSessionId: 1 });      // session ownership check
LocationPingSchema.index({ createdAt: 1 }, { expireAfterSeconds: 0,       // TTL — seconds set dynamically via
  name: 'ttl_locationpings' });                                            // background job reading retentionDays
```

**TTL note:** MongoDB TTL indexes require a fixed `expireAfterSeconds` value. Since `retentionDays` is configurable, the TTL index is managed via `db.collection.createIndex()` with the computed seconds value in the seed script, and updated when `retentionDays` changes via a `SettingsService.updateLocationTracking()` post-hook that calls `db.command({ collMod: 'locationpings', index: { keyPattern: { createdAt: 1 }, expireAfterSeconds: newSeconds } })`. This is a standard MongoDB pattern for dynamic TTL.

## Part 5 — API Design

### 5.1 POST /api/v1/attendance/location — upload location ping

**Auth:** employee JWT  
**Header:** `X-Device-Fingerprint` (existing pattern, for audit)

```typescript
// Request body
{
  latitude:       number,        // required
  longitude:      number,        // required
  timestamp:      string,        // ISO 8601, within ±checkinTimestampWindowMinutes of server time
  accuracy:       number,        // required, ≥ 0
  speed:          number | null, // optional
  batteryLevel:   number | null, // optional, 0–100
  provider:       string,        // optional, one of enum values
  syncStatus:     'synced' | 'queued',  // required — client declares delivery mode
  clientQueuedAt: string | null  // ISO 8601, required if syncStatus='queued', else null
}

// Success response 201
{ "success": true, "data": { "id": "...", "insideGeofence": true, "distanceFromOffice": 245 } }

// Error responses
// 400 — validation failure or timestamp outside window
// 403 — no active session OR session.trackingEnabled = false
// 409 — session is no longer active (checked out or system-closed)
```

**Server logic:**
1. Lookup active `AttendanceSession` for `employeeId` where `isActive: true`
2. If not found or `session.trackingEnabled = false` → 403
3. If `session.isActive = false` → 409 (session closed, mobile should stop tracking)
4. Validate `timestamp` within server time ± `checkinTimestampWindowMinutes`
5. Compute `insideGeofence` and `distanceFromOffice` from `CompanySettings.geoFence`
6. Insert `LocationPing`
7. Write `AuditLog` entry
8. Return 201 with `insideGeofence` + `distanceFromOffice` (mobile can display status)

## Part 6 — Background Execution Strategy

### 6.1 Android — Comparison

| Mechanism | Reliability | Battery | Doze Impact | Kill Recovery | Complexity |
|---|---|---|---|---|---|
| WorkManager PeriodicWork | Medium | Excellent | High impact — deferred to maintenance windows (every 1–6h) | Auto-restarts | Low |
| Foreground Service + Handler timer | High | Good | None — exempt from Doze while running | `START_STICKY` auto-restarts | Medium |
| AlarmManager `setExactAndAllowWhileIdle` | High | Medium | None | Requires BOOT_COMPLETED handler | High |
| WorkManager as heartbeat only | Low (supplemental) | Excellent | High impact | Auto-restarts | Low |

**Doze mode analysis for the employee device context:**

Android enters full Doze when: screen off + stationary + on battery. An employee with their phone on a desk = Doze eligible within ~30 minutes. Under full Doze, WorkManager is deferred to maintenance windows that start at ~1h intervals, expanding to 2h, 4h, etc. This means a 30-minute WorkManager interval would produce pings every 1–4+ hours under Doze — unacceptable for workforce tracking.

**App Standby Buckets (Android 9+):** A daily-used HR app stays in the "active" or "working set" bucket, where WorkManager has minimal restrictions. However, if the employee doesn't open the app for a day (they already checked in via notification), it may fall to "frequent" bucket where WorkManager gets 2 jobs per 24h. This is the failure mode.

**Foreground Service analysis:**

A Foreground Service with `foregroundServiceType="location"` (required Android 10+, mandatory Android 12+) is exempt from Doze restrictions. It runs in the app process with a persistent notification. When killed by the system or user:
- `START_STICKY`: Android restarts the service automatically (typically within 5 seconds)
- Service reads `SharedPreferences` for stored `{ sessionToken, sessionId, intervalMinutes }` and resumes
- If device reboots: `RECEIVE_BOOT_COMPLETED` broadcast triggers a check for active session; service starts if session exists

**Permissions required (Android):**
```
ACCESS_FINE_LOCATION          (already present)
ACCESS_COARSE_LOCATION        (already present)
ACCESS_BACKGROUND_LOCATION    (NEW — Android 10+)
FOREGROUND_SERVICE            (NEW)
FOREGROUND_SERVICE_LOCATION   (NEW — Android 12+)
RECEIVE_BOOT_COMPLETED        (NEW — for reboot recovery)
```

`ACCESS_BACKGROUND_LOCATION` on Android 11+ requires a separate permission request dialog that routes the user to the OS settings page. This is required by Android policy and cannot be bypassed. The app must show a rationale screen before redirecting. If denied, tracking is silently skipped (no crash, no retry loop).

**Final Android recommendation: Foreground Service (primary) + WorkManager heartbeat (backup)**

- Foreground Service owns the per-interval timer; provides reliable, Doze-exempt execution
- WorkManager PeriodicWorkRequest at 60-minute interval as a watchdog — if Foreground Service is dead and session is still active, WorkManager fires a single ping and attempts to restart the service
- This "belt-and-suspenders" approach is used by Hubstaff, TSheets, Connecteam, and Deputy for Android workforce tracking

### 6.2 iOS — Comparison

| Mechanism | Reliability | Battery | Timing Guarantee | App Store Review | Complexity |
|---|---|---|---|---|---|
| BGAppRefreshTask | Low | Excellent | None — system decides | Standard | Low |
| BGProcessingTask | Low | Good | None; requires idle+charging | Standard | Low |
| Significant Location Changes | Medium | Excellent | Event-based, not periodic | Standard | Low |
| `UIBackgroundModes: location` + CLLocationManager | High | Medium | Accurate (client-controlled timer) | Requires justification | Medium |
| `UIBackgroundModes: location` + distanceFilter | High | Good | Movement-triggered, not periodic | Requires justification | Medium |

**BGAppRefreshTask limitation:** Apple says "the system decides when to launch your app." In practice, for an app used every weekday morning, BGAppRefreshTask fires 2–6 times per day — not every 30 minutes. Under Low Power Mode it may not fire at all. Unacceptable for workforce tracking where the contract is "ping every 30 minutes."

**Significant Location Changes:** Fires when the device changes cell towers — approximately every 500m of travel. For a field employee walking between locations: reasonable. For an employee sitting at a client's office for 3 hours: may fire 0 times. Useful as a supplemental mechanism, not the primary one.

**`UIBackgroundModes: location` approach:**

When `UIBackgroundModes` includes `location`, the app can run a `CLLocationManager` with `allowsBackgroundLocationUpdates = true`. This keeps the location manager alive in the background. The app then uses a timer (NSTimer or DispatchQueue `asyncAfter`) that fires every `intervalMinutes`, gets the current position from the active `CLLocationManager`, and POSTs to the API.

This is the only iOS mechanism that provides reliable, time-based periodic location updates without requiring continuous GPS streaming.

**App Store review note:** Apple accepts `UIBackgroundModes: location` for B2B workforce management apps. The review question is "Does your app use location for user tracking?" — the answer for a workforce management app is yes, with the justification that employees consent at device registration and the feature is employer-operated. Apps like Hubstaff, TSheets, and Deputy are approved with this pattern.

**Final iOS recommendation:**

Phase 16.3: `UIBackgroundModes: location` with `CLLocationManager` background mode + interval timer.

Justification: The "employees must never manually start or stop tracking" requirement combined with the "periodic every N minutes" requirement cannot be reliably satisfied with BGAppRefreshTask. The `UIBackgroundModes: location` approach is the only iOS mechanism that delivers on the business requirement. App Store approval is attainable for a B2B workforce app with proper description.

**iOS permissions required:**
```
NSLocationWhenInUseUsageDescription   (already present)
NSLocationAlwaysAndWhenInUseUsageDescription  (already present)
NSLocationAlwaysUsageDescription      (NEW)
UIBackgroundModes: ["location"]       (NEW)
```

No `BGTaskSchedulerPermittedIdentifiers` needed (removing from initial design).

### 6.3 Architecture Recommendation Summary

```
Android:  Foreground Service (primary)  + WorkManager 60min heartbeat (watchdog)
iOS:      CLLocationManager background  + UIBackgroundModes: location
Both:     Shared Dart logic in LocationTrackingService for API calls + offline queue
```

## Part 9 — Future Analytics (Enabled by Proposed Data Model)

The `LocationPing` schema with `timestamp`, `latitude`, `longitude`, `insideGeofence`, `distanceFromOffice`, `speed`, `batteryLevel`, `syncStatus`, `attendanceSessionId`, and `employeeId` enables:

| Analytics | Implementation |
|---|---|
| **Route replay** | Load session pings in order; animate marker along polyline at configurable speed |
| **Distance travelled per day** | Sum haversine distances between consecutive pings per session |
| **Time inside/outside office** | Sum intervals between consecutive ping pairs where both share same `insideGeofence` value |
| **Missed ping detection** | Gap between consecutive ping timestamps > 1.5× `intervalMinutes` → "missed update" |
| **Suspicious movement** | Distance between consecutive pings ÷ time interval > physically possible speed (>200 km/h) → flag as anomaly; triggers `AuditLog` entry |
| **Workforce heatmap** | Aggregate all pings for a date range into grid cells; visualise density on map (future admin report) |
| **Battery drain correlation** | Cross-reference `batteryLevel` trend with tracking gap occurrence — identify employees with consistently low battery |
| **Late arrival indicator** | Compare `checkIn.timestamp` with `workStartTime`; first ping's `insideGeofence` shows whether employee was at office on time |
| **Field time reporting** | `timeOutsideGeofenceMinutes` per session, aggregated by week/month; exportable for payroll/expense analysis |
| **Sync health report** | % of pings with `syncStatus: 'queued'` per employee — identifies connectivity problem areas |
| **Department location patterns** | Group pings by `employeeId → department`; see which departments spend most time in/outside office; input for facility planning |

These analytics require no additional DB schema changes — they are queries and aggregations over `LocationPing` + joins with `AttendanceSession` and `User`/`Employee`.

## Part 10 — Security Analysis (Updated)

| Threat | Mitigation |
|---|---|
| GPS coordinate spoofing | `accuracy` field captured; `distanceFromOffice` computed server-side. Speed anomaly detection (> 200 km/h between consecutive pings) written to `AuditLog`. Cannot fully prevent mock GPS without device attestation (SafetyNet/Play Integrity — future). |
| Replay of old pings | Timestamp validated within `±checkinTimestampWindowMinutes` of server time. |
| Employee uploads pings for another employee's session | Server resolves `employeeId` from JWT `userId` — cannot impersonate another employee. |
| Unauthorized session access | `AttendanceSession` ownership checked before every ping insert; 403 if `session.employeeId ≠ JWT.userId`. |
| Admin reads wrong employee data | Routes enforce admin JWT; no tenant isolation issue (single-tenant). `adminVisibility` setting enforced at service layer. |
| Stale token in background service | On 401 from ping endpoint: background service clears stored token, posts notification to app, stops tracking. Employee must re-authenticate. Token refresh via `/api/v1/auth/refresh` attempted first. |
| Session closed while tracking | `POST /attendance/location` returns 409 if `isActive = false`. Mobile stops tracking, clears queue. |
| Ping flood (rapid repeated pings) | Rate limiter (`attendanceLimiter`, existing middleware) applied to location endpoint. Per-user sliding window. |

## Part 11 — Privacy Analysis (Updated)

1. **Scope:** Location collected only during active attendance sessions where `trackingEnabled = true`. Zero location data collected outside checked-in hours.

2. **Transparency — mobile:** While `trackingEnabled = true`, persistent status chip on home screen: "Location tracked · every 30 min." Not dismissible. Disappears on checkout.

3. **Employee self-access:** `GET /api/v1/attendance/[sessionId]/location` accepts employee JWT scoped to own sessions. Employees can view their own location history.

4. **Data minimisation:** Only lat/lng/accuracy/speed/battery captured. No street address reverse-geocoding stored. No contacts, call log, or app usage collected.

5. **Retention:** TTL index purges pings automatically after `retentionDays` (default 90). On employee offboarding (account deactivation), an explicit `LocationPing.deleteMany({ employeeId })` should be called (separate data retention workflow — not part of Phase 16).

6. **Audit logging:** Every ping upload logged to `AuditLog` with `action: 'LOCATION_PING_RECEIVED'`. Every admin retrieval logged with `action: 'LOCATION_HISTORY_VIEWED'`. Provides compliance evidence.

7. **Employee onboarding consent:** Device registration flow should be updated to include explicit workforce tracking consent disclosure. Seed scripts update company settings description, not a code path change.

## Part 12 — Offline Behaviour

```
Device loses network during active session
        │
        ▼
GPS fix acquired at scheduled interval
        │
        ▼
POST /attendance/location fails (timeout / unreachable)
        │
        ▼
Read settings.offlineQueueEnabled
  ├─ false → skip ping, log locally
  └─ true → enqueue ping to SharedPreferences
                │
                ├─ queue size < maxEntries (20)? → append
                └─ queue full → drop OLDEST entry, append NEW
                                (prefer recent location over old)
        │
        ▼ Network restored (connectivity_plus fires)
        │
        ▼
Prune entries older than maxOfflineQueueDurationHours
        │
        ▼
Flush remaining in chronological order:
  POST each ping with syncStatus='queued', clientQueuedAt=<queued time>
  ├─ 201 → remove from queue, continue
  ├─ 409 → session closed — stop tracking, clear entire queue
  └─ 4xx (other) → discard that ping, continue flushing
  └─ 5xx / timeout → stop flush, retry on next connectivity event
```

**Queue implementation:** `SharedPreferences` key `location_ping_queue` stores JSON array. Max 20 entries. Write-ahead pattern: enqueue before POST attempt, dequeue only on confirmed 201.

## Part 15 — Risks (Updated)

| Risk | Probability | Impact | Mitigation |
|---|---|---|---|
| Apple App Store review flags `UIBackgroundModes: location` | Low | High | B2B workforce apps with employer consent are routinely approved. Prepare App Store description explaining use case. Fallback: ship BGAppRefreshTask-only iOS first while review proceeds. |
| Android `ACCESS_BACKGROUND_LOCATION` denied by majority of users | Medium | Medium | Feature degrades gracefully. Tracking skipped, no crash. UI informs employee. Admin sees "tracking unavailable" in live dashboard. |
| Android foreground service killed permanently (aggressive OEM battery managers — Huawei, Xiaomi, Samsung One UI) | Medium | Medium | WorkManager watchdog partially compensates. Document OEM-specific battery exemption as known limitation in user guide. |
| TTL index update on `retentionDays` change causes brief collection scan on large dataset | Low | Low | MongoDB `collMod` TTL change is a metadata operation, not a full collection scan. Near-instant. |
| Large `locationpings` collection degrades live dashboard query (many active employees) | Low | Medium | Dashboard query: `AttendanceSession.find({ isActive: true, trackingEnabled: true })` → N lookups for latest ping. Add `{ employeeId: 1, createdAt: -1 }` index on `locationpings`. For >500 simultaneous sessions, consider caching latest-ping in Redis (Phase 16.5 optimisation). |
| iOS timer-based approach uses more battery than expected | Low | Low | Use `kCLLocationAccuracyHundredMeters` for periodic pings, not `.best`. GPS fix time with lower accuracy: ~2–5s vs. ~10–20s. Significant battery saving. |
