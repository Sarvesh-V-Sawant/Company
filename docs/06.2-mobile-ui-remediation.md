## R-MOB-001 — Device Registration Lifecycle

### Root Cause

The login screen sends the device fingerprint in `POST /auth/login` body. The API spec specifies that `users.registeredDeviceHash` is set by the admin via `PATCH /employees/:id/register-device`. No error code or UX was designed for the case where `registeredDeviceHash === null` (no device ever registered). The spec conflated three distinct device states into a single `ATT_003 DEVICE_MISMATCH` error, leaving new employees with no path forward.

### UX Impact

New employees receive credentials from admin (email + temp password) and install the app. First login attempt fails with an undifferentiated error. No screen exists to guide them through the only available recovery: share their device fingerprint with admin. Without this, the app is unusable for all new employees.

### Security Impact

Medium. If `AUTH_011 NO_DEVICE_REGISTERED` is introduced, the server reveals that no device is registered for this account. This leaks account existence but does not compromise credentials. Acceptable given corporate internal tool context.

### Data Integrity Impact

None — no data can be written until login succeeds.

### Fix

**Three-part fix:**
1. Server differentiates `ATT_003 DEVICE_MISMATCH` (different device registered) from `AUTH_011 NO_DEVICE_REGISTERED` (no device registered yet)
2. New screen `/device-not-registered` — shows fingerprint, copy button, instructions
3. New screen `/device-awaiting-registration` — waiting state after employee has notified admin

## R-MOB-002 — Attendance State Recovery

### Root Cause

The check-in state machine in Section 4.1 was purely client-side. `CHECKED_IN` state was tracked in Riverpod `StateProvider` — ephemeral, lost on app kill. No mechanism existed to reconcile client state with server state on app restart. The server is the authoritative source of truth for attendance sessions, but the app never queried it to restore UI state.

### UX Impact

Employee checks in at 09:00 → app killed → reopens at 11:00 → app shows IDLE (not checked in) → live timer gone → employee's check-in time unknown → CHECK IN button incorrectly enabled → employee taps it → server rejects duplicate session OR creates erroneous second session.

### Security Impact

Low. No credential exposure. Risk: inflated session counts if duplicate check-ins are accepted by server due to missing deduplication.

### Data Integrity Impact

High. Server may have correct attendance data but app shows incorrect state. Employee presses CHECK IN again → second session created for same day → payroll computation may see incorrect session data.

### Fix

**Server-authoritative state restoration on every app foreground.** `GET /attendance/today` is called:
1. On app startup (Splash → Home)
2. On `AppLifecycleState.resumed`
3. After any check-in/out API call completes

Response is the source of truth for all attendance UI state.

### New API Dependency

`GET /attendance/today` response must include sufficient fields for state restoration. See `docs/06.2-api-gap-analysis.md` for required response shape.

### State Reconciliation Logic

```dart
// AttendanceNotifier.reconcileWithServer()
final todayData = await api.getAttendanceToday();

if (todayData.isCheckedIn) {
  // Currently checked in — restore timer from server timestamp
  state = AttendanceState.checkedIn(
    checkInTimestamp: todayData.currentSessionStart,
    totalMinutesToday: todayData.totalMinutesToday,
  );
} else if (todayData.sessions.isNotEmpty && !todayData.isCheckedIn) {
  // Has sessions but currently checked out
  final totalMinutes = todayData.totalMinutesToday;
  final required = companySettings.requiredDailyMinutes;
  if (totalMinutes >= required) {
    state = AttendanceState.checkedOutComplete(
      totalMinutesToday: totalMinutes,
      sessions: todayData.sessions,
    );
  } else {
    state = AttendanceState.checkedOutPartial(  // R-MOB-004 fix
      totalMinutesToday: totalMinutes,
      sessions: todayData.sessions,
    );
  }
} else {
  // No sessions today — not checked in
  state = AttendanceState.idle();
}
```

### Timer Restoration

When `AttendanceState.checkedIn` is restored:
```dart
// Compute elapsed from server-provided timestamp (IST)
final checkInTime = DateTime.parse(todayData.currentSessionStart).toLocal();
final elapsed = DateTime.now().difference(checkInTime);
// Start timer from this elapsed value (not from 0)
_startTimer(initialElapsed: elapsed);
```

**"Last synced" indicator** in status card:
```
│  ● Checked In              │
│  Since 09:02 AM            │
│  ─────────────────────── │
│  5h 32m elapsed            │
│  🔄 Synced 09:15 AM        │  ← timestamp of last server sync
```
Reassures employee that the timer reflects actual server data, not just local tracking.

### Updated State Machine (with Recovery)

```
APP_OPEN / FOREGROUND_RESUMED
  → GET /attendance/today (always)
  → RECONCILING (brief loading state)
  → [see reconciliation logic above]
  → IDLE | CHECKED_IN | CHECKED_OUT_PARTIAL | CHECKED_OUT_COMPLETE

IDLE
  → [CHECK IN] tapped → GPS flow → CHECKIN_SUBMITTING → CHECKED_IN
  → After success: GET /attendance/today (reconcile again)

CHECKED_IN
  → [CHECK OUT] tapped → CHECKOUT_SUBMITTING → CHECKED_OUT_PARTIAL or CHECKED_OUT_COMPLETE
  → After success: GET /attendance/today (reconcile again)
```

### Loading State During Reconciliation

```
┌──────────────────────────┐
│  ▪▪▪ Loading...          │  ← shimmer card (300ms max)
│  ▪▪▪▪▪▪▪▪▪▪▪             │
│  ─────────────────────── │
│  [          ]            │  ← shimmer button
└──────────────────────────┘
```

Maximum 300ms shimmer. If `GET /attendance/today` takes longer: show shimmer until response. Never show stale client state when server state is being fetched.

### Updated Components

**`AttendanceNotifier` (Riverpod `AsyncNotifier`):**
- `reconcileWithServer()` method called on init and on foreground resume
- `AppLifecycleListener` widget in root app monitors state changes and calls `ref.read(attendanceProvider.notifier).reconcileWithServer()`
- State is `AsyncValue<AttendanceState>` — loading/data/error variants

**`AppLifecycleObserver`:** `WidgetsBindingObserver` registered in root widget. On `didChangeAppLifecycleState(AppLifecycleState.resumed)` → `attendanceNotifier.reconcileWithServer()`.

## R-MOB-003 — FCM Token Lifecycle

### Root Cause

FCM requires a device token to deliver push notifications. The token is generated by `FirebaseMessaging.instance.getToken()` and must be sent to the server after each login and whenever the token refreshes. No endpoint existed in the API spec for storing this token. No lifecycle handling was designed for token refresh, permission denial, or cleanup on logout.

### UX Impact

Silent failure: push notifications stop arriving after token refresh (~60 days), app reinstall, or Firebase project change. Employee misses leave approval/rejection notifications — discovers only by checking app manually.

### Security Impact

Low. FCM tokens are not authentication credentials. Exposure of a token allows sending notifications to that device but not accessing account data.

### Data Integrity Impact

Low. Missed notifications are cosmetic; approval status is queryable from the app.

### Fix

Four-part fix:
1. Send FCM token to server after successful login
2. Listen for FCM token refresh and re-send immediately
3. Request notification permission with graceful denial handling
4. Clear FCM token association on logout

### FCM Token Lifecycle Flow

```dart
// In AuthNotifier — after POST /auth/login success

// Step 1: Request notification permission
final permission = await FirebaseMessaging.instance.requestPermission();

if (permission.authorizationStatus == AuthorizationStatus.authorized) {
  // Step 2: Get FCM token
  final token = await FirebaseMessaging.instance.getToken();
  if (token != null) {
    // Step 3: Send to server
    await api.updateFcmToken(token);   // PATCH /auth/me/fcm-token
    // Step 4: Store locally for comparison
    await prefs.setString('lastFcmToken', token);
  }
}

// Step 5: Listen for refresh
FirebaseMessaging.instance.onTokenRefresh.listen((newToken) async {
  await api.updateFcmToken(newToken);
  await prefs.setString('lastFcmToken', newToken);
});
```

**On app foreground (`AppLifecycleState.resumed`):**
```dart
final storedToken = prefs.getString('lastFcmToken');
final currentToken = await FirebaseMessaging.instance.getToken();
if (currentToken != null && currentToken != storedToken) {
  // Token changed while app was backgrounded/killed
  await api.updateFcmToken(currentToken);
  await prefs.setString('lastFcmToken', currentToken);
}
```

**On logout:**
```dart
// PATCH /auth/me/fcm-token with null (or dedicated DELETE endpoint)
await api.clearFcmToken();   // PATCH /auth/me/fcm-token { fcmToken: null }
await prefs.remove('lastFcmToken');
// Then proceed with POST /auth/logout
```

### Notification Permission UX

Notification permission requested ONCE after login success (not on first app launch — too early, no context). Only requested when `permission.authorizationStatus == AuthorizationStatus.notDetermined`.

## R-MOB-004 — Re-Check-In Workflow (Multiple Sessions Per Day)

### Root Cause

The attendance state machine terminated at `CHECKED_OUT → disabled button`. The API spec and approved database schema allow multiple attendance sessions per day (sessions are an array). The business model supports employees checking out for lunch and returning — a standard scenario. The UX incorrectly disabled re-check-in after first checkout.

### UX Impact

Employee checks out for lunch → sees disabled "CHECKED OUT TODAY" button → cannot record afternoon work hours → payroll for that day reflects only morning hours → incorrect salary computation.

### Security Impact

None.

### Data Integrity Impact

High. Missed afternoon sessions → incorrect `effectivePresentMinutes` → incorrect payroll deduction for that day. Silent error — employee may not notice until payslip review.

### Fix

Add `CHECKED_OUT_PARTIAL` state — distinct from `CHECKED_OUT_COMPLETE`. Determined by comparing `totalMinutesToday` with `companySettings.requiredDailyMinutes`.

### Updated State Machine

```
Full state machine (v2):

APP_OPEN / FOREGROUND_RESUMED
  → RECONCILING
  → (server data) → correct state below

IDLE (no sessions today)
  Button: [CHECK IN] blue
  Timer: not shown
  → tap → GPS flow → CHECKIN_SUBMITTING → CHECKED_IN

CHECKED_IN (active session)
  Button: [CHECK OUT] red
  Timer: live elapsed + remaining
  Status card: ● Checked In · Since HH:mm
  → tap → CHECKOUT_SUBMITTING
      → totalMinutes >= required: CHECKED_OUT_COMPLETE
      → totalMinutes <  required: CHECKED_OUT_PARTIAL

CHECKED_OUT_PARTIAL (checked out, hours incomplete)
  Button: [CHECK IN AGAIN] green-amber
  Status card: ◑ Checked Out (Partial)
  Sub-text: 4h 15m recorded · 4h 45m remaining
  Sessions list: shows completed session
  → tap → GPS flow (same as IDLE) → CHECKIN_SUBMITTING → CHECKED_IN

CHECKED_OUT_COMPLETE (daily hours met or exceeded)
  Button: [DAILY HOURS COMPLETE] disabled gray
  Status card: ✓ Day Complete
  Sub-text: 9h 15m recorded today
  Sessions list: shows all sessions
  Note: employee CAN still tap if they need to record extra hours → 
        optional: show [Record Extra Hours] secondary button (grey outline)

CHECKIN_SUBMITTING (GPS passed, API in flight)
  Button: [CHECKING IN…] disabled spinner

CHECKOUT_SUBMITTING (API in flight)
  Button: [CHECKING OUT…] disabled spinner
```

### CHECKED_OUT_PARTIAL State Design

```
┌──────────────────────────┐

│  Checked Out · Lunch     │

│ Session 1            │
│ In: 09:02 · Out:13:00│

└──────────────────────┘
```

**Threshold logic:**
```dart

}
```

**"Record Extra Hours" secondary button** (when `CHECKED_OUT_COMPLETE`):

```
[+ Record Extra Hours]     ← outline button; rare case for overtime
```
Tapping `[+ Record Extra Hours]` confirms: "You've already met your required hours. Record additional hours?" → same GPS flow → new session.

Prevents accidental checkout. Only shown when remaining > 2 hours (not for end-of-day checkout).

## R-MOB-005 — Duplicate Submission Protection

### Root Cause

All write operations (check-in, check-out, apply leave, submit regularization) used standard Dio requests without idempotency. On network timeout: Dio receives no response → throws `DioExceptionType.connectionTimeout` → app shows error → user retries → server may have already processed the first request → duplicate record created.

### UX Impact

Employee submits leave request → network drops mid-request → app shows error → employee retries → two identical leave requests visible to admin → confusion → admin must manually cancel one.

### Security Impact

Low. Double check-ins could affect payroll. Double leave requests cause admin confusion.

### Data Integrity Impact

High. Duplicate attendance sessions → overstated hours → incorrect payroll. Duplicate leave requests → incorrect leave balance if both approved.

### Fix

**Idempotency key per form submission.** UUID v4 generated BEFORE the API call, persisted in Hive, sent as `X-Idempotency-Key` header. Server uses this to deduplicate. Client clears key only on confirmed success.

### Idempotency Key Storage

```dart
// lib/services/submission_service.dart
class PendingSubmission {
  final String idempotencyKey;   // UUID v4
  final String endpoint;          // e.g. '/leaves'
  final Map<String, dynamic> body;
  final DateTime createdAt;
  SubmissionStatus status;        // pending | confirmed | failed
}

// Hive box: 'pending_submissions'
// Key: idempotencyKey (String)
// Value: PendingSubmission (Hive adapter)
```

### Submission Flow

```
FORM SUBMIT TAPPED
  → Check Hive for existing pending submission for this endpoint
      Found + status = pending → reuse existing key (retry)
      Not found → generate new UUID v4 key → store in Hive
  → Disable submit button + show "Submitting…" banner
  → API call with X-Idempotency-Key header
      
  SUCCESS (2xx)
      → Mark Hive record as 'confirmed'
      → Clear from Hive after 1 minute (grace period for dedup)
      → Navigate / show success
  
  SERVER 409 CONFLICT (server already processed this key)
      → Treat as success (idempotent response)
      → Show success state (same as normal success)
      → Clear Hive record
  
  NETWORK ERROR / TIMEOUT
      → Status remains 'pending' in Hive
      → Show error snackbar + [Retry] button
      → [Retry] → reuse same key → retry API call
      → Button re-enabled
  
  4xx CLIENT ERROR (not 409)
      → Mark as 'failed' in Hive (don't retry automatically)
      → Show error message
      → Clear Hive record after 5 minutes

  APP KILLED mid-submission
      → On restart: check Hive for 'pending' submissions
      → Found → show "You have a pending submission" banner
      → Employee taps [Check Status] → verify via GET on the resource
             Resource found → treat as success, clear Hive
             Not found → show [Retry] to resubmit with same key
```

### Pending Submission Banner

Shown on Home screen if a pending submission exists in Hive after app restart:

```
┌────────────────────────────┐
│  ⏳ Pending Submission      │
│  Leave request from 09:15  │
│  may not have been sent.   │
│  [ Check Status ] [Dismiss]│
└────────────────────────────┘
```

`[Check Status]`:
- Calls `GET /leaves?status=pending` (or `GET /regularizations?status=pending`)
- If record found (matching date + type from Hive): "Submitted successfully!" → clear Hive record
- If not found: "Not submitted. [Retry Now]"

`[Dismiss]`: marks Hive record as 'dismissed'; banner hidden. Does not retry.

### Form States During Submission

```
IDLE
  ┌──────────────────────┐
  │ [   Submit Request ] │   ← enabled
  └──────────────────────┘

SUBMITTING
  ┌──────────────────────┐
  │  ⏳ Submitting…       │   ← disabled, spinner in button
  └──────────────────────┘
  ┌──────────────────────┐
  │  Don't close this    │   ← amber banner above submit
  │  screen yet.         │
  └──────────────────────┘

SUCCESS
  ← Navigate to history screen
  SnackBar: "Request submitted." (Sonner-equivalent: `ScaffoldMessenger`)

FAILED (network)
  ┌──────────────────────┐
  │  [   Retry Submit  ] │   ← enabled (reuses same idempotency key)
  └──────────────────────┘
  SnackBar: "Submission failed. Tap Retry to try again."

FAILED (4xx, non-409)
  ┌──────────────────────┐
  │  [   Submit Request] │   ← re-enabled with fresh key for user to fix
  └──────────────────────┘
  SnackBar: error message from API (validation error, etc.)
```

### Scope: Which Operations Use Idempotency Keys

| Operation | Endpoint | Idempotency Key |
|---|---|---|
| Apply Leave | `POST /leaves` | Yes |
| Submit Regularization | `POST /regularizations` | Yes |
| Check In | `POST /attendance/checkin` | Yes (nonce serves same purpose — align with server) |
| Check Out | `POST /attendance/checkout` | Yes |

**Check-In special case:** The `nonce` field in the checkin request body already serves as an idempotency key server-side. The `X-Idempotency-Key` header aligns client-side Hive persistence with this existing pattern. Same UUID used as both `nonce` and `X-Idempotency-Key` for check-in.

### Updated Components

**`SubmissionService`:** Riverpod `Provider`. Manages Hive box `pending_submissions`. Methods: `beginSubmission()`, `confirmSubmission()`, `failSubmission()`, `retrySubmission()`, `checkPendingOnStartup()`.

**`PendingSubmissionBanner`:** Rendered on Home screen when `SubmissionService.hasPending` is true. Shows endpoint-specific message.

**`IdempotentFormMixin`:** Dart mixin for all form screens. Provides `submitWithIdempotency()` method. Wraps API call with key lifecycle.

### API Dependencies

| Dependency | Type | Details |
|---|---|---|
| `X-Idempotency-Key` header | New | Server must store processed keys for dedup window (24h); return `409 Conflict` on duplicate |
| `POST /leaves` — idempotency | Update | Accept and process `X-Idempotency-Key` |
| `POST /regularizations` — idempotency | Update | Same |
| `POST /attendance/checkin` — nonce alignment | Confirm | Existing `nonce` field is the idempotency key; server should return same response on duplicate nonce |
| `POST /attendance/checkout` — idempotency | Update | Add idempotency support |
