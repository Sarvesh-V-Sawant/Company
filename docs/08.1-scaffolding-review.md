### S-SC-001 — `middleware.ts` Exact Location Ambiguous

**Severity:** HIGH
**Location:** Section 1.2 — `apps/admin/` tree

**Issue:**
The spec places `middleware.ts` at `apps/admin/middleware.ts` (project root). In Next.js App Router, the accepted locations are: (a) project root, or (b) `src/middleware.ts` if the `src/` directory is the source root. The spec uses `src/app/` for the app directory, which implies `src/` is the source root — meaning `middleware.ts` should be at `apps/admin/src/middleware.ts`, not `apps/admin/middleware.ts`.

Placing it in the wrong location causes the guard chain (Maintenance → requiresPasswordChange → Unauthenticated → Role → CSRF) to silently not run. Authenticated routes will be publicly accessible with no error at startup.

**Risk:** All admin routes unprotected if middleware.ts placement is wrong. No startup error — silent failure.

**Fix:**
1. Read `node_modules/next/dist/docs/` to confirm exact middleware placement for Next.js 16.2.9 with `src/` layout.
2. Update the tree in Section 1.2 to the confirmed path before any scaffold work.
3. Add to Definition of Scaffold Complete: "Verify: unauthenticated `GET /dashboard` returns 307 redirect to `/login` (not 200)."

### S-SC-002 — `instrumentation.ts` `register()` Runtime Constraint

**Severity:** HIGH
**Location:** Section 6 — Phase 1 scaffolding + `instrumentation.ts`

**Issue:**
`instrumentation.ts` with `export async function register()` is the correct pattern for initializing Mongoose once per Vercel function instance. However:

1. Some Next.js versions require `experimental.instrumentationHook: true` in `next.config.ts` to enable `instrumentation.ts`. If not set, the file is silently ignored — Mongoose is never initialized, every API route throws `mongoose not connected`.
2. `instrumentation.ts` `register()` runs in both `node` and `edge` runtimes. If Mongoose code runs in edge runtime, it crashes. Must guard with `if (process.env.NEXT_RUNTIME === 'nodejs')`.
3. Vercel Fluid Compute reuses function instances across requests. Without `instrumentation.ts`, each request creates a new Mongoose connection (connection pool exhaustion under load).

**Risk:** Mongoose connection management is entirely broken in production without correct `instrumentation.ts` setup. No error at `npm run build` — fails only at runtime.

**Fix:**
1. Read `node_modules/next/dist/docs/` to confirm whether `experimental.instrumentationHook` is required for Next.js 16.2.9 or if it is now stable.
2. In `instrumentation.ts`: wrap Mongoose connect in `if (process.env.NEXT_RUNTIME === 'nodejs')` guard.
3. Add to `next.config.ts` if required: `experimental: { instrumentationHook: true }`.
4. Add to health check test: verify `register()` log line appears in `npm run dev` output at cold start (not on every request).

### S-SC-003 — Tailwind CSS v4 Config Strategy Not Specified

**Severity:** HIGH
**Location:** Section 2.1 — dev dependencies; Section 5.4 (referenced but not defined)

**Issue:**
The spec lists `tailwindcss@^4.x` and `@tailwindcss/postcss@^4.x` as dev dependencies and notes "v4 uses CSS-first config" with a cross-reference to Section 5.4. Section 5.4 does not exist in the document.

Tailwind CSS v4 is a major breaking change from v3:
- No `tailwind.config.ts` file (replaced by CSS `@import "tailwindcss"` and `@theme {}` blocks)
- Content scanning is automatic (no `content: []` array)
- shadcn/ui may require specific Tailwind v4 compatibility setup

If a developer follows v3 patterns (creating `tailwind.config.ts`, using `@apply` with v3 syntax), the build will fail or produce incorrect styles.

**Risk:** Admin portal styles completely broken if Tailwind v4 config approach not specified. shadcn/ui compatibility unknown without verification.

**Fix:**
1. Before scaffolding: verify shadcn/ui compatibility with Tailwind v4 (`npx shadcn@latest init` behavior).
2. Add Section 5.4 to `08-project-scaffolding.md`:
   - Tailwind v4 CSS config location: `src/app/globals.css`
   - Correct import: `@import "tailwindcss"`
   - Theme customization via `@theme {}` block in CSS (not JS config)
   - PostCSS config (`postcss.config.mjs`) required with `@tailwindcss/postcss`
   - Confirm whether `tailwind.config.ts` should exist (v4 may still support it for backwards compat; read docs)
3. Add to Definition of Scaffold Complete: "shadcn/ui `Button` component renders with correct Tailwind styles in browser."

### S-SC-004 — Flutter `google-services.json` Per-Environment Strategy Not Specified

**Severity:** HIGH
**Location:** Section 1.3 — `apps/mobile/android/app/google-services.json`

**Issue:**
The spec notes `google-services.json` as "gitignored; per-env" but does not specify the mechanism for managing dev vs production Firebase projects.

`google-services.json` is required at `android/app/google-services.json` at compile time — the build fails without it. Two distinct problems:
1. **Dev builds:** developer needs the dev Firebase project's `google-services.json` locally.
2. **CI release builds:** `mobile-release.yml` needs the production `google-services.json` injected as a GitHub Secret.

Without this mechanism, either: (a) the production `google-services.json` is committed to the repo (security risk — exposes Firebase project ID and API keys), or (b) CI release builds fail because the file doesn't exist.

Additionally, using the same Firebase project for dev and production means dev FCM tokens can receive production push notifications — unacceptable for a production system.

**Risk:** CI `mobile-release.yml` fails on first run. Or production Firebase credentials committed to repo.

**Fix:**
1. Create separate Firebase projects: `company-hrms-dev` + `company-hrms-prod`.
2. Add to GitHub Secrets: `GOOGLE_SERVICES_JSON_PROD` (base64 encoded contents of production `google-services.json`).
3. Add step to `mobile-release.yml`:
   ```yaml
   - name: Write google-services.json
     run: echo '${{ secrets.GOOGLE_SERVICES_JSON_PROD }}' | base64 --decode > android/app/google-services.json
   ```
4. Add to Section 1.3 tree and GitHub Secrets table in `08-project-scaffolding.md`.
5. Add to `.gitignore`: `apps/mobile/android/app/google-services.json`.

### S-SC-006 — `scripts/migrations/runner.ts` Not Scaffolded

**Severity:** MEDIUM
**Location:** Section 5.2 — index creation script pattern

**Issue:**
Section 5.2 references `scripts/migrations/runner.ts` as the migration orchestrator that tracks run status in `systemEvents`. The `npm run migrate` and `npm run migrate:rollback` scripts call this file. However `runner.ts` is not specified in the scaffolding order (Section 6 — Phase 1) and its interface (`up()` / `down()` signature, `systemEvents` tracking pattern) is not defined.

If `runner.ts` is not scaffolded in Phase 1, developers building Phase 2+ cannot run migrations, and the `npm run migrate` script in `package.json` will fail.

**Fix:** Add to Phase 1 scaffolding order:
```
scripts/migrations/runner.ts   → reads all YYYYMMDD-*.ts files in directory order;
                                  checks systemEvents for completion; runs pending up();
                                  export interface Migration { up(): Promise<void>; down(): Promise<void> }
```

### S-SC-007 — SWR vs Server Components Strategy Unresolved

**Severity:** MEDIUM
**Location:** Section 7 — Admin Portal Scaffolding; Section 10.2 — Coding Standards

**Issue:**
Next.js App Router defaults to Server Components. Section 10.2 states "Server Components by default; `'use client'` only when needed." However, Section 10.2 also states "Data fetching: SWR hooks only; no raw `fetch` in components." SWR hooks require `'use client'` — they cannot run in Server Components.

This creates an unresolved tension: if all pages are Server Components, SWR cannot be used. If all data-fetching components are Client Components with SWR, the Server Component default is not meaningfully used.

**Risk:** Architecture confusion leads to inconsistent patterns across the admin portal — some pages fetch on server, others on client, no consistent caching strategy.

**Fix:** Add a data fetching decision table to Section 7:

| Scenario | Pattern |
|---|---|
| Initial page render (SEO/performance critical) | Server Component + `fetch` with `cache: 'no-store'` |
| Mutate + refetch (tables, lists after action) | `'use client'` page or child + SWR |
| Admin portal (no SEO concern, auth-gated) | `'use client'` pages with SWR acceptable |
| Static config data (settings on page) | Server Component + cached fetch |

For this project (auth-gated admin portal, no SEO): Client Components with SWR is acceptable as default for all data-fetching pages. Explicitly state this in the spec.

### S-SC-008 — Jest Config for Next.js 16 Not Specified

**Severity:** MEDIUM
**Location:** Section 2.1 — testing dependencies

**Issue:**
`jest.config.ts` and `jest.setup.ts` are listed in the file tree but their contents are not specified. Jest configuration for Next.js App Router requires:
- `jest-environment-node` for API route tests (not `jsdom`)
- Transform config for TypeScript + Next.js (typically `next/jest` transformer or `ts-jest`)
- Module name mapper for path aliases (`@models/*` → `<rootDir>/src/models/*`)
- Setup file for `mongodb-memory-server` global setup/teardown

Without correct Jest config, `npm run test` fails immediately on first run with transform or alias resolution errors.

**Fix:** Add Section 5.5 to scaffolding spec with:
- `jest.config.ts` skeleton (transform, moduleNameMapper for all aliases, testEnvironment)
- `jest.setup.ts` skeleton (mongodb-memory-server global setup)
- Note: read Next.js 16 testing docs in `node_modules/next/dist/docs/` for the exact `next/jest` or custom transform setup

### S-SC-009 — `lib/utils/api-client.ts` (Admin Frontend) Not Scaffolded

**Severity:** MEDIUM
**Location:** Section 7 — Phase 2 admin portal scaffolding

**Issue:**
The admin portal requires a `fetch` wrapper that attaches auth headers, handles 401 refresh, and wraps responses in typed `ApiResponse<T>`. This is listed in Section 7 as `lib/utils/api-client.ts` but is not included in the scaffolding order in Section 6 (which covers the backend only). There is no Section 6 equivalent for the frontend utilities.

The SWR `useEmployees`, `useAttendance`, etc. hooks all depend on this client. If it's not scaffolded, all hooks fail.

**Fix:** Add to Phase 2 admin portal scaffolding (Section 7):
```
src/lib/utils/api-client.ts    → typed fetch wrapper:
                                  get<T>(path): Promise<T>
                                  post<T>(path, body): Promise<T>
                                  patch<T>(path, body): Promise<T>
                                  del<T>(path): Promise<T>
                                  Attaches Authorization: Bearer <accessToken from cookie/localStorage>
                                  On 401: attempt refresh → retry → redirect /login
```

### S-SC-010 — `packages/types` Build Step Not in Scaffolding Order

**Severity:** MEDIUM
**Location:** Section 1.4 — packages/types; CI workflows

**Issue:**
`packages/types` is declared as a workspace package with `"main": "dist/index.js"` in its `package.json`. This requires a build step (`tsc`) to generate `dist/` before `apps/admin` can import from `@company/types`. Neither the scaffolding order in Section 6 nor the CI workflow in Section 9.1 includes building `packages/types` before building `apps/admin`.

CI will fail with "Cannot find module '@company/types'" on first run.

**Fix:**
1. Either: use `"main": "src/index.ts"` in `packages/types/package.json` + add `@company/types` to `tsconfig.json` paths (already done via `"@company/types": ["../../packages/types/src/index.ts"]`) — this avoids a build step.
2. Or: add `npm run build --workspace=packages/types` as first step in `ci.yml` before `apps/admin` build.

Option 1 is simpler — no build step needed; TypeScript resolves directly to source. Update Section 1.4 `package.json` to reflect `"main": "src/index.ts"` (not `dist/`).
