### NM-001 — `companySettings.updatedAt` in TypeScript interface but absent from schema definition
**Severity:** 🟡 MEDIUM
**Introduced by:** Singleton fix (S-004 remediation) — used `{ timestamps: false }` to avoid auto-generating `createdAt`

**Finding:**
`ICompanySettings` declares `updatedAt: Date` in the TypeScript interface. The schema uses `{ timestamps: false }` (intentional — the document has no `createdAt`). However, `updatedAt` is never defined as an explicit field in `CompanySettingsSchema`. Mongoose will not validate or project it.

At runtime, `settingsService.update()` using `findByIdAndUpdate(..., { $set: { updatedAt: new Date() } })` will store the field in MongoDB (MongoDB itself is schemaless), but Mongoose's type-safe `.lean()` results won't include it in the TypeScript return type and won't validate the value. If `settingsService` ever reads settings back via `findById().lean()`, `updatedAt` will appear in the raw document but TypeScript won't know the type.

**Fix:**
Add `updatedAt: { type: Date, required: true }` explicitly to `CompanySettingsSchema` alongside the existing `updatedBy` field. The `{ timestamps: false }` option prevents Mongoose from auto-managing it; the explicit field makes it schema-aware and type-safe.

```typescript
// Add to CompanySettingsSchema definition:
updatedAt: { type: Date, required: true, default: Date.now },
updatedBy: { type: Schema.Types.ObjectId, ref: 'User', required: true },
```

### NM-002 — `leaveYearAllocations` has no immutability protection
**Severity:** 🟡 MEDIUM
**Introduced by:** Addition of `leaveYearAllocations` collection (C-005 remediation)

**Finding:**
`leaveYearAllocations` is described as an allocation audit trail — "source of truth for allocation audits and pro-ration disputes." However, unlike `leaveTransactions` and `auditLogs`, it has no pre-hooks blocking update or delete operations. An application bug or direct DB operation could silently modify an allocation record, making historical allocation disputes unresolvable.

**Fix:**
Add immutability hooks to `LeaveYearAllocationSchema`:

```typescript
LeaveYearAllocationSchema.pre('findOneAndUpdate', () => { throw new Error('LeaveYearAllocation is immutable'); });
LeaveYearAllocationSchema.pre('updateOne',        () => { throw new Error('LeaveYearAllocation is immutable'); });
LeaveYearAllocationSchema.pre('updateMany',       () => { throw new Error('LeaveYearAllocation is immutable'); });
LeaveYearAllocationSchema.pre('save', function()  { if (!this.isNew) throw new Error('LeaveYearAllocation is immutable'); });
```

Note: `bulkWrite` is intentionally omitted here — `LeaveYearAllocation` batch inserts during annual allocation cron are legitimate and necessary. Only update paths need blocking.

### NM-003 — `LeaveTransaction.performedBy` typed as `Schema.Types.Mixed` — no validation
**Severity:** 🟡 MEDIUM
**Introduced by:** Addition of `leaveTransactions` collection (C-001 remediation)

**Finding:**
`performedBy` is declared `Schema.Types.Mixed` to accept either `ObjectId` (human actor) or the string `'system'` (cron job). The `Mixed` type bypasses all Mongoose validation — any value can be stored. A service layer bug could store an empty string, `null`, or an arbitrary object.

The same pattern is used in `LeaveYearAllocation.allocatedBy`.

**Fix:**
Use a Mongoose custom validator instead of `Mixed`:

```typescript
performedBy: {
  type: Schema.Types.Mixed,
  required: true,
  validate: {
    validator: (v: unknown) =>
      v === 'system' || v === 'system-cron' || v instanceof mongoose.Types.ObjectId,
    message: 'performedBy must be an ObjectId or "system" or "system-cron"',
  },
},
```

Apply the same pattern to `LeaveYearAllocation.allocatedBy`.

### NL-001 — `{ timestamps: false, _id: false }` with explicit `_id: String` is non-obvious
**Severity:** 🟢 LOW
**Introduced by:** Singleton fix (S-004 remediation)

**Finding:**
`CompanySettingsSchema` uses `{ timestamps: false, _id: false }` as schema options **and** explicitly defines `_id: { type: String, default: 'company-settings' }`. The `_id: false` option tells Mongoose not to auto-generate an ObjectId `_id`. The explicit `_id` field in the schema body takes precedence and IS stored. This is correct Mongoose behavior but will confuse future developers who see `_id: false` and assume the document has no `_id`.

**Fix:**
Add a comment above the schema options:

```typescript
// _id: false prevents Mongoose auto-ObjectId; the explicit _id: String field above IS stored.
{ timestamps: false, _id: false }
```

No schema change needed.

### NL-002 — `leaveTransactions.leaveType` excludes `'lwp'` — intentional but undocumented
**Severity:** 🟢 LOW
**Introduced by:** Addition of `leaveTransactions` collection

**Finding:**
`LeaveRequest.leaveType` includes `'lwp'`. `LeaveTransaction.leaveType` only includes `'paidLeave' | 'sickLeave' | 'casualLeave'`. LWP (Leave Without Pay) has no leave balance to track — it's a salary deduction, not a balance deduction. So LWP leaves correctly produce no `leaveTransaction` entry. However, this asymmetry is not documented anywhere in either the schema constraints or the service layer notes.

**Fix:**
Add a constraint note to the `leaveTransactions` section:

> LWP leave requests do not produce a `leaveTransaction` entry. LWP is recorded in `payrollSummaries.lwpDays` / `effectiveLwpDays` and results in a salary deduction, not a balance deduction.
