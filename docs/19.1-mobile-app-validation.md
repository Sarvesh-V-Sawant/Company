### H1 — Wrong API Paths: Auth Password Flows

**Files:** `lib/core/constants/api_endpoints.dart:9,12,13`

| Endpoint | Spec path | Implementation path | Status |
|----------|-----------|---------------------|--------|
| Change password | `PATCH /api/v1/auth/me/change-password` | `PATCH /api/v1/auth/me/password` | **WRONG** |
| Forgot password | `POST /api/v1/auth/password-reset/request` | `POST /api/v1/auth/forgot-password` | **WRONG** |
| Reset password | `POST /api/v1/auth/password-reset/confirm` | `POST /api/v1/auth/reset-password` | **WRONG** |

All three auth password flows will receive `404 Not Found` from the server. The Forgot Password and Reset Password screens are completely non-functional. The forced password-change flow on first login will also fail.

**Fix required:** Update `api_endpoints.dart` constants to match spec paths exactly.

---

### H2 — Token Refresh Request Missing `sessionId`

**Files:** `lib/features/auth/data/sources/auth_remote_source.dart:22-25` | `lib/core/network/interceptors/auth_interceptor.dart:72`

API spec login response includes `sessionId`. Spec refresh endpoint requires body `{ refreshToken, sessionId }`.

**Implementation sends:** `{ refreshToken }` only (both in `AuthRemoteSource.refresh()` and inside `AuthInterceptor.onError()`).

`sessionId` is also never stored in `SecureStorage` — there is no `StorageKeys.sessionId` constant. When the backend validates the refresh request, it will reject the missing `sessionId` and terminate the session. Every 401 retry in `AuthInterceptor` will fail, triggering `onSessionExpired` immediately — effectively making token refresh non-functional.

**Fix required:** Store `sessionId` from login response → `StorageKeys.sessionId`. Pass it in every refresh call.

---

### H3 — Device Error Code Routing Broken

**Files:** `lib/features/auth/presentation/screens/login_screen.dart:67,84`

Two defects:

**Defect A — `AUTH_011` does not exist in the API error catalog.**
API spec catalog runs `AUTH_001` through `AUTH_010`. `AUTH_011` (used as the trigger for device-not-registered routing) is not defined. The real server returns `AUTH_004` for `DEVICE_NOT_REGISTERED`. The `DeviceMismatchException` with code `AUTH_011` will never be thrown.

**Defect B — `AUTH_004` mis-mapped in `_mapErrorCode`.**
```dart
// line 84
'AUTH_001' || 'AUTH_004' => 'Invalid email or password.',
```
`AUTH_004` (DEVICE_NOT_REGISTERED) is handled as an authentication failure instead of routing to `/device-not-registered`. Employees without registered devices see "Invalid email or password" — a misleading error that blocks onboarding.

**Correct mapping per spec:**
| Error code | API spec meaning | Required action |
|-----------|-----------------|-----------------|
| `AUTH_004` | DEVICE_NOT_REGISTERED | Navigate to `/device-not-registered` |
| `AUTH_005` | DEVICE_FINGERPRINT_MISMATCH | Navigate to `/device-mismatch` |
| `AUTH_001` | INVALID_CREDENTIALS | Show "Invalid email or password." |

**Fix required:** Remove `AUTH_004` from `_mapErrorCode`. Throw/catch `DeviceMismatchException` for `AUTH_004` and `AUTH_005`, routing appropriately.

### H4 — FCM / Push Notifications Completely Non-Functional

**Files:** `pubspec.yaml`, `lib/main.dart`, `lib/features/auth/data/sources/auth_remote_source.dart:56-58`

`firebase_core` and `firebase_messaging` were removed from `pubspec.yaml` to unblock `flutter analyze` (missing `google-services.json`). Consequences:

1. `updateFcmToken()` method exists in `AuthRemoteSource` but is **never called** — no FCM token is registered after login or refreshed on resume.
2. Background and foreground push notifications are not received.
3. Deep-link routing from notification tap (`getInitialMessage()`, `onMessageOpenedApp`) is not wired.
4. `flutter_local_notifications` (required for foreground FCM display) is also absent from pubspec.
5. `NotificationPermissionScreen` (one-time FCM rationale, Appendix A screen #27) is not implemented.

The Notifications module as a whole only supports pull (polling via `GET /notifications`) — no push delivery path exists.

**Fix required:** Obtain `google-services.json` from Firebase console, restore `firebase_core` and `firebase_messaging` to `pubspec.yaml`, implement FCM token lifecycle (register post-login, refresh on `onTokenRefresh`, clear on logout), implement `NotificationPermissionScreen`.

### H5 — Device Fingerprint Hash Deviates from Spec

**Files:** `lib/features/auth/data/repositories/auth_repository.dart:27`

```dart
// Current implementation
final raw = '${android.id}|${android.model}|${android.brand}';

// Spec (section 9.1) requires
// SHA-256(deviceId + model + brand + androidId)
```

The `androidId` field was removed during implementation because `device_info_plus` 10.x removed the `androidId` property from `AndroidDeviceInfo`. However, this creates a 3-field fingerprint while the specification mandates 4 fields. If the server computed registration using the 4-field formula (which it must per spec), every subsequent login check will produce a different hash, triggering false `DEVICE_FINGERPRINT_MISMATCH` errors for all existing users.

**Fix required:** Use `androidInfo.serialNumber` or the correct replacement for `androidId` in `device_info_plus` 10.x (check package changelog). Alternatively, if `device_info_plus` has genuinely removed a stable cross-device ID, escalate to spec owner to update the fingerprint formula before any users register devices.

### H6 — Notification Detail Screen Missing

**Files:** `lib/core/router/route_names.dart:35` | `lib/core/router/app_router.dart`

`RouteNames.notificationDetail` is defined:
```dart
static String notificationDetail(String id) => '/notifications/$id';
```

But there is **no `GoRoute`** for `/notifications/:id` in `app_router.dart` and **no screen file** `notification_detail_screen.dart` exists anywhere in the codebase. The spec (Appendix A, screen #19) requires this screen to show full notification body and action links.

The `NotificationsScreen` deep-links "generic" type notifications to `notificationDetail(n.id)`, which will crash with a `GoException: no route found for /notifications/<id>` at runtime.

**Fix required:** Create `notification_detail_screen.dart` and register the route `GoRoute(path: '/notifications/:id', ...)` in `app_router.dart`.

## MEDIUM Findings (8)

### M1 — Offline Mode Non-Functional

**Files:** `pubspec.yaml`, `lib/shared/widgets/offline_banner.dart`, all data source files

`connectivity_plus` package is not in `pubspec.yaml`. `OfflineBanner` displays a static widget with no connectivity state subscription. No data source writes to Hive boxes on successful API response. App shows empty states (not cached data) when offline.

Per spec: read-only offline mode is required for Attendance, Leave, Notifications, Profile. Cache must be populated on successful loads and displayed when offline.

**Fix:** Add `connectivity_plus`, wire `OfflineBanner` to a `connectivityProvider`, add Hive write on each successful list/detail fetch in data sources.

### M2 — Profile Change-Password Missing `currentPassword` Field

**File:** `lib/features/profile/presentation/screens/profile_change_password_screen.dart`

Spec (section 8.2) defines the profile change-password form with three fields: Current Password, New Password, Confirm Password. Implementation has only New Password and Confirm Password. The `changePassword` API call sends only `{newPassword}` with no current-password verification. This is a security gap — any authenticated user can change their password without proving they know the current one.

### M3 — `sessionId` Not Stored from Login Response

No `StorageKeys.sessionId` constant exists. The login API response's `sessionId` field is not stored anywhere. This is the root cause of H2 — flagged separately because even after fixing the refresh body, `sessionId` persistence infrastructure must be added first.

### M4 — `GET /settings` Not Fetched on Login

**File:** `lib/features/attendance/presentation/providers/attendance_provider.dart:97`

```dart
return AttendanceNotifier(source, CompanySettings.defaults);
```

`CompanySettings.defaults` uses hardcoded values (540 min day, geofence disabled). The spec requires calling `GET /api/v1/settings` after login and caching the result in Hive. Geofence enforcement, required daily minutes threshold, regularization lookback days, and working days all use wrong defaults until fixed.

### M5 — `Read-All` Notifications HTTP Method Mismatch

**File:** `lib/core/constants/api_endpoints.dart:30`

Spec defines `PATCH /api/v1/notifications/read-all`. Implementation declares the constant but the HTTP method used in `NotificationsRemoteSource` must use `PATCH`, not `POST`. If `POST` is used, the server will return `405 Method Not Allowed`.

### M6 — Leave Apply Screen Missing Half-Day and Balance Display

**File:** `lib/features/leave/presentation/screens/leave_apply_screen.dart`

- Leave type selection must show remaining balance inline (e.g., `Paid Leave (8 days remaining)`)
- Balance-after calculation: `"After this request: X days remaining"`

Implementation has: date-range picker with hardcoded type dropdown (PL/SL/CL/LWP) and no duration type. Half-day leaves cannot be submitted.

### M7 — `requiresPasswordChange` Not Enforced on App Restore

**File:** `lib/core/router/app_router.dart`

Login screen correctly checks `result.requiresPasswordChange` and routes to `/change-password`. However, when the app is restored from background using a cached session (splash → token refresh → home), `requiresPasswordChange` from the refreshed JWT is not re-checked in the router redirect. A user with `requiresPasswordChange: true` who kills and restarts the app will land on `/home` directly.
