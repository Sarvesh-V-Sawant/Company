## R-001 — Timezone Boundary Testing

### Root Cause (from 03.1)
No test covered the IST/UTC split in `dateString` derivation. MongoDB stores all timestamps as UTC. If `dateString` is derived from a raw UTC date instead of an IST-converted date, check-ins between 18:30 UTC (00:00 IST) and 23:59 UTC (05:29 IST) would be attributed to the wrong calendar day.

### Business Impact
Wrong `dateString` attribution causes:
- Attendance for Day N attributed to Day N+1 in payroll
- Carry-forward and leave year boundary calculations silently wrong for night-shift-style scenarios or check-ins after IST midnight
- Cron-closed sessions attributed to wrong day

### Scenarios Added

| TC-ID | What it tests |
|---|---|
| TC-ATT-026 | Cron closes session at 02:00 IST — dateString = check-in IST date, not cron-fire date |
| TC-ATT-027 | Checkout after IST midnight — session stays on check-in date |
| TC-ATT-028 | Month boundary (Jan 31 → Feb 1 IST) — January payroll gets the day, not February |
| TC-ATT-029 | Leave year boundary (Apr fiscal year, Mar 31 23:59 IST) — leaveYear draws from correct year |
| TC-ATT-030 | UTC `2026-06-14T18:30:00Z` → `dateString: '2026-06-15'` (IST date) |

### Implementation Requirement
All `dateString` values must be derived using:
```typescript
import { toZonedTime, format } from 'date-fns-tz';

function toISTDateString(utcDate: Date, timezone: string): string {
  return format(toZonedTime(utcDate, timezone), 'yyyy-MM-dd', { timeZone: timezone });
}
// Called with companySettings.timezone ('Asia/Kolkata')
```
This function must be unit-tested via `E-DAT-*` tests with known UTC/IST pairs.

## R-002 — Employee Reactivation Lifecycle Testing

### Root Cause (from 03.1)
No test covered the deactivate → reactivate cycle. Gaps identified:
- Does deactivation immediately revoke active sessions?
- Does reactivation restore sessions or require fresh login?
- Are leave balances preserved across the cycle?
- Can payroll be computed for months before deactivation?
- Is the audit trail continuous?

### Business Impact
Without these tests, a re-activated employee could:
- Log in with a pre-deactivation token (security breach)
- Find their leave balance zeroed (data loss)
- Have their pre-deactivation payroll blocked
- Have no audit record of the deactivation event

### Scenarios Added

| TC-ID | What it tests |
|---|---|
| TC-ATT-031 | Deactivation blocks check-in AND revokes all `deviceSessions` immediately |
| TC-ATT-032 | Re-activation does not restore sessions — fresh login required on each device |
| TC-ATT-033 | Leave balance preserved across deactivation/reactivation cycle |
| TC-ATT-034 | Audit log contains `EMPLOYEE_DEACTIVATED` and `EMPLOYEE_REACTIVATED` events with no gap |
| TC-ATT-035 | Payroll for pre-deactivation months computable normally |

### Implementation Requirements
- `employeeService.deactivate()` must call `deviceSessionRepository.revokeAllForEmployee(employeeId)` inside the same transaction as the `isActive = false` update
- `employeeService.reactivate()` does NOT call `deviceSessionRepository.restoreForEmployee()` — sessions stay revoked by design
- Both operations must write `auditLogs` entries

## R-003 — Leave Applied While Employee is Checked In

### Root Cause (from 03.1)
No test covered the case where an employee applies (or admin approves) leave for a day on which an attendance session already exists. This is common for sick leave applied after the fact or same-day decisions.

### Business Rule Decision
After analysis of HRMS conventions: **approved leave always overrides attendance status for that day.**

| Priority | Status |
|---|---|
| 1 (highest) | `'leave'` (approved leave) |
| 2 | `'holiday'` |
| 3 | `'weekend'` |
| 4 | `'present'` / `'half-day'` / `'absent'` (attendance-derived) |

When leave is approved for a day that has an attendance session:
- `AttendanceDay.status` is updated to `'leave'` (or `'half-day'` for half-day leave)
- The session record is **preserved** (not deleted) — audit trail and duration data intact
- Payroll uses `paidLeaveDays` for the day, not `presentDays`
- The session's `totalMinutes` is ignored in payroll calculation for that day

### Scenarios Added

| TC-ID | What it tests |
|---|---|
| TC-LVE-026 | Apply leave today while checked in — no conflict error; request created |
| TC-LVE-027 | Approve leave today while session active — `AttendanceDay.status = 'leave'`; session open |
| TC-LVE-028 | Approve half-day leave today with 4+ session hours — leave-driven half-day; session minutes ignored in payroll |
| TC-LVE-029 | Payroll: day counted as `paidLeaveDays`, excluded from `presentDays` |
| TC-LVE-030 | Retroactive leave approval for past day with historical session — status updated; session preserved; draft payroll affected; finalised payroll warns |

### Implementation Requirements
- `leaveService.approve()` must call `attendanceDayRepository.updateStatus(date, 'leave')` inside the transaction (for approved full-day) or `'half-day'` (for half-day)
- If payroll for the month is `'finalised'`, include `warnings` in service response — do NOT block the leave approval
- `payrollEngine` must check `AttendanceDay.status` for all days, not just raw session data — leave-approved days are identified by status, not absence of session

## R-004 — Leave Revocation After Payroll Finalisation

### Root Cause (from 03.1)
When admin revokes an approved leave for a month whose payroll is already `'finalised'`, two systems diverge:
1. Leave balance is restored (correct)
2. Payroll record still reflects the original computation (stale)

No test covered this divergence, and no workflow existed to reconcile it.

### Design Decision: Unfinalize Operation

A new admin-only operation is added to `payrollService`:

**`payrollService.unfinalize(yearMonth, adminId)`**
- Changes `status: 'finalised'` → `'draft'`
- Sets `unfinalisedAt: Date` and `unfinalisedBy: ObjectId`
- Writes `auditLogs { action: 'PAYROLL_UNFINALISED', performedBy: adminId }`
- Returns updated `PayrollSummary`

**Schema additions to `payrollSummaries`:**
```typescript
unfinalisedAt?: Date       // set when admin unfinalizess; cleared on re-finalize
unfinalisedBy?: ObjectId   // reference to Users
```

**API endpoint:** `PUT /api/v1/payroll/:yearMonth/unfinalize` — admin-only, requires `PAYROLL_ALREADY_FINALISED` check inverted (must be finalised to unfinalize).

**Complete workflow for leave-revocation-after-finalization:**
```
1. Admin revokes leave → balance restored + attendance day updated + WARNING returned
2. Admin calls unfinalize → payroll goes back to 'draft'
3. Admin calls compute → payroll recomputed with current attendance/leave data
4. Admin calls finalize → new final payroll with updated payableAmount
5. Audit log has 5 entries: LEAVE_REVOKED, ATTENDANCE_DAY_UPDATED, PAYROLL_UNFINALISED, PAYROLL_COMPUTED, PAYROLL_FINALISED
```

### Scenarios Added

| TC-ID | What it tests |
|---|---|
| TC-PAY-016 | Revoke leave for finalised month — balance restored, warning returned, payroll NOT auto-modified |
| TC-PAY-017 | Recompute blocked on finalised payroll — must unfinalize first |
| TC-PAY-018 | Unfinalize payroll — `status → 'draft'`, audit logged |
| TC-PAY-019 | Recompute + re-finalize after unfinalize — `payableAmount` updated |
| TC-PAY-020 | Audit trail completeness — all 5 events present, no gaps |
| U-PAY-07 | Unit: unfinalize sets correct fields and writes audit log |
| U-PAY-08 | Unit: recompute after unfinalize produces updated `payableAmount` |

## R-005 — Refresh Token Strategy Decision & Tests

### Root Cause (from 03.1)
No refresh token expiry policy was defined. TC-SEC-007 only verified that refresh returns a new access token — it did not verify expiry behaviour, the effect of password reset on sessions, or the effect of deactivation on sessions.

### Design Decision: Hybrid Session Expiry (Option C)

Full rationale documented in Section 2.11 of `docs/03-testing-strategy.md`. Summary:

**Chosen:** Hybrid — 30-day inactivity timeout + 90-day absolute maximum.

**Key parameters:**
- Access token: 15 min (JWT `exp`)
- Refresh inactivity: 30 days (`deviceSessions.expiresAt` — extended on each refresh)
- Refresh absolute max: 90 days (`deviceSessions.absoluteExpiresAt` — set once at registration)

**Why not Sliding (Option A):** Stolen device stays authenticated indefinitely. Unacceptable for HR/payroll access.

**Why not Absolute (Option B):** Daily active users forced to re-login every 30–90 days even when using app every day. Poor mobile UX for an attendance app used for daily check-in.

**Why Hybrid (Option C):** Daily active employees (checking in every weekday) effectively never hit the 30-day inactivity window. The 90-day absolute max bounds worst-case stolen-token lifetime. Both values are configurable in future if requirements change.

### Required Schema Change

Add to `deviceSessions`:
```typescript
absoluteExpiresAt: { type: Date, required: true }
// = createdAt + 90 days. Set at registration. Never mutated on refresh.
```

**Migration for existing sessions:** Set `absoluteExpiresAt = createdAt + 90 days` for all existing `deviceSessions` docs. If `createdAt + 90d < now()`, set `absoluteExpiresAt = now()` (immediate expiry on next refresh — forces re-login on next session use).

### Scenarios Added

| TC-ID | What it tests |
|---|---|
| TC-SEC-021 | 30-day inactivity → TOKEN_EXPIRED |
| TC-SEC-022 | 90-day absolute max → TOKEN_EXPIRED (even if recently active) |
| TC-SEC-023 | Password reset → all sessions revoked → TOKEN_INVALID |
| TC-SEC-024 | Employee deactivation → all sessions revoked immediately → TOKEN_INVALID |
| TC-SEC-025 | Re-activation does not restore old sessions |
| U-AUTH-15 | Refresh extends `expiresAt` by 30d, capped at `absoluteExpiresAt` |
| U-AUTH-16 | Refresh after 30-day inactivity — TOKEN_EXPIRED |
| U-AUTH-17 | Refresh past 90-day absolute max — TOKEN_EXPIRED |
| U-AUTH-18 | `expiresAt` extension capped correctly at `absoluteExpiresAt` |
| U-AUTH-19 | Post-password-reset refresh — TOKEN_INVALID |
| U-AUTH-20 | Post-deactivation refresh — TOKEN_INVALID |
