## 4. Security Score — 95 / 100

### Scoring Dimensions

| Dimension | Score | Rationale |
|---|---|---|
| Authentication security | 97/100 | JWT with short TTL (15 min), hybrid refresh (30d inactivity + 90d absolute), device fingerprint binding, CSRF dual-layer. `SHA-256 + timingSafeEqual` for reset tokens (was bcryptjs — fixed in v1.1). No enumeration on login or password reset. |
| Authorization controls | 96/100 | Role-based on every endpoint. Employees scoped to own data. Admin-only destructive operations explicit. `AUTH_010` enforces password-change gate. Edge Middleware carries JWT claims — no DB round-trip for access decisions. |
| Device security | 94/100 | Single-source fingerprint (header only — fixed in v1.1). SHA-256 stored. `timingSafeEqual` on comparison. Device reset revokes all sessions. |
| Credential security | 95/100 | Forced password change on first login (added in v1.1). bcryptjs for passwords (human-chosen — correct tool). SHA-256 for tokens (random — correct tool). Temp passwords shown once, not logged. Recovery via self-service email (admin cannot see reset password). |
| Input validation | 93/100 | All endpoints have documented validation rules. `GEN_001` with field-level details. Nonce replay prevention (usedNonces TTL). Timestamp window check. GPS mock detection. Still missing: maximum body size limits not specified; SQL injection N/A (MongoDB), but NoSQL injection via `$where` not addressed (mitigated by Mongoose schema typing). |
| Rate limiting | 94/100 | Three limiters: auth (10/min IP), attendance (60/min employee), password-reset dual-keyed (3/hr email + IP). Cron endpoints protected by CRON_SECRET. |
| Session management | 96/100 | Sessions revoked on deactivation, password reset, device reset. Hybrid expiry eliminates indefinite session risk. `absoluteExpiresAt` hard bounds stolen-token exposure. |
| Data exposure | 92/100 | `passwordHash`, `registeredDeviceHash`, `tokenHash` never returned in responses. `ipAddress` excluded from employee-visible audit logs. `monthlySalary` excluded from employee list view. Audit snapshots exclude sensitive fields. |

**Weighted Security Score: 95 / 100**

*Weighted toward: authentication (×1.5), authorization (×1.5), session management (×1.3), credential security (×1.2).*

### What earns 95
- v1.0 had a timing attack vector on password reset (bcryptjs compare is not constant-time in all implementations) — **fixed in v1.1**
- v1.0 had a dual-transport ambiguity that could enable session hijacking — **fixed in v1.1**
- v1.0 allowed indefinite use of admin-assigned passwords — **fixed in v1.1**
- All auth decisions are in JWT claims (Edge Middleware, no DB per-request)
- Nonce replay prevention at DB level (unique index), not application level
- CSRF protection tied to cookie detection — Bearer header requests unconditionally exempt (correct)

### What costs 5 points
- NoSQL injection hardening not explicitly documented (mitigated by Mongoose but should be stated)
- No maximum request body size documented (Vercel default is 4.5MB; should be 1MB or less for API endpoints)
- No Content-Security-Policy or security headers specified for admin portal responses (frontend concern but should be noted here)
- IP address logging without explicit consent language (noted in architecture; not resolved at API layer)

## 8. Approval Recommendation

### Would you approve this API specification for implementation?

**Yes — approved for implementation, subject to 4 conditions.**

---

### Justification

**The specification is now implementation-safe on all HIGH severity findings.** Every finding that would have caused a security defect, an authentication ambiguity, or a broken first-run experience has been resolved in v1.1. The five changes are each individually significant:

**R-API-001 (Bulk mark-read)** closes an unacceptable UX gap for a mobile-first product. A "mark all read" is table stakes for any notification system used daily.

**R-API-002 (Single fingerprint source)** closes a session hijacking attack vector. An implementation team following the v1.0 spec would have built one validation path in middleware and another in the Route Handler, using different fields — a subtle split that is not caught by unit tests but exploitable in production.

**R-API-003 (SHA-256 for tokens)** is not just a performance improvement — it corrects a bcryptjs 72-byte input truncation issue that silently reduced effective token entropy. Any security audit of the codebase would have flagged `bcrypt.compare(rawToken, storedHash)` in a password-reset-confirm handler as a red finding.

**R-API-004 (Forced password change)** is the difference between an HR platform that satisfies a compliance audit and one that doesn't. Admin-assigned passwords that are never changed fail the "employees must own their credentials" control in every HR compliance framework (SOC 2, ISO 27001, PCI if any payroll data is in scope).

**R-API-005 (ObjectId clarification)** is documentation, but documentation that prevents a cross-team integration defect. Without it, two different developers building the admin dashboard and the Flutter app would use different URL formats — discovered only when one tries to use the other's URLs and gets 404.

**The 10 remaining MEDIUM findings are all deferred correctly** — they are edge cases or quality improvements, not functional gaps in the primary user flows. Each one has a "fix before X implementation" note that prevents the gap from being discovered too late.

---

### 4 Conditions for This Approval

1. **Apply R-API-009 (payroll compute concurrency guard) before implementing `payrollService.bulkCompute()`** — a `systemEvents` lock document must gate the bulk operation or two parallel bulk computes for the same month will produce non-deterministic `payrollSummaries` records.

2. **Apply R-API-010 (ExcelJS streaming writer) before implementing any export route** — specifying `stream.xlsx.WorkbookWriter` instead of the in-memory `Workbook` is a 2-line change in the service that cannot be retrofitted without rewriting the entire export pipeline.

3. **Apply R-API-013 (`X-API-Version` header) before first deployment** — adding a response header to a shared Next.js middleware is a single-line change; missing it after deployment means retroactively building version correlation into all past Flutter crash reports.

4. **Apply R-API-014 (employee self-audit trail) before beta launch** — GDPR Article 15 (right of access) requires that employees can see what data is held about them. An admin-only audit log fails this right. `GET /audit-logs/me` must exist before any external user accesses the system.
