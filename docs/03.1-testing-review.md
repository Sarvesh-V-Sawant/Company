## 1. Missing Test Scenarios

### HIGH

**R-001 — Timezone edge case: midnight rollover at non-UTC midnight**
- The attendance matrix covers midnight rollover (`TC-ATT-011`) but only tests that the cron closes sessions. There are no test cases verifying that an employee in IST who checks in at 23:45 IST (18:15 UTC) and the cron fires at 20:30 UTC (02:00 IST) — the session spans UTC midnight but not IST midnight. The `closedBySystem` logic and `AttendanceDay.dateString` need to be in IST consistently.
- **Missing:** TC-ATT-026 — Check-in at 23:45 IST; cron fires at 02:00 IST (00:30 UTC next day); session attributed to correct dateString (the check-in date, not the close date).
- **Severity:** High — timezone bugs in payroll cause incorrect `effectiveWorkingDays`.

**R-002 — Employee re-activation: historical data integrity**
- No test covers deactivating an employee, then re-activating them. Does re-activation reset leave balances? Does payroll ignore months when `isActive = false`? Are prior audit logs still visible?
- **Missing:** TC-ATT-027 — Deactivate employee → verify block → re-activate → verify check-in works; leave balance unchanged; audit log continuity intact.
- **Severity:** High — without this, HR may accidentally grant re-joining employees stale leave balances or miss a pay period.

**R-003 — Leave applied during active session (same day check-in)**
- An employee is currently checked in and simultaneously applies leave for the same day (e.g., decides midday to take sick leave retroactively). No test covers the conflict between an active `attendanceSession` and a pending `leaveRequest` for the same date.
- **Missing:** TC-LVE-026 — Employee has active session today; applies sick leave for today; request created with `affectedDates = [today]`; on approval, active session's day status should be updated to `leave` and session should be closed or noted as overridden.
- **Severity:** High — without this scenario, payroll may double-count a day as both `present` and `leave-approved`.

**R-004 — Leave revocation after payroll finalised**
- If admin revokes an approved leave for a month that has already been finalised in payroll, the `leaveRequest.status` changes but `payrollSummaries` remains stale. No test covers this conflict.
- **Missing:** TC-PAY-016 — Finalise payroll for month → revoke approved leave from same month → verify: payroll record is NOT auto-updated (finalised is immutable); admin is warned that payroll must be manually recomputed; re-compute is blocked by `PAYROLL_ALREADY_FINALISED`.
- **Severity:** High — without this, revoked leave can cause the employee to have balance restored but their salary remain incorrectly computed.

**R-005 — Token refresh sliding window correctness**
- `TC-SEC-007` verifies refresh succeeds, but no test verifies that session expiry is extended on use (sliding window) vs. absolute expiry. If `expiresAt` is absolute (set at device registration), long-term active users will be logged out on an arbitrary future date. If it's sliding (updated on each refresh), a never-logged-out device accumulates session duration indefinitely.
- **Missing:** TC-SEC-021 — Refresh token used within expiry window → `expiresAt` NOT extended (absolute expiry design); TC-SEC-022 — session that hasn't been used for > 30 days is considered stale (policy check, not schema — but this needs a defined decision and a test for it).
- **Severity:** High — expiry design determines security posture for long-lived mobile sessions.

### MEDIUM

**R-006 — Carry-forward from non-January fiscal year (April start)**
- `TC-LVE-018` covers carry-forward but only for a January-start year. With `leaveYearStartMonth: 4`, year-end carry-forward fires at March 31, not December 31. No test validates this interaction.
- **Missing:** TC-LVE-027 — `leaveYearStartMonth: 4`; cron fires on 2026-03-31; employee has 3 PL balance; carry-forward credited for 2026–2027 year; `leaveYear` on the new transaction = 2026.
- **Severity:** Medium.

**R-007 — Pro-rated allocation for employee who joined mid-leave-year then left**
- `TC-LVE-021` covers mid-year joiners but not mid-year leavers. An employee who joins Apr 15 and leaves Oct 1 of the same fiscal year gets a pro-rated allocation then a refund calculation.
- **Missing:** TC-LVE-028 — Employee with `dateOfJoining = 2026-04-15` and `dateOfLeaving = 2026-10-01` in April fiscal year; allocation is pro-rated at join; on leave, is there a clawback of unused allocations? (Business rule needs to be defined — test enforces the decision.)
- **Severity:** Medium.

**R-008 — Half-day leave on first or last working day of leave year**
- Half-day leave at a year boundary could split `affectedDates` across fiscal years if not handled carefully. No test covers this.
- **Missing:** TC-LVE-029 — Apply half-day leave on 2026-03-31 (last day of March-ending fiscal year, `leaveYearStartMonth: 4`); `leaveYear = 2025`; balance drawn from 2025 year.
- **Severity:** Medium.

**R-009 — Regularization approval when `AttendanceDay` for the target date does not exist yet**
- If an employee never checked in on a day, `attendanceDays` may have no document for that date. Regularization approval must create the `AttendanceDay` doc, not just update it. No test covers the creation path.
- **Missing:** TC-REG-013 — No `AttendanceDay` exists for regularization target date; approve `forgotCheckIn` → `AttendanceDay` created AND session created in single transaction.
- **Severity:** Medium.

**R-010 — Payroll computation for employee with zero monthly salary**
- An admin or contractor employee might have `monthlySalary: 0` (tracked for attendance, not paid). No test verifies `payableAmount = 0`, no divide-by-zero in formula, all attendance fields still computed.
- **Missing:** TC-PAY-017 — Employee with `monthlySalary = 0`; payroll computed → `payableAmount = 0.00`; formula fields still populated; no arithmetic exception.
- **Severity:** Medium.

**R-011 — Notification delivery when `fcmTokens` collection is empty for an employee**
- `U-NOT-05` covers the case where no active FCM token exists. But there's no test for the case where the employee record has `fcmTokens` documents that are all `isActive: false` — vs. having no documents at all. The query behaviour differs.
- **Missing:** `U-NOT-06` — Employee has 3 FCM token docs all `isActive: false`; notification send → no push sent; log written; no error thrown.
- **Severity:** Medium.

**R-012 — Attendance on a partial working day (office closes early)**
- No concept of office closure on a non-holiday working day is addressed. If `requiredDailyMinutes` is temporarily reduced by admin (e.g., half-day for festival), the existing settings structure cannot represent this without changing global settings. No test documents what happens with the current model.
- **Missing:** Document as known gap in testing strategy rather than a test case, since the schema doesn't support per-day overrides. Identify as V2 requirement.
- **Severity:** Medium — current design has no per-day working hour override.

**R-013 — Cron: `systemEvents` TTL and idempotency interaction**
- `systemEvents` docs have a 90-day TTL. If the idempotency guard depends on finding a `{ type, status: 'success' }` document, and the document expires, the cron will re-run after 90 days even if it already ran successfully. For monthly crons (payroll allocation), this could trigger double-allocation for the same `leaveYear` three months after the original run.
- **Missing:** TC-CON-008 — `systemEvents` document for year-start allocation artificially expired/deleted → cron re-fires → `leaveYearAllocations` unique index prevents double allocation (database-level guard must compensate for TTL gap in application-level idempotency).
- **Severity:** Medium — the unique index on `leaveYearAllocations` is the actual guard here, but this test documents the dependency explicitly.

**R-014 — Admin changes `leaveYearStartMonth` mid-year**
- If admin changes the leave year start month from January to April mid-year, existing `leaveRequests.leaveYear` values become inconsistent. No test covers this settings change scenario or documents the warning behaviour.
- **Missing:** TC-SET-007 — Change `leaveYearStartMonth` from `1` to `4` in June → service returns a warning in response body noting that existing leave records for the current year use `leaveYear = 2026` (Jan-based) while future records will use fiscal-year-based years; existing records are not migrated.
- **Severity:** Medium.

### LOW

**R-015 — Leap year: Feb 29 in payroll `effectiveWorkingDays`**
- `E-DAT-07` tests that Feb 29 is a valid `dateString`, but no payroll test covers February in a leap year. `getWorkingDaysBetween` must count Feb 29 correctly.
- **Missing:** TC-PAY-018 — Payroll for February 2028 (leap year); 21 working days in month; employee present all; `payableAmount = salary`. Verify Feb 29 counted.
- **Severity:** Low.

**R-016 — Excel report with special characters in employee names**
- No test covers employee names with special characters (accents, unicode) in the Excel export. ExcelJS typically handles this but it should be verified.
- **Missing:** TC-UAT-A18 — Employee with name "Ñoño García" (unicode) → export attendance report → open Excel → name renders correctly; file is not corrupted.
- **Severity:** Low.

**R-017 — Password reset token expiry race: token used at exact `expiresAt`**
- If token `expiresAt` is 10 minutes from creation and the request arrives at exactly T+10:00:00, the comparison `expiresAt < now()` vs `expiresAt <= now()` determines whether it's accepted or rejected. Off-by-one boundary not tested.
- **Missing:** `U-AUTH-15` — Reset token with `expiresAt = now()` exactly → rejected (token is expired at boundary).
- **Severity:** Low.

**R-018 — Audit log `before/after` snapshot for settings update**
- `U-SET-05` verifies audit log written on settings update but doesn't verify that `before` and `after` snapshots exclude sensitive fields or that the diff is computable. An audit log with `after.passwordHash` would be a data leak.
- **Missing:** `U-SET-06` (rename existing to `U-SET-07`) → new test: audit log for settings update has `entityType: 'company-settings'`; `before` and `after` are both JSON-serialisable; neither contains `passwordHash` (settings don't have one, but this establishes the pattern for future auditable entities).
- **Severity:** Low.

## 2. Structural / Coverage Gaps

**R-019 — No negative path tests for `payrollEngine`** (High)
- Section 2.10 defines `payrollEngine` unit tests but every scenario is a valid computation. The engine must reject or guard against invalid inputs: negative `presentDays`, `effectiveWorkingDays = 0` (divide-by-zero), `monthlySalary < 0`. Guard tests are missing.
- **Fix:** Add `E-PAY-12` — `presentDays < 0` → throws `INVALID_PAYROLL_INPUT`; `E-PAY-13` — `monthlySalary < 0` → throws `INVALID_PAYROLL_INPUT`. These are pure function tests; no mocks needed.

**R-020 — `notificationService` has no E2E validation test** (Medium)
- Push notifications and emails are tested via unit mocks (`U-NOT-01` through `U-NOT-05`), but no UAT scenario or integration test verifies that a real FCM push is received on a device or a real Brevo email is received in inbox. This is a significant deployment gap — misconfigured Firebase credentials will only surface in production.
- **Fix:** Add `TC-UAT-A19` — Admin approves leave → verify employee receives push notification on test device within 30 seconds. Requires real Firebase project and test device in UAT environment.

**R-021 — `auditService` not represented in unit testing strategy** (Medium)
- `auditService` writes `auditLogs` after every state change. It is called by every service but has no dedicated unit test section. The risk: `auditService` silently fails and swallows errors (by design — failure must not propagate), but there's no test that verifies the log WAS written.
- **Fix:** Add Section 2.11 `auditService` unit tests (4 scenarios): correct `entityType` logged; `before/after` snapshots captured; failure is swallowed (tested via mock `throw`); `actorRole: 'system'` used for cron-triggered audits.

**R-022 — No test for `ApiErrorCode` completeness / response shape** (Medium)
- No test validates that all 34 `ApiErrorCode` values produce correctly shaped `ApiResponse` objects. If a new error code is added without a message mapping, the API returns an undefined message.
- **Fix:** Add contract test: iterate all `ApiErrorCode` enum values; for each, construct `ApiResponse.error(code)` and assert `{ success: false, error: { code, message } }` where `message` is non-empty string.

**R-023 — Integration tests use `mongodb-memory-server` but concurrency tests need real Atlas** (Medium)
- The document correctly notes this distinction (Section 9), but the CI setup section does not specify how to handle the Atlas test cluster credentials in GitHub Actions. The CI pipeline will fail on TC-CON tests without secret management.
- **Fix:** Add Appendix C — CI/CD configuration: GitHub Actions secrets `ATLAS_TEST_URI`, `CRON_SECRET_TEST`, etc. Integration tests run on every PR (memory server). Concurrency tests run as a separate `test:concurrency` job on merge to `main` only (uses Atlas test cluster).

**R-024 — No accessibility or responsive layout tests for admin portal** (Low)
- UAT scenarios (TC-UAT-A*) cover functional flows but nothing tests that the admin portal renders correctly on tablet screens or meets WCAG 2.1 AA minimum for a business application.
- **Fix:** Add TC-UAT-A20 — Open admin dashboard on tablet (iPad 1024×768 portrait); verify no horizontal scroll, no overlapping elements. Accessibility: Lighthouse accessibility score ≥ 90 (automated, not manual). Mark as Low priority for V1 but document for V2 UAT expansion.

## 3. Tooling / Process Gaps

**R-025 — No test data isolation strategy between parallel CI jobs** (High)
- If multiple CI runs execute simultaneously (PR from two branches), integration tests that use `mongodb-memory-server` share no state, so that's fine. But concurrency tests on real Atlas use the same `company-test` cluster. Two concurrent CI runs will interfere. No isolation strategy is defined.
- **Fix:** Add Appendix C (CI/CD configuration): each concurrency test run creates/drops a unique Atlas database (`test-run-${CI_RUN_ID}`) using the Atlas Data API, runs tests against it, then drops it. Never uses a shared named database.

**R-026 — No mutation testing requirement** (Medium)
- Coverage thresholds (80% lines/branches) measure which lines are executed, not whether tests actually catch regressions. A test that calls a function without asserting the result achieves 100% coverage but catches nothing. `payrollEngine` in particular — 100% coverage does not guarantee all formula branches are verified correct.
- **Fix:** Add to quality gates: run `vitest --coverage` with `c8` and require mutation score ≥ 70% for `payrollEngine.ts` and `geoFenceEngine.ts` using a tool like Stryker or vitest-plugin-mutation. Advisory for V1; mandatory before V2.

**R-027 — Performance tests have no baseline persistence** (Medium)
- `TC-PER-001` through `TC-PER-008` define thresholds but there is no process for storing baseline results or detecting regressions across releases. A 20% latency increase between V1.0 and V1.1 will not be caught.
- **Fix:** Add to Appendix C: k6 results published to InfluxDB + Grafana (or k6 Cloud if budget allows) after every main-branch merge. Alert on 10% P95 regression vs. prior run.

**R-028 — No documented process for test case maintenance** (Low)
- This document defines 255 test scenarios at design time. As features evolve, test cases will become stale. There is no defined owner or review cadence.
- **Fix:** Add to Section 1.3 Definition of Done: "Any PR adding or modifying a feature must update the corresponding TC-* scenarios in `docs/03-testing-strategy.md` or create new ones. Reviewer is responsible for validating test scenario coverage, not just code coverage."

## 5. Validated Strengths

The following areas of the testing strategy are thorough and require no additions:

- **Payroll formula precision** — `E-PAY-01` through `E-PAY-11` cover the rounding contract comprehensively. The `effectivePresentDays` and `effectiveWorkingDays` boundary cases are well covered.
- **Security test matrix** — `TC-SEC-001` through `TC-SEC-020` cover all threat vectors identified in the architecture security score. CSRF, JWT rotation, nonce replay, rate limiting, and privilege escalation are all tested.
- **Concurrency test matrix** — `TC-CON-001` through `TC-CON-007` correctly identify the tests that require real Atlas (not memory server), and the scenarios directly test the DB-level integrity guarantees (partial unique index, atomic balance deduction, `usedNonces` uniqueness).
- **Integration test structure** — the four lifecycle suites (attendance, leave, regularization, payroll) map directly to the four primary transaction tiers. This is the right decomposition.
- **Leave approval ledger coverage** — every `leaveTransaction` type (`deduction-approval`, `restoration-rejection`, `restoration-revocation`, `carry-forward-credit`, `carry-forward-expiry`, `annual-allocation`) has a corresponding test case. This closes the most common financial integrity gap in HRMS implementations.
- **Definition of Production Ready** — the 8 criteria are correct and non-negotiable. The explicit inclusion of "UAT sign-off on physical devices" is important — simulator-only UAT has burned previous mobile-integrated projects.

---

## 6. Recommendation

The testing strategy is **conditionally approved** — well-structured with correct tooling choices and strong coverage of the core financial-integrity scenarios. The 28 findings above should be incorporated before the document is used as the implementation baseline.

**The 5 HIGH findings (R-001, R-002, R-003, R-004, R-005) must be resolved before any service is implemented.** They identify scenarios where the current test matrix would allow a financially incorrect or security-broken implementation to pass all tests.

**Resolution options:**
1. Add the missing TC-* scenarios directly to `docs/03-testing-strategy.md` (preferred)
2. Document as known gaps with explicit owner assignments and milestones (acceptable if implementation starts before document update)
