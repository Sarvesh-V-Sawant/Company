## R-API-001 — No Bulk Notification Mark-Read Endpoint

### Root Cause
The spec provided only a single-item mark-read endpoint (`PATCH /notifications/:id/read`). No batch endpoint existed. In HRMS contexts, employees frequently return to the app after days off and find 20–50 unread notifications — requiring 20–50 serial HTTP requests to clear them, each processed individually through Next.js Route Handler overhead, JWT validation, and a DB write.

### Business Impact
- **UX:** Flutter notification screen unusable when many unread items exist — user sees a multi-second spinner for each mark-read
- **Reliability:** Any network interruption mid-batch leaves notifications partially marked, inconsistent state on next app open
- **Server load:** 50 concurrent employees returning from a long weekend could fire 2,500 sequential write requests in a few seconds

### Security Impact
- Low. No additional attack surface beyond the existing single-item endpoint. Rate limiting inherited from the auth layer. Bulk endpoint bounded by `employeeId` scoping — employees can only mark their own notifications.

### Fix
Add `PATCH /api/v1/notifications/read-all` (Section 9.4):
- Accepts optional `{ "ids": ["id1","id2"] }` body for selective bulk mark-read; omit body for mark-all
- Returns count of notifications marked
- Scoped to authenticated employee's own notifications only
- Idempotent — re-calling with same IDs returns 200

### API Changes
**New endpoint:** `PATCH /api/v1/notifications/read-all`

```json
// Request Body (optional)
{
  "ids": ["string", "string"]  // optional; if omitted, marks ALL unread for this employee
}

// Response 200
{
  "success": true,
  "data": { "markedRead": 12 }
}
```

**New route file:** `src/app/api/v1/notifications/read-all/route.ts`

**Appendix A:** Added as endpoint #69.

### Schema Changes
None. `notifications` collection schema unchanged. The operation is a `updateMany({ employeeId, isRead: false }, { $set: { isRead: true, readAt: now } })` — no new fields.

### Migration Impact
None. No existing data changed.

## R-API-002 — Device Fingerprint Dual-Transport Bypass

### Root Cause
The checkin endpoint required `deviceFingerprint` in **both** the JSON request body and the `X-Device-Fingerprint` request header. Two separate code paths (Edge Middleware reads headers; Route Handler parses body) could validate against different values. The spec did not define which was authoritative on mismatch.

The `/auth/login` endpoint also sends `deviceFingerprint` in the body. This is **correct and intentional** — at login there is no active session or Bearer token, so a header-only approach is impossible. The dual-transport problem applied only to the attendance checkin endpoint.

### Business Impact
- **Correctness:** Two implementations (one using header, one using body) will diverge silently. Integration tests pass; production breaks on specific client builds.
- **Reliability:** Flutter client must send both; any client that omits one fails inconsistently.

### Security Impact

**Critical path:** If Edge Middleware validates the `X-Device-Fingerprint` header for rate limiting or access decisions, but the Route Handler reads `body.deviceFingerprint` for session creation — an attacker can:

1. Send a valid `X-Device-Fingerprint` header (device A's hash — passes middleware)
2. Send a *different* `body.deviceFingerprint` (device B's fingerprint — stored in session record)
3. Session is created with device B's fingerprint; future checkins by device A fail but device B gains an orphaned active session

This creates an **attendance session hijacking vector** in the worst case where the two validation paths use different values.

### Fix
**Single source of truth:** `X-Device-Fingerprint` header only. Remove `deviceFingerprint` from checkin request body.

The Route Handler reads the fingerprint from the header:
```typescript
const fingerprint = request.headers.get('X-Device-Fingerprint');
if (!fingerprint || !/^[0-9a-f]{64}$/i.test(fingerprint)) {
  return errorResponse(ApiErrorCode.DEVICE_NOT_REGISTERED, 401);
}
```

This eliminates the dual-source ambiguity entirely. Edge Middleware and Route Handler both see the same header value.

**Login remains unchanged** — `deviceFingerprint` in the body is the only way to transmit the fingerprint before a session exists.

### API Changes
**`POST /api/v1/attendance/checkin` — Request Body (updated):**
- Removed: `"deviceFingerprint": "string"`
- Header `X-Device-Fingerprint` remains required and is now the sole source

Updated `CheckinRequest` TypeScript interface: `deviceFingerprint` field removed.

Updated BR-ATT-02: "Read fingerprint from `X-Device-Fingerprint` header; compare with `user.registeredDeviceHash`. Missing or malformed header → `AUTH_004`. Mismatch → `AUTH_005`."

### Schema Changes
None. `registeredDeviceHash` storage unchanged.

### Migration Impact
None. Flutter client already sends `X-Device-Fingerprint` header; just stop sending it in the body too.

## R-API-003 — Password Reset Token Uses Wrong Hash Function

### Root Cause
The spec documented "Token is a 32-byte random value; stored as bcryptjs hash in DB" (`BR-AUTH-18`). `bcryptjs` is a key-derivation function designed for **human-guessable secrets** (passwords). Its adaptive cost makes it appropriate for passwords but is wrong for cryptographically random tokens because:

1. `bcryptjs` compare takes 50–100ms per call. At `authLimiter` rate (10 req/min per IP), an attacker rotating IPs can run sustained brute-force. For a properly-sized random token this is computationally infeasible regardless — but `bcryptjs` adds unnecessary latency for legitimate requests.
2. `bcryptjs` truncates inputs at 72 bytes internally — using it with 64-byte hex input (128 chars) means only the first 72 chars are used for the hash, silently halving effective entropy.
3. `bcryptjs` adds 100–300ms of synchronous-equivalent work to the password-reset/confirm hot path with no security benefit over `SHA-256`.

The spec also said `BR-AUTH-21`: "Look up `passwordResetTokens` by email + compare bcryptjs hash of provided token" — this is vague about whether email is stored encrypted or in plaintext, and does not specify `timingSafeEqual`.

### Business Impact
- **Performance:** Password reset confirm adds 100–300ms of unnecessary bcryptjs work to every password reset
- **Correctness:** bcryptjs 72-byte truncation silently reduces the effective token entropy from 256 bits to ~166 bits (72 bytes of the 64-char hex string). Not a practical attack, but incorrect behavior that should be explicit.

### Security Impact
**Not immediately exploitable** given the rate limiter and 15-minute TTL. However:
- Timing side-channel: non-constant-time comparison allows timing oracle attacks to distinguish "email not found" from "wrong token" responses (mitigated only by always-200 behavior of the request endpoint)
- Wrong tool creates maintenance risk: a future developer might see `bcryptjs` and assume truncation is acceptable (it's not intentional here)
- Spec must be authoritative and correct for all future implementors

### Fix
**Token generation:** `crypto.randomBytes(32).toString('hex')` — 64-char hex string, 256 bits of entropy. Raw value embedded in email link as URL parameter.

**Token storage:** `SHA-256(rawToken)` as hex string. SHA-256 is cryptographically appropriate for random tokens:
```typescript
import { createHash } from 'crypto';
const tokenHash = createHash('sha256').update(rawToken).digest('hex');
// Store tokenHash; never store rawToken
```

**Token verification:** Compute SHA-256 of the provided token; compare with stored hash using `crypto.timingSafeEqual`:
```typescript
import { createHash, timingSafeEqual } from 'crypto';
const providedHash = createHash('sha256').update(providedToken).digest('hex');
const storedHash = tokenRecord.tokenHash; // retrieved from DB
const match = timingSafeEqual(
  Buffer.from(providedHash, 'hex'),
  Buffer.from(storedHash, 'hex')
);
if (!match) throw new ApiError(ApiErrorCode.PASSWORD_RESET_TOKEN_INVALID);
```

### API Changes
**BR-AUTH-18 (updated):**
"Token is `crypto.randomBytes(32).toString('hex')` (64-char hex, 256-bit entropy). Stored as `SHA-256(rawToken)` hex string in `passwordResetTokens.tokenHash`. Raw token embedded in email link. Never stored in DB."

**BR-AUTH-21 (updated):**
"Look up `passwordResetTokens` by email. Compute `SHA-256(providedToken)`; compare with `tokenRecord.tokenHash` using `crypto.timingSafeEqual`. Non-match → `AUTH_009`. Record not found → `AUTH_009` (same error — prevents enumeration)."

No change to request/response shapes.

### Schema Changes
**`passwordResetTokens` collection:** Field renamed from `tokenHash` (was `bcryptjs` hash) to `tokenHash` (now `SHA-256` hex string). Same field name, different algorithm. Document comment updated.

The stored value is a 64-char hex string in both cases — **existing migrations:** existing stored bcryptjs hashes will fail `timingSafeEqual` against new SHA-256 values. The 15-minute TTL means all existing tokens expire within 15 minutes of deployment. No migration script needed — expired tokens are rejected as invalid regardless.

### Migration Impact
Tokens stored before deployment expire naturally within 15 minutes. No active password reset sessions persist across the deployment boundary that would be broken.

## R-API-004 — No Forced Password Change on First Login

### Root Cause
`POST /employees` returned a `temporaryPassword` as a one-time plaintext string visible only in the creation response. No mechanism existed to:
1. Force the employee to change this temporary password before accessing any functionality
2. Prevent the employee from using the system indefinitely with the admin-assigned password
3. Recover if the admin missed or lost the one-time display

This left all new employees operating with admin-controlled passwords unless they voluntarily used the change-password flow.

### Business Impact
- **Compliance:** HR platforms must enforce credential ownership. Admin retaining knowledge of employee passwords is a confidentiality violation in most jurisdictions.
- **Operational:** If admin loses the temp password before sharing it with the employee, the only recovery path is a full device reset, which also revokes sessions and requires re-registration — disproportionate to a missed copy-paste.
- **Trust:** Employees with no password-change prompt may never know they should change it.

### Security Impact

**Significant.** Admin knowing employee passwords means:
- Admin can impersonate employees, including logging their GPS attendance
- If admin portal is compromised, all employee credentials are compromised simultaneously
- No credential rotation = indefinite exposure window on any temporary password leak

### Fix

**Three-part fix:**

**Part 1 — Schema field:**
Add `requiresPasswordChange: { type: Boolean, default: true }` to the `users` collection.
- Set `true` on employee creation.
- Set `false` after employee successfully calls `PATCH /auth/me/change-password`.
- Admins (`role: 'admin'`) created via `POST /employees` also get `requiresPasswordChange: true`.

**Part 2 — JWT claim:**
Include `requiresPasswordChange` in the JWT access token payload:
```typescript
// JWT payload
{
  sub: string;                      // employee MongoDB _id
  role: 'admin' | 'employee';
  requiresPasswordChange: boolean;  // new
  iat: number;
  exp: number;
}
```
Edge Middleware reads this claim from the JWT without a DB round-trip. If `requiresPasswordChange: true`, all endpoints except the three below return `AUTH_010`.

**Permitted endpoints in restricted mode (requiresPasswordChange = true):**
1. `PATCH /api/v1/auth/me/change-password` — how they fix it
2. `POST /api/v1/auth/logout` — must be able to log out
3. `GET /api/v1/auth/me` — Flutter reads `requiresPasswordChange` from here to show prompt

**Part 3 — New error code `AUTH_010`:**
```
AUTH_010 | PASSWORD_CHANGE_REQUIRED | 403 | Temporary password must be changed before accessing this endpoint.
```
Flutter receives this on any API call (except the 3 permitted above) and redirects to the change-password screen.

**Recovery path (admin loses temp password):**
Admin calls `PATCH /employees/:id/reset-device` (existing endpoint) → all sessions revoked → admin then calls `POST /employees` ... no wait, the employee is already created. Better: add a note to the `PUT /employees/:id` endpoint that admin can trigger a new temp password via a `POST /employees/:id/reset-password` endpoint (admin-initiated password reset different from user-initiated). 

Actually: the existing `POST /auth/password-reset/request` flow already handles this — admin shares the employee's email; employee uses the self-service password reset link to set a new password independent of the admin. This is the recovery path. Document this explicitly.

### API Changes

**`POST /auth/login` — Response body (updated):**
```json
{
  "data": {
    "accessToken": "string",
    "refreshToken": "string",
    "sessionId": "string",
    "employee": {
      "id": "string",
      "employeeId": "string",
      "email": "string",
      "firstName": "string",
      "lastName": "string",
      "role": "admin | employee",
      "requiresPasswordChange": true   // NEW
    }
  }
}
```

**`GET /auth/me` — Response body (updated):**
```json
{
  "data": {
    ...existing fields...,
    "requiresPasswordChange": true   // NEW
  }
}
```

**`PATCH /auth/me/change-password` — BR-AUTH-29 (new):**
"After successful password update: set `user.requiresPasswordChange = false`. Issue a new access token with `requiresPasswordChange: false` in the response so Flutter can immediately navigate to the main screen without requiring a re-login."

Updated response for change-password to include `accessToken`:
```json
{
  "success": true,
  "data": {
    "message": "Password changed successfully. Other devices have been logged out.",
    "accessToken": "string"   // NEW — fresh token with requiresPasswordChange: false
  }
}
```

**`POST /employees` — BR-EMP-XX (new business rule):**
"BR-EMP-22: `requiresPasswordChange: true` set on all newly created employees. JWT issued at first login will include this claim."

**New error code `AUTH_010`** in error catalog.

**Edge Middleware** — new enforcement rule: if `payload.requiresPasswordChange === true` and requested path is not in permitted list → 403 `AUTH_010`.

### Schema Changes

| Collection | Field | Type | Default | Set When |
|---|---|---|---|---|
| `users` | `requiresPasswordChange` | `Boolean` | `true` | Employee creation |
| `users` | `requiresPasswordChange` | `Boolean` | `false` | After successful password change |

**No new indexes required.** Field is read via JWT claim, not queried directly.

### Migration Impact
**Existing employees:** `requiresPasswordChange` is `undefined` (field doesn't exist). Treat `undefined` as `false` — existing employees who have already set their own passwords are not forced to change again.

Migration script: `db.users.updateMany({ requiresPasswordChange: { $exists: false } }, { $set: { requiresPasswordChange: false } })`. Run before deployment to avoid undefined-field ambiguity.

## R-API-005 — Payroll Route Collision

### Root Cause
The review identified a risk where `/payroll/me/2026-06` could match both:
- `payroll/me/[yearMonth]/route.ts` (employee's own payslip — correct)
- `payroll/[employeeId]/[yearMonth]/route.ts` (admin route — incorrect, if employeeId = "me")

The root cause was ambiguity in what the `:employeeId` path parameter represents — was it the human-readable company ID ("EMP001") or the MongoDB ObjectId ("6826a1b3c4d5e6f7a8b9c0d1")?

### Business Impact
Low in practice (MongoDB ObjectIds cannot be the string "me"). However, the spec was ambiguous, and implementations diverging from the spec (e.g., using company employeeId strings in URLs) would create a real collision.

### Security Impact
If a future developer changes the payroll URL to use company `employeeId` strings instead of MongoDB `_id` values, an employee with `employeeId: "me"` could shadow admin access to their payroll record. The admin route `GET /payroll/me/2026-06` would resolve to the employee's self-view, and the admin would receive that employee's data instead of "employee with ID me"'s data — data leak from employee to admin rather than admin to employee, but still an unintended access pattern.

### Fix

**Definitive clarification: all `/:id` and `/:employeeId` path parameters in this API represent MongoDB ObjectIds (24-char hex strings).** MongoDB ObjectIds:
- Are exactly 24 hexadecimal characters
- Can never be "me", "compute", "admin", or any short English word
- Are generated server-side; clients never generate them

Therefore:
1. No actual route collision exists with the current implementation
2. The path parameter name is renamed from `:employeeId` to `:id` in payroll routes for consistency with all other employee-scoped endpoints

Additionally: `employeeId` (the company-assigned human-readable ID like "EMP001") has **no reserved words restriction** for the `users.employeeId` field because this field never appears in URLs. URLs always use MongoDB `_id`.

### API Changes

**Section 8 — Payroll route paths updated:**
- `GET /api/v1/payroll/:employeeId/:yearMonth` → `GET /api/v1/payroll/:id/:yearMonth`
- `PATCH /api/v1/payroll/:employeeId/:yearMonth/finalize` → `PATCH /api/v1/payroll/:id/:yearMonth/finalize`
- `PATCH /api/v1/payroll/:employeeId/:yearMonth/unfinalize` → `PATCH /api/v1/payroll/:id/:yearMonth/unfinalize`
- `GET /api/v1/payroll/:employeeId/:yearMonth/export` → `GET /api/v1/payroll/:id/:yearMonth/export`

**Section 1.1 — Route file structure updated:**
```
payroll/[id]/[yearMonth]/
  route.ts         # GET (admin single)
  finalize/route.ts
  unfinalize/route.ts
  export/route.ts
```

**Appendix A** — updated route paths for endpoints 44–47.

**New BR-PAY-17 (documentation):** "`:id` in payroll routes is the employee's MongoDB ObjectId (24-char hex). Never the company-assigned `employeeId` string."

**New BR-EMP-23 (documentation):** "The `employeeId` field (company-assigned ID) is never used in URL path parameters. URLs always use the MongoDB `_id`."

### Schema Changes
None. No DB changes required.

### Migration Impact
None. URL path parameter semantics clarified in documentation only. Existing URLs (`/payroll/EMP001/2026-06`) were never valid per the spec — this clarification makes the spec unambiguous, not a breaking change from deployed behavior (feature is not yet implemented).
