## F-006 / C-004 — No Cron Execution Tracking / Missing `systemEvents` Collection

**Root Cause:**
Vercel cron jobs have no built-in idempotency. Vercel retries on timeout; a deployment event can fire a cron twice within the same window. No collection existed to record execution state or prevent duplicate processing.

**Impact:**
- `leave-year-allocation` cron fires twice → every active employee receives double the annual leave allocation
- `carry-forward-expiry` fires twice → no harm (idempotent by nature) but no visibility
- `midnight-session-close` fires twice → second run finds no open sessions (self-healing) but no audit trail
- No historical record of cron execution for debugging or compliance queries

**Fix:**
Add `systemEvents` collection. Every cron handler inserts a `{ status: 'running' }` event before processing and checks for an existing `{ status: 'success' }` event for the same `{ type, targetKey }` combination before proceeding.

**Idempotency Pattern (all cron handlers):**
```typescript
// In every cron Route Handler — before any processing:
const alreadyRan = await SystemEvent.findOne({
  type: 'leave-year-allocation',
  targetKey: leaveYear.toString(),
  status: 'success',
});
if (alreadyRan) {
  return ApiResponse.ok({ message: 'Already ran', skipped: true });
}

const event = await SystemEvent.create({
  type: 'leave-year-allocation',
  targetKey: leaveYear.toString(),
  triggeredBy: 'cron',
});

try {
  let count = 0;
  for (const employee of activeEmployees) {
    await withTransaction(async (session) => { /* ... */ });
    count++;
  }
  await SystemEvent.findByIdAndUpdate(event._id, {
    status: 'success',
    completedAt: new Date(),
    affectedCount: count,
  });
} catch (err) {
  await SystemEvent.findByIdAndUpdate(event._id, {
    status: 'failed',
    completedAt: new Date(),
    error: String(err).slice(0, 1000),
  });
  throw err;
}
```

**Schema Changes — New `systemEvents` collection:**

```typescript
// src/lib/models/SystemEvent.ts
import mongoose, { Schema, Document, Model } from 'mongoose';

export type SystemEventType =
  | 'midnight-session-close'
  | 'leave-year-allocation'
  | 'carry-forward-expiry'
  | 'attendance-reminder-sent'
  | 'payroll-compute-scheduled';

export type SystemEventStatus  = 'running' | 'success' | 'failed';
export type SystemEventTrigger = 'cron' | 'admin';

export interface ISystemEvent extends Document {
  type: SystemEventType;
  targetKey: string;                         // "2026-06-14" (daily) | "2026" (annual)
  status: SystemEventStatus;
  startedAt: Date;
  completedAt?: Date;
  error?: string;
  affectedCount?: number;
  triggeredBy: SystemEventTrigger;
  triggeredByUserId?: mongoose.Types.ObjectId;
  createdAt: Date;
}

const SystemEventSchema = new Schema<ISystemEvent>(
  {
    type: {
      type: String,
      enum: ['midnight-session-close','leave-year-allocation','carry-forward-expiry','attendance-reminder-sent','payroll-compute-scheduled'],
      required: true,
    },
    targetKey:    { type: String, required: true },
    status:       { type: String, enum: ['running','success','failed'], required: true, default: 'running' },
    startedAt:    { type: Date, required: true, default: Date.now },
    completedAt:  { type: Date },
    error:        { type: String, maxlength: 1000 },
    affectedCount:{ type: Number, min: 0 },
    triggeredBy:  { type: String, enum: ['cron','admin'], required: true, default: 'cron' },
    triggeredByUserId: { type: Schema.Types.ObjectId, ref: 'User' },
  },
  { timestamps: { createdAt: true, updatedAt: false } }
);

// Idempotency: check for status='success' with { type, targetKey } before inserting
SystemEventSchema.index({ type: 1, targetKey: 1, status: 1 });
SystemEventSchema.index({ type: 1, startedAt: -1 });
SystemEventSchema.index({ createdAt: 1 }, { expireAfterSeconds: 7_776_000 }); // TTL 90 days

export const SystemEvent: Model<ISystemEvent> =
  (mongoose.models['SystemEvent'] as Model<ISystemEvent>) ??
  mongoose.model<ISystemEvent>('SystemEvent', SystemEventSchema);
```

**Architecture Changes:**
- `SystemEvent.ts` added to `lib/models/`
- `systemEventRepository.ts` added to `lib/repositories/`
- All 4 cron handlers updated to implement idempotency pattern
- `payrollService.compute()` writes to `systemEvents` inside its transaction (already in Tier 1 table — now implemented)
- `leaveAllocationCron.run()` writes to `systemEvents` outside transaction (event created before batch; updated after)

**Migration Impact:**
- New collection — no migration needed for existing data
- No breaking changes to any existing collection

## F-008 — Admin Portal CSRF Protection Not Addressed

**Root Cause:**
Admin portal uses httpOnly cookies for JWT session (correct for web). No CSRF mitigation strategy was defined. A malicious site could craft cross-origin requests that carry the admin's cookie automatically (SameSite defaults vary by browser).

**Impact:**
- Admin-targeted CSRF attack could approve leaves, deactivate employees, change settings, or approve payroll — all state-changing admin actions triggered from an attacker-controlled page
- Severity mitigated by auth being in httpOnly cookie (not accessible to JS), but same-site requests from malicious pages remain possible without explicit SameSite enforcement

**Fix:**
Three-layer strategy. No new packages required.

**Layer 1 — `SameSite=Strict` on auth cookie:**
```typescript
// lib/utils/jwt.ts — cookie creation helper
export function buildAuthCookieOptions(): Partial<CookieOptions> {
  return {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'strict',    // blocks all cross-origin requests, including navigation-driven POSTs
    path: '/',
    maxAge: 15 * 60,       // 15 minutes (access token)
  };
}
```

**Layer 2 — `Origin` header validation in Edge Middleware:**
```typescript
// middleware.ts (Edge) — for cookie-authenticated admin requests
const origin = request.headers.get('origin');
const appUrl = process.env.NEXT_PUBLIC_APP_URL;

if (isCookieAuthRequest && origin && origin !== appUrl) {
  return NextResponse.json({ error: 'CSRF_REJECTED' }, { status: 403 });
}
```

`isCookieAuthRequest` = the request carries a session cookie but no `Authorization: Bearer` header. Flutter always uses `Authorization` header — not affected.

**Layer 3 — No CSRF risk for Flutter:**
Flutter sends `Authorization: Bearer <token>` in headers. Browsers cannot set custom `Authorization` headers cross-origin without a CORS preflight. CORS is already configured to reject unknown origins. Flutter is not affected by CSRF.

**Schema Changes:** None.

**Architecture Changes:**
- `middleware.ts`: add Origin validation for admin (cookie-authenticated) requests
- Cookie options: `SameSite=Strict` documented
- New section in architecture doc: Section 9 — Security Policies

**Migration Impact:** None. Cookie attribute change takes effect on next login.

## I-006 — Missing TTL Cleanup Strategy for `fcmTokens`

**Root Cause:**
FCM tokens are invalidated server-side by Firebase when a device is uninstalled, replaced, or unused for extended periods. No mechanism existed to remove these stale tokens. The only cleanup path was catching `registration-token-not-registered` errors per notification send.

**Impact:**
- `fcmTokens` collection grows unboundedly for inactive devices
- Notification service iterates stale tokens, fires FCM requests, handles errors — wasted API calls on every notification
- No proactive cleanup path

**Fix:**

**Two-tier approach:**

**Tier 1 — Reactive:** On FCM error `messaging/registration-token-not-registered`, set `isActive: false` in `notificationService`. Already implied by design; now explicitly documented.

```typescript
// lib/services/notificationService.ts
try {
  await firebaseAdmin.messaging().send(message);
} catch (err: any) {
  if (err.code === 'messaging/registration-token-not-registered') {
    await FcmToken.findOneAndUpdate({ token }, { isActive: false });
  }
  // do not re-throw — notification failure must not fail the primary operation
}
```

**Tier 2 — Proactive TTL:** Add TTL index on `lastRefreshedAt`. Tokens not refreshed within 90 days are auto-deleted. Flutter app must refresh the FCM token on app launch and call `POST /api/v1/notifications/fcm-token`.

**Schema Changes:**

```typescript
// Add to FcmTokenSchema indexes:
FcmTokenSchema.index({ lastRefreshedAt: 1 }, { expireAfterSeconds: 7_776_000 }); // 90-day TTL
```

**Architecture Changes:**
- `notificationService`: document `registration-token-not-registered` handler
- Flutter contract: refresh FCM token on app launch → `POST /api/v1/notifications/fcm-token`

**Migration Impact:** TTL index is additive. Existing tokens with `lastRefreshedAt` older than 90 days will be deleted by MongoDB's TTL monitor (runs every 60 seconds). Acceptable — stale tokens have no value.

## A-002 — Flutter Timer Anchor Lost on App Restart

**Root Cause:**
`GET /api/v1/attendance/status` endpoint existed in the folder structure but its response contract was never defined. Flutter relies on `serverCheckinTime` from the checkin response to drive the elapsed-time timer. If the app is killed and restarted, this value is gone.

**Impact:**
- Flutter shows 0:00 timer or incorrect time after app restart mid-session
- No reliable way for Flutter to resume timer anchor without calling the status endpoint
- Status endpoint without a contract creates implementation guesswork

**Fix:**

Define the `GET /api/v1/attendance/status` response contract explicitly:

```typescript
// Response type (documented in src/types/index.ts)
export interface AttendanceStatusResponse {
  isCheckedIn: boolean;
  currentSession?: {
    sessionId: string;
    checkInTimestamp: string;          // ISO 8601 — Flutter rebuilds timer from this
    dateString: string;
    totalMinutesToday: number;         // sum of durationMinutes from all closed sessions today
  };
  todaySummary: {
    status: AttendanceDayStatus;       // 'present' | 'absent' | 'half-day' | etc.
    totalMinutes: number;              // cumulative across all sessions today
    requiredMinutes: number;
    overtimeMinutes: number;
  };
}
```

Flutter behaviour on app launch:
```
1. Call GET /api/v1/attendance/status
2. If isCheckedIn = true:
   a. Set timer anchor = checkInTimestamp
   b. Display elapsed = now() - checkInTimestamp
   c. Add totalMinutesToday (from closed sessions) to display total
3. If isCheckedIn = false:
   a. Show "Not checked in" state
   b. Display todaySummary.totalMinutes as today's recorded time
```

**Schema Changes:** None. Response fields come from existing `AttendanceSession` and `AttendanceDay` documents.

**Architecture Changes:**
- `GET /api/v1/attendance/status` response contract added to architecture doc
- Flutter integration contract documented

**Migration Impact:** None.

## P-001 — Floating Point Arithmetic in Payroll Computation

**Root Cause:**
Payroll formula involves `monthlySalary / effectiveWorkingDays` — a non-terminating decimal in IEEE 754. Rounding timing was not specified. `perDaySalary` and `deductions` stored without specifying precision. Different intermediate rounding choices produce different final results.

**Impact:**
- Payable amount varies by ±₹1–₹5 depending on when rounding is applied
- Two admins computing payroll for the same employee may get different results if they use different rounding approaches
- `Math.round(50000/22 * 3 * 100) / 100` ≠ `Math.round(50000/22 * 100) / 100 * 3` in some cases

**Fix:**

**Canonical rounding contract (enforce in `payrollEngine.ts`):**

```typescript
// payrollEngine.ts — canonical computation order
function computePayroll(input: PayrollInput): PayrollOutput {
  // 1. All intermediate values at FULL float precision — no rounding
  const perDaySalary   = input.monthlySalary / input.effectiveWorkingDays;
  const deductibleDays = input.effectiveLwpDays + input.absentDays;
  const deductions     = deductibleDays * perDaySalary;

  // 2. Round ONLY at storage boundary — perDaySalary stored at 4dp for display
  const perDaySalaryStored = Math.round(perDaySalary * 10_000) / 10_000;

  // 3. payableAmount: only value rounded to 2dp; min 0
  const payableAmount = Math.round(Math.max(0, input.monthlySalary - deductions) * 100) / 100;

  return { perDaySalary: perDaySalaryStored, deductions, payableAmount };
}
```

**Rule:** `deductions` stored at full float precision. `payableAmount` is the only value that legally matters — it is rounded to 2 decimal places at output. `perDaySalary` stored at 4dp for display purposes only; computation always uses `monthlySalary / effectiveWorkingDays` directly, never the stored 4dp value.

**Schema Changes:**
Add comments to `PayrollSummary` schema clarifying storage precision:

```typescript
// Rounding contract — enforced in payrollEngine.ts:
// - All intermediate values computed at full float precision
// - perDaySalary stored at 4dp (display only; engine recomputes from monthlySalary / effectiveWorkingDays)
// - deductions stored at full precision
// - payableAmount = Math.round(Math.max(0, monthlySalary - deductions) * 100) / 100  ← only rounded value
perDaySalary:  { type: Number, required: true, min: 0 },
deductions:    { type: Number, required: true, min: 0 },
payableAmount: { type: Number, required: true, min: 0 },
```

**Architecture Changes:** `payrollEngine.ts` rounding contract documented in architecture doc.

**Migration Impact:** None. Existing payroll records (`status: 'draft'`) may differ by ≤₹1 from recomputed values if payroll was computed with inconsistent rounding. Finalised payroll records (`status: 'finalised'`) are immutable — document this caveat.

## SEC-002 — Password Reset Rate Limit Insufficient

**Root Cause:**
Password reset shared the auth route rate limit (10 req/min). This allows ~600 reset emails/hr to any valid address, and doesn't distinguish IP-based abuse from targeted email bombing.

**Impact:**
- Email bombing: attacker sends 600 reset emails/hour to a victim employee's inbox
- Brute-force of reset tokens: 10 attempts/minute against a valid token link until expiry
- User enumeration: timing difference between "email exists" vs "email not found" response

**Fix:**

**Dedicated password reset limiter (3 per hour, dual-keyed):**

```typescript
// lib/utils/rateLimit.ts
import { Ratelimit } from '@upstash/ratelimit';
import { redis } from './redis';

export const passwordResetLimiter = new Ratelimit({
  redis,
  limiter: Ratelimit.slidingWindow(3, '1h'),
  prefix: 'ratelimit:pwd-reset',
});

// In POST /api/v1/auth/password-reset/request route handler:
const [byEmail, byIp] = await Promise.all([
  passwordResetLimiter.limit(`email:${normalizedEmail}`),
  passwordResetLimiter.limit(`ip:${clientIp}`),
]);

if (!byEmail.success || !byIp.success) {
  // Return IDENTICAL response to the success path — no enumeration
  return ApiResponse.ok({ message: 'If that email exists, a reset link has been sent.' });
  // Do NOT return 429 — that reveals whether the limit was hit by email or IP
}
```

**User enumeration prevention:** Always return HTTP 200 with the same message whether or not the email exists. The rate limiter check returns the same response even when limited (not 429) — prevents confirming that a limit was hit on a specific email.

**Schema Changes:** None.

**Architecture Changes:**
- `passwordResetLimiter` added to `lib/utils/rateLimit.ts`
- Rate limit table updated: password-reset at 3/hr per email + 3/hr per IP
- Enumeration prevention contract documented

**Migration Impact:** None.

## SEC-003 — IP Address Storage Is PII — No Privacy Policy Documented

**Root Cause:**
`deviceSessions.ipAddress` and `auditLogs.metadata.ipAddress` stored raw IP addresses without a documented legal basis or privacy policy. Under DPDP Act 2023 (India) and analogous laws, IP addresses are personal data requiring a documented purpose.

**Impact:**
- Legal exposure if accessed without documented purpose
- Subject access requests cannot be answered (no documented scope)
- Erasure requests conflict with 7-year audit log retention

**Fix:**

**Documented policy decision (enforced by architecture — no schema change):**

| Collection | Field | Storage | Legal Basis | Retention |
|---|---|---|---|---|
| `auditLogs` | `metadata.ipAddress` | Raw IP | Fraud investigation / operational security (legitimate interest) | 7 years (existing TTL) |
| `deviceSessions` | `ipAddress` | SHA-256 hash (truncated) | Session correlation / security incident investigation | Until session expires (existing TTL) |

**`deviceSessions.ipAddress` hashing:**
```typescript
// lib/utils/hash.ts — add helper
import crypto from 'crypto';

export function hashIpAddress(ip: string): string {
  // One-way hash — sufficient for correlation, not reversible to raw IP
  return crypto
    .createHmac('sha256', process.env.JWT_SECRET!)
    .update(ip)
    .digest('hex')
    .slice(0, 16); // 16-hex prefix — collision-resistant for audit correlation
}
```

Rename `deviceSessions.ipAddress` → `ipAddressHash` and store the hash. The audit log retains raw IP (legitimate interest for fraud investigation is stronger justification).

**Schema Changes:**

```typescript
// DeviceSession.ts — rename field
ipAddressHash: { type: String, required: true },  // SHA-256(HMAC(ip, JWT_SECRET))[:16]
```

**Architecture Changes:**
- `hash.ts`: `hashIpAddress()` utility documented
- Privacy policy section added to architecture doc
- `deviceSessions.ipAddress` renamed to `ipAddressHash` (breaking change — migration required)

**Migration Impact:**
```javascript
// One-time migration script (run before deploying v1.2):
// db.deviceSessions.updateMany({}, [{ $set: { ipAddressHash: '$ipAddress' } }, { $unset: 'ipAddress' }])
// Note: existing sessions cannot be re-hashed (raw IP not available). Set to 'migrated-hash-unknown'.
db.deviceSessions.updateMany(
  { ipAddress: { $exists: true }, ipAddressHash: { $exists: false } },
  [{ $set: { ipAddressHash: 'migrated-hash-unknown' } }, { $unset: 'ipAddress' }]
);
```

Post-migration: all new device sessions use `hashIpAddress()`. Historical records use `'migrated-hash-unknown'` sentinel.

## SEC-004 — No JWT Secret Rotation Strategy

**Root Cause:**
`JWT_SECRET` was a static env variable with no documented rotation procedure. Refresh tokens live 7 days — secret rotation would log out all users for 7 days without a grace period strategy. `JWT_SECRET_PREVIOUS` was added to env vars in v1.1 but the verification logic was never documented.

**Impact:**
- Compromised `JWT_SECRET` means all active sessions are permanently valid for up to 7 days after discovery (all refresh tokens remain valid)
- Rotation without a grace period forces re-login for all users simultaneously — operational disruption

**Fix:**

**Dual-secret verification (grace period rotation):**

```typescript
// lib/utils/jwt.ts
import { jwtVerify, SignJWT } from 'jose';

const JWT_SECRET          = new TextEncoder().encode(process.env.JWT_SECRET!);
const JWT_SECRET_PREVIOUS = process.env.JWT_SECRET_PREVIOUS
  ? new TextEncoder().encode(process.env.JWT_SECRET_PREVIOUS)
  : null;

export async function verifyAccessToken(token: string) {
  try {
    const { payload } = await jwtVerify(token, JWT_SECRET);
    return payload;
  } catch {
    if (JWT_SECRET_PREVIOUS) {
      const { payload } = await jwtVerify(token, JWT_SECRET_PREVIOUS);
      return payload;
    }
    throw new Error('TOKEN_INVALID');
  }
}

// Same pattern for verifyRefreshToken using JWT_REFRESH_SECRET / JWT_REFRESH_SECRET_PREVIOUS
```

**Rotation procedure (documented in deployment runbook):**

```
Step 1: Set JWT_SECRET_PREVIOUS = current JWT_SECRET in Vercel env vars
Step 2: Generate new JWT_SECRET (64-char random string)
Step 3: Set new JWT_SECRET in Vercel env vars
Step 4: Redeploy (takes ~30 seconds on Vercel)
Step 5: All tokens signed with old secret still verify via JWT_SECRET_PREVIOUS
Step 6: After 7 days (max refresh token lifetime), remove JWT_SECRET_PREVIOUS
Step 7: All sessions are now using new secret; no user disruption
```

**Schema Changes:** None.

**Architecture Changes:**
- `jwt.ts` dual-secret verification pattern documented
- Rotation procedure added to Section 8 (Deployment)
- `JWT_REFRESH_SECRET_PREVIOUS` added to env vars list (for refresh token rotation parity)

**Migration Impact:** None. Zero-downtime rotation. Users re-authenticate naturally as tokens expire.

## M-001 — No Database Seed / Initialization Plan

**Root Cause:**
`src/scripts/seed.ts` was added to the folder structure in v1.1 but its content and contract were never specified. First-deployment setup was left implicit.

**Impact:**
- First deployment for each client requires manual MongoDB operations
- Incorrect initial `companySettings` (e.g., wrong `leaveYearStartMonth`) requires running a correction and potentially re-running leave year allocation
- Missing initial admin user means no way to log in to configure the system

**Fix:**

**Full seed script specification:**

```typescript
// src/scripts/seed.ts
// Usage: MONGODB_URI=... SEED_ADMIN_EMAIL=admin@company.com npx tsx src/scripts/seed.ts
// Idempotent — safe to run multiple times

import mongoose from 'mongoose';

  const required = ['MONGODB_URI', 'JWT_SECRET', 'SEED_ADMIN_EMAIL'];

  // 2. Upsert companySettings singleton
  await CompanySettings.findByIdAndUpdate(
    'company-settings',
    {
      $setOnInsert: {
        companyName: process.env.SEED_COMPANY_NAME ?? 'Company',
        timezone:    'Asia/Kolkata',
        currency:    'INR',
        workStartTime: '09:00',
        workEndTime:   '18:30',
        gracePeriodMinutes: 30,
        requiredDailyMinutes: 540,
        halfDayThresholdMinutes: 270,
        workingDays: ['monday','tuesday','wednesday','thursday','friday'],
        leaveYearStartMonth: 1,
        geoFence: { latitude: 0, longitude: 0, radiusMeters: 200, isEnabled: false },
        gpsAccuracyThresholdMeters: 100,
        regularizationLookbackDays: 7,
        checkinTimestampWindowMinutes: 2,
        leaveTypes: {
          paidLeave:   { annualAllocation: 15, carryForward: { enabled: true,  maxDays: 5,  expiryMonths: 3 }, encashable: false },
          sickLeave:   { annualAllocation: 10, carryForward: { enabled: false, maxDays: 0,  expiryMonths: 0 }, encashable: false },
          casualLeave: { annualAllocation: 5,  carryForward: { enabled: false, maxDays: 0,  expiryMonths: 0 }, encashable: false },
        },
        payrollCutoffDay: 1,
        attendanceReminderEnabled: true,
        attendanceReminderTime: '09:30',
        updatedAt: new Date(),
      },
    },
    { upsert: true, new: true }
  );
  console.log('✓ companySettings upserted');

  // 3. Create initial admin user (idempotent — skip if exists)
  const adminEmail = process.env.SEED_ADMIN_EMAIL!.toLowerCase();

    const tempPassword = crypto.randomBytes(12).toString('hex');

    await User.create({
      employeeId:    'ADMIN001',
      firstName:     'System',
      lastName:      'Admin',
      email:         adminEmail,
      passwordHash,
      role:          'admin',

      dateOfJoining: new Date(),
      isActive:      true,
      leaveBalances: {
        paidLeave:   { currentYear: 0, carriedForward: 0 },
        sickLeave:   { currentYear: 0, carriedForward: 0 },
        casualLeave: { currentYear: 0, carriedForward: 0 },
      },

    // Print to stdout only — never log or store
    console.log('✓ Admin user created');
    console.log(`  Email:    ${adminEmail}`);
    console.log(`  Password: ${tempPassword}  ← CHANGE ON FIRST LOGIN`);
  } else {
    console.log('✓ Admin user already exists — skipped');
  }

  await mongoose.disconnect();
  console.log('Seed complete.');
}

seed().catch(err => { console.error(err); process.exit(1); });
```

**New env var required:**
```bash
SEED_ADMIN_EMAIL=admin@company.com      # required — seed script only
SEED_COMPANY_NAME=Acme Corp             # optional — defaults to 'Company'
```

**Schema Changes:** None.

**Architecture Changes:**
- Seed script contract fully specified in architecture doc Section 8
- `SEED_ADMIN_EMAIL` and `SEED_COMPANY_NAME` added to `.env.example` (seed-only, not runtime)
- Deployment checklist updated: step 5 now references specific env vars

**Migration Impact:** None. Script is idempotent — `$setOnInsert` means it never overwrites an existing settings document.

## M-003 — No Standardized API Error Code Catalogue

**Root Cause:**
`lib/utils/apiResponse.ts` referenced in folder structure but `ApiErrorCode` enum never defined. Different route handlers would return inconsistent error shapes. Flutter app needs machine-readable codes to map to localized user-facing messages.

**Impact:**
- Flutter shows raw error messages (e.g., `"LeaveTransaction is immutable"`) to users
- Two endpoints returning the same logical error (insufficient balance) use different strings
- No way to write Flutter error-handling logic without implementation-specific knowledge

**Fix:**

**Canonical `ApiErrorCode` enum:**

```typescript
// src/lib/utils/apiResponse.ts

export enum ApiErrorCode {
  // Auth (AUTH_xxx)
  INVALID_CREDENTIALS           = 'AUTH_001',
  TOKEN_EXPIRED                 = 'AUTH_002',
  TOKEN_INVALID                 = 'AUTH_003',
  DEVICE_NOT_REGISTERED         = 'AUTH_004',
  DEVICE_FINGERPRINT_MISMATCH   = 'AUTH_005',
  INSUFFICIENT_PERMISSIONS      = 'AUTH_006',
  ACCOUNT_DEACTIVATED           = 'AUTH_007',

  success: true;
  data: T;

export interface ApiErrorResponse {
  success: false;
  error: {
    code: ApiErrorCode;
    message: string;       // human-readable, English — Flutter maps code to localized string
    details?: unknown;     // validation field errors etc.
  };
}

export class ApiResponse {
  static ok<T>(data: T, status = 200): Response {
    return Response.json({ success: true, data } satisfies ApiSuccessResponse<T>, { status });
  }

  static error(code: ApiErrorCode, message: string, status: number, details?: unknown): Response {
    return Response.json(
      { success: false, error: { code, message, details } } satisfies ApiErrorResponse,
      { status }
    );
  }
}

export const rateLimit   = ()                         => ApiResponse.error(ApiErrorCode.RATE_LIMITED, 'Too many requests', 429);
export const serverError = ()                         => ApiResponse.error(ApiErrorCode.INTERNAL_ERROR, 'Internal error', 500);
```

## NM-001 — `companySettings.updatedAt` in Interface but Absent from Schema Definition

**Root Cause:**
`ICompanySettings` declared `updatedAt: Date` but `{ timestamps: false }` prevented Mongoose from auto-generating it, and no explicit schema field was defined. `updatedAt` stored via `$set` in `findByIdAndUpdate` would exist in MongoDB but be invisible to Mongoose's type system.

**Impact:**
- TypeScript interface claims `updatedAt` exists; Mongoose schema disagrees
- `.lean()` query results include `updatedAt` from MongoDB but TypeScript won't recognize it
- Schema validation (if ever run on the full document) would fail silently

**Fix:**

Add `updatedAt` as an explicit schema field:

```typescript
// Add to CompanySettingsSchema definition (alongside updatedBy):
updatedAt: { type: Date, required: true, default: Date.now },
updatedBy: { type: Schema.Types.ObjectId, ref: 'User', required: true },
```

**Schema Changes:** One field addition to `CompanySettingsSchema`.

**Architecture Changes:** None.

**Migration Impact:**
```javascript
// Existing settings document likely has updatedAt already from $set operations.
// If not, run:
db.companySettings.updateMany(
  { updatedAt: { $exists: false } },
  { $set: { updatedAt: new Date() } }
);
```

## NM-002 — `leaveYearAllocations` Has No Immutability Protection

**Root Cause:**
`leaveYearAllocations` was introduced as an allocation audit trail in v1.1 but immutability hooks (standard on `leaveTransactions` and `auditLogs`) were not applied.

**Impact:**
- Application bug or direct DB operation could silently modify a historical allocation record
- Pro-ration disputes ("how many days was I allocated on April 1?") become unresolvable if the record was overwritten
- Inconsistency: two other audit collections are immutable, this one is not

**Fix:**

```typescript
// Add to LeaveYearAllocationSchema:
LeaveYearAllocationSchema.pre('findOneAndUpdate', () => { throw new Error('LeaveYearAllocation is immutable'); });
LeaveYearAllocationSchema.pre('updateOne',        () => { throw new Error('LeaveYearAllocation is immutable'); });
LeaveYearAllocationSchema.pre('updateMany',       () => { throw new Error('LeaveYearAllocation is immutable'); });
LeaveYearAllocationSchema.pre('save', function()  { if (!this.isNew) throw new Error('LeaveYearAllocation is immutable'); });
// Note: bulkWrite NOT blocked — batch inserts during annual allocation cron use insertMany via bulkWrite
```

**Schema Changes:** Four pre-hooks added to `LeaveYearAllocationSchema`.

**Architecture Changes:** None.

**Migration Impact:** None.

## NM-003 — `performedBy` / `allocatedBy` Typed as `Schema.Types.Mixed` Without Validation

**Root Cause:**
Both `LeaveTransaction.performedBy` and `LeaveYearAllocation.allocatedBy` need to accept either an `ObjectId` (human actor) or a string sentinel (`'system'` / `'system-cron'`). `Schema.Types.Mixed` was used as the path of least resistance, bypassing all Mongoose validation.

**Impact:**
- Any value can be stored: empty string, null, object, number
- Audit trail becomes unreliable if a service bug passes wrong value
- TypeScript types claim `ObjectId | string` but runtime has no enforcement

**Fix:**

Custom Mongoose validator on both fields:

```typescript
// LeaveTransaction.ts — replace performedBy field:
performedBy: {
  type: Schema.Types.Mixed,
  required: true,
  validate: {
    validator: (v: unknown) =>
      v === 'system' ||
      (typeof v === 'string' && v === 'system-cron') ||
      v instanceof mongoose.Types.ObjectId,
    message: 'performedBy must be an ObjectId, "system", or "system-cron"',
  },
},

// LeaveYearAllocation.ts — replace allocatedBy field:
allocatedBy: {
  type: Schema.Types.Mixed,
  required: true,
  validate: {
    validator: (v: unknown) =>
      v === 'system-cron' ||
      v instanceof mongoose.Types.ObjectId,
    message: 'allocatedBy must be an ObjectId or "system-cron"',
  },
},
```

**Schema Changes:** Two field definitions updated with inline validators.

**Architecture Changes:** None.

**Migration Impact:** None. Validator only fires on new writes — existing documents unaffected.
