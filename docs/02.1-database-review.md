## 1. Architectural Flaws

---

### F-001 — No MongoDB transaction strategy defined
**Severity:** 🔴 HIGH
**Category:** Architectural

**Finding:**
Multiple write operations span two or more collections with no atomicity guarantee. Current documents mention only service-layer ordering. If any step fails mid-sequence, data is left in an inconsistent state.

Critical multi-write operations that require atomicity:

| Operation | Collections touched |
|---|---|
| Leave approval | `leaveRequests` + `users.leaveBalances` + `attendanceDays` + `notifications` |
| Leave cancellation | `leaveRequests` + `users.leaveBalances` |
| Regularization approval | `regularizationRequests` + `attendanceSessions` + `attendanceDays` |
| Checkout | `attendanceSessions` + `attendanceDays` |
| Employee deactivation | `users` + `deviceSessions` (revoke all) + `fcmTokens` (deactivate all) |

MongoDB Atlas clusters always use replica sets and support multi-document ACID transactions since MongoDB 4.0.

**Proposed Fix:**
Add a transaction strategy section to the architecture document. All multi-write operations must use `mongoose.startSession()` + `session.withTransaction()`. Document which service methods require a session and which do not.

```typescript
// Pattern to adopt in all critical service methods
const session = await mongoose.startSession();
await session.withTransaction(async () => {
  await LeaveRequest.findByIdAndUpdate(id, { status: 'approved' }, { session });
  await User.findByIdAndUpdate(userId, { $inc: { 'leaveBalances.paidLeave': -days } }, { session });
  await AttendanceDay.updateMany(..., { session });
});
session.endSession();
```

### F-002 — Race condition on simultaneous checkin
**Severity:** 🔴 HIGH
**Category:** Architectural / Schema

**Finding:**
The "only one active session per employee" rule is enforced in `attendanceService` with a pre-insert check. On Vercel serverless, two concurrent requests from the same employee (double-tap, poor network retry) can both pass the check before either creates the session. Result: two active sessions for the same employee on the same day.

**Proposed Fix:**
Add a partial unique index on `attendanceSessions`:

```typescript
AttendanceSessionSchema.index(
  { employeeId: 1 },
  {
    unique: true,
    partialFilterExpression: { isActive: true }, // MongoDB partial index
    name: 'unique_active_session_per_employee',
  }
);
```

This makes the DB enforce at most one `isActive: true` document per employee. The service check becomes a fast pre-validation, not the sole guard.

### F-003 — Open session crosses midnight — no rollover logic
**Severity:** 🔴 HIGH
**Category:** Attendance Engine

**Finding:**
Employee checks in at 11:30 PM. App crashes or phone dies. Session remains `isActive: true` forever. Next morning, employee cannot check in — blocked by the orphaned session.

Additionally: the session's `durationMinutes` would include sleep time if auto-closed by midnight cron, inflating attendance unfairly.

**Proposed Fix:**
1. Add `companySettings.workEndTime: string` (e.g. `"20:00"`) — the latest possible checkout.
2. Create a Vercel cron job that runs at `workEndTime + 30 min` daily: find all `isActive: true` sessions older than the current day's work end time, auto-close them with a `closedBySystem: true` flag and a note.
3. Add fields to `AttendanceSession`:
   - `closedBySystem: boolean` (default false)
   - `systemCloseReason?: 'midnight-rollover' | 'manual-admin-close'`

Auto-closed sessions' `durationMinutes` is capped at `(workEndTime - checkIn.timestamp)`, not actual closure time.

### F-004 — No leave year start configuration
**Severity:** 🔴 HIGH
**Category:** HRMS Domain / Schema

**Finding:**
`companySettings` has no `leaveYearStartMonth` field. The carry-forward logic references "expiryMonths after Jan 1" but assumes all companies use a January–December leave year. Indian companies commonly use April–March. The absence of this field makes annual allocation reset, carry-forward calculation, and pro-rated joining logic ambiguous.

**Proposed Fix:**
Add to `companySettings`:
```typescript
leaveYearStartMonth: number; // 1 = January, 4 = April (Indian fiscal). Default 1.
```

All leave balance reset crons, carry-forward calculations, and allocation queries must use this value to determine the leave year boundary.

### F-005 — Settings module has no service — violates module rules
**Severity:** 🟡 MEDIUM
**Category:** Architectural

**Finding:**
Module Boundaries table shows: `Settings | (direct repo call) | settingsRepository`. But settings changes require:
1. Cross-field validation (`halfDayThresholdMinutes < requiredDailyMinutes`)
2. Audit logging (SETTINGS_UPDATED)
3. Cascade effects (if `requiredDailyMinutes` changes, existing `attendanceDays` may need status recomputation)

A direct repo call cannot do any of these.

**Proposed Fix:**
Add `settingsService.ts` to `lib/services/`. Align the Module Boundaries table. Settings route handler calls `settingsService`, not `settingsRepository` directly.

### F-006 — No cron execution tracking
**Severity:** 🟡 MEDIUM
**Category:** Architectural

**Finding:**
Architecture mentions Vercel cron jobs for payroll computation and leave balance resets. Vercel crons have no built-in idempotency. A Vercel deployment event can cause a cron to fire twice. A network timeout causes Vercel to retry. Without tracking, the same payroll month could be computed twice, or leave allocations could be granted twice.

**Proposed Fix:**
Add `systemEvents` collection (see Missing Collections section). Each cron run inserts a `systemEvent` doc before executing. On retry, the cron checks if an event for this `{ type, targetKey }` already succeeded within the same time window and skips execution.

### F-007 — No API versioning strategy
**Severity:** 🟡 MEDIUM
**Category:** Architectural / Maintainability

**Finding:**
Flutter app is deployed to user devices that cannot be force-updated instantly. When the API request/response shape changes (inevitable over time), old app versions will call the old endpoint shape and receive unexpected responses.

Current folder: `app/api/attendance/checkin/route.ts`. No version prefix.

**Proposed Fix:**
Restructure API routes to `app/api/v1/*/route.ts` from day one. Add `NEXT_PUBLIC_API_VERSION=v1` to env. Flutter app reads this version from a remote config or uses a hardcoded `v1`. When breaking changes are needed, add `v2` routes alongside `v1`. Zero effort now, prevents major pain later.

### F-008 — Admin portal CSRF protection not addressed
**Severity:** 🟡 MEDIUM
**Category:** Security

**Finding:**
Admin uses the web portal. If JWT is stored in an httpOnly cookie (correct for web), the portal is vulnerable to CSRF attacks — a malicious site can trigger state-changing admin actions (approve leaves, deactivate employees, change settings) using the admin's browser session.

The architecture mentions httpOnly cookies for web but does not mention CSRF protection.

**Proposed Fix:**
Use the Double Submit Cookie pattern or the `SameSite=Strict` cookie attribute. Next.js 16 may include built-in CSRF protection — verify in docs. Document the chosen strategy. Add a `CSRF_SECRET` env variable if custom CSRF tokens are used.

## 2. Schema Flaws

---

### S-001 — `leaveBalances` on User document — race condition on concurrent approvals
**Severity:** 🔴 HIGH
**Category:** Schema / Data Integrity

**Finding:**
`users.leaveBalances.paidLeave` is a mutable number. Admin approves two pending leave requests for the same employee simultaneously (two browser tabs). Both read `paidLeave: 5`, both see sufficient balance, both approve, both run `$inc: -5`. Result: `paidLeave: -5`. The schema has `min: 0` but that's enforced only on Mongoose save, not on `$inc` updates in raw MongoDB.

**Proposed Fix:**
Use atomic conditional update for balance deduction:
```typescript
const result = await User.findOneAndUpdate(
  { _id: userId, 'leaveBalances.paidLeave': { $gte: daysRequested } },
  { $inc: { 'leaveBalances.paidLeave': -daysRequested } },
  { new: true, session }
);
if (!result) throw new InsufficientLeaveBalanceError();
```

This is safe even without transactions on the balance step, but should still be wrapped in a transaction with the `leaveRequest` status update.

---

### S-002 — `users.leaveBalances` conflates current-year and carry-forward balances
**Severity:** 🔴 HIGH
**Category:** HRMS Domain / Schema

**Finding:**
`leaveBalances.paidLeave` is described as "remaining days including carry-forward." This merged field means:
- Cannot distinguish how many days are current-year vs carry-forward
- Cannot enforce carry-forward expiry at DB level
- Cannot display "X days current year, Y days carry-forward (expires MM/YYYY)" in the UI
- Cannot enforce "carry-forward days used before current-year days" or vice versa (different companies have different policies)

**Proposed Fix:**
Replace `leaveBalances` with a structured breakdown:
```typescript
leaveBalances: {
  paidLeave: {
    currentYear: number;      // from this year's allocation
    carriedForward: number;   // from previous year (subject to expiry)
    carryForwardExpiry?: Date;
  },
  sickLeave: { currentYear: number; carriedForward: number; carryForwardExpiry?: Date; },
  casualLeave: { currentYear: number; carriedForward: number; carryForwardExpiry?: Date; },
}
```

And remove `carryForwardBalances[]` array from User entirely.

### S-003 — `users.carryForwardBalances[]` — wrong design, causes sync issues
**Severity:** 🔴 HIGH
**Category:** Schema

**Finding:**
`carryForwardBalances` is an embedded array on User. Problems:
1. No uniqueness constraint — two entries for the same `leaveType + fromYear` can exist
2. Expiry checking requires an application-level background job to compare `expiryDate` against today and subtract from `leaveBalances` — no TTL mechanism
3. The array and `leaveBalances.*` must be kept manually in sync — two fields representing the same truth
4. Unbounded growth (though rare: ~3 leave types × years active)

**Proposed Fix:**
Remove `carryForwardBalances` from User. Address in `leaveBalances` restructuring (see S-002). If a detailed ledger is needed, create a `leaveTransactions` collection (see Missing Collections).

### S-004 — `CompanySettings` has no singleton DB constraint
**Severity:** 🟡 MEDIUM
**Category:** Schema

**Finding:**
Singleton enforcement relies entirely on application-level `findOneAndUpdate` with upsert. A bug in the settings service, a direct DB insert, or a failed upsert could create a second document. The system would then randomly read either document depending on which `findOne()` returns first.

**Proposed Fix:**
Use a fixed, known `_id` for the singleton document:
```typescript
CompanySettingsSchema.add({
  _id: { type: String, default: 'company-settings' }
});
// Usage: CompanySettings.findByIdAndUpdate('company-settings', update, { upsert: true })
```

The unique `_id: 'company-settings'` is a DB-level guarantee against duplicate documents.

### S-005 — `attendanceDays.sessions[]` ObjectId array is redundant and dangerous
**Severity:** 🟡 MEDIUM
**Category:** Schema

**Finding:**
`AttendanceDay.sessions: ObjectId[]` stores references to all sessions for that day. But `AttendanceSession` already has `attendanceDayId` as a foreign key — querying `AttendanceSessions.find({ attendanceDayId })` retrieves all sessions for a day.

The redundant array creates:
1. A dual-write requirement on every check-in and check-out (session created + array push)
2. A consistency hazard — session exists in `attendanceSessions` but is missing from the day's `sessions[]` if the array update fails
3. Document size growth (ObjectIds in an array)

**Proposed Fix:**
Remove `sessions: ObjectId[]` from `AttendanceDay`. Fetch sessions via `attendanceDayId` FK query when needed. This eliminates a dual-write and a consistency risk.

### S-006 — Nonce replay prevention has no index and wrong storage location
**Severity:** 🔴 HIGH
**Category:** Security / Schema

**Finding:**
Nonce is stored at `attendanceSessions.checkIn.nonce`. Replay prevention requires querying for a matching nonce in recent sessions. Problems:
1. No index on `checkIn.nonce` — every checkin scans recent sessions for the same employee
2. The check is in service layer only — a race condition window exists between check and insert
3. A nonce on a rejected/blocked request is never stored (because no session is created), so it could be replayed immediately after rejection

**Proposed Fix:**
Add a separate `usedNonces` collection (see Missing Collections section):
```typescript
// usedNonces — tiny documents, TTL 10 minutes
{ nonce: string (unique index), employeeId, usedAt }
```

On every checkin attempt (successful or not), insert `{ nonce, employeeId }`. The unique index on `nonce` atomically prevents replay. TTL of 10 minutes auto-cleans the collection.

### S-007 — `passwordResetToken` stored on User document
**Severity:** 🔴 HIGH
**Category:** Security / Schema

**Finding:**
`users.passwordResetToken` and `users.passwordResetExpiry` are stored on the User document. Problems:
1. `select: false` only applies to Mongoose-level queries — raw MongoDB queries or projections bypass it
2. No TTL enforcement at DB level — expiry relies on application logic checking `passwordResetExpiry`
3. A second reset request overwrites a valid token that may have been emailed but not yet used
4. The `passwordHash` and `passwordResetToken` are on the same document — any query touching User must be audited to ensure neither leaks

**Proposed Fix:**
Remove from User. Create separate `passwordResetTokens` collection (see Missing Collections):
```typescript
{ _id, userId, tokenHash, expiresAt (TTL 15 min), usedAt?, ipAddress, createdAt }
```

### S-008 — `leaveRequests` missing `leaveYear` field
**Severity:** 🟡 MEDIUM
**Category:** HRMS Domain / Schema

**Finding:**
`LeaveRequest` has `startDate` and `endDate` but no `leaveYear` field. Queries like "fetch all leaves for employee in leave year 2026" require a date range query that must know the leave year boundaries (which depend on `leaveYearStartMonth` in settings — see F-004). Adding `leaveYear` as a denormalized field simplifies reporting and balance reconciliation.

**Proposed Fix:**
Add `leaveYear: number` to `LeaveRequest`. Computed server-side on creation based on `startDate` and `companySettings.leaveYearStartMonth`. Add index: `{ employeeId: 1, leaveYear: 1, status: 1 }`.

### S-009 — `payrollSummaries.halfDays` count is ambiguous — payroll formula broken
**Severity:** 🔴 HIGH
**Category:** Payroll / Schema

**Finding:**
`presentDays` counts days with `status = 'present'`. `halfDays` counts days with `status = 'half-day'`. But the `payableAmount` formula is:

```
payableAmount = monthlySalary - (lwpDays × perDaySalary)
```

This formula gives full salary credit to half-day attendance. An employee who attends only half-day every working day earns the same as someone who attends full days. This is incorrect HRMS behavior.

Half-day attendance should count as 0.5 of a full day for payroll purposes.

**Proposed Fix:**
Redefine `presentDays` as a decimal representing effective days:
```
effectivePresentDays = (fullPresentDays) + (halfDays × 0.5)
payableAmount = (effectivePresentDays + leaveDays) × perDaySalary
```

Or: keep integer `presentDays` (full days only) and compute:
```
payableAmount = monthlySalary - ((lwpDays + halfDays × 0.5) × perDaySalary)
```

Document the exact formula in `payrollEngine.ts` and here. Remove ambiguity.

### S-010 — `payrollSummaries` does not handle mid-month joiners or leavers
**Severity:** 🔴 HIGH
**Category:** Payroll / Schema

**Finding:**
`perDaySalary = monthlySalary / workingDaysInMonth` uses the total working days in the month. But an employee who joins on the 15th should have `workingDaysInMonth` counted only from their joining date. Similarly, an employee who resigns on the 10th is paid only for 10 days.

`users.dateOfJoining` and `users.dateOfLeaving` exist but the payroll schema and engine description ignore them.

**Proposed Fix:**
Add `effectiveWorkingDays: number` to `PayrollSummary` — the working days between `max(monthStart, dateOfJoining)` and `min(monthEnd, dateOfLeaving ?? monthEnd)`. Use this in place of `workingDaysInMonth` for the `perDaySalary` and payable computation.

```typescript
effectiveWorkingDays: { type: Number, required: true, min: 0 }
// perDaySalary = monthlySalary / effectiveWorkingDays
```

### S-012 — `RegularizationRequest.attendanceDayId` is optional with no invariant
**Severity:** 🟢 LOW
**Category:** Schema

**Finding:**
`attendanceDayId` is optional on `RegularizationRequest`. After approval, the attendance day must be linked. But the schema doesn't enforce that approved regularizations have a non-null `attendanceDayId`. A service bug that approves without setting this field leaves the regularization in an inconsistent state.

## 3. Missing Collections

### C-001 — Missing `leaveTransactions` (ledger)
**Severity:** 🔴 HIGH
**Category:** HRMS Domain

**Finding:**
There is no ledger collection for leave balance changes. `users.leaveBalances` is a running balance only — no history of why it changed. Scenarios that require a ledger:

- Employee disputes: "You show 3 days remaining but I had 10 and only took 5"
- Audit queries: "When was this leave deducted?"
- Year-end carry-forward calculation
- Mid-year pro-rated allocation (employee joins April 15)
- Leave encashment (future feature)

Without a ledger, balance reconciliation is impossible.

**Proposed Schema:**
```typescript
// leaveTransactions
{
  _id: ObjectId,
  employeeId: ObjectId,             // ref: users
  leaveType: 'paidLeave' | 'sickLeave' | 'casualLeave',
  leaveYear: number,
  transactionType:
    | 'annual-allocation'           // start-of-year or pro-rated grant
    | 'carry-forward-credit'        // carry from previous year
    | 'carry-forward-expiry'        // carry-forward days expired
    | 'deduction-approval'          // leave approved
    | 'restoration-rejection'       // leave rejected/cancelled
    | 'restoration-revocation'      // admin revoked approved leave
    | 'manual-adjustment',          // admin manually adjusts
  days: number,                     // positive = credit, negative = debit
  balanceAfter: number,             // running balance (current year only)
  referenceId?: ObjectId,           // ref: leaveRequests or other
  note?: string,
  performedBy: ObjectId,            // actorId
  timestamp: Date,
}
// Indexes:
// { employeeId, leaveYear, leaveType } — balance history
// { referenceId }                      — trace a leave request's transactions
```

### I-006 — Missing TTL cleanup strategy for `fcmTokens`
**Severity:** 🟡 MEDIUM
**Category:** Schema / Maintenance

**Finding:**

2. In `notificationService`, catch `registration-token-not-registered` errors from FCM and mark the token `isActive: false`

```typescript
FcmTokenSchema.index({ lastRefreshedAt: 1 }, { expireAfterSeconds: 7_776_000 }); // 90 days
```

### A-002 — Flutter timer anchor lost on app restart
**Severity:** 🟡 MEDIUM
**Category:** Attendance Engine

**Finding:**
Architecture states: "Flutter displays elapsed time using `serverCheckinTime` received on checkin response." If the app is killed and reopened, the response is gone. The `/api/attendance/status` endpoint exists but its response shape is not defined.

**Proposed Fix:**
Define the status endpoint response contract explicitly:
```typescript
// GET /api/v1/attendance/status
// Response:
{
  isCheckedIn: boolean,
  currentSession?: {
    sessionId: string,
    checkInTimestamp: string, // ISO 8601 — Flutter uses this as timer anchor
    dateString: string,
    totalMinutesToday: number, // minutes from completed sessions today
  },
  todaySummary: {
    status: AttendanceDayStatus,
    totalMinutes: number,
    requiredMinutes: number,
  }
}
```

---

### A-003 — Missing `overtimeMinutes` field on `attendanceDays`
**Severity:** 🟢 LOW
**Category:** Attendance Engine / Future-proofing

**Finding:**
`totalMinutes > requiredMinutes` = overtime, but no field captures this. Future payroll or compliance modules will need overtime data. Retroactive computation from raw sessions is possible but wasteful.

**Proposed Fix:**
Add `overtimeMinutes: number` (default 0) to `AttendanceDay`. Computed on checkout as `max(0, totalMinutes - requiredMinutes)`. Zero-cost to add now; enables future overtime pay module.

## 6. Leave Management Concerns

### L-001 — No admin leave revocation (admin-revoke status)
**Severity:** 🟡 MEDIUM
**Category:** HRMS Domain

**Finding:**
Current status lifecycle: `pending → approved | rejected | cancelled` (employee). No transition for admin to revoke a previously approved leave (e.g., admin approval was an error, or employee's leave was approved but they reported to work).

**Proposed Fix:**
Add `'revoked'` to `LeaveStatus` enum:
```typescript
export type LeaveStatus = 'pending' | 'approved' | 'rejected' | 'cancelled' | 'revoked';
```
Add `revokedBy: ObjectId`, `revokedAt: Date`, `revocationReason: string` fields.
On revocation: restore leave balance, update `attendanceDays` status, create leaveTransaction entry, send notification to employee.

### L-002 — `affectedDates` computation ownership unspecified
**Severity:** 🟡 MEDIUM
**Category:** Leave Management

**Finding:**
`leaveRequests.affectedDates` contains the working days covered by the leave. The schema doesn't specify whether this is client-computed or server-computed. If client-computed, a malicious actor could submit `affectedDates: []` for a 30-day leave request, bypassing balance checks.

**Proposed Fix:**
Document explicitly: `affectedDates` is **always computed server-side** in `leaveService.apply()` using `startDate`, `endDate`, `companySettings.workingDays`, and `holidays`. Client never sends this field. The zod input schema for the leave apply endpoint must not include `affectedDates`.

### L-003 — No `halfDayPeriod` field (morning vs afternoon)
**Severity:** 🟢 LOW
**Category:** HRMS Domain

**Finding:**
`duration: 'half'` leaves don't specify whether the employee is off in the morning or afternoon. For companies with scheduling needs (who needs to cover this morning), this distinction matters. Currently unaddressed.

**Proposed Fix:**
Add optional `halfDayPeriod?: 'morning' | 'afternoon'` to `LeaveRequest`. Default behavior (if null): unspecified half-day. Make visible in admin approval UI. Low priority but zero-cost schema addition now.

## 7. Payroll Concerns

---

### P-001 — Floating point arithmetic in payroll computation
**Severity:** 🟡 MEDIUM
**Category:** Payroll

**Finding:**
`perDaySalary = 50000 / 22 = 2272.727272...` This is a repeating decimal. JavaScript `Number` (IEEE 754 double) will accumulate rounding errors across multiplication. `2272.727272... × 3 = 6818.181818...` — the exact payable amount depends on when rounding happens.

The schema notes "rounded 2dp" but doesn't specify the algorithm or moment of rounding.

**Proposed Fix:**
Define the rounding rule explicitly in `payrollEngine.ts` documentation:
1. Compute all intermediate values at full float precision (do not round)
2. Round only `payableAmount` as the final step using `Math.round(value * 100) / 100`
3. Store `perDaySalary` rounded to 4 decimal places for display, but use full precision in computation
4. Consider using integer arithmetic in paisa (1 INR = 100 paisa) for all computations: `salary_paisa / 100` at output only.

---

### P-002 — No salary component structure — will require schema migration
**Severity:** 🟢 LOW
**Category:** Payroll / Future-proofing

**Finding:**
`users.monthlySalary` and `payrollSummaries.monthlySalary` are flat numbers. Real payroll always decomposes: Basic + HRA + DA + allowances - PF - PT - TDS. Changing to a structured salary later requires a migration on both `users` and all historical `payrollSummaries` documents.

**Proposed Fix:**
Add a voluntary, extensible `salaryComponents` field to both schemas, even if V1 doesn't populate it:
```typescript
salaryComponents?: {
  basic?: number;
  hra?: number;
  allowances?: number;
  pfDeduction?: number;
  ptDeduction?: number;
  otherDeductions?: number;
};
```
Leave `monthlySalary` as the gross total for now. Components are optional and unused in V1.

## 8. Security Concerns

---

### SEC-001 — `AuditLog` immutability hooks don't cover all write paths
**Severity:** 🟡 MEDIUM
**Category:** Security

**Finding:**
`AuditLog` blocks `updateOne`, `updateMany`, `findOneAndUpdate`. But these paths are not covered:
1. `bulkWrite([{ updateOne: ... }])` — not blocked by the hooks above
2. `doc.save()` on a fetched document — triggers `save` hook, not `updateOne`
3. Direct MongoDB Atlas UI or `mongosh` connection bypasses Mongoose hooks entirely

**Proposed Fix:**
Add:
```typescript
AuditLogSchema.pre('save', function () {
  if (!this.isNew) throw new Error('AuditLog is immutable');
});
AuditLogSchema.pre('bulkWrite', function () { throw new Error('AuditLog is immutable'); });
```
Document that Atlas cluster should have a dedicated audit user with `insertOnly` role on `auditLogs` collection, not a full `readWrite` role.

---

### SEC-002 — No rate limit on password reset endpoint
**Severity:** 🟡 MEDIUM
**Category:** Security

**Finding:**
Architecture specifies rate limits: 10 req/min on auth routes, 60 req/min on attendance. Password reset uses `auth` routes (10/min). But password reset has distinct abuse vectors:
- User enumeration via timing attack (does email exist?)
- Email bombing: send 600 reset emails/hour to a valid address (10/min × 60)
- OTP brute force after reset email is sent

**Proposed Fix:**
Separate rate limit for password reset: 3 requests per hour per email address AND per IP. Use Upstash with a sliding window:
```typescript
const limiter = new Ratelimit({
  redis, limiter: Ratelimit.slidingWindow(3, '1h')
});
await limiter.limit(`password-reset:${email}`);
await limiter.limit(`password-reset:ip:${ipAddress}`);
```
Always return same response regardless of whether email exists (prevent enumeration).

---

### SEC-003 — IP address storage is PII — no privacy policy documented
**Severity:** 🟡 MEDIUM
**Category:** Security / Compliance

**Finding:**
`deviceSessions.ipAddress` and `auditLogs.metadata.ipAddress` store raw IP addresses. Under GDPR (and analogous laws in India — DPDP Act 2023), IP addresses are personal data. For a platform deployed internationally or handling Indian citizen data:
- Must disclose IP storage in privacy policy
- Must honor subject access requests (provide audit logs for a user)
- Must honor erasure requests (complicate with 7-year audit retention)

**Proposed Fix:**
1. Document the legal basis for IP storage in each collection
2. For `deviceSessions`: hash the IP (`SHA-256(ip + salt)`) — provides correlation without storing raw PII
3. For `auditLogs`: keep raw IP (legal basis: fraud investigation / legitimate interest) but document the policy

---

### SEC-004 — No JWT secret rotation strategy
**Severity:** 🟡 MEDIUM
**Category:** Security

**Finding:**
`JWT_SECRET` is a static env variable. If compromised:
- Access tokens live 15 minutes — acceptable
- Refresh tokens live 7 days — all active sessions remain valid for 7 days after secret rotation

**Proposed Fix:**
Document a rotation procedure:
1. Add `JWT_SECRET_PREVIOUS` env variable
2. During token verification, try `JWT_SECRET` first; if it fails, try `JWT_SECRET_PREVIOUS`
3. Set `JWT_SECRET_PREVIOUS = old secret`, deploy new `JWT_SECRET`
4. After 7 days (max refresh token lifetime), remove `JWT_SECRET_PREVIOUS`

This allows graceful rotation without logging out all users.

---

### SEC-005 — No distinction between admin and employee failed login attempts
**Severity:** 🟢 LOW
**Category:** Security

**Finding:**
`AUTH_LOGIN_FAILED` audit event doesn't distinguish admin vs employee. An attacker brute-forcing admin credentials is a higher-risk event than an employee who forgot their password. No alerting threshold is defined for repeated admin login failures.

**Proposed Fix:**
Add `AUTH_ADMIN_LOGIN_FAILED` to `AuditAction` enum. In `authService`, detect if the email belongs to an admin role before writing the audit event. Add a business rule: after 5 consecutive `AUTH_ADMIN_LOGIN_FAILED` events within 15 minutes for the same email, send an alert email to all other admin accounts.

## 9. Maintainability Concerns

---

### M-001 — No database seed / initialization plan
**Severity:** 🟡 MEDIUM
**Category:** Maintainability

**Finding:**
On first deployment:
1. `companySettings` singleton must be created
2. At least one admin user must exist
3. Leave year allocations for existing employees must be initialized

No seed script or initialization endpoint is planned. First-time setup for each client is manual and error-prone.

**Proposed Fix:**
Add `src/scripts/seed.ts` — a one-time initialization script that:
1. Creates `companySettings` with client-specific values
2. Creates the initial admin user with a temporary password (printed to stdout, never logged)
3. Is idempotent (safe to run multiple times)

Document this as part of the per-client deployment checklist.

---

### M-002 — `reportService` multi-collection reads lack snapshot isolation
**Severity:** 🟢 LOW
**Category:** Maintainability / Data Integrity

**Finding:**
`reportService` reads from `attendanceRepository`, `leaveRepository`, `payrollRepository` in sequence. If a leave is approved between the attendance read and the leave read, the report shows a day as absent but the leave as approved — inconsistent view of the same data.

**Proposed Fix:**
For report generation, use a MongoDB read session with `readConcern: 'snapshot'` to get a consistent point-in-time view across all collections. This is only possible on replica sets (which Atlas always uses):
```typescript
const session = await mongoose.startSession();
session.startTransaction({ readConcern: { level: 'snapshot' } });
// all reads use session
await session.commitTransaction();
```

---

### M-003 — No standardized error codes for API responses
**Severity:** 🟡 MEDIUM
**Category:** Maintainability

**Finding:**
`lib/utils/apiResponse.ts` is listed in the folder structure but its error code scheme is not defined. The Flutter app needs machine-readable error codes (not just HTTP status codes) to show correct UI messages. Without a defined error code catalogue, different route handlers will return inconsistent error shapes.

**Proposed Fix:**
Define an error code enum before implementation:
```typescript
export enum ApiErrorCode {
  INVALID_CREDENTIALS      = 'AUTH_001',
  DEVICE_NOT_REGISTERED    = 'AUTH_002',
  OUTSIDE_GEOFENCE         = 'ATT_001',
  GPS_ACCURACY_LOW         = 'ATT_002',
  SESSION_ALREADY_ACTIVE   = 'ATT_003',
  LEAVE_BALANCE_INSUFFICIENT = 'LVE_001',
  LEAVE_CONFLICT           = 'LVE_002',
  // ... etc
}
```
Flutter app maps each code to a localised user-facing message.
