## Root Cause Analysis

| Finding | Root Cause |
|---------|-----------|
| C1 | `LoginSchema.deviceFingerprint` was required (no `.optional()`). Admin portal never sends it — browser has no device fingerprint. |
| C2 | `AuthService.login()` applied `registeredDevice` and fingerprint checks unconditionally. The device-binding model is designed for mobile employees; admin web users have no registered device. |
| C3 | `AuthService.login()` returns `{ employee: {...} }` but `AuthContext.LoginResponse` typed `data.user`. Key name mismatch silently produced `undefined` at runtime. |
| C4 | `tryRefresh()` sent an empty `POST /api/v1/auth/refresh` body. `RefreshSchema` requires `{refreshToken, sessionId}`. Neither value was stored after login — only `accessToken` was kept. Sessions could not survive page reload. |
| H1 | Next.js 16 uses `proxy.ts` (not `middleware.ts`) as the Edge function entry point. `proxy.ts` was correctly named but the JWT verification inside used only `JWT_SECRET` with no key-rotation fallback. (Note: the validation report's claim that `proxy.ts` requires renaming to `middleware.ts` was incorrect for this Next.js version — the filename and export name `proxy` are both correct.) |
| H2 | `csrfMiddleware.ts` was a stub. CSRF is not applicable to this portal (Bearer token auth, not cookie auth) — de-scoped with documented rationale. |
| H3 | `requireAuth.ts` and `proxy.ts` both used a single `JWT_SECRET` for verification. No fallback to `JWT_SECRET_PREVIOUS` during key rotation. |
| H4 | `vercel.ts` is a TypeScript module (Vercel deployment tooling reads `vercel.json` — JSON only). Cron paths referenced `/api/cron/*` but actual route handlers are at `/cron/*`. |
| H5 | `AuditService.ts` contained only a stub class. Non-auth audit events (employee CRUD, leave approvals, payroll) were unlogged. |
| H6 | `AUTH_008` and `AUTH_009` were swapped in `AuthService.confirmPasswordReset()`: expired token threw `AUTH_008` (should be `AUTH_009`), invalid token threw `AUTH_009` (should be `AUTH_008`). |

## Remediation Details

### C1 — Admin Login: Missing `deviceFingerprint` ✅ RESOLVED

**Fix:** `deviceFingerprint` in `LoginSchema` changed from required to `.optional()`.

```typescript
// Before
deviceFingerprint: z.string().regex(/^[0-9a-f]{64}$/i).

// After
deviceFingerprint: z.string().regex(/^[0-9a-f]{64}$/i).optional(),
```

Admin portal login body `{email, password}` now passes Zod validation. Mobile employee logins still send `deviceFingerprint` and it is validated when present.

### C2 — Device Registration Check Blocks Web Admin Login ✅ RESOLVED

**Fix:** `AuthService.login()` now branches on `user.role`:

```typescript
// Admin-role users (web portal) bypass device fingerprint checks
if (user.role !== 'admin') {
  if (!user.registeredDevice) throw new AppError('AUTH_004', 401);
  if (!deviceFingerprint) throw new AppError('AUTH_005', 401);
  const fingerprintHash = sha256(deviceFingerprint);
  if (fingerprintHash !== user.registeredDevice.fingerprintHash) {
    throw new AppError('AUTH_005', 401);
  }
}
```

Admin users (seeded with `registeredDevice: null`) can now log in via the web portal. Mobile employee logins continue to enforce device binding as before.

### C3 — Login Response Key Mismatch `employee` vs `user` ✅ RESOLVED

**Fix:** `AuthContext.LoginResponse` updated to match actual API response shape. `AuthService.login()` returns `{ employee: {...} }` — `AuthContext` now reads `json.data.employee`.

```typescript
// Before
interface LoginResponse { data?: { user: AdminUser } }
setUser(json.data.user);

// After
interface LoginResponse { data?: { accessToken, refreshToken, sessionId, employee: AdminUser } }
setUser(json.data.employee);
```

No change to `AuthService.login()` — the API response key remains `employee` (mobile app already reads `data['employee']`).

### C4 — Session Not Persistent Across Page Loads ✅ RESOLVED

Three-part fix:

**1. `api-client.ts` — Session credential storage:**
```typescript
let _refreshToken: string | null = null;
let _sessionId: string | null = null;

// Restored from sessionStorage on module load (survives page reload)
if (typeof window !== 'undefined') {
  _refreshToken = sessionStorage.getItem('_rt');
  _sessionId = sessionStorage.getItem('_sid');
}

export function setSessionCredentials(rt: string, sid: string) {
  _refreshToken = rt; _sessionId = sid;
  sessionStorage.setItem('_rt', rt); sessionStorage.setItem('_sid', sid);
}
```

**2. `tryRefresh()` sends credentials in body:**
```typescript
body: JSON.stringify({ refreshToken: _refreshToken, sessionId: _sessionId }),
```

**3. `AuthContext.login()` stores credentials; `logout()` clears them:**
```typescript
// login
setSessionCredentials(json.data.refreshToken, json.data.sessionId);

// logout — sends sessionId in body (required by LogoutSchema)
const sid = getSessionId();
await apiFetch('/api/v1/auth/logout', { method: 'POST', body: JSON.stringify({ sessionId: sid ?? '' }) });
clearSessionCredentials();
```

**4. Login/refresh routes set `__session` httpOnly cookie** — Edge Middleware (`proxy.ts`) validates it for page-route protection:
```typescript
res.cookies.set('__session', result.accessToken, { httpOnly: true, sameSite: 'strict', maxAge: 15 * 60 });
```

Session now survives page reload. `tryRefresh()` on app init restores the access token from stored refresh credentials.

### H1 — Middleware Configuration ✅ RESOLVED (with correction)

**Correction:** The validation report incorrectly stated that `proxy.ts` must be renamed to `middleware.ts` and the export renamed from `proxy` to `middleware`. In Next.js 16, the proxy file convention is `proxy.ts` with export `proxy` — this is the CURRENT recommended pattern (`PROXY_FILENAME = 'proxy'` in Next.js 16 constants). The file and export name were already correct.

**What was fixed:** The proxy now sets/checks `__session` cookie (set by login/refresh routes) to enable page-level protection. The `config.matcher` was updated to exclude `/cron` routes (cron handlers must not be middleware-protected). The `verifyJwt` function gained `JWT_SECRET_PREVIOUS` fallback (see H3).

**Evidence:** Build output shows `ƒ Proxy (Middleware)` — proxy is registered and running.

### H2 — CSRF Middleware ✅ RESOLVED (de-scoped with documented rationale)

```typescript
// CSRF Protection — De-scoped (approved risk acceptance)
//
// CSRF via cookie-replay attacks are not applicable to this admin portal because:
// 1. All state-mutating API calls send an Authorization: Bearer <token> header.
//    Browsers cannot set custom headers cross-origin without a CORS preflight.
// 2. The __session cookie is HttpOnly + SameSite=Strict.
// 3. Every protected API route calls getAuthUser() which requires a valid Bearer token.
//
// If a cookie-only auth path is added in a future phase, CSRF protection must be implemented.
export {};
```

The admin portal uses Bearer token auth exclusively for API calls. CSRF via cookie-replay is not exploitable. The de-scope is architecturally sound and documented.

### H3 — JWT Rotation: No `JWT_SECRET_PREVIOUS` Fallback ✅ RESOLVED

Both `proxy.ts` and `requireAuth.ts` now implement a `verifyJwt`/`verifyToken` helper that tries the current secret first, then falls back to `JWT_SECRET_PREVIOUS` (if set) on signature failure or expiry:

```typescript
async function verifyToken(token: string) {
  const secret = new TextEncoder().encode(process.env.JWT_SECRET!);
  try {
    const { payload } = await jwtVerify(token, secret);
    return payload;
  } catch (err) {
    const prevSecret = process.env.JWT_SECRET_PREVIOUS;
    if (prevSecret && (err instanceof joseErrors.JWSSignatureVerificationFailed || err instanceof joseErrors.JWTExpired)) {
      const { payload } = await jwtVerify(token, new TextEncoder().encode(prevSecret));
      return payload;
    }
    throw err;
  }
}
```

During key rotation: set `JWT_SECRET_PREVIOUS` = old secret, `JWT_SECRET` = new secret. Existing sessions signed with the old key continue to work until they expire naturally.
