|---|---|---|---|---|---|
| Employee views own payslip list | `payrollSummaries` collection | `GET /payroll/me` | N/A | ❌ Missing | **B** |
| Employee views specific month payslip | `payrollSummaries` by `yearMonth` | `GET /payroll/me/:yearMonth` | N/A | ❌ Missing | **B** |
| Payable amount visible | `payrollSummaries.payableAmount` | ✅ in response | ✅ §9.3 | ❌ No screen | **B** |

| Attendance breakdown visible | All day-count fields present | ✅ in response | ✅ §9.3 | ❌ No screen | **B** |
| Gross vs net salary distinction | ❌ Not modelled | ❌ Not in response | ❌ Not shown | ❌ Missing | **C** |
| Salary component breakdown | ❌ Not modelled | ❌ Not in response | ❌ Not shown | ❌ Missing | **C** |

### 1.2 Evidence

**Present:**
- `payrollSummaries` schema has full attendance breakdown (`presentDays`, `halfDays`, `effectivePresentDays`, `paidLeaveDays`, `sickLeaveDays`, `casualLeaveDays`, `lwpDays`, `halfDayLwpDays`, `absentDays`, `holidayDays`, `weekendDays`).
- `GET /payroll/me/:yearMonth` (§8.4) returns: `payableAmount`, `deductions`, `effectiveWorkingDays`, `effectivePresentDays`, `effectiveLwpDays`, `halfDayLwpDays`, `paidLeaveDays`, `absentDays`, `finalisedAt`.
- Employee payslip self-view endpoints exist and are role-guarded (BR-PAY-09).

**Missing:**
- Mobile app (`docs/06-mobile-ui-ux.md`) has **no payslip screen**. Sections 1–11 cover: Design System, Navigation, Home Dashboard, Attendance, Leave, Regularization, Notifications, Profile, Device Security, Offline Strategy, Accessibility. No payroll/salary screen exists.
- `deductions` is a single flat number. No breakdown into LWP deduction, absent deduction, or any other component.
- No `grossSalary` field. The current model has only `monthlySalary` (gross) and `payableAmount` (net after LWP/absent deductions). The distinction is implicit but not labelled.
- `IEmployeeSnapshot` interface excludes salary: `{ firstName, lastName, employeeId, department?, designation? }`. The API response adds `monthlySalary` from the top-level field at serialization time — this is a discrepancy between DB interface and API response shape.

### 1.3 Overall Rating: **B — Partially Covered**

Admin portal payslip coverage is complete (§9.1–9.6). Mobile employee payslip is entirely absent. Gross/net labelling and deduction breakdown are missing everywhere.

## 2. Payroll Configuration Engine

**Requirement:** Monthly salary, working days, salary calculation method, per-day calculation, and deduction rules are configurable.

### 2.1 Coverage Assessment

| Sub-requirement | DB | API | Admin UI | Rating |
|---|---|---|---|---|
| Monthly salary per employee | `users.monthlySalary` | ✅ create/update employee | ✅ §4.1 employee form | **A** |
| Working days configuration | `companySettings.workingDays` (WeekDay[]) | ✅ `PUT /settings` | ✅ §11 settings screens | **A** |
| Required daily minutes | `companySettings.requiredDailyMinutes` | ✅ in settings | ✅ settings | **A** |
| Half-day threshold minutes | `companySettings.halfDayThresholdMinutes` | ✅ in settings | ✅ settings | **A** |
| Payroll cutoff day | `companySettings.payrollCutoffDay` (1–28) | ✅ in settings | ✅ settings | **A** |
| Per-day salary formula | `perDaySalary = monthlySalary / effectiveWorkingDays` | ✅ canonical formula in §02 | ✅ displayed §9.3 | **A** |
| Deduction formula | `deductions = deductibleDays × perDaySalary` | ✅ canonical formula | ✅ displayed §9.3 | **A** |
| Rounding contract | `Math.round(payableAmount × 100) / 100` | ✅ specified in DB §12 | ✅ displayed | **A** |
| Mid-month joiner proration | `joiningDateSnapshot`, `effectiveWorkingDays` window | ✅ BR-PAY-05 | ✅ computed correctly | **A** |
| Mid-month leaver proration | `leavingDateSnapshot`, window clipping | ✅ BR-PAY-05, BR-EMP-09 | ✅ computed correctly | **A** |
| Salary components config (Basic %, HRA %, allowances) | ❌ Not modelled | ❌ Not configurable | ❌ Not shown | **C** |

### 2.2 Evidence

**Present:**
- Canonical payroll formula fully specified in `docs/02-database-design.md` §12:
  ```
  perDaySalary   = monthlySalary / effectiveWorkingDays
  deductibleDays = effectiveWorkingDays - eligibleDays  (= effectiveLwpDays + absentDays)
  deductions     = deductibleDays × perDaySalary
  payableAmount  = Math.round(Math.max(0, monthlySalary - deductions) × 100) / 100
  ```
- `effectiveWorkingDays` accounts for join/leave dates via `getWorkingDaysBetween(max(monthStart,joinDate), min(monthEnd,leaveDate??monthEnd), workingDays, holidays)` — handles both mid-month joiners and leavers.
- Cross-field validation: `halfDayThresholdMinutes < requiredDailyMinutes` enforced at settings service level (`SET_001`).

**Missing:**
- `companySettings` has no salary component configuration. No Basic salary %, HRA %, transport allowance, or bonus fields.
- `payrollSummaries` stores only the flat `monthlySalary` and derived fields. No component-level breakdown.

### 2.3 Overall Rating: **A — Fully Covered** (flat salary model)

The flat salary model (one `monthlySalary` → `payableAmount` after deductions) is completely specified and internally consistent. Salary component breakdown is a separate business requirement documented under Category 5.

## 3. Half-Day Conversion Rules

**Requirement:** Two half-days equal one full leave day; this rule may be configurable.

### 3.1 Coverage Assessment

| Sub-requirement | DB | API | Admin UI | Mobile UI | Rating |
|---|---|---|---|---|---|
| Half-day attendance counts as 0.5 present | `effectivePresentDays = presentDays + halfDays × 0.5` | ✅ formula | ✅ displayed | ❌ No screen | **B** |
| Half-day LWP counts as 0.5 LWP | `effectiveLwpDays = lwpDays + halfDayLwpDays × 0.5` | ✅ formula | ✅ displayed | ❌ No screen | **B** |
| Half-day leave deducts 0.5 from balance | `leaveRequests.duration = 'half'`; `totalDays = 0.5` | ✅ BR-LVE-07 | ✅ §6 leave management | ✅ §5.4 | **A** |
| 2 half-day leaves = 1 full leave from balance | Implicit via 0.5 arithmetic | Implicit | Implicit | ✅ shown as −0.5 | **A** |
| Configurable half-day conversion ratio | ❌ Hardcoded as 0.5 | ❌ Not configurable | ❌ No setting | N/A | **C** |

### 3.2 Evidence

**Present:**
- Half-day arithmetic is fully canonical and consistent across all layers:
  - Attendance: `effectivePresentDays = presentDays + (halfDays × 0.5)` — DB schema + formula.
  - LWP payroll: `effectiveLwpDays = lwpDays + (halfDayLwpDays × 0.5)` — DB schema + formula.
  - Leave balance: `duration: 'half'` → `totalDays = 0.5` (BR-LVE-07); deducted on approval.
  - Mobile UI §5.4: Shows "Duration: 0.5 days", "Balance after: −0.5".
- Mathematically: 2 half-day leaves = 0.5 + 0.5 = 1.0 day deducted from balance. Satisfied implicitly.

**Missing:**
- The 0.5 multiplier is hardcoded in the engine — there is no `halfDayWeight` setting in `companySettings`. If the business needs "1 half-day = 0.75 days" or another ratio, this is not configurable.
- Half-day payroll visibility on the mobile app: not displayed (no payslip screen).

### 3.3 Overall Rating: **A — Fully Covered** (standard 0.5 model)

The half-day = 0.5 full day rule is consistently applied across DB, API, and UI. Configurability of the ratio is not supported, but a non-standard ratio would be an unusual business requirement.

**Note:** If configurable conversion ratio is a real business requirement, add `halfDayWeight: number` (default 0.5) to `companySettings` and propagate to the engine.

## 4. Late Arrival Policy Engine

**Requirement:** Shift start time, grace period for late arrivals, half-day threshold for late check-in, penalties for repeated late arrivals.

### 4.1 Coverage Assessment

| Sub-requirement | DB | API | Admin UI | Mobile UI | Rating |
|---|---|---|---|---|---|
| Shift start time defined | `companySettings.workStartTime` | ✅ in settings | ✅ settings | ✅ employee visible | **A** |
| Late arrival grace period (check-in) | ❌ `gracePeriodMinutes` is for checkout/cron | ⚠️ `outsideGracePeriod` flag unexplained | ❌ Not shown | ❌ Not shown | **C** |
| Half-day threshold for late arrival time | ❌ Not modelled (only `halfDayThresholdMinutes` = minutes worked) | ❌ Not documented | ❌ Not shown | ❌ Not shown | **C** |
| Late arrival penalty accumulation | ❌ Not modelled | ❌ No tracking | ❌ No screen | ❌ No screen | **C** |
| Salary deduction for late arrivals | ❌ Not modelled | ❌ Not in formula | ❌ Not in payslip | ❌ Missing | **C** |

### 4.2 Evidence

**Present:**
- `companySettings.workStartTime: string` — shift start is defined.
- `halfDayThresholdMinutes` — defines minimum minutes worked for half-day status (e.g., 270 mins). This is a duration-based threshold, not a time-of-day threshold.

**Critical Gap — `gracePeriodMinutes` Ambiguity:**

`companySettings.gracePeriodMinutes` has conflicting documentation:
- **DB schema doc (`docs/02-database-design.md` §9):** `// minutes after workEndTime before midnight-rollover cron closes sessions` — implies this is a checkout grace, not a check-in grace.
- **Check-in API response (`docs/04-api-specification.md` §5.1):** Returns `flags.outsideGracePeriod: false` — implies a grace period evaluated at check-in time.
- **Validation rules in settings API:** `gracePeriodMinutes: 0–120`.

This is an internal specification inconsistency. One of the following is true:
1. `gracePeriodMinutes` serves dual purpose (checkout auto-close AND check-in late tolerance) but is documented only for checkout use.
2. `gracePeriodMinutes` is exclusively for checkout auto-close, and `outsideGracePeriod` in check-in response uses a different undocumented threshold.
3. The DB comment is wrong and `gracePeriodMinutes` is actually a check-in late grace period (minutes after `workStartTime` before check-in is considered late).

**In all three cases, the late arrival policy is not documented.** No attendance engine rule explains:
- What `outsideGracePeriod: true` means for the employee.
- Whether it affects attendance status.
- Whether it affects payroll.
- Whether there is accumulation tracking.

**Missing:**
- No `lateArrivalGraceMinutes` (or clearly-named equivalent) in `companySettings`.
- No late arrival time threshold (distinct from `halfDayThresholdMinutes` which is duration-based).
- No late arrival count tracking in `attendanceDays`.
- No salary deduction component for late arrival penalties.
- No UI in admin portal or mobile for late arrival history.

### 4.3 Overall Rating: **C — Missing**

The late arrival policy engine is absent from all approved documents. `gracePeriodMinutes` has ambiguous documentation. `outsideGracePeriod` flag in check-in response has no documented meaning or effect. Remediation decision required: either scope this feature in (requires DB, engine, API, and UI changes) or explicitly scope it out with a decision note.

## 9. Recommendation

**Changes are required before coding begins.**

### Mandatory (HIGH)

**BR-001** — Mobile payslip screen must be specified in `docs/06-mobile-ui-ux.md` before Phase 5 (Mobile App) build. Employees need payslip access on their primary device.

**BR-002** — `gracePeriodMinutes` meaning must be resolved. Two options:
- **Option A:** Rename to `sessionAutoClosePaddingMinutes` (its actual checkout use), add a separate `lateArrivalGraceMinutes` if late arrival policy is in scope.
- **Option B:** Explicitly document that late arrival policy is out of scope for v1. Record the decision. Remove the unexplained `outsideGracePeriod` flag from the check-in response, or document it as an informational flag with no business effect.

**BR-003** — Salary component breakdown decision required:
- **Option A (Keep flat model):** Document explicitly that the system uses a flat `monthlySalary` with no component breakdown. Admin sees only Gross/Net on payslip. Mark BR-003 and BR-005 as "out of scope v1 — by design."
- **Option B (Add components):** Requires schema changes to `companySettings` and `payrollSummaries`, formula updates, API response changes, admin payslip UI redesign, and mobile payslip design. High-impact — full remediation required.

### Required (MEDIUM)

**BR-004** — Regardless of component decision: label `monthlySalary` as "Gross Salary" and `payableAmount` as "Net Salary" in API responses and UI. Single-word addition to existing fields.

**BR-005** — Follows BR-003 decision.

### Acceptable Risk (LOW)

**BR-006** — Add `monthlySalary` to `IEmployeeSnapshot` TypeScript interface to match the API response shape. One-line DB schema fix.

**BR-007** — Accept hardcoded 0.5 ratio for v1. Note as potential future configurable parameter.
