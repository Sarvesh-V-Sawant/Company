## G-001 — `AUTH_011 NO_DEVICE_REGISTERED`

### Gap Description

`POST /auth/login` currently returns `ATT_003 DEVICE_MISMATCH` for device validation failures. This covers both:
- A. `registeredDeviceHash !== null` AND sent fingerprint ≠ stored hash (true mismatch)
- B. `registeredDeviceHash === null` AND any fingerprint sent (no device registered yet)

Cases A and B require different mobile screens:
- Case A → `/device-mismatch` (employee using wrong phone)
- Case B → `/device-not-registered` (new employee, admin hasn't registered yet)

The mobile app cannot differentiate them without a distinct error code.

### Required Change

**New error code:** `AUTH_011 NO_DEVICE_REGISTERED`

| Property | Value |
|---|---|
| Code | `AUTH_011` |
| Key | `NO_DEVICE_REGISTERED` |
| HTTP Status | 403 |
| Message | "No device is registered for this account. Contact your administrator." |
| When | `POST /auth/login` when `users.registeredDeviceHash === null` |

**`ATT_003` behavior (unchanged):** Returned when `registeredDeviceHash !== null` AND fingerprints don't match.

**Login flow updated logic:**
```
POST /auth/login received
  → validate email/password first (AUTH_001 if wrong)
  → check registeredDeviceHash:
       null → return AUTH_011 NO_DEVICE_REGISTERED
       not null → compare with sent fingerprint
           mismatch → return ATT_003 DEVICE_MISMATCH
           match → continue login flow
```

### Mobile Routing

| Server Response | Mobile Screen |
|---|---|
| `AUTH_011` + `hadRegisteredDevice: false` | `/device-not-registered` |
| `AUTH_011` + `hadRegisteredDevice: true` | `/device-reset-required` (expanded variant) |
| `ATT_003` | `/device-mismatch` (existing) |

## G-002 — `PATCH /auth/me/fcm-token`

### Gap Description

No endpoint exists to store or update a device's FCM push token. Without this, `firebase_messaging` can generate tokens but nowhere to send them. Push notifications (`LVE_approved`, `LVE_rejected`, `REG_approved`, `REG_rejected`, attendance reminders) cannot be delivered.

### Required Endpoint

```
PATCH /api/v1/auth/me/fcm-token
Auth: Bearer token required
Rate limit: standard authenticated (not authLimiter)
```

**Request body:**
```typescript
{ fcmToken: string | null }
```
- `string`: register/update token
- `null`: deregister (on logout)

**Response:**
```typescript
{ success: true }
```

**Server behavior:**
- `fcmToken !== null` → `users.fcmToken = fcmToken` (upsert)
- `fcmToken === null` → `users.fcmToken = null` (clear on logout)
- No validation beyond string format (FCM tokens are ~163 chars; no fixed format)

### Schema Change Required

```typescript
// users collection — new field
fcmToken: {
  type: String,
  default: null,
  index: false,  // queried by userId, not by token
}
```

### Usage by Cron/Backend

When sending FCM (leave approval, regularization result, attendance reminder):
```typescript
// Look up employee's fcmToken
const user = await User.findById(employeeId).select('fcmToken');
if (user.fcmToken) {
  await admin.messaging().send({
    token: user.fcmToken,
    notification: { title, body },
    data: { type, entityId },
  });
}
// If fcmToken null: skip silently (notification permission denied or logout)
```

### Error Handling

| Scenario | Server action |
|---|---|
| `fcmToken` invalid (FCM rejected) | Log error; set `users.fcmToken = null` |
| Employee not found | 404 (shouldn't happen — authenticated) |
| `fcmToken` too long (>500 chars) | 400 with validation error |

## G-003 — `GET /attendance/today` Response Shape

### Gap Description

`GET /attendance/today` exists in the API spec for the admin portal (daily view). Its response shape for mobile use requires additional fields to support:
- State machine restoration (R-MOB-002)
- Re-check-in detection (R-MOB-004)
- Live timer restoration

### Required Response Fields

Current response (admin-oriented): array of all employees' today data.

**Mobile-specific endpoint (employee's own today data):**

Two options:
- **Option A:** New endpoint `GET /attendance/me/today` — employee-scoped, returns own data only
- **Option B:** Reuse `GET /attendance/today` with employee-scoped JWT filtering — already authenticated as employee role, server returns only that employee's data

**Recommended: Option B** (no new endpoint; server applies role-based filter).

**Required response body shape for mobile:**

```typescript
// GET /attendance/today (when called with employee role JWT)
{
  success: true,
  data: {
    date: string;                    // YYYY-MM-DD in IST
    isCheckedIn: boolean;            // true if active session
    currentSessionStart?: string;    // ISO timestamp if isCheckedIn: true
    totalMinutesToday: number;       // sum of all completed + ongoing session durations
    sessions: Array<{
      id: string;
      checkInTimestamp: string;      // ISO
      checkOutTimestamp?: string;    // ISO or null if ongoing
      durationMinutes?: number;      // null if ongoing
    }>;
    dayStatus: 'present' | 'half-day' | 'absent' | 'leave' | 'holiday' | 'weekend';
    holidayName?: string;            // if dayStatus === 'holiday'
  }
}
```

### Mobile State Derivation from Response

```dart
final today = response.data;

if (today.isCheckedIn) {
  // → CHECKED_IN
  // timer: DateTime.now() - DateTime.parse(today.currentSessionStart)
} else if (today.sessions.isNotEmpty) {
  final totalMins = today.totalMinutesToday;
  final requiredMins = settings.requiredDailyMinutes;
  if (totalMins >= requiredMins - 30) {  // 30-min grace
    // → CHECKED_OUT_COMPLETE
  } else {
    // → CHECKED_OUT_PARTIAL
  }
} else {
  // → IDLE
  // Also handle holiday/weekend: show non-working day state
}
```

## G-004 — `X-Idempotency-Key` Header Support

### Gap Description

Mobile app generates a UUID v4 per form submission and sends it as `X-Idempotency-Key` request header. Server must deduplicate requests with the same key within a time window to prevent duplicate records.

### Required Behavior (all affected endpoints)

**Affected endpoints:**
- `POST /attendance/checkin` — existing `nonce` field already provides this; `X-Idempotency-Key` = same UUID
- `POST /attendance/checkout`
- `POST /leaves`
- `POST /regularizations`

**Server implementation:**

```typescript
// Middleware or per-handler:
const idempotencyKey = request.headers['x-idempotency-key'];

if (idempotencyKey) {
  // Check Redis for this key (TTL: 24 hours)
  const cached = await redis.get(`idempotency:${userId}:${idempotencyKey}`);
  if (cached) {
    // Return the original response body
    return Response.json(JSON.parse(cached), { status: 200 });
  }
}

// Process request normally
const result = await processRequest();

if (idempotencyKey) {
  // Store result in Redis with 24h TTL
  await redis.set(
    `idempotency:${userId}:${idempotencyKey}`,
    JSON.stringify(result),
    { ex: 86400 }
  );
}

return Response.json(result);
```

**Conflict response (if Redis not used — simpler approach):**
- Detect duplicate by querying for same-day same-employee checkin, or same leave dates/type
- Return `409 Conflict` with original resource data if duplicate detected
- Mobile app treats 409 as success (Section E of remediation)

**Note on checkin nonce:** Existing `nonce` field in `POST /attendance/checkin` serves as the idempotency key for that endpoint. Server already stores and deduplicates by nonce. `X-Idempotency-Key` header for checkin = same UUID as `nonce` body field — redundant but consistent with other endpoints.

## G-005 — Re-Checkin Same Day

### Gap Description

`POST /attendance/checkin` — behavior when called for an employee who has already checked in and checked out on the same day (second session). Current spec does not explicitly state this is allowed.

### Required Clarification

**Expected server behavior:**
- Employee has `sessions: [{checkIn: 09:00, checkOut: 13:00}]` for today
- Calls `POST /attendance/checkin` again at 14:00
- Server should: create a second `AttendanceSession` for that day (NOT reject as duplicate)
- Server rejects only if: employee is currently checked in (no checkout yet) → `ATT_002` or similar

**Clarification needed in `docs/04-api-specification.md`:**

```
BR-ATT-NEW: Multiple sessions per day
An employee may have multiple attendance sessions in a single day.
POST /attendance/checkin creates a new session only if no session
is currently active (i.e., no session without a checkOutTimestamp).
If an active session exists → return ATT_002 ALREADY_CHECKED_IN.
If the last session is closed (has checkOutTimestamp) → create new session.
```

## G-006 — `AUTH_011` vs `ATT_003` Routing Distinction

### Gap Description

From G-001: the two error codes need to be distinguishable in the mobile routing layer. The routing table:

```dart
// In DioInterceptor or AuthNotifier:
switch (errorCode) {
  case 'AUTH_011':
    final hadDevice = prefs.getBool('hadRegisteredDevice') ?? false;
    if (hadDevice) {
      context.go('/device-reset-required');
    } else {
      context.go('/device-not-registered');
    }
    break;
  case 'ATT_003':
    context.go('/device-mismatch');
    break;
}
```

`hadRegisteredDevice` flag set to `true` in `SharedPreferences` on first successful login. Never cleared except on factory reset (app data cleared).

## G-007 — `POST /attendance/checkout` Idempotency

### Gap Description

`POST /attendance/checkout` has no explicit idempotency mechanism (unlike checkin which has `nonce`). If employee taps CHECK OUT and network drops:
- Server processed checkout → session closed
- Mobile never received response → shows CHECK OUT button still active
- Employee taps again → second checkout attempt on already-closed session → server should return appropriate error

### Required Behavior

Server should handle duplicate checkout gracefully:
- If employee is currently checked in → process checkout normally
- If employee is NOT checked in (already checked out) → return `ATT_004 NOT_CHECKED_IN` (or similar)
- Mobile on `ATT_004` from checkout call → treat as success (reconcile via `GET /attendance/today`)

No Redis-based idempotency needed for checkout — the check-in state itself provides natural deduplication.

## G-008 — Leave Cancel / Regularization Withdraw Endpoints

### Gap Description

Section 5.5 (Leave Detail) references `DELETE /leaves/:id` or `PATCH /leaves/:id/cancel`. Section 6.3 (Regularization Detail) references `DELETE /regularizations/:id`. These operations are specified in the mobile spec but their endpoint paths need confirmation in `docs/04-api-specification.md`.

### Clarification Needed

| Operation | Assumed Endpoint | Confirm |
|---|---|---|
| Cancel pending leave | `PATCH /leaves/:id/cancel` or `DELETE /leaves/:id` | Which one? |
| Withdraw pending regularization | `DELETE /regularizations/:id` or `PATCH /regularizations/:id/withdraw` | Which one? |

**Recommended (consistent with REST patterns used elsewhere in the API spec):** Use `PATCH` with status change (`cancel`/`withdraw`) rather than `DELETE` — preserves audit trail.
