## Schema Consistency — 96/100

### What is complete and correct

**Collections (17 total):**
All 17 collections have:
- Complete TypeScript `I*` interface
- Mongoose schema with field types, constraints (`required`, `min`, `max`, `enum`, `match`, `maxlength`)
- All indexes defined on the schema (not as separate migration files)
- `select: false` on `passwordHash` (User)
- Immutability pre-hooks on all 3 audit-type collections: `auditLogs`, `leaveTransactions`, `leaveYearAllocations`
- TTL indexes on 6 collections: `notifications` (1yr), `auditLogs` (7yr), `deviceSessions` (expiresAt), `passwordResetTokens` (15min), `usedNonces` (10min), `fcmTokens` (90d), `systemEvents` (90d)

**Data integrity guarantees:**
- Negative leave balance: impossible via atomic `$expr $gte` conditional + `$inc`
- Double active session: impossible via partial unique index at DB level
- Nonce replay: impossible via unique index on `usedNonces.nonce`
- Double allocation: impossible via unique compound index `{ employeeId, leaveYear, leaveType }` on `leaveYearAllocations`
- companySettings singleton: enforced by fixed `_id: 'company-settings'`

**Deductions (-4):**
- `leaveTransactions.performedBy` and `leaveYearAllocations.allocatedBy` use `Schema.Types.Mixed` — validators added but the type remains `Mixed` at the Mongoose level, not a discriminated union (-2)
- `payrollSummaries.deductions` stored at full float; display tooling must format carefully or round on read (-1)
- `regularizationRequest.attendanceDayId` approved-invariant not enforced in schema (only in service) (-1)

## Architecture Consistency — 95/100

### What is complete and correct

**Module boundaries:**
- 11 domain modules with clean vertical slices (Route Handler → Middleware → Service → Transaction → Repository → Model)
- No repository calls other repositories
- No route handler contains business logic
- `auditService` and `notificationService` always called outside transactions
- `settingsService` now exists — no direct repo calls from route handlers

**Transaction strategy:**
- Tier 1 (10 service methods) fully documented with collections written
- `withTransaction.ts` wrapper handles session lifecycle
- Atomic balance deduction pattern documented with exact `$expr $gte` pipeline
- `systemEvents` idempotency pattern documented for all 4 cron handlers

**Security:**
- CSRF: `SameSite=Strict` + Origin validation (two independent layers)
- JWT rotation: dual-secret fallback with documented 7-day window procedure
- Rate limiting: three separate limiters (auth/attendance/password-reset), dual-keyed on password reset
- API versioning: `/api/v1/` from day one, deprecation via `Sunset` header

**Deductions (-5):**
- Cron schedules in `vercel.json` are hardcoded UTC times; midnight-session-close at `"30 20 * * *"` assumes IST. Companies in other timezones need a different schedule — not handled dynamically (-2)
- `reportService` multi-collection reads lack snapshot isolation (LOW M-002 deferred) — acceptable V1 tradeoff but a known inconsistency window (-2)
- Admin portal Server Components vs client-side fetch decision still open (Open Question #1) — affects CSRF boundary (-1)

## Security Score — 91/100

### Threats addressed

| Threat | Mitigation | Strength |
|---|---|---|
| JWT forgery | `jose` with proper secret length; Edge Middleware validates every request | Strong |
| JWT secret compromise | Dual-secret rotation with 7-day grace window | Strong |
| Password brute force | `bcryptjs` cost 12; 10/min auth rate limit | Strong |
| Password reset abuse | 3/hr per email + 3/hr per IP; always-200 prevents enumeration | Strong |
| Replay attack (checkin nonce) | `usedNonces` unique index — atomic, DB-level | Strong |
| Double active session | Partial unique index — DB-level, not application-level | Strong |
| CSRF (admin portal) | `SameSite=Strict` + Origin header validation | Strong |
| Sensitive data in queries | `passwordHash` has `select: false` | Strong |
| Password reset token exposure | Separate `passwordResetTokens` collection; token hashed with bcryptjs | Strong |
| Device spoofing | `deviceFingerprint` binding + device registration enforcement | Moderate |
| GPS spoofing | `possibleMockGps` flag; `gpsAccuracy` threshold | Moderate (heuristic only) |
| Audit log tampering | Schema pre-hooks on all write paths; documented insert-only DB role | Moderate (hooks bypassed by Atlas UI / mongosh) |
| IP address PII | `deviceSessions` stores HMAC hash; `auditLogs` stores raw IP with documented legal basis | Adequate |

**Deductions (-9):**
- Atlas UI / `mongosh` direct access bypasses all Mongoose immutability hooks. Requires Atlas RBAC with insert-only role on `auditLogs`/`leaveTransactions`/`leaveYearAllocations` — documented but not enforced automatically (-4)
- No admin-specific brute-force alerting (SEC-005, LOW — deferred) (-2)
- DPDP Act compliance for deactivated employee data retention not formally addressed (-2)
- Device fingerprinting relies on client-provided hash — no server-side verification of hardware authenticity (-1)

## Scalability Score — 88/100

### Why this design scales for the target deployment

**Target scale:** Single company, ~10–500 employees. Daily writes: ~500 checkins/checkouts, ~50 leave operations, ~1 payroll run/month per employee.

**Stateless compute:** Vercel serverless scales to zero and handles bursts without pre-warming. No sticky sessions required — all state in MongoDB.

**Connection management:** `globalThis._mongooseCache` singleton prevents connection storms from concurrent cold starts. `maxPoolSize: 10` appropriate for serverless.

**Index coverage:** All hot query paths indexed:
- Check-in lookup: `{ employeeId, dateString }` on `attendanceDays`
- Active session: `{ employeeId }` partial on `attendanceSessions`
- Leave history: `{ employeeId, leaveYear, status }` on `leaveRequests`
- Balance ledger: `{ employeeId, leaveType, leaveYear, timestamp }` on `leaveTransactions`
- Payroll: `{ employeeId, yearMonth }` unique on `payrollSummaries`

**Unbounded growth prevention:** 6 TTL indexes. `leaveTransactions` and `auditLogs` are the only high-volume collections without TTL — both intentional (financial and legal records).

**Deductions (-12):**
- No read replica configuration for `reportService` — heavy report reads compete with write operations on the same Atlas cluster (-4)
- `attendanceSessions.checkIn` embeds full geo data per session — at 2 sessions/day × 500 employees × 250 days = 250k docs/year with ~600 bytes each. Manageable but not negligible (-2)
- `leaveTransactions` grows O(employees × years × events) — no archival strategy for old leave years (-2)
- Report queries (`reportService`) do not use read sessions with `readConcern: snapshot` — may see inconsistent reads across collections during concurrent writes (-2)
- No Atlas Search index configured — text search on employee names requires full collection scan (-2)

## Personal Approval Recommendation

**Yes — I would approve this architecture and database for production implementation.**

### Justification

**What earns approval:**

The design resolves every category of risk that typically causes expensive mid-project rewrites. The three most common causes of HRMS project failures are: (1) leave balance corruption under concurrent load, (2) payroll formula errors discovered after payslips are issued, and (3) orphaned sessions blocking employee attendance. All three are closed with DB-level enforcement — not application-level hope.

Specifically:
- **Data integrity**: Atomic conditional balance deduction, partial unique index on active sessions, and nonce replay prevention are all enforced at the database layer. Application-layer checks are defence-in-depth, not the primary guard.
- **Auditability**: The `leaveTransactions` ledger means every balance dispute has a verifiable answer. `auditLogs` with 7-year retention covers legal requirements for employment records.
- **Operability**: The `systemEvents` collection eliminates the most common serverless cron failure mode (double execution on retry). The seed script is idempotent. API error codes are catalogued before implementation begins — preventing the "error string hell" that typically accumulates across 50+ endpoints.
- **Security**: The CSRF strategy, JWT rotation procedure, and hashed IP storage are appropriate for an internal HR platform. The threat model is correct for a single-company B2B deployment — not a consumer product.
- **Extensibility**: API versioning from day one. `leaveTransactions` ledger enables encashment, carry-forward disputes, and year-end reports without schema changes. `systemEvents` enables future admin UI for cron health dashboards.

**Conditions for approval (must be resolved before first implementation PR):**

1. **Complete TypeScript migration** — all models and utilities must be `.ts` from the start. Retrofitting TypeScript onto an existing JS codebase mid-project is significantly more disruptive than doing it first.

2. **Configure Atlas RBAC** — `auditLogs`, `leaveTransactions`, and `leaveYearAllocations` collections must have an `insertOnly` MongoDB role assigned to the application service account. Mongoose pre-hooks are a runtime guard; RBAC is the infrastructure guarantee.

3. **Define test strategy** — minimum: unit tests for `payrollEngine.ts` (formula correctness), `geoFenceEngine.ts`, and `dateUtils.ts`; integration tests with a real Atlas M10 test cluster for `leaveService.approve()` and `attendanceService.checkin()` (the two highest-risk transaction paths).

**What is acceptable at V1 (deferred LOW items):**
- No `halfDayPeriod` — UI can note "morning/afternoon TBD" and add later
- No salary components — flat `monthlySalary` is correct for V1 payroll
- No report snapshot isolation — reports are informational, not financial instruments
- No admin failed-login alerting — single-company deployment with small admin team

**Bottom line:** The design is honest about its boundaries, complete where it needs to be, and does not over-engineer for hypothetical future requirements. The 7 remaining LOW findings are intentional scope decisions, not overlooked risks. The architecture will support the defined module scope (attendance + leave + payroll + reporting) without structural changes.

**Approved for implementation — subject to the 3 pre-implementation conditions above.**
