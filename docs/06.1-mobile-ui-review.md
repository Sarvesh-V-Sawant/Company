## HIGH Severity Findings

### R-MOB-001: No Device Registration UX for New Employees

**Severity:** HIGH

**Finding:** The app assumes a device fingerprint exists in `flutter_secure_storage` from a prior install. For a brand-new employee on a brand-new device:
1. No fingerprint is stored
2. App generates one and sends it in `POST /auth/login`
3. **Server behavior undefined in UX spec:** Does the server auto-register this device? Or does it reject if admin hasn't pre-registered?

From the approved API spec: the admin registers the device via the admin portal (Section 5.6) by entering the fingerprint manually. This means an employee **cannot log in until their admin registers their device**. The mobile app has no screen for this state.

Missing UX:
- "Your device is not yet registered. Ask your admin to register this device."
- A way for employee to share their device fingerprint with admin
- A screen explaining the device registration process to new users

**Business Impact:** New employees cannot log in without admin action. Without a clear screen, they will see a confusing generic error or a blank state.

**Fix:** Add **Screen: Device Not Registered** (`/device-not-registered`). Shows:
- Explanation: "Your device needs to be registered before you can log in."
- Device fingerprint displayed (truncated, copyable): "Fingerprint: a3f9...b2c1 [Copy]"
- Instruction: "Share this code with your administrator."
- `[Copy Fingerprint]` button → clipboard copy with confirmation
- `[Try Again]` after admin registers

Trigger: new error code or same `ATT_003` — needs server differentiation between "different device registered" (mismatch) and "no device registered, this is a new device" (not-yet-registered). This requires an API clarification — `ATT_003` covers both cases; a sub-status or separate error code (`ATT_003a` / `ATT_003b`) may be needed.

### R-MOB-002: Check-In Nonce Persistence — Race Condition on App Kill

**Severity:** HIGH

**Finding:** Section 4.1 states "Nonce stored in Hive — if API call fails and user retries, same nonce resent." However:
1. Nonce is generated before the API call
2. If app is killed between nonce generation and API call completion, the nonce may not be stored in Hive yet (write is async)
3. On restart, a new nonce is generated — correct behavior (missed the check-in entirely)
4. BUT: if the API call DID succeed server-side (network delivered the request) but the app was killed before receiving the response, employee is checked in on server but app shows IDLE state

**Business Impact:** Employee's attendance shows checked-in on server, but app shows "not checked in." Employee taps CHECK IN again → server rejects as duplicate session, or creates a second session, or the nonce deduplication catches it. Confusing UX with no recovery path shown.

**Fix:**
- On app launch and on `AppLifecycleState.resumed`: `GET /attendance/today` to sync actual server state
- If server shows checked-in but local state is IDLE: update local state to CHECKED_IN with server's `checkInTimestamp` (no UI prompt needed — silent reconciliation)
- Show "Last synced: 09:02" timestamp in status card to indicate server state is authoritative
- Add explicit sync indicator when live timer starts from server data vs. local tracking

### R-MOB-003: No Background FCM Token Refresh Strategy

**Severity:** HIGH

**Finding:** FCM requires a device token (`FirebaseMessaging.instance.getToken()`). This token:
1. Is generated on first launch
2. Must be sent to the server to receive push notifications
3. Changes when: app is reinstalled, Firebase project is updated, device is factory-reset, token expires (~60 days)

The current spec has no mechanism for:
- Sending the FCM token to the server after login
- Detecting FCM token refresh (`FirebaseMessaging.instance.onTokenRefresh`)
- Re-sending the updated token to the server

Without this, push notifications stop working after any of the above events.

**Business Impact:** Employees stop receiving leave approval/rejection notifications, attendance reminders — silently. No error shown; notifications simply don't arrive.

**Fix:**
- Add `PATCH /auth/me/fcm-token` API endpoint (note: missing from current API spec — requires `docs/04-api-specification.md` update or documentation of this endpoint in mobile spec)
- On login success: call this endpoint with `{ fcmToken: string }`
- On `onTokenRefresh`: call same endpoint immediately
- On app foreground (`AppLifecycleState.resumed`): compare stored FCM token with `getToken()`; if changed, re-send
- Store last-sent FCM token in SharedPreferences (not SecureStorage — not sensitive)

This also requires an API spec addition: `PATCH /auth/me` or `PATCH /auth/me/fcm-token` endpoint. Currently `GET /auth/me` exists but no `PATCH` for fcm token. Flag for API team.

### R-MOB-004: No Multi-Session / Same-Day Recheck-In UX

**Severity:** HIGH

**Finding:** The attendance state machine in Section 4.1 ends at `CHECKED_OUT → [CHECKED OUT TODAY] disabled`. However:
1. The API spec allows multiple sessions per day (`AttendanceSession` is an array)
2. An employee who checks out for lunch may want to check back in
3. The current UX permanently disables the CHECK IN button after first checkout

**Business Impact:** Employee checks out for lunch at 13:00. Wants to check back in at 14:00. Button is disabled. Employee cannot record afternoon attendance.

**Missing states:**
- After checkout: determine if `effectivePresentMinutes < requiredDailyMinutes` → re-enable CHECK IN
- "LUNCH BREAK" intermediate state
- Today's sessions list must show all sessions (partially designed but button state is wrong)

**Fix:**
- Button state after checkout: check `totalMinutesToday < requiredDailyMinutes`
  - If under: re-enable CHECK IN (label: "CHECK IN AGAIN")
  - If met or exceeded: disable (label: "DAILY HOURS COMPLETE")
- Add new state to state machine: `CHECKED_OUT_PARTIAL` (can check in again) vs `CHECKED_OUT_COMPLETE` (daily hours met)
- Sessions list on Home shows each check-in/out pair with session duration

### R-MOB-005: Offline Mode — No User Expectation Setting for Write Failures

**Severity:** HIGH

**Finding:** Section 10.2 states "All mutations require connectivity. User shown clear error with `[Retry]` button." However there is no design for the scenario where:
1. Employee submits a leave request
2. Network drops mid-submission (request sent but no response received)
3. App shows network error → employee taps Retry
4. Server may have already processed the original request → duplicate leave request

Also missing:
- No "draft" state for leave applications started offline
- No way to know if a form submission was lost or processed
- Leave form data lost if network fails during submission

**Business Impact:** Employee applies for leave, network fails, resubmits. Admin sees two identical leave requests. Confusion and manual cleanup required.

**Fix:**
- Form submission: use Dio retry with idempotency key (UUID generated before submit, sent as `X-Idempotency-Key` header)
- On duplicate detection (API returns `GEN_007` or similar): show "Request already submitted." rather than error
- Form fields preserved in `StateProvider` if submission fails — form does not reset
- Add "Submitting… Don't close this screen." banner during submission
- Note: requires API to document `X-Idempotency-Key` header support — flag for API team

## MEDIUM Severity Findings

### R-MOB-006: Change Password — Current Password Field Ambiguity

**Severity:** MEDIUM

**Finding:** Section 8.2 notes: "If the API does not verify current password, omit the 'Current Password' field." From the approved API spec, `PATCH /auth/me/change-password` does not require the current password (it was designed for the forced-change flow). Using the same endpoint for voluntary change from Profile without current password verification is a security gap — any XSS or session hijack allows password change without knowing the current one.

**Fix:** Either:
a) Add current password verification to `PATCH /auth/me/change-password` (API change — requires `docs/04-api-specification.md` update, a MEDIUM finding for the API team)
b) Use a separate `PATCH /auth/me/password` endpoint that requires current password
c) Document this as accepted security risk for V1 (single-user, corporate, low-threat model)

**Recommendation:** Option (a) — add optional `currentPassword` field to the existing endpoint; if `requiresPasswordChange: false`, validate it; if `requiresPasswordChange: true`, skip it. Document decision before Profile screen is built.

### R-MOB-007: Leave Apply — Holiday/Weekend Exclusion From Day Count Requires Cached Holiday Data

**Severity:** MEDIUM

**Finding:** Section 5.4 states: "Days count: computed excluding weekends + holidays (fetched from cached holiday list)." However:
1. Holiday list may be stale (last cached on login)
2. Admin may add a holiday after the employee last logged in
3. Employee sees wrong day count and balance impact in the form

**Fix:**
- Refresh holiday list and working-days config when the Apply Leave form opens (`GET /settings` lightweight call)
- Cache bust the holiday list if last-fetched > 24 hours
- Show "Holiday data as of [date]" caption below day count when using cached data older than 6 hours

### R-MOB-008: Deep Link Handling — App Not Installed (Password Reset Email)

**Severity:** MEDIUM

**Finding:** Screen 0.4 (Reset Password) is triggered by a deep link. If the employee clicks the reset link on a device where the app is not installed:
- Android intent cannot open the app
- Falls back to web browser URL (no web app exists)
- Employee sees a broken page

**Fix:**
- Configure Android App Links (HTTPS deep links via `.well-known/assetlinks.json`) as the primary mechanism — falls back to web browser gracefully
- The web admin portal URL (e.g. `https://app.acme.com/reset-password?token=xxx`) should be handled by the web app (admin portal handles this screen for employees who don't have the app)
- Or: send two links in the reset email — one deep link for mobile, one web link for browser fallback

### R-MOB-009: Regularization — Date Validation Depends on Server-Side `lookbackWindowDays`

**Severity:** MEDIUM

**Finding:** Section 6.1 validates: "max today; min: today − lookbackWindowDays." `lookbackWindowDays` comes from `companySettings` (cached on login). If the admin changes the lookback window while the employee has the app open, the client-side validation uses the stale value.

**Fix:**
- Refresh `companySettings` when Regularization Create form opens (same pattern as R-MOB-007 fix)
- Show "Lookback window: 7 days" as helper text below date picker so employee understands the restriction

### R-MOB-010: Notification Badge Count — Stale After App Kill

**Severity:** MEDIUM

**Finding:** Bottom nav badge count (unread notifications) is fetched on home load and on `AppLifecycleState.resumed`. However:
1. FCM notification arrives while app is killed
2. Employee taps the OS notification → app opens → navigates directly to `/notifications/:id`
3. Home screen never loads → badge count never fetched
4. Badge shows incorrect count (either 0 or stale from last session)

**Fix:**
- Fetch unread notification count in the `ShellRoute` builder (wraps all tabs), not only in Home
- On FCM notification tap: after navigating to the destination, trigger badge count refresh via Riverpod `ref.invalidate(unreadCountProvider)`

---

### R-MOB-011: Attendance History — Pagination Not Specified

**Severity:** MEDIUM

**Finding:** Section 4.4 shows a list of attendance records filtered by month but does not specify how many records to fetch per page. An employee with 365 days of history loaded at once causes performance issues.

**Fix:**
- Use `?page=1&limit=31` (max 31 days per month — no pagination needed per-month view since months cap at 31 records)
- For history view spanning multiple months: paginate by month (each month is a separate API call, loaded on scroll)
- Implement `SliverList` with month-grouped sections and lazy loading

---

### R-MOB-012: No In-App Leave Year Boundary Handling

**Severity:** MEDIUM

**Finding:** When the leave year resets (e.g., Jan 1), `GET /leaves/balance` returns new-year balances. If employee had the app open over midnight on the reset date, stale cached balances are shown. No notification, no refresh prompt.

**Fix:**
- On home load and on `AppLifecycleState.resumed`: compare stored `leaveYearStartMonth` from `companySettings` with current date; if year boundary was crossed, force-invalidate leave balance cache
- Or simply: leave balance cache TTL = 24 hours (already set in Section 10.1) — worst case 24-hour stale data, acceptable

## LOW Severity Findings

### R-MOB-013: No "Already Checked In" Guard for Check-In Button Spam

**Severity:** LOW

**Finding:** If the employee taps CHECK IN very quickly multiple times before the GPS state machine completes, multiple parallel GPS acquisition flows may start. While the button is disabled during `CHECKIN_SUBMITTING`, it is not disabled during `GPS_REQUESTING` and `GPS_ACQUIRING`.

**Fix:** Disable CHECK IN button immediately on first tap (before GPS permission prompt). Use a boolean `isProcessing` flag in the ViewModel to prevent re-entry into the GPS flow.

---

### R-MOB-014: No Dark Mode Strategy

**Severity:** LOW

**Finding:** Design system uses `ColorScheme.fromSeed` with `Brightness.light` only. No dark mode support specified.

**Fix:** Deferred to V1.1. Document: wrap root `MaterialApp` with `ThemeMode.system` so system dark mode doesn't break the app (Material 3 auto-generates a dark theme from the seed color). No custom dark design needed for V1; auto-generated dark scheme is acceptable.

---

### R-MOB-015: No Biometric Authentication Option

**Severity:** LOW

**Finding:** Login requires email + password every time. No biometric (fingerprint) login option. On Android, `local_auth` package provides this. Common expectation for mobile workforce apps.

**Fix:** Deferred to V1.1. Note: requires storing a long-lived access token locally (or using the biometric to unlock the stored token). Complexity warrants separate design.

---

### R-MOB-016: Leave Apply — No Draft/Save Feature

**Severity:** LOW

**Finding:** Apply Leave form has no save draft. If employee starts filling and navigates away, all data is lost. `WillPopScope` confirmation not specified for this form.

**Fix:**
- Add `WillPopScope` on Leave Apply screen: "Discard this leave request? Your changes will be lost." → `[Keep Editing]` / `[Discard]`
- Draft save deferred to V1.1 (requires Hive storage for drafts)

---

### R-MOB-017: Android Back Button on Auth Screens

**Severity:** LOW

**Finding:** On `/change-password` (forced), the spec says "Back button disabled via `WillPopScope`." But `WillPopScope` is deprecated in Flutter 3.16+; replacement is `PopScope(canPop: false)`.

Also: on `/session-expired` and `/device-mismatch`, Android back button behavior is not specified. If back is allowed, user can reach a partial shell state.

**Fix:**
- Use `PopScope(canPop: false)` (not deprecated `WillPopScope`) on all blocked-back screens
- `/change-password`, `/session-expired`, `/device-mismatch`, `/device-reset-required`: `canPop: false` with no-op `onPopInvoked`

## Security Risk Assessment

| Risk | Severity | Description |
|---|---|---|
| No current-password verification on voluntary change | MEDIUM | R-MOB-006 |
| Device fingerprint in SecureStorage — backup/restore risk | LOW | If device backup restores SecureStorage, employee's fingerprint from old device may work on new device. Mitigated by single-device policy on server. |
| FCM token storage in SharedPreferences | LOW | FCM token is not sensitive (cannot authenticate). SharedPreferences is acceptable. |
| Deep link token interception | LOW | Password reset token in deep link URL. Mitigated by short (1h) expiry and SHA-256 hashing on server. Acceptable for V1. |
| Nonce replay within window | LOW | Nonce prevents duplicate check-ins only within server dedup window. Old nonces from Hive should be cleared after 24 hours. |

## Scalability Concerns

### SC-001: Attendance History With 2+ Years of Data
Currently loads by month with no virtual scrolling in the history list. Employee after 2 years may have 24+ months. Month selector handles this but loading 31 records per month per API call is fine. No scalability issue here.

### SC-002: Notifications List Growth
No pagination specified in Section 7.1. After 6 months, an employee may have 300+ notifications. Fix: specify `?page=&limit=20` with `ListView` infinite scroll (`ScrollController` listener at 80% of list).

### SC-003: Multiple FCM Topics vs. Individual Tokens
Current design sends FCM per-employee (individual device token). For 500+ employees, this is individual FCM sends — fine for Firebase scale. No topic-based broadcasting needed for this use case.

## API Gaps (Impacts Mobile)

The following API gaps were identified during mobile UX design that are not covered in `docs/04-api-specification.md`:

| Gap | Impact | Recommendation |
|---|---|---|
| `PATCH /auth/me/fcm-token` endpoint missing | FCM notifications won't work | Add to API spec before mobile build |
| `ATT_003` covers both "mismatch" and "not registered" — no sub-status | Cannot show correct screen | Add `deviceRegistered: boolean` to `ATT_003` error body, or separate error codes |
| `X-Idempotency-Key` header not documented | Duplicate leave/reg submissions on retry | Document header support in API spec |
| Re-check-in after checkout within same day not specified | State machine gap | Confirm API allows multiple `POST /attendance/checkin` same day |
