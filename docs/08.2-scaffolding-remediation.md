## S-SC-001 — Next.js Middleware Strategy

### Root Cause

The scaffold placed `middleware.ts` at `apps/admin/middleware.ts` (project root). Next.js App Router resolves middleware from the project root **or** `src/middleware.ts` when `src/` is the source root. Since this project uses `src/app/` as the app directory, `src/` is the source root — making `apps/admin/src/middleware.ts` the correct location.

Placing middleware at the project root when `src/` is the source root causes Next.js to silently ignore it. The guard chain (Maintenance → requiresPasswordChange → Unauthenticated → Role → CSRF) never runs. All admin routes are publicly accessible with no startup warning.

### Build Risk

- `npm run build` succeeds with wrongly-placed `middleware.ts` — no build error
- Unauthenticated `GET /dashboard` returns 200 instead of 307 redirect
- Only detected by manual browser test or integration test

### Deployment Risk

- Production admin portal has no auth protection if middleware placement is wrong at first deploy
- Security breach at DC-02 (first staging deployment) if not caught by Definition of Scaffold Complete test

### Fix: `src/middleware.ts` + Full Specification

**Correct location:** `apps/admin/src/middleware.ts`

**Rule:** When `src/` directory exists and contains the `app/` folder, Next.js expects `middleware.ts` at `src/middleware.ts`. Verify this against `node_modules/next/dist/docs/` for Next.js 16.2.9 before creating the file.

#### A. Matcher Strategy

The matcher controls which routes Next.js passes to `middleware.ts`. Exclude:
- `_next/static` — static assets (CSS, JS bundles)
- `_next/image` — image optimization
- `favicon.ico`, `robots.txt`, `sitemap.xml` — public files
- `api/cron/*` — protected by `CRON_SECRET` header check, not JWT; middleware excluded to avoid double-checking
- `api/health` — public health check; no auth needed
- `api/v1/auth/login`, `api/v1/auth/forgot-password`, `api/v1/auth/reset-password` — public auth endpoints; handled in code, not middleware

```typescript
// src/middleware.ts
export const config = {
  matcher: [
    /*
     * Match all paths EXCEPT:
     *  - _next/static (Next.js static files)
     *  - _next/image (image optimization)
     *  - favicon.ico, public files (no extension check needed if public/ is minimal)
     *  - /api/cron/* (CRON_SECRET protected, not JWT)
     *  - /api/health (public)
     */
    '/((?!_next/static|_next/image|favicon\\.ico|api/cron|api/health).*)',
  ],
};
```

#### B. Public Route Strategy

Routes that must pass through without JWT validation:

| Route | Reason |
|---|---|
| `/(auth)/login` | Login page — no auth yet |
| `/(auth)/forgot-password` | Password reset request |
| `/(auth)/reset-password` | Password reset link |
| `/api/v1/auth/login` | Login endpoint |
| `/api/v1/auth/forgot-password` | Forgot-password endpoint |
| `/api/v1/auth/reset-password` | Reset-password endpoint |

Routes accessible **only** when `requiresPasswordChange: true`:

| Route | Reason |
|---|---|
| `/(auth)/change-password` | Forced password change page |
| `/api/v1/auth/me/password` | Password change endpoint |

All other routes require valid JWT with `requiresPasswordChange: false`.

#### C. Auth Protection Strategy

Guard chain execution order (per `05-admin-ui-ux.md` Section 0):

```
Request
  │
  ├─ Is maintenance mode active?  → Yes → Redirect /maintenance (or return 503 for API)
  │
  ├─ Is public route?             → Yes → NextResponse.next() (pass through)
  │
  ├─ Has valid JWT cookie?        → No  → API route: 401 JSON  │  Page: redirect /login
  │
  ├─ requiresPasswordChange?      → Yes → API /me/password: pass │ All others: redirect /change-password
  │
  ├─ Role check for admin routes? → Fail→ API: 403 JSON  │  Page: redirect /dashboard
  │
  └─ CSRF on state-mutating API?  → Fail→ 403 JSON
       │
       └─ NextResponse.next()      ← request proceeds
```

JWT is read from `HttpOnly` cookie (name: `access_token`). Middleware uses `jose` to verify the token — `jose` is compatible with the Next.js middleware runtime.

**API routes vs page routes:** Middleware distinguishes by checking `request.headers.get('accept')` or by URL prefix (`/api/` prefix → return JSON error; else → redirect).

#### D. Updated Scaffold Structure

`middleware.ts` moves from project root to `src/`:

```
apps/admin/
├── src/
│   ├── middleware.ts             ← HERE (was wrongly at project root)
│   ├── app/
│   │   ├── api/
│   │   ...
```

Project root no longer contains `middleware.ts`:
```
apps/admin/
├── instrumentation.ts            ← stays at project root (correct)
├── vercel.ts
├── next.config.ts
├── tsconfig.json
...
```

#### Updated Critical Note

> `src/middleware.ts` is the Next.js **route middleware** (auth guard chain). It is distinct from `src/middleware/` which contains API-route helper functions (`requireAuth.ts`, `requireRole.ts`, etc.). The route middleware runs at the network edge before any route handler; the helper functions run inside route handlers. Never import from `src/middleware/` into `src/middleware.ts` — the middleware runtime has limited Node.js API access.

## S-SC-002 — `instrumentation.ts` Strategy

### Root Cause

`instrumentation.ts` runs in both `node` and `edge` runtimes by default. Mongoose has no compatibility with the edge runtime — it requires Node.js APIs (`net`, `tls`, etc.). Without a `NEXT_RUNTIME === 'nodejs'` guard, `register()` attempts to import Mongoose in the edge runtime and crashes at cold start.

Additionally, some Next.js versions require `experimental.instrumentationHook: true` in `next.config.ts`. If omitted, `instrumentation.ts` is silently ignored — Mongoose is never connected, every API route fails with a connection error.

### Build Risk

- `npm run build` succeeds — `instrumentation.ts` issues are runtime-only
- Missing `experimentalInstrumentationHook` → every API call fails in production: `MongooseError: connect ECONNREFUSED`
- Missing runtime guard → Next.js edge runtime crash on cold start (Vercel function error)

### Deployment Risk

- Undetectable at `npm run build` or `npm run typecheck`
- Vercel function crash at DC-02 first deployment if `next.config.ts` is wrong
- No error logging until first request hits the function cold start

### Fix: Full `instrumentation.ts` Specification

#### A. File Location

`instrumentation.ts` stays at **project root** (`apps/admin/instrumentation.ts`) — this is correct and different from `middleware.ts`.

| File | Location | Why |
|---|---|---|
| `middleware.ts` | `src/middleware.ts` | Next.js resolves from `src/` when `src/app/` exists |
| `instrumentation.ts` | `instrumentation.ts` (project root) | Always at project root regardless of `src/` presence |

#### B. `next.config.ts` Setting

For Next.js versions prior to 15: `experimental.instrumentationHook: true` is required.
For Next.js 15+: `instrumentationHook` is stable (no `experimental` wrapper).

Since Next.js 16.2.9 is beyond 15, it is likely stable. **Verify against `node_modules/next/dist/docs/` before assuming.** If the setting does not exist in v16 docs, omit it.

```typescript
// next.config.ts — minimum required settings
// READ node_modules/next/dist/docs/ BEFORE MODIFYING
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  // Only include if required by Next.js 16 docs:
  // experimental: { instrumentationHook: true },

  // Required for Mongoose — prevents bundling for edge runtime
  serverExternalPackages: ['mongoose'],
};

export default nextConfig;
```

#### C. `instrumentation.ts` Implementation Pattern

```typescript
// instrumentation.ts (project root — apps/admin/instrumentation.ts)
export async function register() {
  // Guard: only run in Node.js runtime, not edge runtime
  if (process.env.NEXT_RUNTIME === 'nodejs') {
    // Dynamic import prevents Mongoose from loading in edge runtime
    const { connectDB } = await import('./src/lib/db/connect');
    await connectDB();
  }
}
```

**Why dynamic import:** Static `import { connectDB } from './src/lib/db/connect'` at the top of `instrumentation.ts` would cause Mongoose to be parsed in the edge runtime at bundle time, crashing before `register()` even runs. The `await import()` inside the `if` block ensures Mongoose is never loaded in the edge runtime.

#### D. `lib/db/connect.ts` Dev/Production Pattern

Vercel Fluid Compute reuses function instances. Mongoose maintains a connection pool per instance. The `connectDB` function must guard against creating duplicate connections on warm restarts (dev HMR) or multiple `register()` calls:

```typescript
// src/lib/db/connect.ts
import mongoose from 'mongoose';

declare global {
  // Persists across HMR in dev; irrelevant in production
  // eslint-disable-next-line no-var
  var __mongoose_conn: typeof mongoose | undefined;
}

export async function connectDB(): Promise<void> {
  if (global.__mongoose_conn?.connection.readyState === 1) {
    return; // Already connected — warm instance reuse
  }

  const uri = process.env.MONGODB_URI;
  if (!uri) throw new Error('MONGODB_URI environment variable not set');

  const conn = await mongoose.connect(uri, {
    maxPoolSize: 10,        // Vercel instances × pool ≤ Atlas M10 connection limit
    serverSelectionTimeoutMS: 5000,
    socketTimeoutMS: 45000,
  });

  global.__mongoose_conn = conn;
  console.log('[DB] Mongoose connected');
}
```

#### E. Development Behavior

- `npm run dev`: `register()` fires once on server start (not on every HMR reload)
- `global.__mongoose_conn` check prevents duplicate connections on file changes
- Log `[DB] Mongoose connected` appears once in terminal at startup (not per request)
- Verify: restart dev server and confirm log appears exactly once

#### F. Production Behavior

- Vercel cold start: `register()` fires once per new function instance
- Warm request: `global.__mongoose_conn` check returns immediately (no reconnect)
- Connection pool (maxPoolSize 10) is shared across all requests on same instance
- If Mongoose crashes mid-session: next cold start reconnects automatically

#### G. Updated Tooling: `next.config.ts`

Section 5.6 (new) added to `08-project-scaffolding.md`. `next.config.ts` skeleton specifies `serverExternalPackages: ['mongoose']` as minimum required setting.

## S-SC-003 — Tailwind CSS v4 Strategy

### Root Cause

The scaffold listed `tailwindcss@^4.x` without defining the configuration approach. Tailwind CSS v4 eliminates the `tailwind.config.ts` file in favor of CSS-native configuration. A developer following v3 patterns would create `tailwind.config.ts` (ignored by v4), write `content: [...]` arrays (automatic in v4), and use `theme.extend` (replaced by `@theme {}` in CSS). The result: styles silently not applied.

shadcn/ui v4 of its components is Tailwind v4-compatible when installed via the latest CLI (`npx shadcn@latest`). However, the default shadcn setup path differs between v3 and v4.

### Build Risk

- `npm run build` succeeds — Tailwind v4 with wrong config produces a valid CSS bundle (just empty)
- Admin portal renders with no Tailwind styles — discovered only in browser
- shadcn/ui components render without design system styles

### Deployment Risk

- Staging deploy appears broken visually (no styles) at DC-02
- No `npm run build` error — purely a runtime/visual failure

### Fix: Tailwind CSS v4 Full Specification

#### A. Installation

```bash
# In apps/admin/
npm install tailwindcss@^4 @tailwindcss/postcss@^4
# Do NOT install @tailwindcss/vite or tailwind.config.ts equivalents
```

Do **not** create `tailwind.config.ts`. Tailwind v4 does not use it.

#### B. PostCSS Configuration

```javascript
// apps/admin/postcss.config.mjs
export default {
  plugins: {
    '@tailwindcss/postcss': {},
  },
};
```

This replaces any `autoprefixer` or `tailwindcss` PostCSS plugins from v3.

#### C. CSS Entry Point

```css
/* src/app/globals.css */
@import "tailwindcss";

@theme {
  /* Design tokens — replaces theme.extend in tailwind.config.ts */
  --font-sans: "Inter", ui-sans-serif, system-ui, sans-serif;

  /* shadcn/ui CSS variables (injected by `npx shadcn@latest init`) */
  /* Do not hardcode here — shadcn init writes these automatically */
}

/* shadcn/ui base layer (injected by shadcn init) */
@layer base {
  :root {
    --background: 0 0% 100%;
    --foreground: 222.2 84% 4.9%;
    /* ... all CSS variables written by shadcn init ... */
  }
}
```

> **Do not hand-write the full `@layer base` block.** Run `npx shadcn@latest init` and let it write the CSS variables. The above is a structural placeholder only.

#### D. shadcn/ui Compatibility

`npx shadcn@latest init` detects Tailwind v4 automatically and:
- Does NOT create `tailwind.config.ts`
- Adds CSS variables to `globals.css` using the `@layer base` pattern
- Configures `@tailwindcss/postcss` in `postcss.config.mjs` (may overwrite — verify after)
- Outputs components to `src/components/ui/`

**shadcn/ui init sequence:**

```bash
# From apps/admin/
npx shadcn@latest init
# Answer prompts:
#  Style: Default (or New York — pick at scaffold time, cannot change later)
#  Base color: Neutral
#  CSS variables: Yes
#  Components path: src/components/ui
#  Utils path: src/lib/utils
#  RSC: Yes (App Router)
#  Tailwind config: (for v4, shadcn may skip this — let it decide)
```

Run `npx shadcn@latest add button` as a smoke test after init. If `Button` renders with correct Tailwind styles in browser, Tailwind v4 + shadcn is working.

#### E. Theme Structure

Tailwind v4 uses CSS custom properties (`--color-*`, `--font-*`, `--spacing-*`) via `@theme` block. No JavaScript config object.

```css
/* src/app/globals.css — @theme additions after shadcn init */
@import "tailwindcss";

@theme {
  /* Custom additions beyond shadcn defaults */
  --color-brand: #1e40af;        /* company primary */
  --color-brand-dark: #1e3a8a;
  --radius-card: 0.75rem;
}
```

#### F. Updated Tooling

Add `postcss.config.mjs` to the `apps/admin/` file tree. Add to Section 5.4 (new section added to spec).

Updated dev dependencies in `package.json`:

| Package | Version | Change |
|---|---|---|
| `tailwindcss` | `^4.x` | No change — was already listed |
| `@tailwindcss/postcss` | `^4.x` | No change — was already listed |
| ~~`postcss`~~ | — | Not needed separately — `@tailwindcss/postcss` bundles it |

Add `postcss.config.mjs` to project root of `apps/admin/`:

## S-SC-004 — Flutter Firebase Strategy

### Root Cause

`google-services.json` was marked "gitignored; per-env" without specifying the mechanism for: (a) local dev setup (where does the file come from?), (b) CI injection (how does the release build get it?), (c) dev vs prod Firebase project separation. Without explicit handling, developers will either commit the production `google-services.json` (credential leak) or have CI release builds fail with missing file.

### Build Risk

- `flutter build apk --release` fails in CI with: `File not found: android/app/google-services.json`
- No fallback — the Firebase Gradle plugin fails the build hard

### Deployment Risk

- First mobile release CI run (Phase 11) blocked immediately
- If dev `google-services.json` is accidentally committed and the prod Firebase project config is different, production FCM push notifications fail silently

### Fix: Two-Project Firebase Strategy

#### A. Firebase Project Structure

| Environment | Firebase Project | google-services.json Source |
|---|---|---|
| Dev / local | `company-hrms-dev` | Downloaded from Firebase Console (dev project) |
| Staging CI | `company-hrms-dev` (acceptable for staging) | GitHub Secret: `GOOGLE_SERVICES_JSON_DEV` (base64) |
| Production CI | `company-hrms-prod` | GitHub Secret: `GOOGLE_SERVICES_JSON_PROD` (base64) |

Separate projects prevent dev FCM tokens from receiving production push notifications and production event data from reaching dev logging.

#### B. Local Development Setup

Every developer on the project must:

1. Download `google-services.json` from Firebase Console → `company-hrms-dev` → Android app → download config
2. Place at `apps/mobile/android/app/google-services.json`
3. File is already in `.gitignore` — will not be committed

This is a one-time setup per machine. Document in `DEPLOYMENT.md`:
```
== Flutter Local Setup ==
1. Go to Firebase Console → company-hrms-dev → Project settings → Your apps → Android
2. Download google-services.json
3. Copy to apps/mobile/android/app/google-services.json
4. This file is gitignored — never commit it
```

#### C. CI/CD Injection

**GitHub Secret setup:**

```bash
# Encode the production google-services.json for GitHub Secret storage:
base64 -i apps/mobile/android/app/google-services.json | tr -d '\n'
# → paste this value as GitHub Secret: GOOGLE_SERVICES_JSON_PROD
```

**`mobile-release.yml` injection step (added before `flutter pub get`):**

```yaml
- name: Write google-services.json (production Firebase)
  run: |
    echo '${{ secrets.GOOGLE_SERVICES_JSON_PROD }}' | base64 --decode \
      > android/app/google-services.json
```

Full updated step order in `mobile-release.yml`:
```
1. actions/checkout@v4
2. subosito/flutter-action@v2
3. Write prod env file (.env.prod.json)
4. Write google-services.json  ← NEW (must be before flutter pub get)
5. Write signing key (release.jks + key.properties)
6. flutter pub get
7. flutter build apk --release
8. Firebase Distribution upload
```

#### D. `.gitignore` Rules

All security-sensitive Flutter files must be in `.gitignore` at workspace root AND/OR `apps/mobile/.gitignore`:

```gitignore
# Flutter Firebase (per-environment — never commit)
apps/mobile/android/app/google-services.json

# Flutter signing (never commit)
apps/mobile/android/key.properties
apps/mobile/android/app/release.jks
apps/mobile/android/app/*.jks

# Flutter environment (compile-time inject via --dart-define-from-file)
apps/mobile/.env.dev.json
apps/mobile/.env.prod.json

# Flutter build output
apps/mobile/build/
apps/mobile/.dart_tool/
apps/mobile/.flutter-plugins
apps/mobile/.flutter-plugins-dependencies
```

#### E. GitHub Secrets Table Addition

New secret required:

| Secret | Used By | Notes |
|---|---|---|
| `GOOGLE_SERVICES_JSON_PROD` | `mobile-release.yml` | `base64 google-services.json` from `company-hrms-prod` Firebase project |

Optional (for staging CI if needed):
| `GOOGLE_SERVICES_JSON_DEV` | `mobile-ci.yml` (if integration tests run) | `base64 google-services.json` from `company-hrms-dev` |

#### F. Build Pipeline Integration

The `mobile-ci.yml` (PR lint/test) does NOT need `google-services.json` because:
- `flutter analyze` does not require it
- `flutter test` (unit tests only) does not require it
- Only `flutter build apk` requires it

If integration tests are added to CI (Phase 12), add `GOOGLE_SERVICES_JSON_DEV` injection to `mobile-ci.yml` at that time.

## Implied Dependency Update — `packages/types` Build Strategy (S-SC-010)

This MEDIUM finding has a direct build impact on CI (blocks `npm run test`) and is resolved as part of this remediation to prevent CI failure on first scaffold run.

**Fix:** Change `packages/types` `package.json` `"main"` from `"dist/index.js"` to `"src/index.ts"`.

Since `apps/admin/tsconfig.json` already maps `"@company/types": ["../../packages/types/src/index.ts"]`, TypeScript resolves the package directly from source — no build step (`tsc`) required for `packages/types`.

Updated `packages/types/package.json`:
```json
{
  "name": "@company/types",
  "version": "0.1.0",
  "private": true,
  "main": "src/index.ts",
  "types": "src/index.ts"
}
```

No `dist/` directory, no `tsc` build step, no CI pre-build step needed.
