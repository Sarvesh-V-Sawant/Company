## HIGH Findings

### R-API-001 — No bulk notification mark-read endpoint
**Category:** Missing Endpoint
**Severity:** HIGH

**Description:**
The spec provides `PATCH /notifications/:id/read` to mark one notification as read. There is no batch endpoint. Flutter apps typically show a notification list with a "Mark all as read" button. Without a bulk endpoint, the Flutter client must fire N serial requests — N can reach 50+ for employees who haven't opened the app in days.

**Impact:**
- 50 serial requests on startup = 50× round-trip latency on notification dismissal
- Each request hits rate limiter separately; risk of throttling
- Poor UX: spinner visible for seconds on notification screen open

**Recommended Fix:**
Add `PATCH /api/v1/notifications/read-all` (no body required):
```json
// Response 200
{
  "success": true,
  "data": { "markedRead": 12 }
}
```
Or accept an array of IDs: `PATCH /api/v1/notifications/read` body `{ "ids": ["id1", "id2"] | "all" }`.

### R-API-002 — `X-Device-Fingerprint` header duplicates body field
**Category:** Security Gap
**Severity:** HIGH

**Description:**
The checkin endpoint requires `deviceFingerprint` in **both** the request body (`"deviceFingerprint": "string"`) **and** the `X-Device-Fingerprint` header. The spec does not define which one is authoritative when they differ. A client or proxy could send mismatched values. The Edge Middleware reads headers; the Route Handler reads body — they may validate against different values.

**Impact:**
- If Edge Middleware validates header and Route Handler uses body value for session creation, an attacker can send a valid header (for rate limiting / auth bypass) and a different body value (to link the session to a different device hash)
- Inconsistency creates confusion during implementation — two implementations will disagree on which is authoritative

**Recommended Fix:**
Pick one transport. Recommendation: keep `X-Device-Fingerprint` header only (consistent with standard practice of putting auth-relevant material in headers, not body). Remove `deviceFingerprint` from the request body. Edge Middleware validates the header; Route Handler reads it from the parsed request headers via `request.headers.get('X-Device-Fingerprint')`.

### R-API-003 — Password reset confirm has weak token binding
**Category:** Security Gap
**Severity:** HIGH

**Description:**
`POST /auth/password-reset/confirm` accepts `{ token, email, newPassword }`. The spec says "look up `passwordResetTokens` by email + compare bcryptjs hash of provided token." However, if an attacker intercepts or guesses the token, they can try it against any email — the email is provided by the attacker, not derived from the token itself.

More critically: the spec says tokens are stored as `bcryptjs hash` in the DB. `bcryptjs` is a slow hash (50–100ms per compare). At the `authLimiter` limit of 10 req/min per IP, an attacker rotating IPs can run sustained brute-force on a short token. A 32-byte random token is brute-force-resistant; but if the implementation uses a shorter token (e.g. 6-digit OTP), this is critical.

**Impact:**
- Token length not specified in the spec — implementors may choose a short value
- bcryptjs comparison for token lookup is slower than SHA-256 + constant-time compare; wrong tool for this use case

**Recommended Fix:**
1. Clarify token is exactly 32 bytes of cryptographic randomness (`crypto.randomBytes(32).toString('hex')` = 64 hex chars). Document this explicitly.
2. Store `SHA-256(token)` in DB, not `bcryptjs(token)`. Use `timingSafeEqual` for comparison. bcryptjs is for passwords (human-guessable secrets). Random 32-byte tokens need constant-time compare, not adaptive cost.
3. The email lookup is still valid (for sharding the lookup), but verify token against the DB record's hash using the stored email's record — don't allow the client to specify a different email.

### R-API-004 — No mechanism for admin to set employee initial password securely
**Category:** Security Gap
**Severity:** HIGH (conceptual, not missing endpoint)

**Description:**
`POST /employees` returns `temporaryPassword` in the response body: `"shown ONCE; admin must share securely."` This is the only mechanism for employee initial access. The spec acknowledges this but does not define:
- What "share securely" means operationally
- Whether Brevo email delivery of the temp password is used
- Whether the employee is forced to change this password on first login
- What happens if admin loses or misses the one-time display

**Impact:**
- If admin doesn't copy the temp password before navigating away, employee cannot log in without a device reset AND new password reset flow — disruptive
- If temp password is emailed (not via spec), it travels in plaintext email — security regression
- No forced-change-on-first-login requirement leaves employees indefinitely using the admin-chosen password

**Recommended Fix:**
Add to the employee creation business rules:
- BR-EMP-XX: `requiresPasswordChange: true` flag set on new employee; enforced at login — access token contains `requiresPasswordChange` claim; Flutter routes to change-password screen before any other action
- BR-EMP-XY: Optionally, send temp password via Brevo to employee's email directly from the create endpoint (not admin-mediated) — admin confirms email is correct, system sends
- At minimum, document the forced-change requirement and the recovery path if admin loses the one-time display

### R-API-005 — Payroll route collision risk
**Category:** Design Issue
**Severity:** HIGH

**Description:**
The spec defines these payroll routes:
```
GET /api/v1/payroll/me            → employee own list
GET /api/v1/payroll/me/:yearMonth → employee own month
GET /api/v1/payroll/:employeeId/:yearMonth → admin
```

In Next.js App Router, `payroll/me` and `payroll/:employeeId` are siblings. Next.js will correctly resolve `me` as a literal path segment before trying `:employeeId` — but only if `me/route.ts` and `me/[yearMonth]/route.ts` exist as static segments.

The real risk: if an employee's `employeeId` is the string `"me"`, the static segment wins and the admin route breaks for that employee. The spec also defines `GET /payroll` (admin list) as the root, meaning the directory structure is:
```
payroll/
  route.ts           # GET admin list, POST compute ← conflict!
  compute/route.ts   # POST compute
  me/route.ts
  me/[yearMonth]/route.ts
  [employeeId]/[yearMonth]/route.ts
```

`POST /payroll/compute` is at `compute/route.ts` but the spec also uses `POST /payroll/compute` — this means `route.ts` and `compute/route.ts` must coexist correctly.

**Impact:**
- Route ambiguity causes 404 or wrong handler for the `employeeId = "me"` edge case
- `POST /payroll/compute` vs `GET /payroll` on the same `route.ts` creates a dual-method route file — fine for Next.js but the spec mixes this with a separate `compute/` subdirectory

**Recommended Fix:**
Separate the payroll routes cleanly:
```
payroll/
  compute/route.ts                          # POST
  admin/route.ts                            # GET (admin list)
  admin/[employeeId]/[yearMonth]/route.ts   # GET, PATCH finalize/unfinalize
  me/route.ts                               # GET (employee list)
  me/[yearMonth]/route.ts                   # GET (employee month)
  me/[yearMonth]/export/route.ts            # GET (employee export — rare but valid)
```
Or add a prefix convention: employee-facing payroll routes under `/payroll/self/` and admin routes under `/payroll/admin/`. Add a business rule: `employeeId` cannot be the string `"me"`, `"compute"`, `"admin"`, or other reserved words.

## MEDIUM Findings

### R-API-006 — No month-filtered regularization endpoint for Flutter
**Category:** Missing Endpoint
**Severity:** MEDIUM

**Description:**
`GET /regularizations` accepts `startDate`/`endDate` filter but these are general date strings. Flutter's attendance calendar screen needs to show regularization status per day — querying `startDate=2026-06-01&endDate=2026-06-30` works but requires the client to know to do this. More importantly, no endpoint returns "regularization for a specific date" (single-day lookup for the day-tap detail view).

**Recommended Fix:**
Either: add `?date=YYYY-MM-DD` param to `GET /regularizations` for single-day lookup; or document that the general list with `startDate=endDate=date` serves this purpose. The spec should document this pattern explicitly for Flutter consumers.

### R-API-007 — `GET /employees/me` not explicitly defined
**Category:** Missing Endpoint
**Severity:** MEDIUM

**Description:**
The spec says employees should use `GET /auth/me` for their profile. However, `GET /auth/me` is an auth endpoint that returns auth-context data. An employee endpoint at `GET /employees/me` is conventional REST and may be expected by Flutter. The spec should either (a) explicitly document that `GET /auth/me` is the canonical employee profile endpoint, or (b) add `GET /employees/me` as an alias.

**Recommended Fix:**
Explicitly state in the employees section: "Employees use `GET /api/v1/auth/me` for their own profile. No `/employees/me` endpoint exists; Flutter must use the auth endpoint."

### R-API-008 — Duplicate behaviour: `GET /attendance/history` vs `GET /employees/:id/attendance`
**Category:** Overlapping
**Severity:** MEDIUM

**Description:**
Both endpoints serve the same data with identical query parameters:
- `GET /attendance/history?employeeId=:id&startDate=X&endDate=Y` (admin)
- `GET /employees/:id/attendance?startDate=X&endDate=Y` (admin)

No functional difference is specified between them.

**Impact:**
- Two route files to maintain, two integration tests, two OpenAPI paths for the same data
- Implementors may diverge on subtle behaviour (e.g., one applies 31-day window limit and other doesn't)

**Recommended Fix:**
Eliminate `GET /employees/:id/attendance` — it is redundant. Admin dashboard links to `GET /attendance/history?employeeId=:id`. If the employee-scoped URL is preferred for REST purity (resource-under-resource pattern), eliminate `GET /attendance/history?employeeId` and redirect to the employee-scoped route instead.

### R-API-009 — Bulk payroll compute has no concurrency guard
**Category:** Security Gap
**Severity:** MEDIUM

**Description:**
`POST /payroll/compute` with no `employeeId` processes all active employees. If two admin users (or a runaway retry) trigger this simultaneously for the same `yearMonth`, race conditions occur:
- Two processes both see `status: 'draft'`, both compute, both write — last write wins but with no atomicity between the two computes
- The `employeeSnapshot` in the two concurrent computes may differ if an employee update occurred between them
- MongoDB's `withTransaction` only protects the write of one employee's record at a time; does not prevent two concurrent bulk compute jobs

**Recommended Fix:**
Add a `systemEvents` guard: before starting bulk compute, `insertOne({ type: 'PAYROLL_COMPUTE_LOCK', yearMonth, lockedAt: now })` with a unique index on `{ type, yearMonth }`. If this insert fails (duplicate), return `GEN_006 CONFLICT: "Payroll computation for this month is already in progress."` Delete the lock document when the job completes (in a `finally` block).

### R-API-010 — Excel export memory pressure
**Category:** Scalability Concern
**Severity:** MEDIUM

**Description:**
`GET /reports/attendance/export` with a 366-day window and 500 employees could return ~180,000 `AttendanceDay` rows. The spec mentions "streamed to avoid memory pressure" but:
- ExcelJS streaming API requires using `xlsx.stream.createMultiSheetData()` writer, not the default in-memory `Workbook`
- The spec does not specify which ExcelJS API to use
- Vercel Fluid Compute has a 1GB memory limit per function; 180,000 rows with metadata could easily exceed available memory before streaming begins

**Recommended Fix:**
Specify in the export business rules:
- Use ExcelJS `stream.xlsx.WorkbookWriter` (streaming writer, not `Workbook`)
- Set `Response` with `new ReadableStream` and stream chunks from ExcelJS
- Add a row count guard: if projected rows > 50,000, return `GEN_001` with message "Date range too large for export. Maximum 50,000 rows. Reduce date range or add filters."

### R-API-011 — Cron CRON_SECRET validated "in each route handler"
**Category:** Security Gap
**Severity:** MEDIUM

**Description:**
The spec states CRON_SECRET is "validated in each route handler before any operation." This means each of the 4 cron route files contains duplicated auth logic. If one of the 4 route handlers is implemented incorrectly or the validation is accidentally removed during a refactor, that cron endpoint becomes unauthenticated.

**Recommended Fix:**
Create a shared `withCronAuth(handler)` higher-order function (or a utility `validateCronRequest(request)` that throws on failure):
```typescript
// src/lib/auth/cronAuth.ts
export function validateCronRequest(request: NextRequest): void {
  const auth = request.headers.get('Authorization');
  if (auth !== `Bearer ${process.env.CRON_SECRET}`) {
    throw new ApiError(403, ApiErrorCode.INSUFFICIENT_PERMISSIONS);
  }
}
```
All 4 cron route handlers call `validateCronRequest(request)` as first line. Document this shared utility in the spec.

### R-API-012 — `DELETE /settings/holidays/:id` returns 200, not 204
**Category:** Design Issue
**Severity:** MEDIUM

**Description:**
The spec returns `{ "success": true, "data": { "message": "Holiday removed." } }` with (implied) HTTP 200. RFC 7231 recommends 204 No Content for successful DELETE with no body. Returning a body with 200 is not wrong but inconsistent with REST conventions — especially for a `{ success, data }` envelope where `data` is just a message string.

**Recommended Fix:**
Return HTTP 204 with empty body, OR explicitly state HTTP 200 with the message envelope in the spec. Either is acceptable if documented — the issue is ambiguity, not incorrectness. Update to: `// Response 204 — No Content`.

### R-API-013 — No `API-Version` response header
**Category:** Versioning Gap
**Severity:** MEDIUM

**Description:**
The spec defines URL versioning (`/api/v1/`) but no response header communicates the precise API build version. Flutter clients in production cannot distinguish between v1.0.0 and v1.3.0 if both share the `/api/v1/` prefix. If a breaking change is deployed under the same version prefix (shouldn't happen but does), clients have no way to detect the change.

**Recommended Fix:**
Add response header from all Route Handlers:
```typescript
headers: {
  'X-API-Version': process.env.NEXT_PUBLIC_APP_VERSION ?? '1.0.0',
}
```
Document this in Section 1.9 (Versioning Strategy). Flutter client logs this header for crash reports.

### R-API-014 — Employees cannot view their own audit trail
**Category:** Missing Endpoint
**Severity:** MEDIUM

**Description:**
`GET /audit-logs` is admin-only. Employees have no way to see what actions were taken on their account. This is a GDPR/transparency concern for a platform that tracks attendance and leave. An employee who is deactivated, has leave rejected, or has device reset has no visibility into the admin audit trail for their own record.

**Recommended Fix:**
Add `GET /api/v1/audit-logs/me` (employee-only) that returns audit events where `entityId = employee's own ID` or `actorId = employee's own ID`. Exclude `ipAddress` and other admin-visible fields. This does not expose other employees' data. Alternatively, extend `GET /audit-logs` to allow employees to call it with implicit `employeeId = self` filter.

### R-API-015 — `GET /attendance/today` computes `elapsedMinutes` at query time
**Category:** Scalability Concern
**Severity:** MEDIUM

**Description:**
The `GET /attendance/today` response includes `"elapsedMinutes": 230` — a real-time duration computed as `now() - checkInTimestamp`. At 200 concurrent employees, this field requires:
1. A DB query to fetch all active sessions for today
2. Computing elapsed time for each active session server-side at query time

If the admin dashboard auto-refreshes every 30 seconds, this generates 200 elapsed-time computations every 30 seconds — unnecessary server load since elapsed time can be computed client-side from `checkInTimestamp`.

**Recommended Fix:**
Remove `elapsedMinutes` from the server response. Return `checkInTimestamp` (already present) and let the client compute `Date.now() - new Date(checkInTimestamp).getTime()`. Add this note to Section 5.5.

## LOW Findings

### R-API-016 — `POST /payroll/compute` returns different response shapes for single vs bulk
**Category:** Design Issue
**Severity:** LOW

**Description:**
The spec shows two distinct response shapes for `POST /payroll/compute`:
- With `employeeId`: returns a single `PayrollSummaryResponse` object
- Without `employeeId`: returns `{ computed: 45, skipped: 0, errors: [] }`

Flutter or admin portal SDKs must handle two different `data` shapes from the same endpoint based on the request body — fragile client logic.

**Recommended Fix:**
Normalize the response. Option A: always return `{ computed, skipped, errors, summaries: [] }` where `summaries` is an array (1 item for single, N items for bulk). Option B: separate endpoints: `POST /payroll/compute/:employeeId` (single) and `POST /payroll/compute` (bulk). The spec currently combines both into one endpoint — either normalize the shape or split.

### R-API-017 — Cron schedule for attendance reminder cannot self-update
**Category:** Versioning Gap
**Severity:** LOW

**Description:**
Section 13.4 states the cron runs "at `companySettings.attendanceReminderTime` (converted to UTC)". Vercel Cron schedules are defined statically in `vercel.json` / `vercel.ts` at deploy time — they cannot read runtime settings. If admin changes `attendanceReminderTime` from 09:30 to 10:00, the cron continues firing at the old time until the next deployment.

**Recommended Fix:**
Document this limitation explicitly: "The attendance reminder cron schedule is set at deployment time. Changing `attendanceReminderTime` in settings requires a corresponding update to `vercel.ts` cron schedule and a redeployment." Consider: run the cron hourly, check `companySettings.attendanceReminderTime` at runtime, and send only if the current IST hour:minute matches. This makes it runtime-configurable without needing a redeployment.

### R-API-018 — In-app report view endpoints lack max date-range guard
**Category:** Security Gap
**Severity:** LOW

**Description:**
`GET /reports/attendance` (in-app view, paginated) accepts `startDate` and `endDate` with only "max 90-day window" documented. `GET /reports/leave` has no stated date range limit. An admin could query with `startDate=2020-01-01&endDate=2026-12-31` and paginate through every record — effectively a data dump via the view endpoint.

**Recommended Fix:**
Apply same 90-day window to `GET /reports/leave`. Add explicit validation rule: "If `endDate - startDate > 90 days`, return `GEN_001`." For legitimate long-range analysis, the export endpoints (which have explicit limits) should be used.

### R-API-019 — `GET /leaves/balance` uses `?employeeId` query param (inconsistent pattern)
**Category:** Design Issue
**Severity:** LOW

**Description:**
The rest of the spec uses `/employees/:id/attendance`, `/employees/:id` etc. for admin access to employee-specific data. `GET /leaves/balance?employeeId=X` is an outlier — it puts the employee identifier in a query parameter rather than a path segment.

**Recommended Fix:**
For admin access to another employee's balance, use `GET /api/v1/employees/:id/leave-balance` (path segment, consistent with other employee-scoped admin endpoints). Keep `GET /leaves/balance` (no params) for the employee's own balance.

### R-API-020 — No `PATCH /leaves/:id` endpoint to correct pending leave
**Category:** Missing Endpoint
**Severity:** LOW

**Description:**
An employee who submits leave with the wrong date range or leave type cannot correct it before admin acts on it. The only option is to cancel (`PATCH /leaves/:id/cancel`) and resubmit. Cancelling and resubmitting loses the submission timestamp order (may affect queue position if admin reviews in order).

**Recommended Fix:**
Add `PATCH /api/v1/leaves/:id` restricted to `status: 'pending'` and own leave only:
```json
{
  "startDate": "string",    // optional
  "endDate": "string",      // optional
  "leaveType": "string",    // optional
  "reason": "string"        // optional
}
```
Re-run all validation rules on update. If balance would be insufficient after update, return `LVE_001`.

## Recommended Pre-Implementation Actions (HIGH Only)

### 1. Fix R-API-002 — Device fingerprint transport (immediately)
Remove `deviceFingerprint` from checkin/checkout request body. Use only `X-Device-Fingerprint` header. One canonical source.

### 2. Fix R-API-003 — Password reset token security (immediately)
- Specify 32-byte (`crypto.randomBytes(32).toString('hex')`) token
- Store `SHA-256(rawToken)` in DB, not bcryptjs
- Use `timingSafeEqual` for comparison

### 3. Fix R-API-005 — Payroll route structure (before scaffold)
Resolve the route collision before creating the directory structure. Adopt explicit path separation between admin and employee payroll routes. Reserve `"me"`, `"compute"`, `"admin"` as disallowed `employeeId` values.

### 4. Fix R-API-001 — Bulk notification mark-read (before Flutter integration)
`PATCH /api/v1/notifications/read-all` — one-liner on the server; significant UX win for Flutter.

### 5. Document R-API-004 — Forced password change on first login (immediately)
Add `requiresPasswordChange: boolean` to `users` schema. JWT claim carries it. Flutter routes to change-password screen. Prevents indefinite use of admin-assigned temp passwords.

## Outstanding Questions for Product Approval

1. **Employee audit trail (R-API-014):** Should employees be able to view changes made to their own account? This is a privacy/trust question, not just a technical one. Recommend YES for GDPR alignment.

2. **Payroll compute shape (R-API-016):** Prefer single vs bulk separation (`POST /payroll/compute/:employeeId` and `POST /payroll/compute`)? Or normalize the response envelope?

3. **Forced password change (R-API-004):** Temp password via Brevo email (bypasses admin) or admin-visible one-time display (current spec)? Recommend Brevo email to reduce admin liability.

4. **Leave correction (R-API-020):** Allow `PATCH /leaves/:id` on pending requests? Or is cancel-and-resubmit acceptable UX for V1?
