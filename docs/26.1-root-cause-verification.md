## Why Authentication Reaches Session Creation Before Failing

Trace through `AuthService.login()` for `admin@genesis.com` / `Admin@123456`:

| Step | Check | Result | Reason |
|------|-------|--------|--------|
| 1 | `connectDB()` | ✅ PASS | Mongoose already connected (health: db ok) |
| 2 | `User.findOne({ email: 'admin@genesis.com' })` | ✅ FOUND | User seeded successfully |
| 3 | `user.isActive` | ✅ true | Seeded with `isActive: true` |
| 4 | `bcrypt.compare('Admin@123456', user.passwordHash)` | ✅ MATCH | Seeded with bcrypt.hash('Admin@123456', 12) |
| 5 | `user.role !== 'admin'` | ✅ false | Role is 'admin' → device checks SKIPPED |
| 6 | `DeviceSession.create({ deviceFingerprint: null })` | ❌ FAIL | Schema: `required: true` rejects null |

All preceding checks pass. The failure occurs on the first write operation — session creation. The password validation (step 4) succeeds because the seeded hash is correct.

---

## Why MongoDB Authentication Is Not The Problem

Three independent confirmations:

1. **Health endpoint:** `GET /health → {"status":"ok","db":"ok","redis":"ok"}` — `mongoose.connection.readyState === 1` (connected and authenticated)

2. **Seed script success:** `[seed-admin] Connected to MongoDB` + `[seed-admin] Admin created: admin@genesis.com` — a write to MongoDB succeeded, proving auth credentials are valid

3. **`User.findOne()` succeeds** inside the login handler — if MongoDB auth had failed, this query would throw, not `DeviceSession.create()`. The error occurs 5 steps into the flow, after a successful read from MongoDB.

The error `kind: 'required'` is a Mongoose client-side schema validation error — it is thrown **before** any database write is attempted. Mongoose validates the document in memory and rejects it without making a network call.
