## 2. HIGH Findings

### R-RD-001 — Settings Backend Placed Too Late

**Severity:** HIGH

**Location:** Phase 10 (Admin Portal — Settings)

**Issue:**
`companySettings` data is required in Phase 4 (geo-fence config, required daily minutes, working days), Phase 5 (leave types, carry-forward limits, holiday list), and Phase 6 (regularization window). The roadmap acknowledges this with a note ("move Settings backend to Phase 1.5") but does not formally define Phase 1.5 as a distinct deliverable. If a developer follows the phase order without reading the note, they will begin Phase 4 without `companySettings` endpoints, causing hard blockers.

**Impact:** Phase 4 geo-fence validation, day status computation, and Phase 5 leave type validation cannot be implemented without `companySettings` data accessible via API. Missed dependency blocks 2–3 phases.

**Fix:**
1. Extract Settings backend into a formal sub-phase between Phase 2 and Phase 3: **Phase 2.5 — Settings Bootstrap**.
2. Phase 2.5 deliverables: `companySettings` Mongoose model, `SettingsRepository`, `SettingsService` (read + seed), `GET /settings/company`, `GET /settings/holidays`, `GET /settings/leave-types`, seed script with defaults.
3. Full Settings CRUD (update endpoints, admin UI) remains in Phase 10.
4. Mark Phase 2.5 as a dependency for Phase 3, 4, 5.

### R-RD-002 — `PayrollStaleBanner` Cross-Phase Dependency Not Tracked

**Severity:** HIGH

**Location:** Phase 5 (Leave Management) → Phase 7 (Payroll Assistance)

**Issue:**
`meta.staleEmployeeIds` logic is split across two phases: Phase 5 (leave revocation writes to staleEmployeeIds) and Phase 7 (payroll list reads staleEmployeeIds). The roadmap notes this as a "cross-phase concern" but does not specify the implementation order or the exact API field contract between the two phases. If Phase 5 is implemented without knowledge of Phase 7's `meta.staleEmployeeIds` field shape, the Phase 5 developer must make assumptions or leave stubs, risking inconsistency.

**Impact:** `PayrollStaleBanner` in admin portal cannot render correctly if Phase 5 and Phase 7 implement conflicting `staleEmployeeIds` logic.

**Fix:**
1. Define `meta.staleEmployeeIds` contract in Phase 7 payroll design section.
2. Add explicit deliverable to Phase 5: "On leave revocation, write `employeeId` to `payrollRecords.staleEmployeeIds` array for the affected month/year if payroll already computed. **Contract: array of MongoDB ObjectId strings.**"
3. Add Phase 5 → Phase 7 dependency note: "Phase 5 staleEmployeeIds write must use the same field path as Phase 7 reads."

### R-RD-003 — Cron UTC/IST Offset Not Specified Per Cron Job

**Severity:** HIGH

**Location:** Phases 4, 5, 7 — Vercel cron jobs

**Issue:**
Three cron jobs are defined:
- `attendance-reminder` — "daily at 09:00 IST"
- `leave-year-rollover` — "Jan 1 (or configured month)"
- `payroll-reminder` — "last day of month"

None have their Vercel cron expressions (UTC) specified. Vercel `vercel.ts` cron syntax uses UTC. IST is UTC+5:30. If a developer sets `"0 9 * * *"` thinking that's IST, the reminder fires at 14:30 IST instead of 09:00 IST. The `leave-year-rollover` cron on Jan 1 at midnight IST = Dec 31 18:30 UTC — an easy mistake that causes the rollover to fire in the wrong year in UTC time.

**Impact:** Attendance reminders fire 5.5 hours late. Leave year rollover fires a day early. Payroll reminder fires on the wrong calendar day.

**Fix:** Add a Cron Schedule table to the roadmap with explicit UTC expressions:

| Job | IST Time | UTC Expression | Notes |
|---|---|---|---|
| `attendance-reminder` | 09:00 IST daily | `"30 3 * * *"` | 09:00 IST = 03:30 UTC |
| `leave-year-rollover` | 00:05 IST Jan 1 | `"35 18 31 12 *"` | 00:05 IST Jan 1 = 18:35 UTC Dec 31 |
| `payroll-reminder` | 09:00 IST last day of month | Complex — use `"30 3 28-31 * *"` + code-level day check | Last day varies by month |

The `leave-year-rollover` case is especially tricky with the day boundary. Add code comment requirement: "Verify current date is Jan 1 IST before running rollover."

### R-RD-004 — No Seed Admin Account Specification

**Severity:** HIGH

**Location:** Phase 1 / Phase 2 seed data

**Issue:**
The roadmap mentions "Admin account seeded with initial password" in the pre-production checklist (Section 12), but never specifies HOW the initial admin account is created. There is no:
- Seed script specification
- First-run setup endpoint
- Environment variable for admin email/password

This is a production blocker: without an admin account, no other action can be taken. If each developer creates the admin account differently, staging and production will have divergent setup procedures.

**Impact:** Production deployment blocked; inconsistent staging setup; potential security risk if seed script hardcodes credentials.

**Fix:**
1. Add to Phase 2 deliverables: "Admin seed script (`scripts/seed-admin.ts`) — reads `ADMIN_EMAIL` and `ADMIN_INITIAL_PASSWORD` from environment variables; creates `users` record with `role: admin, requiresPasswordChange: true`; idempotent (no-op if admin already exists)."
2. Add to Phase 1 deliverables: "`.env.example` with `ADMIN_EMAIL` and `ADMIN_INITIAL_PASSWORD` documented."
3. Add note: "ADMIN_INITIAL_PASSWORD must be changed on first login (enforced by `requiresPasswordChange` flow)."

## 3. MEDIUM Findings

---

### R-RD-005 — Mobile and Admin Parallel Build Not Feasible Without Feature Flags

**Severity:** MEDIUM

**Location:** Phases 10 + 11 (Parallel)

**Issue:**
Phase 10 (Admin Portal) and Phase 11 (Mobile App) are marked as buildable in parallel. However, both depend on the same backend API. If a single developer is building both simultaneously, context-switching between Flutter/Dart and Next.js/TypeScript adds cognitive overhead and slows both. If multiple developers, the admin and mobile teams will both be hitting APIs that may still be incomplete (Phase 7 payroll, Phase 8 notifications). No feature flag strategy is specified for unreleased backend modules.

**Impact:** API integration may block both teams simultaneously if a Phase 7/8 endpoint has a bug. No strategy for partial API availability.

**Fix:** Add to Phase 10/11: "Use mock providers in Riverpod (mobile) and SWR stubs (admin) during initial screen build. Replace with real API calls incrementally. This allows screen build to proceed before final API stabilization."

### R-RD-006 — Leave Year Rollover Cron: No Manual Trigger Specified

**Severity:** MEDIUM

**Location:** Phase 5 — `leave-year-rollover` cron

**Issue:**
The leave year rollover cron fires once per year. There is no mechanism to trigger it manually (e.g., for testing, for year correction, or for a company that changes their leave year mid-year). The roadmap specifies `systemEvents` idempotency guard — meaning a manual trigger after the cron has run will no-op. But if the cron fails silently, there is no recovery path specified.

**Impact:** If rollover fails, employees start the new year with 0 carry-forward balance. No recovery path. No admin UI to retry.

**Fix:** Add to Phase 5: "Implement `POST /api/admin/cron/leave-year-rollover` (admin-only, rate-limited to 1/hour) that bypasses the `systemEvents` idempotency guard with a `?force=true` parameter. Document in admin runbook."

### R-RD-007 — No APK Distribution Strategy

**Severity:** MEDIUM

**Location:** Phase 12 / Deployment

**Issue:**
The roadmap mentions "APK distributed to internal test track" but does not specify the distribution mechanism. Options:
- Firebase App Distribution (most common for internal testing)
- Play Store internal track
- Direct APK share (WhatsApp/email — insecure for production)
- MDM deployment

No CI/CD for APK build and distribution is specified.

**Impact:** APK distribution requires manual steps each release cycle. No automated build pipeline means human error risk on every mobile deployment.

**Fix:** Add to Phase 12: "Configure GitHub Actions mobile CI: `flutter build apk --release` → upload to Firebase App Distribution (or Play Store internal track) on merge to main. Store keystore in GitHub Secrets."

### R-RD-008 — Payroll Compute Lock TTL Not Specified

**Severity:** MEDIUM

**Location:** Phase 7 — `PayrollLockService`

**Issue:**
The roadmap specifies a Redis lock for payroll compute (guard against concurrent compute), and notes "implement lock TTL + admin manual unlock endpoint" as a risk mitigation. However, no TTL value is specified. If the lock TTL is too short (e.g., 30s), a long-running compute job will unlock mid-compute and allow a second compute to start — exactly the race condition the lock is designed to prevent. If too long (e.g., 24h), a crashed job leaves the system locked for a day.

**Impact:** Payroll compute lock provides false safety if TTL is misconfigured.

**Fix:** Add to Phase 7: "Payroll compute Redis lock TTL = 10 minutes (600s). Rationale: 500-employee compute at worst ~5 minutes. Lock renews every 30s via a heartbeat if compute still running. Admin unlock endpoint: `DELETE /api/v1/payroll/lock` (admin-only). Lock key: `payroll:compute:lock:{month}-{year}`."

### R-RD-009 — Testing Checkpoint TC-04 Too Dense

**Severity:** MEDIUM

**Location:** Section 8 — Testing Checkpoints

**Issue:**
TC-04 (after Phase 4 — Attendance) requires: attendance unit + integration tests, multi-session test, idempotency test, geo-fence unit test, cron manual trigger test, AND mobile RECONCILING state test. Phase 4 is already rated Very High complexity. Bundling mobile testing into the backend testing checkpoint means the admin and mobile implementations must both be complete before TC-04 passes. This forces Phase 4 mobile work to block Phase 5 backend work.

**Impact:** Backend can be ready to proceed to Phase 5 while mobile attendance screens are still being built. Coupling them in TC-04 slows backend progress unnecessarily.

**Fix:** Split TC-04:
- TC-04a (backend): attendance unit + integration + idempotency + geo-fence + cron tests — backend team can proceed to Phase 5
- TC-04b (mobile): RECONCILING state + state machine tests + offline queue tests — mobile team resolves before Phase 12 UAT

### R-RD-010 — No Database Migration Strategy

**Severity:** MEDIUM

**Location:** Section 10 (Rollback Strategy)

**Issue:**
The rollback strategy covers MongoDB schema changes (additive-only, two-phase deploy, never rename). However, there is no formal database migration tooling specified. MongoDB is schema-less, but as the codebase evolves:
- Index additions/removals need to be applied to existing Atlas clusters
- Seed data updates (new leave types, new settings fields) need to be propagated
- Production data fixes (e.g., backfilling a new required field) need scripted migration

Without migration tooling, these are done ad-hoc, leading to drift between environments.

**Fix:** Add to Phase 1 deliverables: "Create `scripts/migrations/` directory. Migration naming convention: `YYYYMMDD-description.ts`. Each migration: `up()` + `down()` function. Migrations tracked in `systemEvents` collection (`eventType: 'migration', name: '...'`). CLI command: `npm run migrate` (runs all pending up()); `npm run migrate:rollback` (runs last down())."

### R-RD-015 — No Mention of `vercel.ts` Cron Syntax

**Severity:** LOW

**Location:** Phase 1 — Foundation

**Issue:**
Vercel crons are defined in `vercel.ts` (per Vercel knowledge update: `@vercel/config` package). The roadmap does not mention installing `@vercel/config` or the cron configuration format in `vercel.ts`. A developer unfamiliar with the new `vercel.ts` format (replacing `vercel.json`) may use deprecated syntax.

**Fix:** Add to Phase 1 deliverables: "Install `@vercel/config`. Create `vercel.ts` with cron stubs (all 3 cron jobs as stubs). Use `routes.cron()` syntax or cron array in `VercelConfig`. Reference: `docs/01-system-architecture.md` cron section."

## 9. Missing Phases Assessment

| Assessment | Conclusion |
|---|---|
| Is "Settings" its own phase? | No — but Settings backend must be Phase 2.5 (HIGH R-RD-001). Settings admin UI stays in Phase 10. |
| Is "Email/Notification Infrastructure" its own phase? | No — email (Brevo) is set up in Phase 1; per-feature notifications are built within their respective phases. Phase 8 is for in-app notification list + audit log UI only. |
| Is "Security Hardening" its own phase? | No — security is baked into every phase (rate limiting in Phase 2, CSRF in Phase 2, idempotency in Phase 4, etc.). Phase 12 adds security test execution. |
| Is "Performance Optimization" its own phase? | No — Phase 12 includes performance testing. Optimizations identified in Phase 12 are fixed in Phase 12. |
| Is there a missing "Onboarding Flow" phase? | No — onboarding is the first-run admin setup (seed admin account) + employee welcome email + device registration. These are distributed across Phases 2 and 3. |
| Should "Audit Logs" be its own phase? | No — audit log model + `AuditMiddleware` should be implemented in Phase 2 and applied retroactively. Phase 8 adds admin UI only. Update Phase 2 to include `AuditLog` model + middleware stub. |

**One genuine missing deliverable (not phase):** `AuditMiddleware` should be initialized in Phase 2 (not Phase 8) so that all subsequent phases' admin mutations are automatically logged from the start. Otherwise, Phase 3–7 admin actions will have no audit trail.

## 10. Would You Approve This Roadmap for Implementation Start?

**Yes, with 2 mandatory changes before scaffolding begins.**

### Justification

**Why YES:**
The roadmap is comprehensive, internally consistent, and traces every approved design document (01–06) to a concrete implementation deliverable. The 12 phases are appropriately ordered, the implementation sub-orders (MongoDB, backend, admin, mobile) are detailed enough for a developer to follow without re-reading design docs, and the Definition of Complete is verifiable rather than subjective.

**The 2 mandatory changes:**

**Change 1 — Add Phase 2.5 (Settings Bootstrap) before scaffolding.**
R-RD-001 is a genuine blocker. Phase 4 and Phase 5 cannot be built without `companySettings` API. This is a 1-day fix to extract Settings backend into a formal phase and update all dependency links.

**Change 2 — Add Cron UTC Table to roadmap (R-RD-003) before first cron job is written.**
The cron UTC offset issue will silently cause wrong-time or wrong-day execution. Add the UTC cron expression table before any Phase 4/5/7 cron code is written.

**Changes that can be applied during implementation (not pre-conditions):**
- R-RD-002: `staleEmployeeIds` contract — document at Phase 5 start
- R-RD-004: Admin seed script — implement at Phase 2 start
- R-RD-009: Split TC-04 — apply at Phase 4 testing start
