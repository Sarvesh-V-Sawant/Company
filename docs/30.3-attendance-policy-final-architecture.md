## Executive Summary

Three architecture iterations identified an incremental progression toward a workforce tracking capability. This document performs a final challenge of every prior decision and introduces two new first-class entities — **Attendance Policy** and **Temporary Attendance Override** — that transform the design from a simple tracking feature into a reusable, enterprise-grade attendance behaviour framework.

**Key architectural shifts from doc 30.2:**

| Decision | Doc 30.2 | This Document |
|---|---|---|
| Tracking configuration | Single `CompanySettings.locationTracking` block | Per-policy: each `AttendancePolicy` defines its own tracking behaviour |
| Policy resolution | `TrackingPolicyResolver` (tracking only) | `AttendancePolicyResolver` (all attendance behaviour) |
| Session snapshot | `trackingPolicy: { enabled, intervalMinutes, policySource }` | `resolvedPolicy: ResolvedAttendancePolicy` (full behaviour snapshot) |
| Tracking trigger | Policy-driven (confirmed from 30.1) | Policy-driven via `resolvedPolicy.trackingEnabled` — unchanged |
| Override system | Not designed | `TemporaryAttendanceOverride` — first-class entity with approval workflow |
| Geofence admin UX | Manual lat/lng entry | Interactive map picker (Leaflet + Nominatim, no API key) |
| Company geofence | `CompanySettings.geoFence` (single) | Preserved + extensibility path to `offices[]` documented |
| RBAC | Admin/employee binary | Integrated into existing binary model; permission codes documented for future granular RBAC |

**New entities introduced:** `AttendancePolicy`, `TemporaryAttendanceOverride`  
**Total file touches:** 45 (17 new, 28 modified) across 6 implementation phases.

## Part 1 — Attendance Policy Architecture

### 1.1 Problem with the current model

The existing system has a single set of attendance rules for all employees. Every employee is validated against the same geofence, the same GPS accuracy threshold, and the same device registration requirement. Companies with mixed workforces — office employees, field workers, remote workers, hybrid employees — cannot configure appropriate behaviour per group. Workforce tracking either applies to everyone or no one.

### 1.2 Attendance Policy entity

An `AttendancePolicy` is a named, reusable configuration document that defines how attendance works for any employee assigned to it. Multiple policies can co-exist within a single company.

**Built-in policy archetypes (seeded at setup, fully editable):**

| Policy Name | Use Case | Geofence | Tracking | Device Required |
|---|---|---|---|---|
| Office Attendance | Standard office employees | Required (hard) | Disabled | Yes |
| Field Workforce | Sales, technicians, delivery | None | Enabled, 30 min | Yes |
| Hybrid Workforce | Employees split between office and remote | Soft (warn if outside) | Enabled, 60 min | Yes |
| Work From Home | Fully remote employees | None | Disabled | Yes |

**Schema:**

```typescript
interface IAttendancePolicy extends Document {
  name:        string;          // "Office Attendance", "Field Workforce", ...
  description: string;
  isDefault:   boolean;         // exactly one policy must be default (company-wide fallback)
  isActive:    boolean;         // soft-delete; cannot delete policy assigned to employees

  // Geofence behaviour
  geofenceRequired:       boolean;                        // must be in geofence to check in
  geofenceValidationMode: 'hard' | 'soft' | 'none';      // hard=block, soft=warn+flag, none=skip
  locationAccuracyThresholdMeters: number;               // minimum acceptable GPS accuracy

  // Workforce tracking
  trackingEnabled:         boolean;
  trackingIntervalMinutes: 15 | 30 | 60;

  // Check-in requirements
  deviceRegistrationRequired: boolean;   // employee must have a registered device

  // Future-ready fields (stored in schema now; not enforced until feature is implemented)
  selfieRequired:           boolean;     // future: require photo at check-in
  wifiValidationEnabled:    boolean;     // future: must be on company Wi-Fi
  bluetoothValidationEnabled: boolean;  // future: must be near a company Bluetooth beacon
  vpnRequired:              boolean;     // future: must be connected to company VPN

  // Attendance correction rules
  regularizationAllowed:     boolean;
  regularizationLookbackDays: number;   // overrides CompanySettings.regularizationLookbackDays

  // Location data retention
  locationRetentionDays: number;        // overrides CompanySettings.locationTracking.retentionDays

  createdBy:  mongoose.Types.ObjectId;
  createdAt:  Date;
  updatedAt:  Date;
}
```

**Indexes:**
```typescript
{ isDefault: 1 }     — find the default policy (queried at every check-in)
{ isActive: 1 }      — list active policies
```

**Business rules:**
- Exactly one `isDefault: true` policy must exist. Creating a new default automatically demotes the previous one.
- `isActive: false` policies cannot be assigned to new employees but retain existing assignments (employees fall through to company default at next check-in).
- `locationAccuracyThresholdMeters` on policy overrides `CompanySettings.gpsAccuracyThresholdMeters` when set.
- `regularizationLookbackDays` on policy overrides `CompanySettings.regularizationLookbackDays` when set.

### 1.3 Employee → Policy assignment

`User` model gains one field:

```typescript
attendancePolicyId: mongoose.Types.ObjectId | null;
// null = use company default policy
```

When `null`, the resolver falls through to `AttendancePolicy.isDefault = true`. This means zero-migration: all existing employees automatically use the default policy without any data change.

### 1.4 Why this is better than the current design

| Scenario | Current system | With AttendancePolicy |
|---|---|---|
| Field technician should not be geofence-blocked | Manually adjusting company-wide settings affects all employees | Assign to "Field Workforce" policy |
| WFH employee should not get geofence flags | No mechanism | Assign to "Work From Home" policy |
| New policy rollout (e.g. weekly-office) | No mechanism | Create policy, assign group of employees |
| Employee moves from office to field role | No mechanism | Reassign `attendancePolicyId` |
| Per-policy tracking interval (office: none, field: 30 min) | Not possible | Native to the policy entity |

## Part 2 — Temporary Attendance Override

### 2.1 Purpose

Some employees are permanently assigned to an office policy. On specific dates, they need to work outside the office for a limited period. Rather than permanently reassigning their policy, an admin creates a **Temporary Attendance Override** that grants them a different policy for a specific date-time window.

### 2.2 Override entity

```typescript
type OverrideReasonCategory =
  | 'client_visit' | 'site_inspection' | 'service_call'
  | 'business_travel' | 'installation' | 'audit'
  | 'emergency_assignment' | 'other';

type OverrideStatus = 'pending' | 'approved' | 'rejected' | 'expired' | 'cancelled';

interface ITemporaryAttendanceOverride extends Document {
  employeeId:          mongoose.Types.ObjectId;   // ref: User
  attendancePolicyId:  mongoose.Types.ObjectId;   // ref: AttendancePolicy — policy to apply during window
  
  startDateTime:       Date;
  endDateTime:         Date;
  
  reasonCategory:      OverrideReasonCategory;
  reason:              string;    // free-text description
  notes:               string | null;
  
  // Approval workflow
  status:              OverrideStatus;
  requiresApproval:    boolean;   // snapshot of company setting at creation time
  
  createdBy:           mongoose.Types.ObjectId;
  approvedBy:          mongoose.Types.ObjectId | null;
  approvedAt:          Date | null;
  rejectedBy:          mongoose.Types.ObjectId | null;
  rejectionReason:     string | null;
  
  // Lifecycle
  expiryNotificationSentAt: Date | null;
  cancelledBy:         mongoose.Types.ObjectId | null;
  cancelledAt:         Date | null;
  
  createdAt:           Date;
  updatedAt:           Date;
}
```

**Indexes:**
```typescript
{ employeeId: 1, status: 1, endDateTime: 1 }   — resolver query: active overrides for employee
{ startDateTime: 1, endDateTime: 1 }            — expiry sweep
{ createdBy: 1, createdAt: -1 }                 — admin history view
```

### 2.3 Approval workflow

Controlled by `CompanySettings.requiresOverrideApproval: boolean`.

- `false` (default): Override is auto-approved on creation. `status → 'approved'` immediately. `approvedBy = createdBy`. Simple companies without a dedicated HR approval process.
- `true`: Override is created with `status: 'pending'`. Admin receives notification. Admin approves or rejects. Override only affects policy resolution when `status: 'approved'`.

### 2.4 Edge case matrix

| Scenario | Behaviour |
|---|---|
| **Employee already checked in when override is created** | Override takes effect at **next check-in**. Active session was resolved at its own check-in time; the snapshot is immutable. No retroactive change. |
| **Override expires before employee checks out** | Active session continues under the policy snapshot captured at check-in. Override expiry has zero effect on the running session. Employee reverts to base policy at their next check-in. |
| **Override expires during active session — GPS tracking** | Tracking continues until checkout. The resolved policy on the active session still says `trackingEnabled: true`. The session owns its snapshot. |
| **Employee never checks out (missed checkout)** | Override expires normally. Midnight cron auto-closes session. Next check-in uses fresh policy resolution (override is now expired; base policy applies). |
| **Admin cancels override (no active session)** | Set `status: 'cancelled'`, `cancelledBy`, `cancelledAt`. No sessions affected. Employee's next check-in uses base policy. |
| **Admin cancels override (active session exists)** | Block cancellation with 409 error: "Cannot cancel override while an active session is using it." Admin must wait for employee to check out or force-close the session first. |
| **Admin deletes override** | Hard delete is disallowed. Only soft cancellation. Reason: audit trail must be preserved. |
| **Policy referenced by override is updated** | Override references the `attendancePolicyId`. Policy is evaluated fresh at each check-in. If the policy changed between override creation and use, the updated policy applies. (Override grants access to that policy, not a frozen snapshot of it.) |
| **Policy referenced by override is deactivated** | Resolver falls through to employee's base policy, then company default. Override is now effectively inert. Admin should be notified. |
| **Multiple active overrides requested for same employee** | Blocked. At most one `status: 'approved'` or `'pending'` override per employee at any time. Error: "Employee already has an active override." Admin must cancel existing override first. |
| **Override approval pending but employee checks in** | Pending override is ignored by resolver. Employee uses base policy. |
| **Override start time is in past when admin approves** | Allowed. The override is immediately active from the moment of approval until `endDateTime`. |
| **Override end date is before start date** | Validation error on creation. |
| **Notification failures** | Override lifecycle is not blocked by notification delivery. Override proceeds regardless. Failed notification is retried via existing notification infrastructure. |

### 2.5 Notifications

Extend `NotificationType` and `Notification.referenceType`:
```typescript
// New NotificationType values:
| 'overrideCreated'          // employee notified when override created (pending or auto-approved)
| 'overrideApproved'         // employee notified when admin approves
| 'overrideRejected'         // employee notified when admin rejects
| 'overrideExpiring'         // employee + admin notified 1 hour before expiry
| 'overrideExpired'          // employee notified after expiry

// New referenceType:

```

## Part 3 — Policy Resolution Engine

### 3.1 Resolution order

```
Priority (highest → lowest):

  1. Temporary Attendance Override   (active, approved, within startDateTime–endDateTime)
  2. Employee-assigned Policy        (User.attendancePolicyId)
  3. Company Default Policy          (AttendancePolicy.isDefault = true)
  4. System Defaults                 (hardcoded; should never be reached in configured system)
```

Levels 2 and 3 are both `AttendancePolicy` documents — the difference is whether the employee has been explicitly assigned one or falls through to the company default. This is a single Mongoose query:

```typescript
const policy = await AttendancePolicy.findById(
  user.attendancePolicyId ?? await getDefaultPolicyId()
);
```

Future extensibility: Department-level policy assignment is implemented at the **admin UI level** — an admin assigns the same `attendancePolicyId` to all employees in a department. No new data model needed; the resolver stays identical.

### 3.2 AttendancePolicyResolver service

```typescript
// apps/admin/src/services/AttendancePolicyResolver.ts

export interface ResolvedAttendancePolicy {
  // Geofence
  geofenceRequired:                boolean;
  geofenceValidationMode:          'hard' | 'soft' | 'none';
  locationAccuracyThresholdMeters: number;

  // Tracking
  trackingEnabled:                 boolean;
  trackingIntervalMinutes:         number;

  // Check-in
  deviceRegistrationRequired:      boolean;
  selfieRequired:                  boolean;       // future (stored, not enforced yet)
  wifiValidationEnabled:           boolean;       // future
  bluetoothValidationEnabled:      boolean;       // future
  vpnRequired:                     boolean;       // future

  // Corrections
  regularizationAllowed:           boolean;
  regularizationLookbackDays:      number;

  // Retention
  locationRetentionDays:           number;

  // Resolution metadata
  resolvedFrom:      'override' | 'employee_policy' | 'company_default' | 'system_default';
  resolvedPolicyId:  string;          // AttendancePolicy._id.toString()
  resolvedPolicyName: string;         // "Field Workforce" — for display in session and admin UI
  resolvedOverrideId: string | null;  // TemporaryAttendanceOverride._id.toString() if override
}

export class AttendancePolicyResolver {
  static async resolve(
    employeeId: string,
    now: Date = new Date()
  ): Promise<ResolvedAttendancePolicy> {
    // Step 1: Check for active, approved temporary override
    const override = await TemporaryAttendanceOverride.findOne({
      employeeId: new ObjectId(employeeId),
      status: 'approved',
      startDateTime: { $lte: now },
      endDateTime:   { $gt: now },
    }).lean();

    const policyId = override
      ? override.attendancePolicyId
      : (await User.findById(employeeId).lean())?.attendancePolicyId;

    // Step 2: Resolve policy (employee-assigned or company default)
    const policy = policyId
      ? await AttendancePolicy.findById(policyId).lean()
      : await AttendancePolicy.findOne({ isDefault: true, isActive: true }).lean();

    if (!policy) return SYSTEM_DEFAULTS;  // defensive fallback

    const resolvedFrom = override
      ? 'override'
      : (policyId ? 'employee_policy' : 'company_default');

    return {
      geofenceRequired:                policy.geofenceRequired,
      geofenceValidationMode:          policy.geofenceValidationMode,
      locationAccuracyThresholdMeters: policy.locationAccuracyThresholdMeters,
      trackingEnabled:                 policy.trackingEnabled,
      trackingIntervalMinutes:         policy.trackingIntervalMinutes,
      deviceRegistrationRequired:      policy.deviceRegistrationRequired,
      selfieRequired:                  policy.selfieRequired,
      wifiValidationEnabled:           policy.wifiValidationEnabled,
      bluetoothValidationEnabled:      policy.bluetoothValidationEnabled,
      vpnRequired:                     policy.vpnRequired,
      regularizationAllowed:           policy.regularizationAllowed,
      regularizationLookbackDays:      policy.regularizationLookbackDays,
      locationRetentionDays:           policy.locationRetentionDays,
      resolvedFrom,
      resolvedPolicyId:   policy._id.toString(),
      resolvedPolicyName: policy.name,
      resolvedOverrideId: override ? override._id.toString() : null,
    };
  }
}
```

### 3.3 AttendanceSession — full resolved policy snapshot

`AttendanceSession` stores the complete `ResolvedAttendancePolicy` at check-in time. This snapshot is immutable after the session is created.

```typescript
// Replace previous trackingPolicy/trackingEnabled fields with:
resolvedPolicy: ResolvedAttendancePolicySnapshot | null;
// null = session created before Phase 16.1 (backward compatible)

// Schema sub-document
const ResolvedPolicySchema = new Schema({
  geofenceRequired:                { type: Boolean, required: true },
  geofenceValidationMode:          { type: String, enum: ['hard','soft','none'], required: true },
  locationAccuracyThresholdMeters: { type: Number, required: true },
  trackingEnabled:                 { type: Boolean, required: true },
  trackingIntervalMinutes:         { type: Number, enum: [15,30,60], required: true },
  deviceRegistrationRequired:      { type: Boolean, required: true },
  selfieRequired:                  { type: Boolean, required: true },
  regularizationAllowed:           { type: Boolean, required: true },
  regularizationLookbackDays:      { type: Number, required: true },
  locationRetentionDays:           { type: Number, required: true },
  resolvedFrom:      { type: String, enum: ['override','employee_policy','company_default','system_default'], required: true },
  resolvedPolicyId:  { type: String, required: true },
  resolvedPolicyName: { type: String, required: true },
  resolvedOverrideId: { type: String, default: null },
}, { _id: false });

// On AttendanceSessionSchema:
resolvedPolicy: { type: ResolvedPolicySchema, default: null }
```

**Why store the full snapshot (not just a policy reference):**
- Policy can change after the session is created — snapshot preserves what governed this specific session
- Historical analytics can correctly attribute behaviours to the policy that was in effect, even if that policy was later modified
- No join required to render session details — all behaviour facts are on the session document

## Part 4 — Workforce Tracking Trigger

Tracking starts when `session.resolvedPolicy.trackingEnabled === true`. No geofence evaluation, no location check. The policy is the sole authority.

The existing per-ping `insideGeofence` computation (server-side from `CompanySettings.geoFence`) continues unchanged — every ping independently records whether the employee is inside or outside the office perimeter. This is observational data, not a trigger condition.

**Why this is correct:**
- An "Office Attendance" policy employee does not need tracking — they're office-bound by design
- A "Field Workforce" policy employee is always tracked — they're expected to be mobile
- A "Hybrid" policy employee is tracked so admin can see when they're in/out
- A temporary override to "Field Workforce" enables tracking for the override duration

This model is clean, predictable, and policy-first. No special cases anywhere in the codebase.

### 5.3 Multi-office future extensibility

The current schema stores a single `CompanySettings.geoFence` object. For future multi-office support:

**No schema migration needed during Phase 16.** The `AttendancePolicy` already has `geofenceRequired` and `geofenceValidationMode`. When multi-office is introduced:

1. Add `CompanySettings.offices: IOfficeLocation[]` array (additive — no breaking change)
2. Add `AttendancePolicy.officeId: ObjectId | null` (null = primary/only office)
3. `AttendancePolicyResolver` reads `policy.officeId ?? settings.offices[0]._id ?? legacyGeoFence`
4. Legacy `CompanySettings.geoFence` becomes an alias for `offices[0]`

This migration is zero-downtime and fully backward-compatible. For Phase 16, the resolver always uses `CompanySettings.geoFence` and no `officeId` field is added to `AttendancePolicy`.

## Part 12 — Security Review

| Threat | Enterprise-grade Mitigation |
|---|---|
| **GPS coordinate spoofing** | (1) `accuracy` field stored; pings with accuracy > policy threshold flagged. (2) Impossible travel detection: consecutive pings with implied speed > 250 km/h write `LOC_SUSPICIOUS_MOVEMENT` to AuditLog. (3) Mock GPS detection via `possibleMockGps` flag already in `AttendanceSession.flags` (extended to per-ping in Phase 16.5). |
| **Timestamp manipulation (clock skew)** | Server validates `ping.timestamp` within `±checkinTimestampWindowMinutes` of server time. Pings with out-of-window timestamps rejected with 400 and `LOC_SUSPICIOUS_TIMESTAMP` written to AuditLog. Server time is authoritative. |
| **Replay of old location pings** | Timestamp window validation (above) prevents replaying pings older than N minutes. |
| **Employee impersonating another for location upload** | `employeeId` resolved from JWT `userId` on all location endpoints. Cannot impersonate another user with a valid JWT. |
| **Admin viewing wrong employee's data** | Single-tenant SaaS. `adminVisibility` setting enforced in `LocationService`. Query always scoped to `performedBy` role check. |
| **Stale background JWT used after logout** | On `POST /attendance/location`: 401 returned. Mobile clears stored token, stops tracking, posts notification to user. Token refresh via `/auth/refresh` attempted first (if refresh token present and valid). |
| **Override creation without approval** | `requiresOverrideApproval` enforced. Auto-approval is a company-level choice, not a security bypass. |
| **Ping flood / DoS via location endpoint** | Existing `attendanceLimiter` (Upstash Redis sliding window) applied to location endpoint. Rate limit: same as attendance actions. |
| **Sensitive session ID in URL** | `GET /attendance/[sessionId]/location` requires admin JWT. SessionId is not guessable (MongoDB ObjectId). |
| **Export of tracking data** | `LOC_EXPORT_INITIATED` AuditLog event written on every data export. Admin-only endpoint. |
| **Policy escalation via override** | Override grants access to a named policy only. Cannot grant more capabilities than that policy defines. Admin creates both policy and override — no self-escalation path. |

## Part 13 — Privacy Review

1. **Tracking scope:** Location collected only during active attendance sessions where `resolvedPolicy.trackingEnabled = true`. Zero data collected outside checked-in hours, on non-tracking sessions, or while app is not in foreground/background-location mode.

2. **Transparency — mobile:** Persistent status card during tracked sessions displays policy name, override reason (if applicable), and tracking interval. Not dismissible. Disappears on checkout.

3. **Employee self-access:** Employees can view their own location history via scoped `GET /attendance/[sessionId]/location` with employee JWT. Cannot view other employees' data.

4. **Retention per policy:** `AttendancePolicy.locationRetentionDays` allows field-worker data to be retained for compliance (e.g., 1 year) while office-worker data (when/if tracked) is purged faster (90 days). TTL index on `locationpings.createdAt` is set to the minimum retention across all active policies; individual document pruning respects the originating session's policy retention.

   *Practical implementation:* Since MongoDB TTL is collection-wide, the TTL is set to the maximum retention needed. A separate nightly cron queries `LocationPing` documents older than their session's `resolvedPolicy.locationRetentionDays` and deletes them. The TTL index serves as a hard ceiling.

5. **Data minimisation:** Lat/lng, accuracy, speed, battery. No reverse-geocoding stored at the server level. No contact data, app usage, or content.

6. **Consent:** Employee onboarding text updated to include tracking disclosure. Device registration flow is the natural consent point — the consent describes the employer monitoring policy. No code change needed; updates to `seed-admin.ts` onboarding content.

7. **Audit logging:** Every ping upload, every admin location view, every override lifecycle event logged to `AuditLog`. Provides compliance evidence for GDPR Article 30 (Records of Processing Activities).

8. **Encryption:** MongoDB Atlas encryption at rest covers all location data. Transport is TLS (HTTPS). No application-layer field-level encryption required for operational data of this type.

9. **Access control:** `POST /attendance/location` — employee, own session only. `GET` location routes — admin only. Both enforced at middleware level (existing `getAuthUser` + role check pattern).

If disabled: skip ping, log locally. | No notification during brief outage. | **Phone powered off** | All pings missed. No status event sent. | No UX | Health → `no_update_threshold_exceeded` after gap > 3× interval | Device powers on → app restores tracking state; queued pings (if any) flush |
| **Background service killed (Android)** | `START_STICKY` flag restarts service. SharedPreferences restores `{sessionId, token, intervalMinutes}`. | Transparent — brief gap (< 30s typically) | Brief gap in ping timeline | Auto-recovery within 30s |
| **User force closes app (Android)** | Same as background kill — `START_STICKY` | Same | Same | Same |
| **User revokes background location permission** | Mobile detects on next background launch. Sends `LOC_PERMISSION_REVOKED` status event. Stops tracking. | Banner: "Location permission removed. Tracking paused. Contact admin." | Health → `permission_revoked`. Tracking may be affected." | Health → `battery_optimized`. `🔋` warning in dashboard. | Battery charged → normal tracking resumes; no special recovery needed |

| **iOS Background Restrictions (Low Power Mode)** | `CLLocationManager` throttles update frequency. Mobile detects `ProcessInfo.isLowPowerModeEnabled`. Uses lower accuracy. Pings may arrive less frequently. | Transparent | Ping gaps may appear in route timeline. Health remains `healthy` if within 3× interval. | Device exits Low Power Mode → normal accuracy resumes |

| **AttendancePolicy changes mid-session** | Session snapshot is immutable. | Transparent | Policy change takes effect at next check-in for affected employees. | N/A |
| **Temporary override expires mid-session** | Session snapshot is immutable — session was resolved at check-in. Employee logs in fresh. | Transparent after admin registers new device. | Admin sees old session closed, new session from new device. | Standard device registration flow. |
| **Clock manipulation by employee** | Ping `timestamp` validated against server time ± `checkinTimestampWindowMinutes`. Rejected if outside window. `LOC_SUSPICIOUS_TIMESTAMP` written to AuditLog. | HTTP 400 returned. Mobile logs error, skips ping for that interval. | AuditLog event visible. Repeated occurrences are a red flag. | N/A — server rejects invalid timestamps unconditionally. |

Receiving two identical pings (same `attendanceSessionId`, same `timestamp`) is harmless — they appear as two points at the same location on the route. Mobile write-ahead queue design prevents duplicates under normal operation. | Transparent | Route may show two overlapping markers — not visually significant. | N/A |

## Final Recommendation

The two new entities — **Attendance Policy** and **Temporary Attendance Override** — should be implemented before the location tracking feature. They are foundational. Without them, every employee is subject to identical attendance rules, making the tracking feature less useful and requiring future breaking schema changes to add per-employee behaviour.

The sequencing (Policy first, then Tracking) is correct: the tracking trigger depends on `resolvedPolicy.trackingEnabled`, and the resolver depends on the Policy model. No circular dependencies.

The **Geofence Map Picker** should replace the current manual coordinate inputs in Phase 16.5 — it is a UX requirement, not an optional enhancement.

The **RouteSession** optimization is explicitly deferred. The API contract is defined now so it is a zero-impact performance upgrade when needed.
