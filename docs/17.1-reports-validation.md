## 3. Authorization & Security

### 3.1 Auth Flow (per route)

All 9 routes:
1. Call `getAuthUser(request)` — verifies JWT via `jose.jwtVerify`, supports `Authorization: Bearer` + `__session` cookie
2. Catch `AuthError` → `apiError(err.code, 'Unauthorized.', err.httpStatus)` → 401
3. Call `assertRole(payload, 'admin')` — throws `AuthError('AUTH_006', 403)` for non-admin
4. Catch `AppError` → `apiError(...)` → but see M1

### 3.2 Input Injection Risk

All query parameters are routed through Zod schemas before reaching the service:
- ObjectId format enforced by regex `/^[0-9a-f]{24}$/i`
- Date strings enforced by `/^\d{4}-\d{2}-\d{2}$/`
- `yearMonth` enforced by `/^\d{4}-\d{2}$/`
- Enum values (status, leaveType) constrained by `z.enum([...])`
- Numeric coercion (page, limit, month, year) with `.int().min().max()` bounds

No raw user input reaches MongoDB queries. NoSQL injection surface: none.

### 3.3 Export Filename Safety

Attendance: `filename="attendance-report-${query.startDate}-to-${query.endDate}.xlsx"` — both dates are Zod-validated to YYYY-MM-DD format before use. No path traversal possible.

Payroll: `filename="payroll-report${query.yearMonth ? `-${query.yearMonth}` : ''}.xlsx"` — `yearMonth` validated to YYYY-MM. Safe.

## 9. Findings

### HIGH

**H1 — `departmentSummary`: attendance and leave bucketing keyed by wrong ObjectId** ✅ FIXED

**File:** `src/services/ReportService.ts` (was lines 619–631; now corrected)

The `departmentSummary` method fetched attendance docs with projection `'employeeId status'` and leave docs with projection `'employeeId totalDays'`, then used `a._id` (the attendance/leave document's own ObjectId) to look up the employee's department, instead of `a.employeeId` (the employee's User ObjectId).

```typescript
// Bug (was)
type AttDoc = { _id: mongoose.Types.ObjectId; status: string };  // missing employeeId
for (const a of attDocs) {
  const dept = userDeptMap.get(a._id.toHexString()) ?? 'Unassigned';  // WRONG
```

`userDeptMap` is keyed by `User._id`. An AttendanceDay's `_id` is its own document ObjectId, completely unrelated. Lookup always missed; all departments returned `presentDays = 0`, `totalDays = 0`, `attendanceRate = null`.

Same bug appeared in the leave loop (`l._id` instead of `l.employeeId`).

**Unit test U-REP-09 was a false positive**: mock used the same `EMP_OID`/`EMP_OID2` constants for both `User._id` and `AttendanceDay._id`, so the wrong lookup coincidentally matched.

**Fix applied:**
- Added `employeeId: mongoose.Types.ObjectId` to `AttDoc` and `LeaveDoc` local types
- Changed `a._id.toHexString()` → `a.employeeId.toHexString()`
- Changed `l._id.toHexString()` → `l.employeeId.toHexString()`
- Rewrote U-REP-09 to use distinct ObjectIds for user `_id` vs attendance doc `_id`
- `npx tsc --noEmit`: PASS; `npx jest --forceExit` 151/151: PASS

### MEDIUM

**M1 — `assertRole` throws `AuthError`; route catches `AppError`: wrong role returns 500 not 403**

**Files:** All 9 report route files (same pattern)

`requireRole.ts` defines:
```typescript
export function assertRole(...): void {
  if (!roles.includes(payload.role)) throw new AuthError('AUTH_006', 403);
}
```

`AuthError` extends `Error` directly. `AppError` (from `AuthService.ts`) also extends `Error` directly. They are independent classes — `AuthError` is NOT a subtype of `AppError`.

Route catch block:
```typescript
try { assertRole(payload, 'admin'); }
catch (err) {
  if (err instanceof AppError) return apiError(err.code, err.message, err.httpStatus);
  throw err;  // AuthError propagates here → Next.js returns 500
}
```

For an authenticated non-admin user, all report endpoints return HTTP 500 instead of 403. No data is leaked, but the contract is wrong and the 500 is misleading.

**Note:** This is a pre-existing codebase-wide pattern, identical in payroll, regularization, and other admin-only routes. It was not flagged in prior validation cycles. It is noted here for completeness; the fix belongs in a global pass, not reports specifically.

**Fix:** Change `if (err instanceof AppError)` to `if (err instanceof AppError || err instanceof AuthError)` (import `AuthError` in routes), or change `assertRole` to throw `AppError` instead of `AuthError`.

**M2 — `payrollExport`: `yearMonth` should be required per API spec but is optional** ✅ FIXED

**File:** `src/validators/report.ts`

API spec section 10.5 declares `yearMonth: YYYY-MM — Required`. Implementation had it optional via inherited `PayrollReportQuerySchema`.

**Fix applied:**
```typescript
export const PayrollExportQuerySchema = PayrollReportQuerySchema
  .omit({ page: true, limit: true })
  .extend({ yearMonth: z.string().regex(/^\d{4}-\d{2}$/, 'Must be YYYY-MM') });
```
Calling `GET /api/v1/reports/payroll/export` without `yearMonth` now returns `GEN_001 / 400`.

**M3 — BR-REP-02 (streaming large exports) not implemented**

**File:** `src/services/ReportService.ts:213-215, 333, 434-436`

API spec states: "BR-REP-02: Large exports (>500 employees × >30 days) are streamed to avoid memory pressure."

All 3 export methods load all matching documents into memory in a single query:
```typescript
const docs = (await AttendanceDay.find(filter).sort(...).lean()) as LeanAttDay[];
```

There is no cursor-based streaming, batching, or memory guard. For a large dataset (e.g. 1000 employees × 366 days = 366,000 rows), the entire result set is materialized in memory before ExcelJS processes it.

**Impact:** Potential memory exhaustion and timeout for large date ranges. The 366-day export limit mitigates somewhat but does not eliminate the risk for large employee counts.

**Note:** No fix is required to unblock Phase 10; this is a performance concern for scale.
