## R-UI-001 — Authentication Screens

### Root Cause

Docs/05-admin-ui-ux.md scoped only authenticated screens. Pre-authentication flows were listed in the sitemap but never given a design section. Login is the system entry point; its absence means developers have no reference for the first user-visible screen.

### UX Impact

- **Critical path gap:** Developers cannot build the portal entry point without this specification.
- **Error state coverage missing:** AUTH_001 (invalid credentials), AUTH_002 (rate limited), AUTH_004 (email not found), AUTH_007 (account inactive), AUTH_009 (invalid reset token) — all render on pre-auth screens that were undesigned.
- **`requiresPasswordChange` flow incomplete:** New employees receive a temp password via admin. The forced-change flow blocks all portal access until resolved — the most important first-login UX was absent.

### Security Impact

- Without specifying rate-limit error messaging, developers might display raw error codes or implement their own inconsistent patterns.
- Session expiry handling is not a pre-auth issue per se but is closely coupled: expired sessions redirect to login; if login is undesigned, the redirect destination is undefined.

### Fix

Add **Section 0 — Pre-Authentication Screens** to `docs/05-admin-ui-ux.md` covering five screens:

1. **Login** — email + password form with full error state catalog
2. **Forgot Password** — email input + success state
3. **Reset Password** — new password + confirm + token validation
4. **Forced Change Password** — temp-password replacement form (restricted shell)
5. **Session Expired** — non-dismissible overlay pattern (global, not just pre-auth)

```
┌──────────────────────────────────────────────────────────────────┐
│  (blurred page content behind overlay)                           │
│                                                                  │
│         ┌────────────────────────────────────┐                  │
│         │                                    │                  │
│         │  🔒  Session Expired               │                  │
│         │                                    │                  │
│         │  Your session has expired or was   │                  │
│         │  revoked. Please sign in again     │                  │
│         │  to continue.                      │                  │
│         │                                    │                  │
│         │  [       Sign In Again       ]     │                  │
│         │                                    │                  │
│         └────────────────────────────────────┘                  │
└──────────────────────────────────────────────────────────────────┘
```

**Trigger conditions:**
1. `POST /auth/refresh` returns `401` (refresh token invalid/expired/revoked)
2. `POST /auth/refresh` returns `403 AUTH_010` (unexpected; handle defensively)
3. Any API call returns `401` AND silent refresh has already been attempted

**Implementation (global Axios/fetch interceptor):**
```typescript
// In api-client.ts — response interceptor
if (response.status === 401 && !isRefreshAttempted) {
  try {
    await refreshToken();     // POST /auth/refresh
    return retry(originalRequest);
  } catch {
    triggerSessionExpiredOverlay();  // show modal, block all interaction
  }
}
```

**Behavior:**
- Overlay is non-dismissible (no X button, no outside-click close)
- `[Sign In Again]` → navigate to `/login?redirect=<current-path>` 
- On `/login` after successful auth: redirect back to `redirect` param
- Background page content is blurred (`backdrop-blur-sm`) + `pointer-events-none` to prevent interaction
- `role="alertdialog"`, `aria-modal="true"`, focus trapped inside

**Do NOT** use the standard shadcn/ui `<Dialog>` for this — it must not be closeable. Use a custom overlay with `position: fixed, inset: 0, z-index: 9999`.

**Authentication flow (updated):**

```
/login
  → POST /auth/login (with device fingerprint if present)
  → 401/400 errors → show inline error
  → 200: check requiresPasswordChange
       true  → /change-password (restricted shell)
                 → PATCH /auth/me/change-password
                 → success: redirect /dashboard (full shell)
       false → /dashboard (full shell)

       failure → session expired overlay
                   → [Sign In Again] → /login?redirect=<path>
```

**Forgot password flow:**
```
/forgot-password
  → POST /auth/password-reset/request
  → success state (regardless of email existence)
  → user checks email
  → clicks link → /reset-password?token=xxx
  → POST /auth/password-reset/confirm
  → success → /login (auto-redirect 3s)
```

## R-UI-002 — Payroll Concurrency UX

### Root Cause

`POST /payroll/compute` (bulk) is a long-running operation (5–60 seconds depending on employee count). The original design showed a progress bar (`38/45 processed`) but did not specify:
- How the UI knows progress (API returns a single response, not a stream)
- What prevents double-submission
- What happens when a second admin triggers compute while one is running
- How partial failures (some employees fail mid-batch) are displayed and recovered

API finding R-API-009 (concurrency guard) was deferred to implementation, meaning the UI also lacked its corresponding design.

### UX Impact

- Admin double-clicks compute → two batch operations triggered → data inconsistency
- Two logged-in admins both trigger June payroll compute simultaneously → race condition
- Partial failure (3/45 employees failed) → admin doesn't know which employees need retry
- No way for admin to know "is a compute already running" when they land on the payroll page

### Security Impact

Low direct security risk. Operational risk: duplicate payroll computations could result in incorrect payable amounts being finalized if two computes run with different effective dates.

### Fix

Replace the compute modal design with a four-state flow. Introduce the concept of **Payroll Compute Lock** — a server-side mutex stored in Redis (implementation detail from R-API-009) surfaced to the UI as a locked state indicator.

### New Screens / States

**State A — Idle (Compute Available)**

Payroll list page: `[Generate Payroll ▾]` button is enabled. No lock indicator.

---

**State B — Pre-Compute Confirmation Modal**

```

    overwritten. Finalised records are protected.

  Do not close this tab during computation.

```

`[Start Computation]` button:
- Disabled after first click (immediate, before API response)
- Shows inline spinner: "Starting..."
- Prevents double-submission in same browser tab

**State C — Computation In Progress (Modal stays open)**

```
Computing Payroll for June 2026...

  ⏳ Processing employees...

  This may take up to 30 seconds.
  Please keep this tab open.

  ─────────────────────────────

  [    Running — Please Wait    ]  ← disabled, spinner
```

**Technical reality:** `POST /payroll/compute` is a single API call. The UI cannot show real per-employee progress without a polling endpoint or SSE. In V1, show an indeterminate progress state (spinner + "Processing..."). No fake progress bar.

After API responds:
- Success → transition to State D (success)
- Conflict error → transition to State E (locked)
- Partial failure → transition to State F (partial failure)

---

**State D — Computation Success**

```
✓  Payroll Computed

  June 2026 payroll computation complete.

  ✓ Computed:   43
  ⊘ Skipped:     2  (already finalised)
  ✗ Failed:      0

```

`[View Payroll →]` closes modal and refreshes the payroll list. `[Generate Payroll]` button re-enabled.

---

**State E — Compute Locked (Concurrency Conflict)**

Triggered when API returns a concurrency conflict (another compute is running):

```
⚠  Payroll Computation In Progress

  Another admin is currently computing payroll
  for June 2026. Only one computation can run
  at a time.

  Please wait for the current computation to
  complete before starting a new one.

  Try again in approximately 30 seconds.

                [Close]   [Refresh Status]
```

On the **Payroll list page** (when a lock is active):
- `[Generate Payroll]` button shows amber "🔒 Computing..." state (disabled)
- Small banner below page header: "⚠ Payroll computation for June 2026 is in progress. The list will refresh automatically."
- SWR `refreshInterval: 10000` (10s) active while lock banner is visible
- When lock clears (next poll shows normal state): banner disappears, button re-enables, toast: "Payroll computation complete. List refreshed."

**Implementation note for developers:** The Payroll list API (`GET /payroll?yearMonth=YYYY-MM`) should return a `meta.isComputeLocked: boolean` field. If `true`, the UI enters the locked visual state. This is the signaling mechanism; no separate polling endpoint needed.

- Hover tooltip on badge: "Computation failed — [error reason]"
- Row `⋮` menu option: "Retry Computation" (triggers single-employee compute)

**State G — Payroll Recompute Protection (Payroll Already Finalized)**

When admin tries to trigger bulk compute for a month where ALL employees are finalized:


### Updated Workflows

**Payroll compute flow (v2):**
```
[Generate Payroll] clicked
  → Check meta.isComputeLocked
       locked → show State E (locked banner, button disabled)
       unlocked → open State B (confirmation modal)
  → [Start Computation] clicked
       → disable button immediately (double-click guard)
       → POST /payroll/compute (bulk)
       → all finalised → show State G
       → conflict response → show State E
       → success + no failures → show State D
       → success + failures → show State F
       → [View Payroll] → refresh list
```

---

### Updated Components

**`PayrollComputeButton`:** Stateful. Renders as normal dropdown when unlocked, as disabled amber "🔒 Computing..." when locked. Reads `isComputeLocked` from page data.

**`PayrollComputeModal`:** 6-state machine (Confirmation → InProgress → Success | Locked | PartialFailure | AllFinalised). State lives in React `useState`. Each state renders different modal body without closing/reopening the dialog.

**`PayrollLockBanner`:** Persistent alert banner shown on payroll list page when `isComputeLocked: true`. Auto-refreshes via SWR. Dismisses automatically when lock clears.

## R-UI-003 — Leave Revocation / Payroll Conflict UX

### Root Cause

Two separate modules (Leave and Payroll) share a state dependency: revoking an approved leave for a month whose payroll is finalized creates a data inconsistency (finalized payroll now reflects incorrect absent days). The API correctly returns `warnings[]` on revocation of leave in a finalized-payroll month, but the UI only showed a `toast.warning` — no guided next step, no visibility into which payroll month was affected, no cross-module workflow.

### UX Impact

- Admin revokes leave, sees a toast warning, dismisses it, moves on
- Payroll for that month remains finalized with incorrect data
- Month-end payroll export contains wrong figures
- No visual indicator anywhere that a payroll record is now stale

### Security Impact

None direct. Financial data integrity risk: incorrect payroll figures could be sent to payroll processor without admin awareness.

### Fix

Three-part fix:

1. **Enhanced revocation modal** — warn BEFORE the API call when the affected month's payroll is known to be finalized
2. **Cross-module alert banner** — persists on Leave History and Payroll List until resolved
3. **Payroll "Stale" indicator** — visual badge on payroll records that have had post-finalization changes

### New Screens / States

**State A — Revocation Pre-Check (Enhanced Revoke Modal)**

When admin clicks "Revoke" on an approved leave, the UI first checks if the affected month's payroll is finalized. This check happens **before** the API call using client-side data already loaded in the payroll list SWR cache.

If payroll for that month is NOT finalized:
```
Revoke Approved Leave

Revoke 3 days of Paid Leave for John Doe
(20–22 Jun 2026)?

This will restore 3 days to John Doe's
paid leave balance.

Reason * (required)
[___________________________________________]

              [Cancel]  [Revoke Leave]
```

If payroll for that month IS finalized (amber warning variant):
```
⚠  Revoke Leave — Payroll Already Finalised

  Revoking John Doe's leave (20–22 Jun 2026)
  affects a month with finalised payroll.

  After revoking:
  ┌─────────────────────────────────────────┐
  │  June 2026 payroll for John Doe will   │
  │  be outdated. You must:                │
  │                                        │
  │  1. Revoke the leave                   │
  │  2. Unfinalize June payroll            │
  │  3. Recompute June payroll             │
  │  4. Re-finalize June payroll           │
  └─────────────────────────────────────────┘

  Reason * (required)
  [___________________________________________]

  [Cancel]   [Revoke & Open Payroll Workflow]
```

`[Revoke & Open Payroll Workflow]`:
- Submits revocation API call
- On success: navigates to `/payroll/2026-06?employee=john-doe-id&action=recompute-required`
- A guided workflow banner appears on the payroll page (see State B)

---

**State B — Payroll Recompute Required Banner**

Appears on the Payroll list page when navigated from a leave revocation, OR when `meta.staleEmployeeIds` is non-empty in the payroll list API response.

```
┌────────────────────────────────────────────────────────────────────┐
│  ⚠  Action Required: Payroll Update Needed                     [×] │
│                                                                    │
│  John Doe's approved leave (20–22 Jun) was revoked after this     │
│  payroll was finalized. The payroll amounts below are outdated.   │
│                                                                    │
│  To correct: Unfinalize → Recompute → Re-finalize the affected    │
│  employee(s).                                                      │
│                                                                    │
│  Affected:  John Doe (EMP001)                [Unfinalize & Fix →] │
└────────────────────────────────────────────────────────────────────┘
```

- Banner color: amber (`bg-amber-50 border-amber-300`)
- `[×]` dismisses for this session only (banner returns on next page load until resolved)
- `[Unfinalize & Fix →]` triggers the Payroll Reopen Flow (State C)
- Banner persists until payroll for affected employees is re-finalized

**Payroll list — "Stale" row indicator:**

Affected employee rows show an amber `⚠ Stale` badge next to their status:
```
│  John Doe   │  22   │  21.0  │  ₹47,727  │  ✓ Finalised  ⚠ Stale  │  ⋮  │
```

Hover tooltip on `⚠ Stale`: "Leave revoked after finalization. Payroll requires recomputation."

**How `Stale` is detected:** The payroll list API returns `meta.staleEmployeeIds: string[]` — employee IDs where post-finalization changes have occurred (leave revocations, regularizations approved on finalized dates). This field is populated server-side. If an employee's ID is in `staleEmployeeIds`, their row renders with the `⚠ Stale` badge.

---

**State C — Payroll Reopen Flow (Guided Unfinalize → Recompute → Re-finalize)**

Triggered by `[Unfinalize & Fix →]` from the banner, OR from the row `⋮` → "Unfinalize" when row has `⚠ Stale`.

**Step 1 of 3 — Unfinalize Modal:**
```
Step 1 of 3 — Unfinalize Payroll

Unfinalize June 2026 payroll for John Doe?

This is required to update payroll after the
leave revocation.

Reason (pre-filled): "Leave revoked post-finalization"
[Leave revoked post-finalization____________]

        [Cancel]    [Unfinalize — Step 1 of 3]
```

Reason pre-filled with context-aware text. Admin can edit. On confirm: PATCH `/payroll/:id/2026-06/unfinalize`.

**Step 2 of 3 — Recompute Confirmation:**

After unfinalize succeeds, the modal transitions (no close/reopen):
```
Step 2 of 3 — Recompute Payroll

John Doe's June 2026 payroll status: Draft

Recompute now with updated attendance data?

John Doe was absent on 20–22 Jun (leave revoked).
New payable amount will reflect 3 absent days.

         [Cancel]    [Recompute — Step 2 of 3]
```

## R-UI-004 — Global Error & Edge Case Pages

### Root Cause

Next.js App Router relies on specific files (`not-found.tsx`, `error.tsx`, `global-error.tsx`) for error boundary rendering. The UI design had no specification for these, leaving developers to implement ad-hoc error pages with no design consistency or UX guidance.

Additionally, session expiry (covered as Screen 0.5 in R-UI-001) is the most common "edge case" but other states were also missing: genuine 500 errors, maintenance windows, and access-denied states.

### UX Impact

- Without these pages, React will render its default error overlay in development or a blank white page in production
- Admins with expired sessions hitting the page directly (no JS redirect) would see a blank page
- No maintenance page means during deployments/downtime, users see server errors instead of a friendly message

### Security Impact

- Unhandled 500 errors in Next.js can leak stack traces in non-production environments unless explicitly caught
- Access denied (wrong-role access) must redirect cleanly to avoid revealing portal structure to non-admin users

### Fix

Add **Section 15 — Error & Edge Case Pages** to `docs/05-admin-ui-ux.md`. Five pages:

1. **404 — Not Found** (`not-found.tsx`)
2. **500 — Server Error** (`error.tsx` / `global-error.tsx`)
3. **Maintenance** (middleware-served static page)
4. **Unauthorized** (middleware redirect)
5. **Access Denied** (`app/unauthorized/page.tsx`)

### Updated Workflows

**Error handling flow:**

```
Any page load error:
  → HTTP 404 → next/not-found.tsx (Screen 15.1)
  → Unhandled thrown error → error.tsx (Screen 15.2)

  → middleware → /unauthorized

  → SessionExpiredOverlay (Screen 0.5) — not a navigation, an overlay
```

### Updated Components

**`not-found.tsx`:** Next.js App Router file. Uses authenticated shell (or unauthenticated if no session).

**`error.tsx`:** Client component. Receives `error` (Error object) and `reset` (retry function). Shows Screen 15.2 with `error.digest`.

**`global-error.tsx`:** Root-level fallback. Same design as Screen 15.2 but with minimal shell (in case the shell itself crashed). Must be a client component.

**`public/maintenance.html`:** Static HTML file. Zero dependencies. Meta-refresh every 30s. Shows Screen 15.3.

**Middleware additions:**
```typescript
// middleware.ts
const ADMIN_ROUTES = ['/dashboard', '/employees', '/attendance', '/leave', 
                       '/regularization', '/payroll', '/reports', '/notifications',
                       '/audit-logs', '/settings'];

export function middleware(request: NextRequest) {
  const pathname = request.nextUrl.pathname;

  // Maintenance mode
  if (process.env.MAINTENANCE_MODE === 'true' && pathname !== '/maintenance') {
    return NextResponse.rewrite(new URL('/maintenance.html', request.url));
  }

  // requiresPasswordChange redirect
  const jwt = getJwtFromRequest(request);
  if (jwt?.requiresPasswordChange && pathname !== '/change-password') {
    if (isAdminRoute(pathname)) {
      return NextResponse.redirect(new URL('/change-password', request.url));
    }
  }

  // Unauthenticated → login
  if (isAdminRoute(pathname) && !jwt) {
    return NextResponse.redirect(new URL(`/login?redirect=${pathname}`, request.url));
  }

  // Wrong role → access denied
  if (isAdminRoute(pathname) && jwt?.role !== 'admin') {
    return NextResponse.redirect(new URL('/unauthorized', request.url));
  }
}
```
