## R-RD-001 — Settings Bootstrap Phase

### Root Cause

`companySettings` was grouped with the Admin Portal UI (Phase 10) because the Settings screens are an admin UI concern. However, the backend data model and read API for settings are an infrastructure concern — required by Phase 4 (attendance engine) and Phase 5 (leave engine) to function. The phase was sequenced by UI ownership rather than data dependency.

### Project Risk

Phase 4 attendance engine references `companySettings` for:
- `geoFenceCenter` / `geoFenceRadius` / `geoFenceEnabled` — geo-fence validation on every check-in
- `requiredDailyMinutes` — CHECKED_OUT_PARTIAL vs. CHECKED_OUT_COMPLETE threshold
- `workingDays` — `dayStatus = weekend` if day not in working days
- `shiftStartTime` / `shiftEndTime` — auto-close cron target time; session validation

Phase 5 leave engine references `companySettings` for:
- `leaveTypes[]` — valid leave type list; validation on apply
- `annualLeaveQuota` per type — balance allocation
- `maxCarryForwardDays` per type — rollover cap
- `leaveYearStartMonth` — year boundary for allocation reset
- `holidays[]` — cannot apply leave on a holiday

Without `companySettings` seeded and readable, Phases 4 and 5 cannot validate business rules. Developers must hardcode defaults as temporary stubs — stubs that will be forgotten, breaking validation silently when settings are eventually populated.

### Implementation Impact

Affects 4 phases directly:
- Phase 3 (Employee Management): `employees.department` may reference settings if departments are configurable
- Phase 4 (Attendance): geo-fence, day status, session validation all blocked
- Phase 5 (Leave): leave type validation, balance computation, holiday calendar blocked
- Phase 6 (Regularization): regularization window (`maxRegularizationDays`) from settings

### Fix: Phase 2.5 — Settings Bootstrap

**Position in sequence:** After Phase 2 (Auth), before Phase 3 (Employees).

**Why this position:** Auth middleware is required to protect settings endpoints (admin-write, employee-read). Employees, attendance, and leave all depend on settings data. Phase 2.5 provides settings data before any business domain is built.

## R-RD-002 — Cross-Phase Contracts

### Root Cause

The roadmap described cross-phase data dependencies verbally ("cross-phase concern") without defining the exact field paths, update conditions, and clear rules. When Phase 5 and Phase 7 are built at different times, the absence of a written contract means each developer makes independent assumptions about field names, types, and update logic.

### Project Risk

- `staleEmployeeIds` field name / type inconsistency between Phase 5 (write) and Phase 7 (read)
- Payroll compute trying to read `AttendanceRecord.dayStatus` before it is populated
- Leave balance computation reading uninitialized `leaveYearAllocation` records
- Phase 5 leave revocation writing to a `payrollRecords` schema that doesn't exist yet (Phase 7)

### Implementation Impact

All four cross-phase contracts must be documented and agreed upon before Phase 5 implementation begins (since Phase 5 is the first phase that writes across phase boundaries to Phase 7 data).

### Fix: Explicit Cross-Phase Contracts

---

#### Contract A — `staleEmployeeIds` (Phase 5 writes → Phase 7 reads)

**Field location:**
```
Collection:    payrollRecords
Field path:    staleEmployeeIds
Type:          String[]   (MongoDB ObjectId stored as string)
Default:       []
```

**Write conditions (Phase 5 `LeaveService.revokeLeave()`):**
```typescript
// Called when admin revokes an approved leave
async function onLeaveRevoked(leave: Leave): Promise<void> {
  const { employeeId, startDate } = leave;
  const month = startDate.getMonth() + 1;   // 1-12
  const year  = startDate.getFullYear();

  const payrollRecord = await PayrollRecord.findOne({
    employeeId,
    month,
    year,
    status: { $in: ['computed', 'finalized'] },  // only stale if already processed
  });

  if (!payrollRecord) return;  // no payroll yet — nothing to mark stale

  await PayrollRecord.updateOne(
    { _id: payrollRecord._id },
    { $addToSet: { staleEmployeeIds: employeeId.toString() } }
    // $addToSet prevents duplicates
  );
}
```

**Note:** `staleEmployeeIds` is stored at the payroll *period* level (month+year document), not per-employee. It lists which employees within that period have stale data. The field name is slightly misleading — it is an array on a PayrollRecord that represents a period, not per-employee. Future: consider renaming to `staleForEmployeeIds` in v2.

**Read conditions (Phase 7 `PayrollRepository.findByMonthYear()`):**
```typescript
// Admin GET /payroll?month=6&year=2026
const records = await PayrollRecord.find({ month, year });
// Aggregate into response:
return {
  data: records,
  meta: {
    isComputeLocked: await redis.exists(`payroll:compute:lock:${month}-${year}`),
    staleEmployeeIds: records
      .flatMap(r => r.staleEmployeeIds ?? [])
      .filter(unique),
  }
};
```

**Clear condition (Phase 7 `PayrollReopenModal` — Step 2: Recompute):**
```typescript
// After recompute completes for a specific employee
await PayrollRecord.updateOne(
  { month, year },
  { $pull: { staleEmployeeIds: employeeId.toString() } }
);
```

**Schema addition to `payrollRecords` (must be in Phase 7 model):**
```typescript
staleEmployeeIds: {
  type: [String],
  default: [],
}
```
**Phase 5 requirement:** Phase 5 developer must know this field exists in Phase 7's schema. Solution: Add `staleEmployeeIds` as an optional field to the `PayrollRecord` Mongoose model **in Phase 7 model definition**, and add a Phase 5 deliverable: "Import `PayrollRecord` model and call `$addToSet` on revoke." Since Phase 7 is built after Phase 5, the Phase 5 `onLeaveRevoked` function should check if the model exists gracefully (or use a stub that is filled in during Phase 7).

**Practical solution:** Add `staleEmployeeIds: [String]` to `PayrollRecord` schema in Phase 7. During Phase 5 implementation, add a stub comment: `// TODO Phase 7: implement onLeaveRevoked staleEmployeeIds write`. Implement the write during Phase 7, not Phase 5. This avoids importing a non-existent model in Phase 5.

#### Contract B — Attendance → Payroll (Phase 4 produces → Phase 7 consumes)

**What payroll needs from attendance:**

| Field | Source | Used For |
|---|---|---|
| `attendanceRecord.dayStatus` | Phase 4 `DayStatusService` | Classify each day: present/half-day/absent/leave/holiday/weekend |
| `attendanceRecord.totalMinutesWorked` | Phase 4 (sum of sessions) | Verify minimum hours for present status |
| `attendanceSession[].checkInTimestamp` | Phase 4 | Audit trail in payslip |

**Contract:**

- Phase 7 payroll compute queries `AttendanceRecord.find({ employeeId, date: { $gte: monthStart, $lte: monthEnd } })` and counts by `dayStatus`
- `dayStatus` must be set to `'absent'` (not null/undefined) for working days with no attendance sessions
- Responsibility: Phase 4 `DayStatusService` must run nightly (or on checkout) and backfill missing days for the current month

**Phase 4 deliverable to add:** Nightly `dayStatus` backfill for all employees (part of the Session Auto-Close cron or a separate lightweight cron). Ensures no gaps in `dayStatus` values for past dates.

#### Contract C — Leave → Payroll (Phase 5 produces → Phase 7 consumes)

**What payroll needs from leave:**

| Field | Source | Used For |
|---|---|---|
| `leaves` with `status: 'approved'` and `leaveType.isPaid: false` (LWP) | Phase 5 | LWP deduction days in payroll |
| `leaveYearAllocations.usedDays` per type | Phase 5 | Payslip leave summary |
| `leaves` date range overlapping payroll month | Phase 5 | Which days are leave days (don't count as absent) |

**Contract:**
- Phase 7 queries: `Leave.find({ employeeId, status: 'approved', startDate: { $lte: monthEnd }, endDate: { $gte: monthStart } })`
- LWP calculation: count approved LWP leave days overlapping the payroll month
- Paid leave: already reflected in `dayStatus = 'leave'` from Phase 4 attendance (Phase 4 must set `dayStatus = 'leave'` for approved leave days via `DayStatusService`)
- **Cross-dependency:** Phase 4 `DayStatusService` must query Phase 5 `Leave` collection to set `dayStatus = 'leave'` for approved leave dates. This creates a Phase 4 → Phase 5 data dependency that must be handled: either Phase 4 `DayStatusService` accepts a leave data source interface (filled in Phase 5), or `dayStatus` is set to `'absent'` initially and corrected when leave is approved.

**Chosen approach:** `dayStatus` is recomputed on every leave status change:
- Leave approved → `LeaveService` calls `DayStatusService.recomputeForDates(employeeId, dates)`
- Leave revoked → `LeaveService` calls `DayStatusService.recomputeForDates(employeeId, dates)`
- This keeps `dayStatus` always current regardless of when leave was applied

## R-RD-003 — Cron Architecture

### Root Cause

Three cron jobs were specified by IST time without UTC cron expressions. `vercel.ts` cron syntax requires UTC. IST is UTC+5:30 — a non-integer offset that is easy to miscalculate. Two cron jobs needed for a complete system (session auto-close, leave carry-forward expiry) were missing from the original roadmap entirely.

### Project Risk

- Attendance reminder fires at 14:30 IST (5.5h late) if developer writes `"0 9 * * *"` (UTC)
- Leave year rollover fires Dec 31 (previous year) if midnight IST = 18:30 UTC Dec 31 is not accounted for
- No session auto-close means employees who forget checkout are permanently stuck as CHECKED_IN, blocking next day's check-in
- No leave carry-forward expiry means balances accumulate indefinitely if company has expiry rules

### Implementation Impact

All 6 cron jobs must be defined in `vercel.ts` from Phase 1 (as stubs), then implemented in their respective phases. UTC expressions must be correct before any cron fires in staging.

### Fix: Cron Schedule Matrix

#### IST → UTC Conversion Reference
```
IST = UTC + 5h30m
To get UTC from IST: subtract 5h30m
  00:05 IST = 18:35 UTC (previous calendar day)
  08:00 IST = 02:30 UTC
  09:00 IST = 03:30 UTC
  10:00 IST = 04:30 UTC
  10:30 IST = 05:00 UTC
  18:00 IST = 12:30 UTC
  19:00 IST = 13:30 UTC
  23:30 IST = 18:00 UTC
```

#### Full Cron Schedule Matrix

| # | Job Name | Purpose | IST Time | UTC Cron Expression | Phase | `vercel.ts` Path |
|---|---|---|---|---|---|---|
| C-01 | `session-auto-close` | Close any attendance sessions still active at end of working day | 23:30 IST daily | `"0 18 * * *"` | Phase 4 | `/api/cron/session-auto-close` |
| C-02 | `leave-year-allocation` | Create `leaveYearAllocation` records for all active employees for the new leave year | 00:05 IST Jan 1 (or configured month 1st) | `"35 18 31 12 *"` | Phase 5 | `/api/cron/leave-year-allocation` |
| C-03 | `leave-carryforward-expiry` | Zero out expired carry-forward balances after grace period | 00:05 IST April 1 (configurable) | `"35 18 31 3 *"` | Phase 5 | `/api/cron/leave-carryforward-expiry` |
| C-04 | `attendance-reminder` | FCM push to employees not yet checked in by 10:30 IST | 10:30 IST daily (working days only) | `"0 5 * * 1-5"` | Phase 4 | `/api/cron/attendance-reminder` |
| C-05 | `checkout-reminder` | FCM push to employees still checked in at 18:30 IST | 18:30 IST daily (working days only) | `"0 13 * * 1-5"` | Phase 4 | `/api/cron/checkout-reminder` |
| C-06 | `payroll-month-end` | FCM + email reminder to admin on last working day of month | 09:00 IST last working day | `"30 3 28-31 * *"` + code check | Phase 7 | `/api/cron/payroll-month-end` |

**Note on `"* * 1-5"` (Mon-Fri):** Days-of-week: `0=Sun, 1=Mon, 5=Fri, 6=Sat`. Working-day restriction is approximate — the code must also check `companySettings.workingDays` since some companies work Saturdays. Cron fires Mon-Fri; code returns early if today is not in `companySettings.workingDays`.

**Note on C-02 (Leave Year Allocation):** If `leaveYearStartMonth ≠ 1` (January), the cron expression must be adjusted. Use month = `leaveYearStartMonth`, day 31 of previous month at 18:35 UTC is not always correct. Cleaner approach: run on **1st of every month** (`"35 18 L * *"` or `"35 18 28-31 * *"`) and exit early in code if `currentMonth !== leaveYearStartMonth`. This allows runtime config changes without redeploying `vercel.ts`.

**Note on C-06 (Payroll Month-End):** `"30 3 28-31 * *"` fires on days 28, 29, 30, 31 of each month. Code checks: `if (tomorrow.getDate() === 1) runPayrollReminder()` — fires only on the last day of the month.

**Note on C-03 (Carry-Forward Expiry):** `"35 18 31 3 *"` only fires on March 31 (UTC = April 1 00:05 IST). If `carryForwardExpiryMonth` is configurable, use: `"35 18 28-31 * *"` + code checks `leaveTypes[].carryForwardExpiryMonth`.

#### Per-Cron Specification

**C-01 — Session Auto-Close**

*Purpose:* Any employee who checked in but did not check out by 23:30 IST will have their session automatically closed. Prevents next-day check-in being blocked by a dangling active session.

*Trigger:* Daily at 23:30 IST (`"0 18 * * *"` UTC). Runs regardless of working day — catches edge cases on weekends/holidays if someone accidentally checked in.

*Logic:*
```typescript
// Find all AttendanceRecords for today with an active session (no checkOutTimestamp)
const today = getCurrentDateIST();  // 'YYYY-MM-DD'
const records = await AttendanceRecord.find({
  date: today,
  'sessions.checkOutTimestamp': null,  // has at least one open session
});

for (const record of records) {
  const settings = await SettingsService.getSettings();
  const autoCloseTime = parseShiftEndTime(settings.shiftEndTime);  // e.g., 18:00 IST as Date

  for (const session of record.sessions) {
    if (!session.checkOutTimestamp) {
      session.checkOutTimestamp = autoCloseTime;  // set to shift end, not 23:30
      session.autoClosedBySystem = true;          // flag for audit trail
    }
  }
  record.dayStatus = recomputeDayStatus(record, settings);
  await record.save();
}

// Log to systemEvents for idempotency
await SystemEvent.create({ eventType: 'cron:session-auto-close', date: today });
```

*Failure recovery:*
- If cron fails: sessions remain open; next day's check-in blocked for affected employees
- Recovery: Admin can manually check out via attendance correction (Phase 4 admin correction endpoint)
- Alert: Cron handler sends admin notification on error (`console.error` → Vercel logs → set up Vercel log drain alert)
- Idempotency: `systemEvents` check prevents double-close if cron fires twice

**C-02 — Leave Year Allocation**

*Purpose:* On the first day of the new leave year, create `leaveYearAllocation` records for all active employees. Sets their annual quota for each leave type.

*Trigger:* `"35 18 28-31 * *"` UTC (fires days 28–31 of every month). Code checks: `if (currentMonth_IST !== leaveYearStartMonth) return`.

*Logic:*
```typescript
const settings = await SettingsService.getSettings();
const currentMonth = getCurrentMonthIST();
if (currentMonth !== settings.leaveYearStartMonth) return;  // early exit

// Idempotency check
const today = getCurrentDateIST();
const existing = await SystemEvent.findOne({ eventType: 'cron:leave-year-allocation', date: today });
if (existing) return;

const employees = await Employee.find({ status: 'active' });
const leaveYear = getCurrentLeaveYear(settings.leaveYearStartMonth);

for (const employee of employees) {
  for (const leaveType of settings.leaveTypes.filter(lt => lt.isActive)) {
    const existingAllocation = await LeaveYearAllocation.findOne({
      employeeId: employee._id,
      leaveYear,
      leaveTypeCode: leaveType.code,
    });
    if (existingAllocation) continue;  // already allocated

    // Compute carry-forward from previous year
    const previousYearBalance = await LeaveBalanceService.getRemainingBalance(
      employee._id,
      leaveType.code,
      leaveYear - 1
    );
    const carryForward = Math.min(previousYearBalance, leaveType.maxCarryForwardDays);

    await LeaveYearAllocation.create({
      employeeId: employee._id,
      leaveYear,
      leaveTypeCode: leaveType.code,
      annualQuota: leaveType.annualQuota,
      carryForwardDays: carryForward,
      totalAvailable: leaveType.annualQuota + carryForward,
    });
  }
}

await SystemEvent.create({ eventType: 'cron:leave-year-allocation', date: today });
```

*Failure recovery:*
- Missing allocation means employees see 0 balance on new year's first day
- Recovery: `POST /api/admin/cron/leave-year-allocation` (admin manual trigger, `?force=true` bypass idempotency)
- Partial completion: cron is per-employee idempotent (`existingAllocation` check prevents re-allocation)

**C-03 — Leave Carry-Forward Expiry**

*Purpose:* After the carry-forward grace period ends (configurable per leave type via `carryForwardExpiryMonth`), zero out any unused carry-forward balance. Prevents indefinite accumulation.

*Trigger:* `"35 18 28-31 * *"` UTC. Code checks: does today match any leave type's `carryForwardExpiryMonth`?

*Logic:*
```typescript
const settings = await SettingsService.getSettings();
const currentMonth = getCurrentMonthIST();

const expiringTypes = settings.leaveTypes.filter(
  lt => lt.carryForwardExpiryMonth === currentMonth && lt.maxCarryForwardDays > 0
);
if (expiringTypes.length === 0) return;

const today = getCurrentDateIST();
const existing = await SystemEvent.findOne({ eventType: 'cron:leave-carryforward-expiry', date: today });
if (existing) return;

const leaveYear = getCurrentLeaveYear(settings.leaveYearStartMonth);
for (const leaveType of expiringTypes) {
  await LeaveYearAllocation.updateMany(
    { leaveYear, leaveTypeCode: leaveType.code, carryForwardDays: { $gt: 0 } },
    { $set: { carryForwardDays: 0 }, $inc: { totalAvailable: /* negate carryForward */ } }
  );
  // Write LeaveTransaction with type: 'expiry' for audit trail
}

await SystemEvent.create({ eventType: 'cron:leave-carryforward-expiry', date: today });
```

*Failure recovery:*
- Carry-forward not expired: employees retain balance past expiry date
- Recovery: Admin manual trigger `POST /api/admin/cron/leave-carryforward-expiry?force=true`

**C-04 — Attendance Check-In Reminder**

*Purpose:* FCM push to all active employees who have not checked in by 10:30 IST on a working day.

*Trigger:* `"0 5 * * 1-5"` UTC (10:30 IST Mon-Fri). Code verifies today is a working day and not a holiday.

*Logic:*
```typescript
const settings = await SettingsService.getSettings();
const today = getCurrentDateIST();
if (!isWorkingDay(today, settings)) return;

const checkedInEmployees = await AttendanceRecord.distinct('employeeId', {
  date: today,
  'sessions.0': { $exists: true },  // has at least one session
});

const allActive = await Employee.find({ status: 'active' }).select('_id userId');
const notCheckedIn = allActive.filter(e => !checkedInEmployees.includes(e._id.toString()));

for (const employee of notCheckedIn) {
  const user = await User.findById(employee.userId).select('fcmToken');
  if (!user?.fcmToken) continue;
  await FcmService.send(user.fcmToken, {
    title: 'Attendance Reminder',
    body: 'Don\'t forget to check in for today.',
    data: { type: 'ATTENDANCE_REMINDER', path: '/attendance' },
  });
}
```

*Failure recovery:*
- FCM batch send: on partial failure, log failed tokens; retry on next scheduled run (next day)
- Idempotency: check `systemEvents` — send once per day per employee

**C-06 — Payroll Month-End Reminder**

*Purpose:* Email + FCM push to admin on the last working day of the month as a reminder to run payroll.

*Trigger:* `"30 3 28-31 * *"` UTC. Code checks: `isTomorrow(1st of next month)`.

*Logic:*
```typescript
const tomorrow = addDays(new Date(), 1);
if (tomorrow.getDate() !== 1) return;  // not last day of month

const today = getCurrentDateIST();
const existing = await SystemEvent.findOne({ eventType: 'cron:payroll-month-end', date: today });

// Check if payroll already computed for this month
const computed = await PayrollRecord.findOne({ month, year, status: { $ne: 'draft' } });

// Send to all admin users
const admins = await User.find({ role: 'admin', fcmToken: { $ne: null } });
for (const admin of admins) {

}

await SystemEvent.create({ eventType: 'cron:payroll-month-end', date: today });
```

*Failure recovery:*
- Admin reminder not sent: admin may miss payroll deadline
- Recovery: Admin can manually check payroll status in admin portal
- The cron fires days 28–31 so there are multiple opportunities if one day's cron fails

## R-RD-004 — Admin Seed Strategy

### Root Cause

No initial admin account creation mechanism was specified. Production cannot be used without at least one admin user. If not specified, each developer creates admin accounts differently across environments, leading to inconsistent setup procedures and potential security risks (hardcoded credentials, wrong roles).

### Project Risk

- Production deployment blocked: no admin → cannot log in → cannot configure settings → cannot onboard employees
- Staging/dev divergence: each environment has differently-created admin accounts
- Security risk: if seed script is implemented naively, initial password may be logged or hardcoded in code

### Implementation Impact

Admin seed must be:
- Implemented in Phase 2 (auth infrastructure exists)
- Idempotent (run multiple times safely)
- Driven by environment variables (not hardcoded)
- Auditable (admin account creation written to `auditLogs`)
- Secure (password never logged; `requiresPasswordChange: true` enforced)

### Fix: Admin Seed Strategy

#### Initial Admin Creation

**Seed script:** `scripts/seed-admin.ts`

```typescript
#!/usr/bin/env tsx
// scripts/seed-admin.ts
// Usage: npm run seed:admin
// Environment: ADMIN_EMAIL, ADMIN_INITIAL_PASSWORD
// Idempotent: no-op if admin user already exists

import mongoose from 'mongoose';
import bcrypt from 'bcryptjs';
import { User } from '../src/models/User';
import { Employee } from '../src/models/Employee';

async function seedAdmin() {
  const email = process.env.ADMIN_EMAIL;
  const password = process.env.ADMIN_INITIAL_PASSWORD;

  if (!email || !password) {
    throw new Error('ADMIN_EMAIL and ADMIN_INITIAL_PASSWORD must be set');
  }

  await mongoose.connect(process.env.MONGODB_URI!);

  // Idempotency check
  const existing = await User.findOne({ email, role: 'admin' });
  if (existing) {
    console.log(`Admin ${email} already exists. No-op.`);
    await mongoose.disconnect();
    return;
  }

  const passwordHash = await bcrypt.hash(password, 12);

  const user = await User.create({
    email,
    passwordHash,
    role: 'admin',
    requiresPasswordChange: true,
    registeredDeviceHash: null,    // admin does not use device fingerprint
  });

  await Employee.create({
    userId: user._id,
    employeeCode: 'ADMIN-001',
    firstName: 'System',
    lastName: 'Administrator',
    status: 'active',
    department: 'Administration',
    designation: 'System Administrator',
    joiningDate: new Date(),
    grossMonthlySalary: 0,
  });

  console.log(`Admin seeded: ${email}`);
  console.log('IMPORTANT: Change password on first login. requiresPasswordChange=true is set.');

  await mongoose.disconnect();
}

seedAdmin().catch(err => {
  console.error('Seed failed:', err.message);
  process.exit(1);
});
```

  }
}
```

|---|---|

#### First Login Flow

```
Admin opens /login
  → enters ADMIN_EMAIL + ADMIN_INITIAL_PASSWORD
  → server validates: password correct, requiresPasswordChange: true
  → server issues JWT with { requiresPasswordChange: true }
  → Next.js middleware detects requiresPasswordChange → redirects to /change-password
  → Admin enters new password (must meet policy: 12+ chars, mixed case, digit, special char)
  → server: updates passwordHash, sets requiresPasswordChange: false, re-issues JWT
  → Admin redirected to /dashboard
  → First action: Settings → configure company, shift, working days, holidays, leave types
```

**Security constraints:**
- Initial password is never stored in plaintext anywhere after seeding (bcrypt hash only)
- Initial password is communicated to the first admin via a secure channel (not email, not code)
- Document in `DEPLOYMENT.md` (not committed to repo): "Initial admin credentials are in [secure vault]"
- `requiresPasswordChange: true` means admin cannot access any admin route until password is changed

#### Ongoing Admin Creation

Additional admin accounts are created by the initial admin via the Admin Portal (not via seed script). The `POST /api/v1/employees` endpoint with `role: 'admin'` (or a separate admin creation endpoint if roles are managed separately).

```
