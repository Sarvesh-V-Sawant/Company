## 6. Approval Decision

**Would you approve this Employee Mobile App UI/UX for implementation?**

**Yes, with 4 conditions.**

---

### Justification

**Why YES:**

The v1.1 specification is implementation-grade across all 27 screens and 27 workflows. All 5 HIGH findings are resolved with detailed Flutter component specs, state machine definitions, Riverpod provider architectures, and server reconciliation logic. The four most operationally complex areas — device registration, attendance state recovery, FCM lifecycle, and duplicate submission protection — now have complete and consistent designs.

Key strengths:
- **Device registration lifecycle** is fully specified end-to-end: new employee → `AUTH_011` → device not registered screen → admin registers → device awaiting approval screen → re-login. Three distinct error screens for three distinct device states.
- **Attendance state machine v2** is server-authoritative. The app never diverges from server state for longer than one reconciliation cycle. Timer restores from `currentSessionStart` server timestamp — not from local state that could be lost to an app kill.
- **Re-check-in workflow** is explicitly modeled with two distinct post-checkout states (PARTIAL and COMPLETE) and a 30-minute grace threshold, preventing the COMPLETE lock-out near end-of-day.
- **Duplicate submission protection** uses a consistent UUID that doubles as both the nonce (for check-in) and the `X-Idempotency-Key` header (for all write operations), keeping the client and server deduplication mechanisms aligned.
- **FCM token lifecycle** is fully specified: first registration post-login, `onTokenRefresh` listener, pre-notification foreground check, logout cleanup. The `FcmTokenService` is a standalone Riverpod provider with clear responsibilities.
- **Offline strategy** covers read-only access from Hive cache, write queuing with retry, and state reconciliation on reconnect — critical for field employees with unreliable connectivity.

**Why 4 Conditions (not unconditional):**

**Condition 1 — `docs/06.2-api-gap-analysis.md` gaps G-001 through G-005 must be resolved in `docs/04-api-specification.md` before any API integration work begins.**
Five HIGH API gaps are blocking: `AUTH_011`, `PATCH /auth/me/fcm-token`, `GET /attendance/today` response shape, `X-Idempotency-Key` support, and re-check-in multi-session behavior. Mobile implementation can proceed with mocked APIs, but backend integration is blocked until these are added to the API spec.

**Condition 2 — MEDIUM R-MOB-006 (change password current-password field) must be resolved before Profile module build.**
The change-password form as designed does not include a `currentPassword` field. This is a security requirement, not a UX preference. The API decision must be made and the form spec updated before `ChangePasswordScreen` is coded.

**Condition 3 — MEDIUM R-MOB-007 (holiday cache) and R-MOB-009 (company settings cache) must be resolved before Leave and Regularization module builds respectively.**
Both forms could show stale data to employees — a public holiday not appearing, or regularization type list not reflecting admin changes. Both are simple Hive stale-while-revalidate additions, but must be specified before the affected forms are built.

**Condition 4 — LOW R-MOB-014 (skeleton loader consistency) must be resolved before the first Flutter widget build.**
`ShimmerCard` is a shared component used across all loading states. If its spec is inconsistent when developers start, six different shimmer implementations will result. Define it once in the design system before any module build begins.

All other MEDIUM and LOW findings are module-local and can be resolved just before the relevant module build begins.
