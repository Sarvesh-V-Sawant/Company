      { isActive: true },

## 6. Findings

### H1 — HIGH: forgot-checkout reconciliation is functionally broken

**Severity:** HIGH
**File:** `src/services/RegularizationService.ts:261`
**Impact:** Scope item #3 (forgot check-out handling) and #11 (attendance session reconciliation) are non-functional for all real use cases.

**Root cause:** `approve()` looks for `{ isActive: true }` session on the target date. The `session-auto-close` cron (`POST /admin/cron/session-auto-close`) runs nightly and calls `AttendanceService.autoCloseSessions(dateString)`, which marks all sessions `isActive: false, closedBySystem: true, systemCloseReason: 'midnight-rollover'`. By the time an employee submits a `forgot-checkout` regularization for any past day (minimum 1 day ago per lookback window enforcement), the session is already closed. The `findOne({ isActive: true })` query returns `null`, and approve() throws REG_006.

**Evidence:**
- `AttendanceService.ts:754` — `autoCloseSessions` sets `isActive: false, closedBySystem: true, systemCloseReason: 'midnight-rollover'`
- `RegularizationService.ts:261` — `findOne({ employeeId, dateString, isActive: true })` — never matches after midnight rollover
- Test U-REG-07a passes only because mock returns synthetic open session — does not reflect real DB state

**Required fix:**
```typescript
// src/services/RegularizationService.ts — approve(), forgot-checkout branch
const openSession = await AttendanceSession.findOne({
  employeeId: employeeOid,
  dateString,
  $or: [
    { isActive: true },
    { isActive: false, closedBySystem: true, systemCloseReason: 'midnight-rollover' },
  ],
}).sort({ createdAt: -1 }).session(dbSession).lean();
```

When session is `midnight-rollover` closed, also update `systemCloseReason` to `'admin-force-close'` and override the checkout timestamp with the requested time. Recompute durationMinutes from actual `checkIn.timestamp` to `requestedCheckOut`.

### M1 — MEDIUM: RegularizationType enum values deviate from API spec

**Severity:** MEDIUM
**File:** `src/types/enums.ts`, `src/validators/regularization.ts`

**Spec defines:** `forgotCheckIn | forgotCheckOut | workAwayFromOffice | officialTravel | clientVisit`
**Implementation uses:** `forgot-checkin | forgot-checkout | work-from-client | official-travel | attendance-correction`

Two deviations:
1. Case convention: camelCase (spec) vs kebab-case (impl)
2. Value name changes: `workAwayFromOffice` → `work-from-client`, `clientVisit` → missing, `attendance-correction` added (not in spec)

Mobile clients and admin UI built against the spec will send `forgotCheckIn` and receive a Zod validation error. This breaks client interoperability.

**Resolution options:**
- Option A: Update spec to reflect kebab-case implementation (requires spec amendment approval)
- Option B: Accept both forms in the validator (add Zod transform or alias mapping)
- Option C: Change implementation to match spec camelCase values

The enum values were intentionally set in Phase 6 start — user approval for the specific values used. This requires explicit decision before Phase 7.

### M2 — MEDIUM: Missing requestedCheckIn/requestedCheckOut date boundary validation

**Severity:** MEDIUM
**File:** `src/validators/regularization.ts`

Spec states:
- `requestedCheckIn`: must be on the same calendar day as `date` (IST)
- `requestedCheckOut`: must be on same or next day (if crossed midnight)

Current validator only checks presence (superRefine) but not date boundary. An employee could submit `requestedCheckIn` for a different date than `date`, creating a mismatch between the session timestamp and the AttendanceDay record's dateString.
