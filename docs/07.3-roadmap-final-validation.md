## 6. Cron Validation

### 6.1 UTC Schedule Correctness

IST = UTC + 5h30m. All expressions verified by subtracting 5h30m from IST target:

| # | Job | IST Target | UTC Math | UTC Expression | Correct? |
|---|---|---|---|---|---|
| C-01 | `session-auto-close` | 23:30 IST daily | 23:30 − 5:30 = 18:00 UTC | `"0 18 * * *"` | ✅ |
| C-02 | `leave-year-allocation` | 00:05 IST 1st of month | 00:05 − 5:30 = 18:35 UTC prev day | `"35 18 28-31 * *"` | ✅ |
| C-03 | `leave-carryforward-expiry` | 00:05 IST expiry month 1st | 00:05 − 5:30 = 18:35 UTC prev day | `"35 18 28-31 * *"` | ✅ |
| C-04 | `attendance-reminder` | 10:30 IST Mon–Fri | 10:30 − 5:30 = 05:00 UTC | `"0 5 * * 1-5"` | ✅ |
| C-05 | `checkout-reminder` | 18:30 IST Mon–Fri | 18:30 − 5:30 = 13:00 UTC | `"0 13 * * 1-5"` | ✅ |
| C-06 | `payroll-month-end` | 09:00 IST last day | 09:00 − 5:30 = 03:30 UTC | `"30 3 28-31 * *"` | ✅ |

**Result: All 6 UTC expressions mathematically correct.**

### 6.2 IST Mapping Edge Cases Verified

| Edge Case | Handled? |
|---|---|
| C-02/C-03 fire on day 28–31 — wrong month for short months | ✅ Code-level check: `currentMonth_IST !== leaveYearStartMonth → return` |
| C-01 uses 18:00 UTC = 23:30 IST — does not drift with DST | ✅ India does not observe DST; IST is always UTC+5:30 |
| C-06 fires days 28–31 — only one is the last day | ✅ Code-level check: `isTomorrow(1st) → run; else → return` |
| C-04/C-05 fire Mon–Fri — company may work Saturdays | ✅ Code-level check: `isWorkingDay(today, settings.workingDays) → else return` |
| C-01 fires on weekends/holidays (intentional) | ✅ Documented: catches edge cases; idempotency prevents duplicate close |

**Result: All IST mapping edge cases handled at code level.**

### 6.3 Failure Recovery Coverage

| # | Job | If Cron Fails | Recovery Path | Covered? |

### 8.2 First Login Flow

```
/login (ADMIN_EMAIL + ADMIN_INITIAL_PASSWORD)
  → JWT issued: { requiresPasswordChange: true }
  → Next.js middleware intercepts
  → Redirect: /change-password
  → Admin sets new password (policy: 12+ chars, mixed case, digit, special char)
  → passwordHash updated; requiresPasswordChange: false
  → New JWT issued
  → Redirect: /dashboard
  → First action: Settings → configure company before any employee operations
```

**Result: First login flow complete. No admin action possible before forced password change.**

### 8.3 Forced Password Change Enforcement

| Layer | Enforcement |
|---|---|
| JWT | `requiresPasswordChange: true` claim in payload |
| Next.js middleware | Guard order: `Maintenance → requiresPasswordChange → Unauthenticated → Role → CSRF` — `requiresPasswordChange` guard runs before role check |
| API routes | All admin routes require valid JWT; JWT with `requiresPasswordChange: true` is only valid for `POST /auth/change-password` |

**Result: Password change enforced at JWT, middleware, and route layers. No bypass path.**
