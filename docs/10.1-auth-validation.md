### 2.3 FCM Token — Request Schema Mismatch

| Field | Spec | Implementation |
|---|---|---|
| `token` | ✅ | ✅ |
| `deviceId` | `string` (stable device identifier) | ❌ Missing |
| `platform` | `"android" \| "ios"` | ✅ |
| `deviceFingerprint` | ❌ Not in spec | ✅ Present (wrong field) |
| `deviceInfo` | ❌ Not in spec | ✅ Present (extra field) |

### 4.2 Password Reset Ordering (BR-AUTH-21 violation)

Spec mandates: hash comparison first (BR-AUTH-21) → expiry check (BR-AUTH-22).

Implementation does the reverse:

```
Impl: query(isUsed: false) → not-found? → expiresAt check → hash check
Spec: query(email)         → not-found? → hash check     → expiry check
```

**Impact:** If a valid reset token exists but is expired, attacker submitting any token value with the victim email receives `AUTH_008` (expired) rather than `AUTH_009` (invalid). This reveals "a password reset was requested for this email recently" within the 15-minute TTL window. After TTL expiry, MongoDB TTL index deletes the document, returning `AUTH_009` again.

Risk window: 15 minutes. Practical exploitability: low. Spec deviation: confirmed.

### 4.3 Missing `dynamic = 'force-dynamic'`

Spec §1.1 mandates `export const dynamic = 'force-dynamic'` on all route handlers:
> "disable Next.js GET caching for all API routes"

`GET /api/v1/auth/me` has no such export. Next.js 16 Turbopack may cache the profile response, causing stale `role`, `requiresPasswordChange`, and `isActive` to be returned after changes.

All 8 route handler files are missing this export. For mutation-only routes (POST/PATCH) the risk is minimal. For `GET /auth/me` it is a functional correctness issue.
